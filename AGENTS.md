# Agent Execution Policy

## Build and Task Orchestration

- Use `mise` tasks as the default execution path for build, test, fmt, and vet workflows.
- Prefer `mise run <task>` over ad-hoc `go build`/`go test` invocations when an equivalent `mise` task exists.

## Workspace Layout

- The repo root is the icelake library module itself — the public API lives here. The only test file that stays at the root is the runnable godoc example (`example_test.go`), which pkg.go.dev can only render from the package's own directory.
- `docs/` — the design documents: `ARCHITECTURE.md`, `SCHEMA.md`, `TESTING.md`, `PLAN.md`, `RELEASING.md`. Prose throughout the repo cites them by bare name; this is where they live (moved 2026-08-05; before that they sat at the root).
- `internal/e2e/` — the end-to-end scenario suite: every root-package test that is not a godoc example (the numbered scenarios, crash-child harness, benchmarks, tripwire). They were external `package icelake_test` files at the root until 2026-08-05 and exercise only the exported API plus `internal/` test infrastructure, which is what made the move a rename and not a refactor.
- `cmd/` — deployable Go binaries (one Go module per app; the directory was `apps/` until 2026-08-05, renamed to the conventional Go name). They are deliverables, not API: never imported, never published, and no part of what a consumer gets when it imports the root library module.
- An app that has a library package to wrap is a thin wrapper with no logic of its own, and that is the default shape for anything new: `cmd/icelake-rebuild` parses flags and calls `rebuild.Rebuild` (`PLAN.md`, M6), and `cmd/icelake` reads its configuration, loads a schema document, opens one dynamic writer per table and pumps stdin through `InsertJSON` (`PLAN.md`, M13). The one refusal that command owns rather than passes along is its `rebuild` subcommand in local-only mode: there is no catalog to rebuild, and the command decides that from its own environment rather than by calling a library that would have to invent an error for it. The second one is the case that proves the rule rather than the easy one: everything a reader might take for the daemon's own behaviour — batching, retention, local-only mode, replay after a crash, backpressure when staging fills — is a library decision it passes along, and anything that looks like new behaviour belongs in the library and not in that `main`.
- **`cmd/icelake` is configured by environment variables and takes no flags on `run`, which is a deliberate deviation from the flags-first shape of its two siblings.** Recorded here so it reads as a decision rather than as drift. It is a daemon, and a daemon is started by a process manager — systemd, mise, a container runtime — every one of which configures a child by environment and none of which makes a long flag line pleasant to maintain. And it takes secrets: a credential bound as a flag's default value is printed back by the `flag` package in the block it produces for `-h` and for every parse error, which is a mistake the R2 check command's tests already exist to guard against, and which one configuration channel makes unrepresentable rather than guarded. One channel also means the resolved configuration has exactly one source to print at startup, and one table that the help output is generated from and the embedded manual is checked against by that command's own tests — which is what keeps the two of them from drifting apart as variables are added. The siblings keep flags because they are operator tools run by hand, where a flag is the better interface and no secret needs a default.
- **Decision (2026-08-04, at M15's review): the descriptive thin-wrapper rule above is superseded by one mechanical test, because the descriptive version failed in practice** — M15 placed the ingest pump (chunking, halving a group the ceiling refuses, truncating at a refused line) in `cmd/icelake`, every downstream check passed because each checks code against docs rather than placement against this rule, and the violation was caught only by the owner asking where the settings flow. The rule is now this, and it is short enough to hold in one hand. The library is the product; a CLI only translates between a shell and the library. A CLI may contain exactly four translations: environment and flags into library values; stdin and stdout into a library call; signals into context cancellation; library errors into exit codes and messages. It may contain nothing else — no retry, no backoff, no batching decision, no truncation, nothing a crash or refusal test would assert on. The test has no judgment in it: every subcommand names the one exported library call it delegates to (`rebuild` names `rebuild.Rebuild`), and a subcommand whose work cannot be named as one library call is the defect — the fix is always a new library entry point, never code in the CLI. Equivalently: delete the CLI and nothing is lost but the shell. **Closed at M16 (2026-08-04).** When this bullet was written `run` failed the test — its ingest pump could not be named as a library call — and M16 was scheduled to create the entry point. It did: the pump is `icelake.IngestStream`, `run` names it, and what is left between the environment and that call is the four translations and nothing else. Two things about how it closed are worth keeping, because they are what the rule predicted and are the argument for it. The move needed no behaviour change at all — the three streaming tests M15's review had to write to catch the pump's defects pass unaltered against the new `run`, which is what "the behaviour did not move, only its address did" looks like when it is true. And the milestone that followed it, adding a second input encoding, made `run` *smaller*: the encoding is decided per record by the library's own grammar, so the environment variable that would have selected it does not exist, and a feature arrived without the CLI growing a line. A rule that keeps paying out in the direction it points is the kind worth keeping. (`cmd/icelake-r2check` keeps its recorded exception below: it wraps no library, and this rule is about wrappers.)
- **Decision (2026-08-05, M19): a command may contain a second category of code beside the four translations — process management — and the same decision forbids that category in the library.** Process management is how the process runs, not what it does: backgrounding (the re-exec, the new session), the pid file and its flock, where the log goes, readiness signaling to a starter, and the signal wiring `main` always had. It lives in the CLI because it can live nowhere else — a library that daemonized, locked pid files or redirected stderr would be managing the process that embeds it, which is the embedder's job; the placement rule's direction simply reverses here. The boundary stays mechanical: process-management code may not touch a record, a batch, a retry or anything a crash or refusal test on data would assert on — the test is that deleting it leaves the daemon fully functional, only attached to the shell. It is also why `run` takes exactly one flag, `-f`/`--foreground`, and the top level takes `-v`/`--version` and `-h`/`--help`: none carries a value, so the env-only configuration channel and its no-secrets-in-flags property are untouched, and what `-f` selects is process management, which is the CLI's own. Configuration still never travels in flags.
- **Decision (2026-08-05, M21): validation and status probing live in the library's `inspect` package; `icelake check` is a thin wrapper over `inspect.Inspect` plus the two facts only the process owns.** The rule is the placement rule applied to reading: what a staging row means, how the warehouse prefix is laid out, and which metadata file is a table's current one are library knowledge, so the probes live in `inspect` — read-only by construction (the staging connection carries SQLite's `query_only` pragma; nothing anywhere in the package writes an object, a file, a row or DDL), safe beside a live daemon, one `Err` per probe because the failures are the findings. The current-metadata rule is extracted to `internal/metascan` and shared with `rebuild`, because two implementations of one ordering are two chances to disagree. The command contributes exactly its two sanctioned categories: configuration translation (the same `readSettings`/`loadTables` as `run`, refused the same way) and process management (the daemon probe — a shared non-blocking flock on a pid file it opens read-only and never creates). The report on stdout is a product under the logging rule, like the rebuild report; the run's own failure line stays one logfmt record on stderr. `check` takes no flags, and a check that failed is exit 1 while "not running" and "new table, nothing written yet" pass — check judges the setup, not whether the operator has started anything yet.
- `cmd/icelake-r2check` is the deliberate exception — it implements the one-off manual R2 verification procedure itself (`TESTING.md`, "Real R2 verification"), because there is nothing in the library for it to wrap and there should not be. Do not "fix" this by moving its checks into the library: that would add several hundred lines of operator-procedure code, whose whole reason to exist is a run by hand against a real bucket that is never automated, to the public API every consumer carries forever, in order to make one binary conform to a rule that was only ever about wrappers.
- **Corrected at the post-M9 completeness audit (2026-08-01):** the layout bullet above used to say "thin wrappers with no logic of their own" of `cmd/` as a whole, and one of the apps plainly is not that — `icelake-r2check` carries a preflight that decides whether a bucket may be written into at all, three provider checks, an ordered cleanup that deletes out of a real paid bucket and then lists it to see, and its own S3 calls. It has been narrowed to the rule that is actually true rather than the code being bent to fit the sentence.
- **Amended the same day, at the repair round, because that correction's survey was wrong.** It claimed "the other documents never made the blanket claim", and named `PLAN.md`, which says "no logic of its own" of `icelake-rebuild` specifically and pointedly does not repeat it for `icelake-r2check`, and `ARCHITECTURE.md`, which calls that binary "the program that performs" the verification. Both of those hold. What the survey missed is `TESTING.md`, which introduced the same program as "a thin `main` in the same spirit as the rebuild CLI" — and since `ARCHITECTURE.md` says of the rebuild CLI that it has "no logic of its own", that sentence asserted transitively exactly what this file was being corrected for, in the one document a reviewer of that program consults for its requirements. So this file was not the outlier; it was the more explicit of two. `TESTING.md` has been corrected in the same voice, and the claim to have surveyed the tree is withdrawn: it was made on a reading of two documents out of three.
- **Amended once more at the audit's third round (2026-08-01), for a smaller thing in the same bullet.** The exception bullet above used to describe that program's code as "run by hand against a real bucket and never in CI". The second half stopped being true earlier the same day: the repair round gave the program a substrate-backed test, so its code — preflight, cleanup, and the three checks' happy path — runs against the MinIO container on every `mise run check`. The clause has been narrowed to the part that is still true and is the part the argument actually needs: what is never automated is the run against a real bucket. `TESTING.md` owns that decision and states the coupling it accepts; `PLAN.md` carried the same four words and has been corrected too.
- **Amended a third time, at the audit's fifth round (2026-08-01), for a number that was wrong in the correction bullet above.** That bullet used to size the program at "a little over five hundred lines", and the figure was overtaken by the very commit it was written into: 523 lines at the commit before, 892 at the commit that introduced this correction, which is the same change that gave the program its substrate-backed test and the preflight and cleanup work that test was written for. It reads as a number taken from the program before that round's own changes to it and not read again afterwards, which is the ordinary way this happens: nobody recounts a file to write a sentence that is about something else. The wrong number was doing real work in this file, which is what makes it worth a dated entry rather than a quiet edit: this bullet is where the `cmd/` thin-wrapper exception is justified, and the bullet above it uses the size of the code to argue against moving it into the public API. It has been replaced with what the program *contains* rather than how long it is, and deliberately not with today's count, because a line count written into prose is a fact about one commit that goes on being read as a fact about the file — which is how this one came to be copied into a third document, `PLAN.md`, at the round after the one that wrote it here, by an author who had every reason to believe it. `PLAN.md` carried the same figure in its dependency-cost argument and has been corrected the same way, as did `TESTING.md`; all three copies went in the same commit.
- `go.work` at the repo root ties the root library module and each `cmd/` module together. A new app module must be added to it with `go work use ./cmd/<name>`.
- Module paths use `github.com/gvkhna/icelake` — the real, finalized path (2026-08-04). Before that date the tree carried a syntactically valid stand-in for the `<owner>` placeholder, find-and-replaced when the owner was chosen (`PLAN.md`, "Distribution").
- Build order, module/package layout, distribution, and dependency pins live in `PLAN.md`. Read the design docs in the order `PLAN.md` states before writing code.
- **Releasing a fix or feature** (from the first release, 2026-08-04): the procedure is `RELEASING.md` and it is short on purpose — commit, push `main`, let CI pass, run `GOFLAGS=-count=1 mise run check` and `mise run release-check` locally, then `git tag vX.Y.Z && git push origin vX.Y.Z`. The tag push is the release: the workflow builds and *publishes* it, a stable tag becomes latest, and installers (`mise use -g github:gvkhna/icelake`, `mise up`) resolve it from there. Fixes bump the patch, new behaviour bumps the minor, and nothing about the release is manual after the tag. A tag is permanent the moment the module proxy sees it — never tag a tree whose gates have not passed.
- Commit messages and identities carry no tool or model attribution; the tracked hook in `.githooks/` enforces this and `mise install` registers it (see `mise.toml`, `[hooks]`).

## Database Access (made explicit 2026-08-04, at M15 — the rule had been convention plus gate, and a review question showed nothing stated it)

- Every query against a database whose schema this repo owns goes through sqlc: the SQL is authored in `queries.sql`, the generated code is committed, and `mise run generate` (the pinned sqlc) is the only way to regenerate it. A raw SQL string handed to the driver from Go is refused in review. The `generate-check` gate proves the generated code matches its sources, but it cannot see a string the generator never saw — which is exactly why this rule has to exist in words and not only as a gate.
- **A new sanctioned exception, added at M17 with the ClickHouse mirror: the mirror's own SQL.** It is written out honestly rather than waved through, because this rule's whole value is that an exception has to be argued. Three facts together are the reason. **sqlc has no ClickHouse engine** — it generates for PostgreSQL, MySQL and SQLite, so there is no configuration of the pinned generator under which this SQL could go through it at all, and the rule cannot be obeyed by trying harder. **The DDL is generated rather than authored**: `CREATE DATABASE`, `CREATE TABLE` and `ALTER TABLE ... ADD COLUMN` are computed from the table's declared schema document, column by column, which is the same act the goose exception covers — schema definition, not a query — with the difference that here even the text is derived, so there is no hand-written statement for a generator to check. **And the insert is not composed at all**: the rows are handed to `clickhouse-go`'s batch API, which builds the wire protocol itself from an explicit column list, so the only SQL string in the insert path is `INSERT INTO <table> (<columns>)` with the identifiers quoted, and every value travels as a typed column rather than as text in a statement. What is left that is genuinely a query is the reconciliation read against `system.columns`, which is parameterised and reads a server's own catalog — a schema this repository does not own, which is the same reason `internal/catalogdb`'s one insert is on the list below.
- The sanctioned exceptions, each with its reason: goose migrations (schema definition, not queries); the `PRAGMA` setup and read-back in `internal/staging`'s open path (connection configuration, which sqlc does not model); `internal/catalogdb`'s one insert (that schema is created and owned by iceberg-go, so this repo has no migrations to hand sqlc); DuckDB validation queries in tests (a different engine entirely, used precisely because it is independent of the write path); and the test suite's direct reads of the staging and spool tables (a test that asserted durability by asking the library would be believing the thing under test — reading the file itself is the point, and generating a query API for every assertion a test wants to make would put test-only surface into the production package).

## Configuration and Data (rule set 2026-08-05, owner's call)

- Configuration never travels in the schema document. The document declares the data's shape — tables, columns, types, field ids — and nothing operational: no thresholds, no cadences, no mirror settings. Configuration travels through `Config`, the per-table configuration types (`TableConfig`, `DynamicTableConfig`), or the daemon's environment. The rule exists because a first draft mixed them, and the two change for different reasons on different schedules; `SCHEMA.md` records the argument.

## Logging (rule set 2026-08-05, owner's call — after a bulk load's cut-short drain logged "context deadline exceeded" and nothing else)

The daemon's log exists to answer four operator questions at any moment: **is my data safe, what is it doing, is anything wrong, when will it be done.** A log line a reader cannot answer those from is a defect, whatever else it says. The rules that make that checkable:

- **One format, no exceptions — and the boundary is log versus product, never machine versus human.** A log line is anything a command says *about its own run*: status, progress, warnings, errors, the starter's "started in the background", the final line on the way to an exit code. Every log line, in every command in this repository, is one logfmt record through `log/slog` (`time= level= msg=` then keys; the daemon's logger is `newLogger` in `cmd/icelake/log.go`, constructed once by whichever mode owns the destination decision). No plain-text logging exists, because the format reads perfectly well as a human message — "human-facing" is not a licence, and a first draft of this rule that carved out "lines for a person" was refused by the owner the day it was written. What is *not* a log, and therefore not an exception but simply out of scope, is a command's **product**: the output the person asked the command for, on stdout — the manual `usage` prints, the help table, the version string, `rebuild`'s report, the R2 check's verification report, a flag package's help block. The test is one question: does this text report on the run, or is it what the run was for? Reports on the run are logfmt, everywhere, always.
- **The sentence and the data never mix.** `msg` is a plain sentence naming the event; every number, count, path, table name, duration and error rides in a key. A value interpolated into `msg` is a value no grep can find and the defect this rule exists for.
- **Every stopping line carries the account.** A line that ends a run, cuts a drain short, or reports records not committed must carry: `staged=` (how many records are not yet committed), `staging=` (the file they are in), `lost=` (stated outright, and it is `0` — if it ever cannot be, that line is the least of the problems), and `action=` (what happens next, e.g. "the next run replays and commits them").
- **A setting's failure names the setting.** When a configured value caused the outcome, the line carries `variable=<ICELAKE_…>` — the environment variable an operator can actually change, never a Go field name, and never a bare mechanism phrase like "context deadline exceeded".
- **Levels are meanings, not volumes.** `error`: an operator should act. `warn`: degraded but self-healing, no data at risk — and the line says so. `info`: state transitions only; a healthy daemon at `info` is quiet between them, and that quiet is a promise (it is why the debug heartbeat exists). `debug`: following activity — the 30-second per-table heartbeat, the urgent drain cadence.
- **Cadence.** Periodic lines at `info` level are only permitted while a drain is running: every five minutes normally, every five seconds once a signal makes someone wait. Everything else periodic is `debug`.
- **New events answer the four questions first.** Before adding a line, say which question it answers; a line that answers none is noise and is refused in review. The lifecycle's fixed points — `starting` (full resolved config, secrets as `set`/`unset`), `table ready` per table, `reading records`, the end-of-input or signal summary with `accepted=`/`uncommitted=`, `committing` progress, and a final line that is either `drained; every accepted record is committed` or the account above — are the contract; scenario 13's tests match on them, and `usage.md`'s log section documents them for operators. Change a line, change all three together.

## Open Source Posture

- This repository is intended for public, open-source release (`PLAN.md`, "Distribution"). Write everything in it as if it were already public.
- Motivating cases, examples, and rationale are described generically. Never name or describe private projects, internal infrastructure, sibling repositories, or their operators — the engineering story stands on its own without them.
- Never commit credentials, endpoints, bucket names, or account identifiers; secrets reach tools only via flags or environment variables at run time.
- Publication went through the pre-publication scan-and-sanitize pass in `PLAN.md` before the first tag (2026-08-04). This posture is what kept that pass a verification rather than a cleanup, and it is still what every commit is written under.

## Testing Policy (binding — the rule is `TESTING.md`, "Test philosophy"; this section is a pointer to it, not a copy of it)

- Read `TESTING.md`'s "Test philosophy" section, as it stands on the day you are reading it, before writing a test or judging one in review. It is binding, it is what a reviewer quotes when refusing a test, and it is where the decisions live: what form a test takes by default, which narrower forms are sanctioned and on what conditions, and what is rejected on sight. This file states none of that, deliberately — see the correction below.
- Never review against a remembered or summarised version of it, including a summary in this file — which is how this section came to need the correction below.

- **Corrected at the completeness audit's fifth round (2026-08-01), and what was wrong was this file's summary rather than the policy it was summarising.** Until this round the section carried three bullets restating the rule: end-to-end scenarios as the default form; unit tests "only where an exact calculation must be asserted (canonical encoding/hash bytes, adapter conversions, backoff schedule), against independently derived expected values"; and a list of what is never acceptable. The middle bullet was accurate when it was written: it landed in the same change that first wrote `TESTING.md`'s philosophy section — the one whose own text is dated 2026-07-30 — and at that point that section sanctioned exactly one exception to the end-to-end default, which is what the bullet said. It stopped being accurate at the audit's second round, when that document widened the philosophy to sanction a second category — a package-internal behaviour test of a layer that is either pure computation or owns a local file, admitted only when all four of the rules stated there hold, one of which requires the test's own comment to name which of two claim shapes it holds — and it now names the eight files that sit in that tier. This file's bullet said "only", so a reviewer working from it alone would have refused tests `TESTING.md` explicitly permits, and would have refused them while citing, in the section heading directly above, the document that permits them. That is the failure `TESTING.md` has spent five consecutive rounds correcting inside itself, reintroduced from outside by a stale copy sitting in the file an agent reads first.
- **The repair is a pointer rather than a corrected summary, and the reason is general rather than a judgement about this particular bullet.** A summary of a rule that lives in another document is a copy, and a copy drifts the moment the original is edited: this one went wrong at the second round and stayed wrong through the repair round and the two after it, every one of which was an audit of the very section it was summarising and none of which looked here. Rewriting it accurately would buy correctness until the next amendment and would leave the same trap armed for the next reviewer, who cannot tell a current summary from a stale one without reading the original — and once they have read the original, the summary's only remaining function is to be believed instead of it. The banned list went the same way, and reading it closely on the way out turned up a smaller version of the same defect, which is worth recording rather than deleting quietly: it said "Never: mock-based tests", flatly, where `TESTING.md` bans mocks and fakes *of the storage substrate* and then, in the paragraph directly under its banned list, explicitly allows one seam that is not a mock — the injected clock that every timer-dependent scenario in that document is driven by. A reviewer holding this file's four words would have refused the fake clock the suite already runs on. Same failure, smaller, and it was there from the day the bullet was written rather than arriving with an amendment: two copies of one rule, both wrong in the direction of refusing what the rule allows, is the argument for keeping none.
- **One note on this correction's own reach, since a survey that reports "clean" is exactly what the last five rounds kept getting wrong.** What was checked is five files — this one, `PLAN.md`, `README.md`, `ARCHITECTURE.md` and `SCHEMA.md` — searched case-insensitively for the phrases a restatement of the policy would have to use: "unit test", "end-to-end scenario", "test philosophy". "end-to-end scenario" matches nowhere outside this file. The other two match in seven places outside it, and every one of the seven is listed here so the next reader can re-run the grep and check this account rather than believe it. `README.md` has one: a link line calling the test philosophy binding, stating no rule of its own. `PLAN.md` has three — two name the philosophy as binding and point at it without restating it, and the third says of `internal/canon` that "the golden-fixture unit tests live here", which is a statement about where files sit rather than about what may be written. `SCHEMA.md` has one, in the adapter decision: the millisecond re-wrap "is the arm a direct unit test exercises", which says which arm one existing test covers and asserts nothing about the rule. `ARCHITECTURE.md` has two, and only one of them is of the shape this bullet corrects — the encoder/decoder/hash trio as "the canonical example of the one place unit tests are wanted", a second document's summary of the same widened rule, named here rather than fixed because another pass owns that file; the other reports correctly that `TESTING.md` puts the backoff schedule on its closed list, which is a citation rather than a summary. Nothing beyond those five files was examined: Go doc comments and test file headers were not surveyed at all, and this correction makes no claim about them.
- **The survey above was itself wrong when it was first written, at the round that wrote it, and the correction is dated the fifth round's repair pass (2026-08-01).** Its first draft said "`SCHEMA.md` matched none of them" and then disposed of the other files in a sentence each without enumerating what they matched. The `SCHEMA.md` claim had been true when the grep was run and was false by the time the round shipped, because a concurrent agent added the adapter sentence quoted above to that file in the same round; and the one-sentence disposals quietly passed over three of the seven matches: `PLAN.md`'s "unit tests", `ARCHITECTURE.md`'s second one, and the `SCHEMA.md` line just named. Neither omission changed the conclusion — none of the seven is a restatement of the testing policy — but both were checkable claims that a reader re-running the stated grep would have found false, in the one bullet whose whole point is that a survey claim has to be checkable rather than believed. That is the reason the seven are now written out one by one instead of summarised: a survey that names its members can be falsified by a reader in a minute, and a survey that reports a verdict can only be re-done.
