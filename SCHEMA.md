# icelake — schema declaration and evolution

This document is the detailed design for the one piece of `ARCHITECTURE.md`'s write path that is icelake's own API surface: how a caller declares a table's shape, and how that shape is allowed to change over time. **A declaration has two sources: a tagged Go struct, decided first and described first, and a JSON schema document read at runtime, decided at M10 and built at M12.** The second is designed in "A second source of a declaration: the runtime schema document" below, and it is a second *source*, not a second design: both produce the same `*Declaration`, and everything from "Table lifecycle at startup" onward applies to either without knowing which one it came from. It exists because that surface turned out to have real, non-obvious design decisions behind it — worth writing down precisely rather than leaving as an assumption. Everything here is the write-side story only; nothing in this document is read by, or relevant to, anything on the query side (`ARCHITECTURE.md`'s "Query side: deliberately not this project's problem" still holds completely — DuckDB and PyIceberg never see any of icelake's own Go types, only the real Iceberg metadata that results from this process).

## Declaring a table's schema: one Go struct, tagged, per table

This section is the *compile-time* source of a declaration, and it is the one every Go caller uses; the runtime source is below and produces the identical artifact through the identical calls. A table's shape is a single, plain, hand-written Go struct, using `apache/arrow-go`'s existing Parquet struct-tag support (`github.com/apache/arrow-go/v18/parquet/schema`, function `NewSchemaFromStruct`) — not a reflection trick over an arbitrary business object already used elsewhere in the caller's program, but a small struct whose only job is to be this declaration.

```go
type Fill struct {
    Symbol      string `parquet:"name=symbol, logical=String, fieldid=1" arrow:"symbol"`
    Side        string `parquet:"name=side, logical=String, fieldid=2" arrow:"side"`
    Price       int64  `parquet:"name=price, logical=decimal, precision=18, scale=9, fieldid=3" arrow:"price"`
    Quantity    int64  `parquet:"name=quantity, logical=decimal, precision=18, scale=9, fieldid=4" arrow:"quantity"`
    SequenceID  int64  `parquet:"name=sequence_id, fieldid=5" arrow:"sequence_id"`
    OrderID     string `parquet:"name=order_id, logical=String, fieldid=6" arrow:"order_id"`
    Source      string `parquet:"name=source, logical=String, fieldid=7" arrow:"source"`
    VenueTimeMS int64  `parquet:"name=venue_timestamp_ms, logical=timestamp, logical.unit=millis, logical.isadjustedutc=true, fieldid=8" arrow:"venue_timestamp_ms"`
}
```

The struct name (`Fill` above) carries no meaning to icelake beyond being a Go identifier — it is an arbitrary example, not a required or reserved name. Any adopting service names its own tables' structs whatever fits its own domain.

Every tag key used above was read directly out of `arrow-go`'s own tag parser (`parquet/schema/reflection.go`) rather than assumed: `name`, `type`, `length`, `scale`, `precision`, `fieldid`, `repetition`, `converted` and `logical`, plus `logical.<key>` sub-options, of which `logical.unit` (`millis`/`micros`/`nanos`) and `logical.isadjustedutc` are the ones a timestamp needs. (The parser's full key set also includes the map-specific `keytype`/`valuetype`/`keyfieldid`/`valuefieldid`/`keylogical`/`valuelogical` family, which this design never uses.) Physical type names in a `type=` tag are the Parquet thrift spellings (`BYTE_ARRAY`, `FIXED_LEN_BYTE_ARRAY`, `INT64`, …), uppercased before lookup. Note also that the tag parser reports errors by panicking internally; `NewSchemaFromStruct` recovers those and returns them as an error, so a malformed tag surfaces as a failed startup rather than a crash — which is the behaviour the "fail loudly" rules below depend on.

**`logical=String` on every `string` column is mandatory, not decoration.** A Go `string` field with no logical annotation becomes a bare Parquet BYTE_ARRAY, which `pqarrow` maps to Arrow `binary` and `iceberg-go` therefore records as Iceberg **`binary`** — a blob column, not a text column, in every downstream reader. Worse, it breaks the two-derivation cross-check below outright: `arreflect` infers Arrow `utf8` from the same Go `string`, so a bare `string` column disagrees with its own declaration on every table. `logical=String` makes the declared column Arrow `utf8` → Iceberg `string`, which is what `arreflect` produces anyway, so the two derivations agree with no adaptation. `converted=UTF8` is byte-identical in effect — both set the same Parquet String logical type *and* the same UTF8 converted type — and the tag parser lowercases its values before lookup, so `logical=string` and `logical=STRING` work too. `logical=String` is therefore a house convention picked for one consistent spelling, not the only form that works; a reviewer seeing `converted=UTF8` in a declaration is looking at a style difference, not a bug. An earlier version of this document's example structs omitted this and would have produced binary columns and a failed cross-check on first run.

**Corrected at the post-M9 completeness audit (2026-08-01):** the sentence above used to end with the parenthetical "all five spellings verified to produce the same column", and that claim outran its evidence. The audit re-ran all five against the pinned libraries and every one of them does still derive to the same Iceberg `string` column, so nothing here was wrong — but "verified" in this document's voice is a claim that something is held, and no test in the repository held it. What the five spellings really are is an observation about a third-party tag parser's lowercasing, recorded here as one from now on rather than asserted as a fact of icelake's own. No test was added to hold it, and the reason is worth stating rather than leaving as a silent omission for the next audit to find again. A test that declared five structs and asserted five identical columns would enumerate `arrow-go`'s parser with no icelake guarantee behind it, which is exactly the shape `TESTING.md`'s philosophy rules out; and the property a caller actually needs protecting is already enforced on every startup by the two-derivation cross-check described below. A spelling that stopped producing `utf8` on the declared side would immediately disagree with the `utf8` `arreflect` infers from the same Go `string`, and `OpenWriter` would refuse the table naming the column rather than quietly writing a binary blob into it. The failure mode here is a loud refusal, not a silent corruption, which is both why the cross-check is a stronger guard than an enumeration would be and why the enumeration is not worth owning. The one thing to take from the paragraph above is therefore unchanged and is the part that carries a real rule: some string annotation is mandatory, and a bare `string` is a binary column.

And the raw-payload analogue (`TESTING.md`'s Case B), which is the same machinery with a binary column:

```go
type EventArchive struct {
    SourceID        string `parquet:"name=source_id, logical=String, fieldid=1" arrow:"source_id"`
    EventKind       string `parquet:"name=event_kind, logical=String, fieldid=2" arrow:"event_kind"`
    SequenceOrdinal int64  `parquet:"name=sequence_ordinal, fieldid=3" arrow:"sequence_ordinal"`
    ObservedAtMS    int64  `parquet:"name=observed_at_ms, logical=timestamp, logical.unit=millis, logical.isadjustedutc=true, fieldid=4" arrow:"observed_at_ms"`
    Payload         []byte `parquet:"name=payload, type=BYTE_ARRAY, fieldid=5" arrow:"payload"`
    PayloadSHA256   string `parquet:"name=payload_sha256, logical=String, fieldid=6" arrow:"payload_sha256"`
}
```

**Rules that must hold for every declared struct, enforced by the tooling described below, not left to convention:**

- Every field must carry an explicit `fieldid` (and, where nesting is permitted at all — see below — that includes every field inside a sub-struct or a list of structs). An untagged field is not auto-numbered: `NewSchemaFromStruct` gives it field ID `-1`, `pqarrow` carries that through as `PARQUET:field_id="-1"`, and the third call in the chain below then refuses the whole schema with `invalid schema: arrow schema does not have field-ids and no name mapping provided` — even when only one field out of many is untagged. So the library already fails loudly here; icelake's own check exists to name the offending field rather than to catch something that would otherwise slip through.
- A `fieldid`, once shipped, is permanent: never reordered, never reused for a different field later, even if the original field is later removed. **Declared IDs must also match the schema's pre-order numbering, starting at 1, for a table's initial creation** (for a flat struct that is simply 1..N in declaration order) — see "Field IDs at creation" below, which is a real constraint imposed by `iceberg-go`, not a style rule.
- Every `string` field must carry `logical=String`, per the paragraph above. A bare `string` is a binary column and fails the cross-check.
- **Every field's Go type must be one of exactly seven: `bool`, `int32`, `int64`, `float32`, `float64`, `string`, `[]byte` — or a pointer to one of them, which is how an optional column is declared.** This is a closed whitelist enforced in code, not a style guide; anything else is refused before any derivation runs, with an error naming the field and its Go type. **Decision (2026-07-31): a plain `int` or `uint` is refused, and the reason is worth stating because the failure it prevents is invisible.** An `int` field derives cleanly — but `arrow-go`'s reflection branches on the type's bit width, so it becomes an Iceberg `long` on a 64-bit build and an Iceberg `int` on a 32-bit one. Nothing downstream objects, because both are perfectly valid columns. The damage is further along: the column type is recorded in the schema descriptor `ARCHITECTURE.md` stores in `staging_schemas`, that descriptor is hashed into `schema_fp`, and it is hashed again into every batch's content hash — so the same declaration compiled for two architectures would produce two different schema fingerprints and two different data-file object keys for identical data. `uintptr` is refused for the same reason. `int8`, `int16`, `uint8`, `uint16`, `uint32` and `uint64` are refused for a different one: they derive to a column the canonical encoding carries as a Go `int32` or `int64`, so an unsigned value past the signed ceiling would wrap silently once rows were staged. A caller with a `uint32` in its own domain converts it at the boundary, in its own code, where it can decide what to do about the range — exactly the discipline the decimal scaling rule above already asks for. (A nested struct or a slice is not covered by this whitelist; those are refused separately, by the flat-only scoping rule above.)
- Every field must also carry an `arrow:"<same name>"` tag alongside its `parquet:"..."` tag, naming the identical column. Two separate libraries read this one struct — `parquet/schema` for the declared schema and `arrow/array/arreflect` for the actual row data — and they read *different tag namespaces*. Requiring both, with matching names, is verbose but removes an entire class of silent divergence, and it is machine-checked at startup (see "Two derivations of one struct" below). It also means icelake does not depend on the incidental fact that `RecordFromStructArray`'s current validation ignores column names: if a future arrow-go tightened that check, a table declared this way would keep working.
- **Nesting is supported for declaring a table, but not for evolving one — and only for a plain sub-struct, not a slice of structs.** A struct field containing another struct becomes a nested group of columns and survives the full three-call derivation chain with its children's declared field IDs intact (verified: a `struct` field with children tagged `fieldid=10,11` derives to Iceberg `struct<10: …, 11: …>`). "Through the derivation" is the whole of that claim: those IDs are what the in-memory `declaredSchema` holds, and `CreateTable` then renumbers them along with everything else — the same `10, 11` come back from the catalog as `3, 4`. See "Field IDs at creation" below. A **slice** of structs does not: `NewSchemaFromStruct` builds the list's synthesized `element` node with no field ID, and the third call then refuses the schema with `cannot convert element: … missing field_id`. There is no tag that fixes this — `fieldid` on the slice field names the list, not its element. So lists of groups are not declarable through this path at all, regardless of the evolution question below. That is what the two libraries do in isolation, and it is *not* the refusal a caller actually receives: through icelake's own path the flat-only rejection below fires between the second call and the third, so the caller is handed a `CrossCheckError` naming the list column — the same check, and the same error, that refuses a plain sub-struct — and the third call's `missing field_id` is the backstop that would refuse it one call later if that check were ever removed. The two limits differ in lifetime rather than in which line stops them today: unblocking nested evolution would retire the flat-only rejection and leave the list of groups refused by the third call exactly as described here. This is a narrower limit than an earlier draft of this document claimed, and it costs nothing today because neither example table nests. But **Decision (2026-07-30): the reconciliation loop below is scoped to flat, top-level fields only**, and a declared struct containing a nested group is rejected at startup with a clear error rather than half-supported. The loop diffs single-segment field paths; it has no handling for a field inside a group, and pretending otherwise would mean a nested column change either silently doing nothing or producing a wrong `AddColumn` against a top-level path. Neither example table in `TESTING.md` needs a nested column, so this costs nothing today. It is recorded as a known, deliberately deferred limitation in `ARCHITECTURE.md`'s open questions, and this document previously contradicted itself on exactly this point.
- Any field added to a table **after** that table already exists must be declared as optional (a pointer type, e.g. `*string`), never required. See "Why optional" below for the mechanical reason this is enforced, not just recommended. A pointer field is treated as nullable by *both* libraries independently — `Optional` repetition on the Parquet side, `Nullable: true` on the `arreflect` side — which is why this rule survives the two-derivation cross-check without special handling.

## Column types: money, time, and raw payloads

Earlier drafts of this document left these as whatever the example snippet happened to show (`float64` for a price, a bare `int64` for a timestamp). That is a real decision hiding as an example, so it is made here explicitly.

**Decision (2026-07-30): money-like values — prices, quantities, amounts — use Parquet's DECIMAL logical type, never `float64`.** The motivating concern is financial data where exact fidelity is the whole point; a binary float cannot represent most decimal fractions exactly, so a price that round-trips through `float64` is not necessarily the price that was observed, and errors accumulate the moment anything sums or averages a column. Mechanically this is a `logical=decimal, precision=P, scale=S` tag on an `int64` field holding the *unscaled* integer value (a price of `1.234567890` at scale 9 is stored as `1234567890`). The Go field being an `int64` rather than a decimal value type is not a compromise on the storage side — the column really is DECIMAL(18,9) in Parquet, and really is `decimal(18,9)` in the resulting Iceberg schema, and every downstream reader sees it as such. **Worth being exact about the physical type, corrected at M4:** the *declared* Parquet schema derives an INT64-backed decimal from the `int64` field, and that is where the precision cap below comes from — but the file icelake actually writes does not go through that schema. Data files are built from Arrow `Decimal128` columns through `pqarrow`, so a committed object carries `FIXED_LEN_BYTE_ARRAY` DECIMAL(18,9), verified by reading one back. Nothing downstream can tell the difference (both are `decimal(18,9)` to Iceberg, and DuckDB reads both as `DECIMAL(18,9)`), and the cap of 18 is real regardless — it just lives at the declaration seam rather than in the bucket. It does mean the caller is responsible for scaling its own values into the declared scale before insertion, which is the same discipline any fixed-point representation demands.

The precision ceiling is 18 and is not arbitrary: `arrow-go`'s own applicability check (verified in `parquet/schema/logical_types.go`) allows precision 1–9 on INT32, 1–18 on INT64, and higher precision only on a fixed-length byte array. That check runs against the *declared* schema, which is INT64-backed, so the cap holds even though the written file is already a fixed-length byte array. A fixed-length-byte-array decimal is not currently *declarable* through this path, because the two derivations described below disagree about what a `[16]byte` field means. 18 digits with 9 decimal places covers both motivating cases comfortably; the limitation is recorded in `ARCHITECTURE.md`'s open questions rather than papered over.

**Decision (2026-07-30): timestamps use Parquet's TIMESTAMP logical type with an explicit millisecond unit and explicit UTC adjustment, never a bare `int64`.** The tag is `logical=timestamp, logical.unit=millis, logical.isadjustedutc=true` on an `int64` field holding epoch milliseconds. Milliseconds match the `_ms` naming already used for these columns; `isadjustedutc=true` is what tells every downstream reader the value is a real instant rather than a wall-clock reading with no zone. `arrow-go` defaults `isadjustedutc` to true when it is omitted, but it is written out explicitly anyway, because "what timezone is this column" is not a question worth answering by knowing a library default. The payoff is entirely on the read side and is free: DuckDB, PyIceberg, and anything else that speaks Iceberg render the column as a timestamp automatically, instead of every consumer independently remembering that column 8 is epoch millis.

The `_ms` suffix stays in the column name even though the type now carries the unit. It documents the *source* precision — what the caller's Go `int64` holds — not the stored precision. The stored precision is microseconds, and that is not negotiable: Iceberg's `timestamptz` type is defined as microseconds since epoch, so a declared Arrow `timestamp[ms, tz=UTC]` column becomes `timestamptz` in the table and the values are upcast on write. **Corrected at M4: icelake performs that upcast itself, and has to.** The M0 verification behind this paragraph went through `iceberg-go`'s own append path, which writes the Parquet file and upcasts on the way; icelake's write path writes its own Parquet file, so it derives the schema its data files are written with from the declared one by widening every millisecond UTC column to microseconds, and the column adapter multiplies the values to match. Getting this wrong would not fail anywhere — a file storing milliseconds under a column the table calls `timestamptz` is perfectly well-formed — it would just read back a thousand times too small, which is why the round-trip assertion in `TESTING.md`'s scenario 1 compares the instant a reader reports against the exact epoch milliseconds the record was written with. Verified end to end: a row written with `VenueTimeMS = 1700000000000` reads back as raw `1700000000000000` at microsecond unit — the same instant, losslessly, just at a finer stored unit. Nothing rounds or drifts; the only thing the `_ms` name now tells a reader is that the underlying observation had millisecond granularity.

**Decision (2026-07-30): a raw payload column is `[]byte`, stored as a plain Parquet BYTE_ARRAY with no logical type.** `arrow-go` maps `[]byte` to BYTE_ARRAY by default; the `type=BYTE_ARRAY` tag in the Case B struct above says so explicitly rather than relying on that default. No logical annotation is applied — not JSON, not BSON, not String — regardless of what the bytes actually are. This is the format-agnostic choice on purpose: the same column has to hold msgpack today, possibly JSON tomorrow, possibly something compressed inside a provider's response, and annotating it as JSON would be a claim that some future reader will try to enforce and some future payload will violate. Bytes in, identical bytes out, verified by the `payload_sha256` round-trip in `TESTING.md`. A caller that genuinely has JSON and wants readers to know can annotate `logical=json` on its own column — icelake's position is only that this is not the default.

## From a struct to a real Iceberg schema: three verified library calls

Turning the struct above into the object `iceberg-go` actually uses to create or evolve a table is three calls, chained, each into the next. All three are real, existing functions in the two libraries icelake already depends on (pinned in `PLAN.md`'s "Dependency pins" section) — nothing here is generated code, and nothing here is a new dependency.

```go
parquetSchema, err := schema.NewSchemaFromStruct(Fill{})
// github.com/apache/arrow-go/v18/parquet/schema
// Reads the struct via reflection at runtime (the same mechanism
// encoding/json uses for its own tags) and returns a real Parquet
// schema tree — the same shape the Parquet writer itself consumes.

arrowSchema, err := pqarrow.FromParquet(parquetSchema, nil, nil)
// github.com/apache/arrow-go/v18/parquet/pqarrow
// Converts to the in-memory Arrow representation the writer builds
// records from. Every field's permanent ID is carried across into
// the Arrow field's own metadata, under the literal key
// "PARQUET:field_id" — confirmed directly from source, not inferred.

declaredSchema, err := table.ArrowSchemaToIceberg(arrowSchema, false, nil)
// github.com/apache/iceberg-go/table
// Reads that same "PARQUET:field_id" metadata key back out and
// produces the *iceberg.Schema used to create or compare against a
// real table. If any field is missing that metadata key while
// others have it, this call fails outright with an explicit error
// ("missing field_id") rather than silently guessing an ID — this
// is a real, load-bearing safety property of the library itself,
// not something icelake has to build.
```

This whole sequence is pure, local, in-memory computation. No network call, no catalog access, and no data file is touched by any of it — it only ever produces `declaredSchema`, an in-memory answer to "what should this table's shape be, according to the struct, right now."

### Field IDs at creation: `CreateTable` renumbers, so declarations must match the pre-order numbering

`declaredSchema` carries the field IDs a human wrote in the struct tags — but a catalog's `CreateTable` does **not** store them as-is. It builds the table's first metadata through `table.NewMetadata`, which calls `reassignIDs` → `iceberg.AssignFreshSchemaIDs(schema, nil)`, handing out `1, 2, 3, …` in **pre-order traversal of the schema tree**, and the declaration's own numbers are discarded entirely. Whatever the struct asked for, the table gets the pre-order numbering.

For a flat struct that is the same thing as "`1..N` in declaration order", and a declaration numbered that way survives creation untouched. For a struct declared with gaps — say `fieldid = 1, 5, 9`, the natural result of removing a column before a table is first created — the table is created with `1, 2, 3` instead. That is worth stating carefully, because it is a *silent* rewrite, not a rejection: `CreateTable` returns no error at all, the table is created, and only later does every reconciliation pass diff a declaration of `1, 5, 9` against a live table of `1, 2, 3` and try to add three brand-new columns. Verified directly: a three-field struct declared `1, 5, 9` comes back from `CreateTable` as `1, 2, 3`, no error raised.

**Pre-order is not the same as "declaration order" once anything nests**, which is why the rule has to be phrased against the traversal rather than against the top-level field list. A struct declared `1: a`, `2: grp<10: x, 11: y>`, `3: c` satisfies "top-level IDs are `1..N` in declaration order" and is still renumbered, because the group's children consume IDs between the group and the field after it. Verified: that declaration comes back from `CreateTable` as `1: a`, `2: grp<3: x, 4: y>`, `5: c`.

So the rule is mechanical, not aesthetic: **at the moment a table is first created, its declared field IDs must equal the pre-order numbering of the declared schema** — assign `1` to the first field, then continue depth-first through any nested group's children before moving to the next sibling. icelake computes that numbering and refuses to call `CreateTable` if the declaration disagrees, rather than letting the silent rewrite happen. Gaps and out-of-order IDs are fine — expected, even — for every *subsequent* version of that struct, because after creation nothing renumbers anything. (Today the flat-only scoping decided above means a nested declaration is rejected before this check ever runs, so in practice the check only ever sees flat structs, where pre-order and declaration order coincide. The rule is written against the traversal anyway, so that it stays correct rather than merely lucky if nesting is ever unblocked.)

There is a matching consequence on the evolution side. `UpdateSchema.AddColumn` takes no field-ID argument at all: it assigns the new column's ID itself, from the table metadata's monotonic `last-column-id` counter, so the `fieldid` in a newly added field's tag is never transmitted to the library and never consulted. A caller who adds `fieldid=20` to a table whose highest ID is 8 gets a column with ID 9. So **the number in a `fieldid` tag is authoritative only for fields that already exist in the table**; for a newly added field it is a request nothing ever reads.

The reasoning about what happens next was previously stated as reasoning rather than as a result: if the declaration keeps saying `20` after the table has assigned `9`, the following startup's reconciliation loop looks up field ID 20, does not find it, and calls `AddColumn` for a column name the table already has. That specific library behaviour *was* exercised — adding an already-present column name fails with `multiple fields for name c: 3 and 4` — but the full startup narrative around it had not been run end to end, and this note carried it as an expectation to confirm at **M4**.

**Confirmed at M4, and the answer is better than the expectation.** The declaration is refused, loudly and with a typed error naming the field — but it is refused *earlier* than the narrative supposed, at declaration, before the catalog is contacted at all. The pre-order field-ID rule above applies to every declaration icelake derives, not only to one about to create a table, so `fieldid=20` on the ninth field of a nine-field struct fails `Declare` with a `FieldIDError{Field: "venue_order_type", FieldID: 20, WantID: 9}` and `OpenWriter` returns no writer. The reconciliation loop never runs, no `AddColumn` is issued, and the table is left exactly as the previous run committed it — asserted in the M4 test suite, including that the table's data files are untouched by the refused open.

That earlier refusal is not a coincidence, and it is what makes the confusing failure the narrative predicted unreachable through icelake's own path. Every ID icelake declares is the pre-order numbering, `1..N` for a flat struct; `AddColumn` assigns exactly `last-column-id + 1`; so a table icelake created and has only ever evolved through this loop has contiguous IDs `1..N` at every point in its life, and a declaration that gets past `Declare` can only ever carry IDs that table agrees with. The `multiple fields for name` failure remains reachable in principle — against a table icelake did not create, or one whose numbering something else moved — which is why the loop still returns a `ReconcileError` wrapping whatever the library says rather than assuming it cannot happen. The discipline it reduces to is unchanged and is what icelake requires: **when adding a field, give it the next ID after the table's current maximum**, so the tag and the assignment agree by construction. That is the pre-order rule above, applied one column at a time.

(This note previously pointed at M1 before being retargeted. M1 built the schema layer — derivation, name validation, nested rejection, the pre-order field-ID check, the two-derivation cross-check and the column adapter — all of which is pure in-memory computation against no table at all. The narrative was about the *reconciliation loop* running against a live table, which is `PLAN.md`'s M4, and that is where it was confirmed.)

## Two derivations of one struct, and the gap between them

One struct is read by two independent reflection layers: `parquet/schema` derives the *schema* (above), and `arrow/array/arreflect` derives the *row data* (below, under "What's hand-written"). They were written separately, they read different tag namespaces, and — checked against `arrow-go`'s source rather than assumed — **they do not agree on the two logical types the section above just adopted.**

Specifically, for a declared `int64` field:
- the schema path produces Parquet DECIMAL(18,9) → `pqarrow` maps it to Arrow `Decimal128(18,9)`, and TIMESTAMP(millis, UTC) → Arrow `Timestamp(ms, "UTC")`;
- the data path (`arreflect`) infers from the Go type alone and produces plain `Int64` for both.

There is a third disagreement, and it is the one that bites first because every table has string columns: a Go `string` field with no logical annotation produces Arrow `binary` on the schema path and Arrow `utf8` on the data path. That one is not adapted, it is *declared away* — `logical=String` on every string column (see the tag rules above) makes the schema path produce `utf8` too, and the two sides agree with no conversion at all. Verified column by column: with `logical=String` applied, the only remaining disagreements on a fully-featured declaration struct are exactly the decimal and timestamp cases below, and pointer fields agree on nullability on both sides without help.

And there is no Go field type that satisfies both sides: `arreflect` produces `Decimal128` from an `arrow-go` `decimal128.Num` field and `Timestamp` from a `time.Time` field, but `NewSchemaFromStruct` turns *any* struct-typed field into a nested group node (only `float16.Num` and `parquet.Int96` are special-cased), so declaring either of those types would produce a group of columns where a single column was meant. Going the other way — deriving the schema from `arreflect.InferSchema[T]()` instead — is worse: its tag vocabulary has no field-ID concept at all, so it would throw away the permanent IDs the entire evolution design rests on.

Left unhandled, this is not a silent corruption — `array.RecordFromStructArray`'s own validation compares raw type per column and would reject the mismatch — but it *is* a hard failure the first time anyone declares a decimal or a timestamp, which is to say immediately.

**Decision (2026-07-30): icelake owns a small, explicitly-whitelisted column adapter between the two derivations, and cross-checks them at startup.** Two pieces:

1. **The adapter.** After `arreflect` produces the columns for a batch, each column whose inferred Arrow type differs from the target type is converted. There are two whitelists, not one, and they are deliberately different sizes — a column pair is judged against a different list depending on whether the question is "may a caller *declare* this?" or "may icelake *write* this?". The declaration-time list has two conversions on it: `Int64` → `Timestamp(ms, UTC)`, a re-wrap of the same buffer with a different type (Arrow stores timestamps as int64; no value is touched, and the output shares the input's value buffer), and `Int64` → `Decimal128(P,S)`, a real per-value sign-extension into 16 bytes. The write-time list is those two plus `Int64` → `Timestamp(us, UTC)`, which multiplies each millisecond value by 1000 into a newly allocated buffer. Anything not on the list being asked — any other type pair — is a hard error, not a best-effort cast. This is the only place icelake reinterprets a caller's data, it is one `switch` with an identity arm, three conversion arms and a loud `default`, and it is bounded by the type decisions above rather than open-ended.

   **Which conversion actually reaches a data file is the part worth being precise about, because it is not the one this section named from M4 until this round.** The target type a column is adapted *to* on the write path is not the declared type: it is the corresponding field of the file schema, which is the declared schema with every millisecond UTC column widened to microseconds (the widening described under "Timestamps" above, and the reason it has to happen at all). So a declared `timestamp[ms, tz=UTC]` column is asked for microseconds by the time a batch is being encoded, and the conversion that runs is the rescale: a pass over every value, a multiply, and a new buffer, per column per batch. The millisecond re-wrap is what a *declaration* is allowed to ask for and is the arm a direct unit test exercises; the write path does not reach it, because the file schema it adapts against has already replaced every declared millisecond column with a microsecond one. That is worth stating in this order because the re-wrap is the cheap one, and a reader costing out the write path from the old sentence would have been costing the wrong arm — free, sharing a buffer, when the real one allocates and touches every value.

   **Corrected at the completeness audit's fifth round (2026-08-01).** This item used to say "only these conversions exist" and name exactly two, then call itself "roughly one `switch` with two cases and a loud `default`"; the switch in `internal/schemamap/adapt.go` has four non-default arms, and the timestamp conversion the old text named as *the* timestamp case is the one arm the write path never takes. The error was not a stale count on its own — a count can be fixed by counting again. It was that the two whitelists were folded into one sentence, so a real design decision (declaring microseconds is refused; writing microseconds is compulsory) read as a single closed list, and the arm that carries the whole timestamp story to disk had no place in it. What makes this a particularly poor sentence to have left standing is that this document had already recorded the truth elsewhere and in its own voice: the "Timestamps" bullet above says, corrected at M4, that icelake performs the upcast itself and that "the column adapter multiplies the values to match". A reader who met both would have had to decide which half of the same document to believe. It is also worth naming what this correction is *not* fixing, since "two cases" appears more than once here: the cross-check item immediately below says "exactly one of the two whitelisted adaptations" and is correct as written, because the cross-check runs before any row exists and is precisely the declaration-time list; and the M0 verification note further down describes a run through "the two-case adapter", which is an accurate record of the build that existed at M0 — the microsecond arm was added at M4, and that run reached Parquet through `iceberg-go`'s own append path, which did the widening itself. Neither has been rewritten, because neither is wrong.
2. **The cross-check, at `OpenWriter` time, before a single row is accepted.** icelake computes both derivations for `T` and requires: identical column count, identical order, identical names, identical nullability, and per column either an identical type or exactly one of the two whitelisted adaptations. Any disagreement fails the table open, loudly, naming the column.

That cross-check also settles something this document previously carried as an unverified assumption: whether `arreflect`'s column order for a struct always matches `NewSchemaFromStruct`'s order. It no longer needs to be assumed, and it no longer needs a test to *prove* it in general — it is checked at every startup for every real table, on the actual struct in use, and a mismatch stops the program rather than writing something wrong. (A test still covers the check itself firing correctly; see `TESTING.md`.)

## A second source of a declaration: the runtime schema document

**Decision (2026-08-01, M10): a table's declaration has a second source — a JSON schema document, read at runtime — and everything downstream of the declaration is the same code, reached through the same three calls, producing the same `*Declaration`.** The gap this closes is structural rather than a matter of taste. `OpenWriter[T]` needs a Go type at compile time, so every table icelake can write has to have been known to whoever compiled the binary; and the moment this project ships a program of its own (`apps/icelake`, which reads JSON lines on stdin and whose tables belong to the operator, not to the build), there is no type for it to name. The two alternatives were both considered and are worse in the same direction. Shipping a fixed set of structs in the CLI would make icelake's binary decide what tables an operator may have, which is precisely backwards. Generating Go from a document and compiling it at run time puts a toolchain inside a daemon. What is actually needed is much smaller: the declaration is the only part of this design that reads a Go type at all, so a second way to state a declaration is a second front door onto machinery that never cared where the shape came from.

### The document

```json
{"tables": [
  {"namespace": "market", "table": "fills", "fields": [
    {"name": "symbol", "type": "string",        "fieldid": 1},
    {"name": "price",  "type": "decimal(18,9)", "fieldid": 2},
    {"name": "ts_ms",  "type": "timestamptz",   "fieldid": 3},
    {"name": "note",   "type": "string",        "fieldid": 4, "optional": true}
  ]}
]}
```

Parsed with the standard library's `encoding/json` and `DisallowUnknownFields`, which adds no dependency and refuses a misspelled key rather than ignoring it — a `"feildid"` that parsed as "no field id" would be the exact class of silent shape change the permanent-ID rule exists to make impossible.

**The type vocabulary is exactly the nine canonical kinds** from `ARCHITECTURE.md`'s "Batch identity" section: `boolean`, `int`, `long`, `float`, `double`, `string`, `binary`, `decimal(P,S)`, `timestamptz`. Not the Go whitelist, and not `arrow-go`'s tag spellings. That is a decision rather than a convenience, and the reason is that the Go whitelist exists to work around an ambiguity a document does not have: `int32` and `int64` are on that list, and plain `int` is off it, because reflection over a Go type cannot say which width the author meant. A document names the column type outright, so the smallest honest vocabulary is the set of types the rest of this system already speaks — the same nine the canonical encoding carries, one-to-one with the Iceberg types the table ends up with, with no third spelling to keep in step. `timestamptz` values are epoch milliseconds and are stored as Iceberg microseconds, which is the identical contract the struct path's `logical.unit=millis` tag creates and is upcast by the identical adapter arm; the `_ms` naming convention has no analogue here because the unit is in the type rather than in the column name.

**`fieldid` is mandatory on every field and carries exactly the meaning it carries in a struct tag** — permanent, never reordered, never reused — and it is subject to the same pre-order rule at creation set out under "Field IDs at creation" above, which for the flat shapes this path can express means `1..N` in document order. Nothing about that rule is relaxed for being easier to edit; a document is easier to edit than a struct, which is an argument for the rule rather than against it. `"optional": true` is what a pointer type says on the struct path, and it is absent-means-required for the same reason a value type is required there: a column that is optional by omission is a column nobody decided about.

**The refusals, all of them before any table is touched:** an unknown key anywhere, a duplicate `namespace`/`table` pair, a table with no fields, two fields with the same name, a type spelling not in the nine, a malformed `decimal(P,S)` or one whose precision exceeds the 18 the declaration path caps at, and a `decimal` whose scale exceeds its precision. Each is a `SchemaDocError` naming the table and, where one field is at fault, the field. Field-ID violations are the deliberate exception and reuse `FieldIDError`: the rule being broken is the same permanence rule a struct breaks, and a caller matching on it should not have to know which of the two declaration sources produced the table.

### Deriving it: a programmatic twin of the first library call, and then the same two

The struct path is three chained library calls. This path replaces **only the first**. Where `schema.NewSchemaFromStruct` reads tags off a Go type to build a Parquet schema tree, `DeclareFields(namespace, table, []FieldSpec)` builds the same tree directly, node by node, through `arrow-go`'s own constructors (`schema.NewPrimitiveNodeLogical` for each column, `schema.NewGroupNode` for the root). Calls two and three — `pqarrow.FromParquet` and `table.ArrowSchemaToIceberg` — are then the identical shared tail, factored out of `Declare` so that both sources run the same code rather than two copies of it. That is the whole of the mechanism, and it is why nothing downstream of `*Declaration` had to change: the artifact is not merely equivalent, it is produced by the same functions.

Two details of the twin are load-bearing and are recorded so a later reader does not "simplify" them. **A decimal column is built on physical `INT64`**, because that is what the struct path derives from an `int64` field, and it is where the precision-18 ceiling comes from. **A timestamp column is built with logical unit millis and `isAdjustedToUTC` true**, for the same reason.

**Corrected at M12, when both were built and then deliberately broken to see what would catch them: the consequence stated here was wrong, and being wrong about it put the wrong test in charge of the property.** This paragraph used to say that a decimal built on a fixed-length byte array would derive "a *different* Iceberg column" and "a different schema fingerprint for a table two writers share", and that the timestamp detail carried "the same consequence". Neither survives contact with the code, and neither mutation moves the fingerprint. `pqarrow.FromParquet` maps a decimal logical type to the same Arrow decimal whichever physical type carries it, so the Iceberg column comes out `decimal(18, 9)` either way. The microsecond timestamp looks like a different case and is not: Iceberg's `timestamptz` carries no unit at all — `iceberg-go` maps millisecond and microsecond Arrow timestamps to the identical type, special-casing only nanoseconds — so the Iceberg column is the same there too. The descriptor records id, name, type, precision, scale and requiredness, and nothing about physical storage or timestamp units, so it fingerprints identically under both mutations. That was measured, not reasoned: each mutation was made in turn, and the runtime fingerprint cross-check passed both times while `TestStructAndFieldsDeriveOneSchema` failed both times. So the fingerprint cross-check below catches neither of the two, and what it actually pins is worth stating in its own terms rather than as a claim about physical nodes: that the Parquet-to-Arrow-to-Iceberg round trip preserves every column's id, name, type and requiredness — which is the property the write path depends on, since that is what the descriptor is taken over. The physical-node and unit fidelity is pinned instead by `TestStructAndFieldsDeriveOneSchema`, which compares the two declarations' **Parquet** schemas as well as their Arrow and Iceberg ones; that comparison catches both mutations — the decimal at the Parquet layer, the timestamp at both the Parquet and Arrow layers — and it was verified by making both of them and watching it fail. The lesson is the ordinary one for this repo: a cross-check is only as good as the artifact it compares, and a claim about what a check catches is a claim to be tested rather than reasoned about.

**The risk this introduces is drift, and it is pinned by a cross-check that is a twin of the struct path's cross-check rather than a copy of it.** The struct path compares two independent reflections of one struct against each other — `parquet/schema` against `arreflect` — and that check has no analogue here, because a document is read once and there is no second reader to disagree with. The exposure is different in kind: it is that the hand-built Parquet nodes stop matching what the tag parser would have built for the equivalent struct, silently, on some future `arrow-go` bump. So the check runs against the thing that actually matters downstream. The fingerprint of the descriptor derived *through the chain* — `canon.Describe(table, decl.IcebergSchema())` — must equal the fingerprint of a descriptor built **directly from the field specs**, by `canon.FromFields`, which never touches Parquet or Arrow at all. Two independent routes from one input to one canonical form; equality of the two fingerprints is exactly the property the write path depends on, since that fingerprint keys `staging_schemas` and is hashed into every batch key and therefore into every object name. A disagreement is a `CrossCheckError`, raised at open, before a row is accepted, and the check walks the two descriptors to name the first column they differ on so that the error carries the `Table`/`Column` pair it already promises. `TESTING.md` pins the same property from the other side, with a struct and an equivalent document asserted to produce equal Arrow schemas, equal Iceberg schemas and equal fingerprints — which is what makes "a struct writer and a dynamic writer can share a table, and replay can cross between them" a checked fact rather than an intention.

**`DeclareFromDescriptor(namespace, table, *canon.Descriptor)` is a third entry onto the same path, and it exists for one caller.** `ARCHITECTURE.md`'s transition drain has to reconcile a table forward to the shape of a spool file written weeks earlier, with no struct and no document in the process that describes it — what it has is the descriptor the spool stored beside the file. A `canon.Field` already carries an id, a name, a kind, a precision and scale, and a required flag, which is a `FieldSpec` under another name, so this is a conversion into `DeclareFields` rather than a fourth derivation. It follows that a table the drain creates is created from a persisted descriptor, and that the pre-order check at creation applies to it exactly as it applies to anything else.

**Corrected at M11, when it was built: the parameter is the descriptor's columns as `[]iceberg.NestedField`, not the `*canon.Descriptor` itself, and `DeclareFields` takes the same list rather than a `FieldSpec` type of its own.** The signature above assumed `internal/schemamap` may import `internal/canon`, and it may not: `internal/canon`'s package-internal tests import `schemamap` — deliberately, so the golden descriptor is derived through the real declaration chain rather than hand-built — and Go refuses the resulting cycle in that package's test binary. So `canon.Descriptor` grew `IcebergFields`, the exact inverse of the `describeField` mapping that produced it, and the drain hands that list to `schemamap.DeclareFromDescriptor`. Nothing about the design changes: the columns are the same columns, the derivation is still `DeclareFields` and then the shared tail, and the pre-order check still applies. What changes is which package owns the conversion, and the reason it has to is worth keeping — the Iceberg field list is the one shape vocabulary both packages already speak, so using it costs no second spelling of the nine types, which is what a `FieldSpec` living in `schemamap` would have been. The document path M12 builds derives into the same `DeclareFields`, mapping its nine type spellings onto the same list.

### Rows without a Go type: the JSON coercion table

A dynamic writer's row is `Record = map[string]any` and its front doors are `InsertJSON(ctx, line []byte)` and, from M16, `InsertCBOR(ctx, item []byte)`; the first one, which decodes with `json.Decoder.UseNumber()` — the exact-number path, where a JSON number arrives as its own digits rather than as a `float64` that has already lost them. `DynamicWriter` is a defined struct that embeds `*Writer[Record]` — deliberately a wrapper rather than an alias, because Go does not allow a method to be declared on an instantiated generic type and `InsertJSON` has to be a method. Embedding promotes `Insert`, `Flush`, `Close`, `Pending` and `Status` unchanged, so there is exactly one writer implementation in this library and the wrapper adds a single method to it: flush, replay, status, the staging ceiling, poison checking and every guarantee this project makes are the same objects doing the same work.

**Decision (2026-08-01, M10): the JSON-to-column mapping is a closed table, and every value it does not cover is a loud, typed refusal — never a best-effort conversion.** This is the same discipline as the column adapter's whitelist and the Go type whitelist, applied at the one seam where data now enters without a compiler having looked at it. Each refusal is a `RecordError` naming the namespace, the table, the field and a `Kind`; a refused row is not accepted, exactly like a `PoisonError`, so the caller still owns it.

| declared column | accepted | refused, and why |
|---|---|---|
| `boolean` | JSON `true`/`false` | `0`, `1`, `"true"` — a boolean spelled as something else is a caller's bug, not a dialect |
| `int`, `long` | a `json.Number` with an integral value inside the column's range; a `float64` that is integral and in range | any non-integral value; **any value whose magnitude exceeds 2^53 and only reached the column through a binary float**, refused as inexact even when it looks whole, because past that point the value in hand is already not necessarily the value that was written. That covers a `float64` and, equally, a `json.Number` that does not parse as an integer on its own — `"1.0"`, `"10.00"` and `"1e3"` are integral values a caller may reasonably write, are accepted as such, and are read through a `float64` to find out, so they obey the same exactness rule. A `json.Number` whose digits *are* an integer is taken exactly as written and is bounded only by the column's range, which is the whole reason `InsertJSON` decodes with `UseNumber` |
| `float`, `double` | any JSON number | — |
| `decimal(P,S)` | a `json.Number` or a string, in JSON's own number grammar with the exponent removed — an optional minus, at least one digit, and optionally a point and at least one more digit — with at most `S` fraction digits, scaled to the declared scale | **a `float64`, always, whatever its value** — the whole of the money decision above is that a decimal never travels through a binary float, and an exception here would be the one place it did. An exponent is refused rather than expanded; and `".5"`, `"5."` and `"+1.5"` are refused for the reason the binary row gives, that a value two producers can spell two ways is a value they can disagree about while both believing they are right |
| `timestamptz` | an integral number read as epoch milliseconds, or an RFC3339 string with whole-millisecond precision | a string carrying microseconds or finer, refused rather than rounded — a silently truncated instant is the failure this column type exists to prevent |
| `string` | a JSON string, valid UTF-8 by the same poison check the struct path runs | — |
| `binary` | a string in standard base64 with padding, or a Go `[]byte` handed to `Insert` directly | any other text encoding; there is exactly one accepted *text* spelling so that a round trip is a fact rather than a guess. `[]byte` joined the accepted Go values at M16 with the CBOR column below, because a format that can carry bytes should not have to base64 them to get in |
| any optional column | JSON `null`, or the key absent | — |
| any required column | — | `null`, or the key absent: a required column has no zero value to substitute, and substituting one is inventing data |
| any key not in the declaration | — | refused; an unknown key is either a typo or a schema the document has not caught up with, and both want a person |

**Decision (2026-08-04, M16): a record may also arrive as CBOR, the mapping is a second closed column of the same table, and it is a column rather than a second table because the rules are the same rules.** A `DynamicWriter` gained `InsertCBOR` and `InsertCBORBatch` beside the two JSON doors, and `IngestStream` reads either encoding off a record's first byte with nothing configured (`ARCHITECTURE.md`, M16). What travels differently is the bytes; what a column may hold does not move at all. The mechanism is that a CBOR value is read into exactly the Go values the table above already names — an integer becomes its own decimal digits as a `json.Number`, which is the same exact-digits shape `InsertJSON`'s `UseNumber` decode produces — so the coercion table below it is not merely equivalent, it is the same code. The one addition to the Go-value whitelist is `[]byte`, decided under `binary` below.

| declared column | accepted as CBOR | refused, and why |
|---|---|---|
| `boolean` | CBOR `true`/`false` | an integer 0 or 1, a text `"true"` — exactly as in JSON |
| `int`, `long` | a CBOR integer inside the column's range, taken as written; a CBOR float that is integral and inside 2^53 | **an integer past 2^53 is *accepted*, and this is the one row where CBOR can do something JSON's number path cannot** — a CBOR integer is an integer by construction and never travelled through a binary float, so there is nothing for the 2^53 rule to protect against. A *float* reaching one of these columns meets exactly the JSON rule: non-integral is refused, and integral above 2^53 is refused as inexact. An integer outside the int64 range, or outside an `int` column's 32 bits, is refused as out of range |
| `float`, `double` | any CBOR float — half, single or double | — . The three widths are one column type: nothing about the column changes because a producer chose fewer bytes for the same value. A CBOR integer is accepted too, on the same terms a JSON integer is |
| `decimal(P,S)` | a text string of digits in the same grammar the JSON column states, or a CBOR integer | **a CBOR float, always, whatever its value and whatever its width** — the money decision is that a decimal never travels through a binary float, and this format makes that easier to get wrong rather than harder: a producer who would have had to type digits into JSON can hand over a double here without noticing. Tag 2 and tag 3 bignums are refused with every other tag, below |
| `timestamptz` | a CBOR integer read as epoch milliseconds, or a text string in RFC3339 at whole-millisecond precision — **exactly the two JSON forms and no third one** | a string finer than a millisecond, refused rather than rounded; and **CBOR tag 0 and tag 1, the format's own date/time tags**, refused with every other tag, below |
| `string` | a CBOR text string, valid UTF-8 by the decoder's own rule *and* by the poison check the struct path runs | a CBOR **byte string**, which is the row this format adds: bytes are not text, and reading them as text is the silent misreading the whole table exists to prevent |
| `binary` | a CBOR byte string, **as it stands, with no base64 anywhere**; or, still, a text string in standard base64 with padding | any other text encoding. Both arms end at the same `[]byte`: a format that can carry bytes carries them, and a format that cannot spells them exactly one way |
| any optional column | CBOR `null`, or the key absent | **CBOR `undefined`**, which is refused rather than read as null: null means a column has no value, undefined means something else, and treating them alike would decide quietly that they are the same |
| any required column | — | `null`, `undefined`, or the key absent |
| any key not in the declaration | — | refused, exactly as in JSON |
| **any tagged value, in any column** | — | **refused, all of them, including tags 0, 1, 2 and 3** — see the decision below |
| any array or map as a column's value | — | refused: no column holds one, and guessing which one a caller meant is how a value ends up in a column that will not say what happened to it |

**Decision (2026-08-04, M16): every CBOR tag is refused, in every column, and the two that look most like they should be accepted — tag 0 and tag 1, the format's own date/time tags — are refused with the rest.** The argument for accepting them is real and is worth writing down before rejecting it: tag 1 is exactly "this integer is an epoch time", which is the meaning a `timestamptz` column already gives an integer, so accepting it would cost nothing and would let a producer say what it means. It is rejected on the rule this table has enforced since M10 — one value, one spelling. A `timestamptz` accepts an integer and an RFC3339 string, and that is two; adding tag 0 and tag 1 makes it four, of which two are refusable only by their content (tag 1 admits a *float* epoch time, which this column refuses, so half of a tag the table had said it accepted would still be refused). Tag 2 and tag 3 are worse in the same direction: a bignum is a second numeric grammar for the column that has spent this whole document refusing second numeric grammars. And an allow-list of tags is not a closed table but a growing one, since the registry has hundreds of them and a producer's library applies them without being asked. So the refusal is on the *shape* rather than on the number: a value whose first byte is major type 6 is refused, whatever the tag is, which makes a tag icelake has never heard of behave exactly like tag 0. The cost accepted is that a producer whose encoder tags timestamps by default has to turn that off, and the refusal names the column and says so.

**One consequence of the tag rule reaches how the decode is written, and it is recorded because it looks like an inefficiency.** The row is decoded in two steps — into its fields' raw bytes first, then each field on its own — rather than straight into a map. Decoding straight into a map hands back a value with the tag already applied and the field it came from already forgotten: tag 1 arrives as a `time.Time`, tag 2 as a `big.Int`, and `undefined` as the same `nil` that `null` produces. The two-step decode is what lets a tagged value be refused *as a tagged value, naming its column*, and lets `undefined` be told from `null` at all. It is measurably slower than a one-step decode would be — roughly ten to fifteen percent, measured in `TESTING.md`'s benchmark section — and the exactness is what that buys.

Everything in that table is about *representability*, not meaning — the same boundary the poison decision draws in `ARCHITECTURE.md`. A wild timestamp, an unexpected string in a column an application treats as an enum, a negative quantity: all perfectly representable, all accepted, all the caller's own business rules to enforce on their own side of the line.

## Table lifecycle at startup

This runs once per declared table, every time the program starts — deliberately unconditional **in bucket mode**, for the same reason explained in "Why no migration log is needed" below. Concretely it runs inside `OpenWriter[T]` — and, identically, inside `OpenDynamicWriter` (`ARCHITECTURE.md`, "Public API surface") — after the namespace/table name validation and the cross-check the declaration's own source ran, and before the writer accepts its first record. Nothing below distinguishes the two sources: what this lifecycle consumes is a `*Declaration`, and by the time it runs, a document-derived declaration and a struct-derived one are the same thing.

**Local-only mode skips this lifecycle entirely, and the honest place to say so is here rather than in a footnote.** A local-only store opens no catalog and has no Iceberg table (`ARCHITECTURE.md`, "Catalog design"), so there is nothing to load, nothing to create and nothing to compare a declaration against — no branch below runs, and `OpenWriter` goes straight from the declaration to accepting records. The declaration is still fully derived and fully cross-checked, because it is what the canonical encoding, the schema fingerprint and every batch key are computed from; what it is not, in that mode, is *checked against a live table*, which means a local-only declaration is never validated by anything outside this process. That is not a loophole in the field-ID rules: the transition drain is where this lifecycle first runs for those tables, against the descriptors the spool recorded, and it is the moment a shape declared locally is finally judged by a real catalog. A declaration that was wrong all along is found there, in the drain, rather than at the first `Insert` — which is later than a bucket-mode caller would meet it, and is the price of a mode with no table in it.

**Decision (2026-07-30): a reconciliation failure blocks that one table, not every table in the process.** Because reconciliation happens in the per-table constructor, this falls out of the API shape rather than needing machinery: `OpenWriter` returns an error for the table it could not reconcile, every other table's writer is unaffected, and the process-level `Store` does no schema work at all and is still perfectly usable. Tables are independent everywhere else in this design — separate Iceberg tables, separate catalogs entries, separate flush queues, separate snapshots — and making one table's bad field ID take down an unrelated table's ingestion would be a coupling invented purely by icelake. What the caller does with that error is the caller's decision, and both answers are legitimate: a service whose tables are genuinely independent can log it and carry on with the writers that opened, while a service whose tables are only meaningful together can treat any error from any `OpenWriter` as fatal to startup. icelake deliberately does not choose for them — but it must never make the choice *for* them by half-opening a writer against a table it could not verify, so a failed `OpenWriter` returns no usable writer at all.

**Branch A — the table does not exist yet.**

```go
tbl, err := cat.LoadTable(ctx, tableIdent)          // (ctx, Identifier) — no third argument
if isNotFound(err) {
    tbl, err = cat.CreateTable(ctx, tableIdent, declaredSchema,
        catalog.WithLocation(tableLocation))         // no WithPartitionSpec, no WithSortOrder
}
```

For a brand-new table, `declaredSchema` becomes the table's schema directly, subject to the ID renumbering described in "Field IDs at creation" above. Nothing is compared *ahead of* creation — there is nothing yet to compare against, so every field can be required from day one if the domain calls for it. Creation properties are verified against the library: `CreateTable(ctx, ident, schema, opts ...catalog.CreateTableOpt)` with no partition-spec and no sort-order option produces exactly what `ARCHITECTURE.md` decided — an unpartitioned spec, the unsorted sort order, and format version 2, which is `table.DefaultFormatVersion`. Nothing extra has to be passed to get any of the three.

**Corrected at the post-M9 completeness audit's second round (2026-08-01): the paragraph above used to say "no comparison of any kind runs on this path", and that is false in the worst way a sentence in this document can be false — it described a failure a caller can really receive as one that does not exist.** A comparison does run on the creation path. It runs *after* `CreateTable` returns rather than before it is called, it is the third step of the lifecycle described below, and it applies to Branch B in exactly the same way. The only claim the original sentence was entitled to is the one about ordering that has replaced it: nothing is compared before the table exists, which is why a brand-new table may declare every one of its fields required and why Branch A needs no reconciliation loop. A reader who took the old sentence at face value would have concluded that `OpenWriter` cannot hand back a `ReconcileError` for a table it has just successfully created, and it can. That is precisely the kind of thing a design document exists to tell someone, and this one was telling them the opposite.

**Branch B — the table already exists.**

```go
liveSchema := tbl.Schema()
```

`Schema()` returns the table's real, current shape, straight from the catalog. From here, icelake's own hand-written code runs — this is the one piece of this whole design with no library equivalent (see "What's hand-written" below):

```go
txn := tbl.NewTransaction()
upd := txn.UpdateSchema(true /*caseSensitive*/, false /*allowIncompatibleChanges*/)

for _, want := range declaredSchema.Fields() {
    have, found := liveSchema.FindFieldByID(want.ID)

    switch {
    case !found:
        if want.Required {
            return fmt.Errorf("field %d (%s) is new but required — new fields must be optional", want.ID, want.Name)
        }
        upd.AddColumn([]string{want.Name}, want.Type, "", false, nil)

    case have.Name != want.Name:
        upd.RenameColumn([]string{have.Name}, want.Name)

    case !have.Type.Equals(want.Type):
        upd.UpdateColumn([]string{have.Name}, table.ColumnUpdate{
            FieldType: iceberg.Optional[iceberg.Type]{Valid: true, Val: want.Type},
        })

    default:
        // identical — nothing to do
    }
}

if err := upd.Commit(); err != nil {   // validates and stages the updates into txn
    return err
}
if _, err := txn.Commit(ctx); err != nil { // writes the new metadata via the catalog
    return err
}
```

Every call above is source-verified against the pinned `iceberg-go`, and two of them differ from what earlier drafts of this document assumed.

- `Transaction.UpdateSchema(caseSensitive bool, allowIncompatibleChanges bool, opts ...table.UpdateSchemaOption) *table.UpdateSchema` — it takes **two required booleans**, not zero arguments. icelake passes `caseSensitive=true` (column identity is exact) and `allowIncompatibleChanges=false` (the whole point is to let the library refuse unsafe changes on icelake's behalf).
- `UpdateSchema.AddColumn(path []string, fieldType iceberg.Type, doc string, required bool, defaultValue iceberg.Literal) *UpdateSchema` — as previously documented.
- `UpdateSchema.RenameColumn(path []string, newName string) *UpdateSchema` — as previously documented. Internally it is sugar for an `UpdateColumn` with only the name set.
- `UpdateSchema.UpdateColumn(path []string, update table.ColumnUpdate) *UpdateSchema` — **not** `(path, type)`. `ColumnUpdate` is a struct of five independently-optional fields, each an `iceberg.Optional[T]` (a `{Valid bool; Val T}` pair): `Name`, `FieldType`, `Required`, `WriteDefault`, `Doc`. Only the fields with `Valid: true` are applied; a `ColumnUpdate` with nothing set is a silent no-op. icelake sets `FieldType` and nothing else.
- All of these are builders that queue an operation and return the receiver for chaining. Nothing is validated at call time — every queued op runs when `Commit` is called, which is why a bad path or an illegal change surfaces there rather than at the call that requested it.

**The commit chain is two commits, not one, and both are required.** `UpdateSchema.Commit() error` does not touch the catalog: it runs the queued operations, builds the resulting `[]table.Update` plus the matching requirements, and applies them to the owning `Transaction`. It returns `nil` and does nothing at all if the diff turned out to be empty — which is the overwhelmingly normal case for icelake, since most startups find the table already matching. `Transaction.Commit(ctx) (*table.Table, error)` is what actually writes the new metadata file and updates the catalog row, and it returns the new `*table.Table`. Calling only the first leaves the change staged and lost; calling only the second commits nothing. Verified end to end: an add + rename + `int32`→`int64` widening applied through this exact chain, then reloaded from the catalog with `LoadTable`, comes back with all three changes present.

Deliberately absent from this loop: nothing walks `liveSchema` looking for a field that disappeared from the struct and tries to drop it. A field missing from the current declaration is silently left alone. Dropping a column must always be its own separate, explicit call — never something inferred from an omission, since an accidentally-omitted field is a much more dangerous failure mode than a deliberately-kept one.

The loop as written walks `declaredSchema.Fields()`, which is the table's top-level field list, and builds single-segment paths (`[]string{want.Name}`). That is the flat-only scope decided above: a declared struct containing a nested group never reaches this loop, because it is rejected earlier, at declaration.

**The third step — after both branches, the live table is verified against the declaration.**

Neither branch ends the lifecycle. Whichever one ran, `OpenWriter` takes the table it is about to hand back — the one `CreateTable` returned on Branch A, or the one `Transaction.Commit` returned on Branch B — and walks the declared fields one final time against that table's *live* schema, requiring each declared field to be present under the same permanent ID, with the same name, and with the same type. Any disagreement is a `ReconcileError` naming the field and what the two sides say about it, and `OpenWriter` returns no writer at all. This step is unconditional in exactly the sense the lifecycle above is: it runs on every start, on both branches, whether the reconciliation loop had anything to do or not.

It is deliberately a second look at something both branches have just been through, and the reason is the one silent rewrite in this whole design. `CreateTable` renumbers a new table's fields into the pre-order numbering and does it without raising an error — the "Field IDs at creation" section above is entirely about that — so a declaration whose IDs disagreed would produce a real, successfully created table whose IDs that declaration can never match again, and every later start would diff `1, 5, 9` against `1, 2, 3` and try to add three columns that are already there. The pre-order check at declaration refuses that *before* creation, on the numbers the struct asked for; this step proves it *afterwards*, against the table the catalog actually made. Those are two different statements — one about a declaration, one about a table — and the second is the one everything downstream leans on. The schema descriptor `ARCHITECTURE.md` records in `staging_schemas` is derived from the *declared* schema, that descriptor is hashed into `schema_fp`, and it is hashed again into every batch's content hash and therefore into every data file's object key. All of that is only correct if the declared schema really is the live one, and this is the step that makes "really is" a checked fact rather than a hope carried from one library call to the next.

**The consequence for a caller is worth stating plainly, because it is the one failure in this document that arrives after work has already been committed.** On Branch B, `UpdateSchema.Commit` and `Transaction.Commit` can both succeed — the new metadata file is written, the catalog row is updated, the table has genuinely changed shape — and this step can *still* fail, at which point `OpenWriter` returns a `ReconcileError` and no writer. Nothing is rolled back. That is the right ending rather than an awkward one: a schema change that committed is now a fact about the table, and undoing it would mean a second commit that could fail in all the same ways, leaving a worse mess than the one it was cleaning up. What the error means is that reconciliation did exactly what the declaration asked and the result is still not what the declaration says, which is a statement about this table being outside what this design can reconcile — and the alternative to refusing is handing back a writer that will key, encode and upload batches against a schema the table does not have. The next start re-reads the table, reaches the same conclusion, and refuses again, loudly, until someone changes the declaration or the table. On Branch A the same failure means the table icelake just created is not the table it asked for, which is the `CreateTable` renumbering hazard caught one call after the fact rather than never.

Through icelake's own path this refusal should be unreachable, and that is the point of having it rather than an argument against it. Every ID icelake declares is the pre-order numbering, because `Declare` refuses anything else; `AddColumn` assigns `last-column-id + 1`; a rename and a type widening are applied and then confirmed by the library's own validation. So a table icelake created and has only ever evolved through this loop satisfies this step by construction, and the only way to reach it is a table icelake did not create, or one whose columns something outside this process moved in between. **That reachability is also why no test in the suite holds this step *refusing* anything, which is recorded here rather than left for a later audit to rediscover.** Producing the failure means building a table through `iceberg-go` directly, with field IDs the declaration cannot match, and then pointing `OpenWriter` at it. Nothing in `TESTING.md` forbids that — it would be an ordinary end-to-end test against the same real substrate every other scenario uses — so this is an unwritten test rather than a refused one, and the honest reason it is unwritten is that it asserts icelake's behaviour against a table icelake did not make, which is one step further out than any scenario in that document currently goes. What the suite does hold is weaker, and worth naming as exactly what it is: every reconciliation test in the tree passes *through* this step on one branch or the other, so a version of it that started refusing correct tables would fail the suite immediately — but nothing in the suite proves it refuses an incorrect one.

**Fail loudly, every time, on:**
- A declared struct containing a nested group or a list of groups (rejected before this loop runs — flat top-level fields only, per the 2026-07-30 scoping decision above).
- A new field declared as required against a table that already exists (checked explicitly, above).
- An unsafe type change — already refused by `iceberg-go` itself, provided `allowIncompatibleChanges` is `false` as above. Confirmed by running it: a `long`→`int` narrowing fails at `UpdateSchema.Commit` with `cannot resolve type: cannot promote long to int`, straight out of the library's own `PromoteType`. The same guard rejects adding a required column with no default (`required field X has no default value`) and changing a column from optional to required. icelake reimplements none of this; it only has to avoid passing `allowIncompatibleChanges=true`.
- The live table not matching the declaration *after* the lifecycle has run — a declared field the table does not have, a field whose name differs, or a field whose type differs — checked by the third step above, on both branches. This is the one entry in this list that can arrive after a schema change has already been committed to the catalog, and a caller reasoning about where a `ReconcileError` can come from should expect it from that position as well as from the checks that run before anything is written.
- Any error at all from this reconciliation step. The program must not proceed to writing data against a table it isn't certain matches the declared shape.

## Why optional

A field added after a table already has real rows cannot be required, because there is no value to give those older rows — Iceberg simply refuses to add a required column to an existing table's schema without one. (Iceberg does support supplying an explicit default value for this exact case, letting a required column be added to an existing table with old rows reading back as that default — a real option, but a deliberate opt-in for later, not the default path this design takes.) A field declared before the table ever held data can safely stay required forever, since every row since the table's creation has always included it.

## Why no migration log is needed here

The reconciliation loop above works by comparing "what the struct says right now" against "what the table actually is right now" — it never needs to know the sequence of changes that got the table from one state to the other. This is only possible because every column's identity is a permanent number, not its position or the order it was introduced in. One direct comparison always yields the complete, correct set of changes, whether zero, one, or several fields changed since the last time the program ran.

This is a deliberately different mechanism from the other schema-management system in this project: `goose`-driven migrations for the local SQLite staging table (`ARCHITECTURE.md`, "Local write-ahead durability"). That system needs an explicit, ordered list of migration files, because plain SQL columns carry no permanent ID — a database's `ALTER TABLE` has no built-in notion of "this is the same column, just renamed," so replaying an explicit history really is required there. Two different mechanisms, in two different places, for a real underlying reason: one data store's columns have durable identity to diff against, and the other's don't.

## What's hand-written code, and what's a library call — summary

- The struct itself, and its tags: hand-written, once per table, by whoever owns that table. Or, on the runtime path, the schema document — hand-written once per table by whoever operates the program.
- Struct → Parquet schema → Arrow schema → Iceberg schema: three real library calls, in that order. Zero new code.
- Field specs → Parquet schema, on the runtime path: hand-written, and the one call of the three that has an icelake-owned twin. It builds the same Parquet nodes the tag parser would have built (`NewPrimitiveNodeLogical` per column, `NewGroupNode` for the root, decimal on physical `INT64`, timestamp at millis with `isAdjustedToUTC`), and then hands off to the same second and third calls. Its fidelity is not assumed, and the guard is a test rather than the runtime cross-check: `TestStructAndFieldsDeriveOneSchema` compares the two declarations' Parquet schemas and fails on a wrong physical type or unit, which the descriptor fingerprint — measured under both mutations in the M12 correction above — cannot see.
- Coercing a parsed JSON value into a declared column: hand-written, closed, and loud — the table in that same section. There is no library for it and there should not be, because every interesting entry in it is a refusal this project decided on rather than a conversion someone could look up.
- Deciding what changed between the declared shape and the live table's shape, and calling the right one of `AddColumn`/`RenameColumn`/`UpdateColumn`: hand-written. No library, in Go or otherwise (Java and Python's reference Iceberg implementations were checked and have the same gap — this is unbuilt territory across the ecosystem, not something icelake is missing that everyone else already solved), does this comparison for you. Earlier drafts of this document warned against reaching for `iceberg-go`'s `UnionByNameWith` as a shortcut; that warning is now moot, because no such symbol exists anywhere in the pinned version. The by-name union approach would have been wrong for this anyway — matching fields by name rather than by permanent ID cannot recognize a rename — but there is nothing to be tempted by.
- Turning a batch of `Fill` values into the actual Arrow record the Parquet writer needs: resolved. `arrow-go` v18.6.0 shipped `arrow/array/arreflect`, built for exactly this (closing its own previously-open issues #44 and #64). The path: `arreflect.FromSlice(rows, mem)` — signature `FromSlice[T any](vals []T, mem memory.Allocator, opts ...Option) (arrow.Array, error)`, so an allocator is a required argument, not optional — produces the raw column data via reflection as an `*array.Struct`. Official, non-test code, not a workaround. That struct array's columns then go through the adapter below, and the adapted columns are assembled into the record with the *same* Arrow schema object already derived above. `array.RecordFromStructArray(structArray, declaredSchema)` is the one-liner for the case where no column needed adapting; because icelake's decimal and timestamp columns always do, the general path is `array.NewRecordBatch(declaredArrowSchema, adaptedColumns, n)`, which is exactly what `RecordFromStructArray` calls internally. The check this goes through (`NewRecordBatch`'s `validate()`) only compares column count and raw type per column, never metadata — so `declaredSchema`'s permanent field IDs ride through untouched, and any real mismatch between the two derivations would fail loudly and immediately rather than silently writing something wrong. A genuine bonus found in the process: `arreflect` already treats a pointer field as a nullable column (nil pointer → a real empty value), lining up exactly with the "later-added fields must be optional" rule above, for free — and, verified, its nullability agrees with the declared side field for field with no adaptation needed.

  This entire path was run end to end at M0: a two-row batch of a struct carrying a string, a decimal, a plain `int64`, a UTC-millisecond timestamp, an optional (`*string`) column with one null, and a `[]byte` payload was taken from Go values through `arreflect.FromSlice`, the two-case adapter, `NewRecordBatch`, an Iceberg append, and back out through a scan — with every value, the null, and the decimal scale intact.

  The two items this bullet previously carried as unverified are now both settled, in opposite directions. Column-order agreement between `arreflect` and `NewSchemaFromStruct` is no longer an assumption to test in the abstract: it is part of the startup cross-check described in "Two derivations of one struct" above, run against every real table on every start. Nested struct handling on the data side no longer needs answering at all, because nested declarations are rejected at declaration time under the flat-only scoping decision; the question returns only if and when the nested-evolution work in `ARCHITECTURE.md`'s open questions is picked up.

- Reconciling the two derivations of the same struct — the startup cross-check, which admits two adaptations (`Int64`→`Timestamp(ms,UTC)`, `Int64`→`Decimal128(P,S)`), and the column adapter that makes the decimal and timestamp column types above actually reach Parquet, which performs those two plus the `Int64`→`Timestamp(us,UTC)` rescale the file schema asks for: hand-written, and unavoidable. `arrow-go` does not offer a "build this Arrow record from these Go values *according to this existing schema*" entry point; `arreflect` infers its types from the Go types alone and takes no target schema. This is small (one switch, an identity arm, three conversion arms, a loud default) but it is genuinely icelake's code, and it is the second place — alongside the reconciliation loop — where this design owns logic no library provides. **Corrected at the completeness audit's fifth round (2026-08-01):** this bullet called it "the two-case column adapter" and listed the declaration-time pair as though it were the whole of it, which is the same mistake the adapter's own decision above was carrying and is corrected there at length. The count is the visible half of it; the half worth carrying away is that the conversion which actually reaches a data file — the microsecond rescale, a multiply and a fresh buffer per value — was the one name missing from both places.

- Decoding a staged payload back into a typed row for replay: hand-written, symmetric to the encoder, and driven by the schema descriptor recorded in `staging_schemas` rather than the current declaration (`ARCHITECTURE.md`'s schema-fingerprint decision) — decode yields values keyed by permanent field id, mapped into the current struct by id, with pointer fields carrying nulls. Pinned by golden-fixture round-trip tests under `TESTING.md`'s calculation exception.
- Deciding a batch's identity, and encoding a record for staging: hand-written, and deliberately not delegated. `ARCHITECTURE.md`'s "Batch identity" section explains why the canonical record encoding is icelake's own (ascending permanent field-ID order, typed and length-prefixed) rather than `gob` or JSON: the determinism of that encoding is the thing file-key idempotency rests on, so it cannot be inherited from a library that never promised it. It reuses the same permanent field IDs this document is otherwise about.

## Open risk: an ID reuse looks identical to a deliberate rename

The reconciliation loop cannot tell the difference between "this field was deliberately renamed" and "this field ID was accidentally reused for an unrelated column" — both present identically: same ID, different name (and possibly a compatible type change alongside it). Nothing in this design catches that mistake mechanically. The realistic mitigation is procedural, not tooling: a `fieldid` value, once shipped, should get the same review scrutiny as a rename or a delete — a reviewer needs to recognize "this PR is renaming column 5" versus "this PR happens to reuse the number 5 for something new" by reading the change, the same way a protobuf-based design would still rely on human review to catch this even with `buf breaking` running (that tool also cannot distinguish an intentional rename from an accidental field-number collision on its own). Worth carrying forward as an open item, not treating as solved.
