# icelake — testing strategy

This document lays out the end-to-end test design for icelake, written before implementation so tests are designed intentionally around the claims `ARCHITECTURE.md` makes, rather than retrofitted after the fact. Every scenario here exists to prove a specific claim from that document, not just to exercise code.

## Test philosophy: end-to-end scenarios only, with one narrow exception

**Binding requirement (2026-07-30), applying to every test ever written in this project — not a preference, a rule a reviewer enforces.**

The default, near-universal test form is the end-to-end scenario: drive icelake through its public API against the real substrate described below — a real MinIO container, real `staging.db`/`catalog.db` files on disk, real DuckDB reading back what was written — and assert on real observable outcomes: rows committed and queryable, objects present in the bucket, errors returned to the caller, files byte-identical across an operation that promised not to touch them. Every numbered scenario in this document is that shape except five, each of which says so in its own text rather than leaving a reader to notice: scenario 4, which is proven entirely at the package-internal tier described below because reaching its second claim needs a migration no public API can express; scenario 12's local-only half, which drives the public API against real files on a real disk and a real DuckDB but no container, because the mode under test has no substrate in it (see the note beside the mocks ban below); the hermetic half of scenario 13, which tests a `main`'s own argument handling in the tier described under "Three things this second category does not cover"; scenario 13's local-only run of the built binary, which is an end-to-end run in every sense except that the mode it exercises reaches no bucket, so there is no container in it either; and scenario 14's regression tripwire and its benchmarks, which run a local-only store against a real staging file because what they measure is the cost of accepting a record, which ends at the staging transaction and is the same object doing the same work in either mode — they make no claim about a bucket at all, which is the boundary the local-only note beside the mocks ban draws. Any future test should be the default shape too.

**Unit tests are permitted for exactly one purpose: asserting a calculation whose exact output matters.** The known candidates in this design: the canonical record encoding, its decoder (the round-trip property — decode of encode returns the identical row — plus decoding golden fixtures recorded under older schema fingerprints), and the batch content hash (golden-byte determinism — file-key idempotency rests on these exact bytes never changing across releases, so a checked-in expected-bytes fixture is the honest way to pin them); the `Int64`→`Decimal128` sign-extension adapter (exact 16-byte output, including negative values); and the retry backoff schedule (exact delay sequence and jitter bounds). In each case the assertion compares computed output against an independently derived expected value — never against the code's own prior output re-run, which asserts nothing. This is a **closed list**: it names the calculations this design has, and a test claiming this category has to be one of them, not merely resemble one.

**A second category is sanctioned, and it is narrow: a package-internal behaviour test of a layer that is either pure computation or owns a local file.** A package-internal test is one that lives *inside* the package it exercises rather than driving icelake through its public API — `package canon`, `package staging`, `package schemamap`, `package flush` — and it is a different thing from the calculation exception above, because what it asserts is behaviour rather than an exact output. Not every internal package is eligible for it. `internal/schemamap` derives a schema from a struct through three library calls and compares two reflections of the same struct against each other; `internal/canon` encodes, decodes, hashes and remaps rows; `internal/staging` owns one SQLite file on the local disk. None of those touches the bucket, the catalog, or another process. A test of a layer like that, in the layer's own package, is permitted when **all four** of the following hold, and a test that misses any one of them is refused:

- **The layer is eligible.** It is pure in-memory computation, or it owns a local file it fully controls. A layer that reaches the object store, the Iceberg catalog, or a child process is not eligible, and no version of this carve-out makes it eligible: those claims are proven end to end, through the public API, against the real substrate, in the numbered scenarios below. This is the rule that keeps the substrate real, and it is the same rule as the mock ban — stated once more here so that "it is only an internal package" is never an argument for standing the substrate in.
- **Nothing is stood in for.** The test drives the layer's own API — the entry points the layer above it actually calls — with the real libraries, the real reflection, and, where a file is involved, a real database file on a real disk that is closed and reopened whenever the claim is about durability. Fixtures come from the real code that produces them in production: a staged payload is built by the real encoder from a real declaration, never from invented bytes. Reaching past the layer's own entry points to an unexported helper is allowed only where the entry point cannot express the case at all — a substituted migration set, a pair of shapes stated as field lists — and never to assert what the helper computes in place of what the layer does.
- **It holds one of two claims, and its comment says which.** *Either* the caller-facing half of the same claim is already proven end to end through the public API and this test pins the seam more precisely or more cheaply than the substrate can — one Go type at a time, one column at a time, one shape pair at a time, with no container to start and no bucket to read back — *or* the claim is a defence the layer holds against its own in-process callers, which the public path is designed to make unreachable, so an end-to-end test could only ever show that today's public path does not reach it while the layer would still be wrong on the day some other caller does.
- **It asserts an outcome.** A typed error matched with `errors.Is`/`errors.As`, the state the layer is left in afterwards, the bytes it produced, the rows the file still holds after a reopen. Not that a function was called, not that a constant is itself, not that a comparison against a constant returns what the comparison says.

**The second limb of the third rule is the one that could become a loophole, so it is bounded here explicitly: "the public path cannot reach this line" is half an answer, not a whole one.** The other half is naming the invariant the line defends and what it would cost to lose it — a batch whose stored key stops naming its own bytes, a staged payload whose shape is unrecorded, a table's fields renumbered underneath a declaration — and a test in this category that cannot name that is a coverage test with a better excuse. Everything in the banned list below applies to this category word for word, in every package, however internal the seam: a test that restates the code, that matches a substring of a message, that asserts Go's own semantics, or that stands anything in for the storage substrate is refused by citing this section, and being package-internal is not a defence but the circumstance that makes the refusal more likely to be needed. The question a reviewer asks here is the question they ask of every other test in this project: which sentence of which document does this hold, and what would be silently wrong if it were deleted.

One consequence, because the argument turns up further down: where scenario 7's M7 clarification refuses a direct test of the encoder's length ceiling on the grounds that "the allowed unit-test category is a closed list of calculations", it is invoking the first category, and that list is still closed — this second category adds nothing to it and is not a calculation exception. The test that clarification refuses stays refused here too, on this section's own terms: calling the unexported length check with a made-up length reaches past the layer's entry point to assert what a helper computes, and it leaves behind no typed refusal a caller could ever meet and no state to observe, which fails the second and fourth rules above independently of the first category's closed list.

**Corrected at the post-M9 completeness audit's second round (2026-08-01), and the defect being corrected is this document's own.** The philosophy above was written on 2026-07-30, before a single internal package existed, and it was never revisited as they were built. By M9 the tree held a substantial package-internal tier that the rule as written did not describe: `internal/schemamap/declare_test.go` unit-tests name validation, the order the declaration checks run in, the pre-order field-ID rule, nested and list-of-groups rejection, the closed whitelist of Go field types, the decimal precision ceiling from both sides, and the four cross-check disagreements, all by calling `Declare` directly; `internal/staging/store_test.go` holds fifteen package-level tests of sealing, quarantine, replay grouping and the ceiling counters against a real staging file; `internal/staging/migration_test.go` opens by declaring itself scenario 4's proof; `internal/canon`'s refusal and aliasing tests sit alongside its golden fixtures without being golden fixtures themselves. Almost none of that is a calculation whose exact output matters, so this document, read literally, condemned a large part of the suite it exists to govern. That is not strictness, it is a defect: the first reviewer to enforce the rule to the letter would have deleted good tests, and every author before that had to quietly decide the rule did not mean what it said. `declare_test.go` had already written that decision into its own header, describing itself as "the storage-free slices of `TESTING.md` scenario 7" — a sanction this document had never granted, invented in good faith because the tests were plainly worth having, and exactly the kind of private amendment that a rule nobody can follow produces.

The rule has been widened to say what this project actually practises and deliberately no further. Nothing else moved: the banned list is untouched, the no-mocks rule is untouched and is restated inside the new category rather than relaxed by it, the closed list of calculations is still closed, and the default form of a test here is still an end-to-end scenario through the public API against a real MinIO. The boundary above is written so that it can still be used to *reject* — if it cannot be quoted in review to refuse a bad test, then this correction traded one defective document for another.

**And the correction above was itself incomplete for a day, which is worth recording rather than tidying away.** The third rule requires a test's comment to say which of the two claim shapes it holds, and the four-rule list above refuses a test that misses any one of them — but when that rule was written, not one package-internal test file in the tree said any such thing. `declare_test.go` still described itself as "the storage-free slices of `TESTING.md` scenario 7", the exact self-granted sanction the paragraph above names as the defect; `store_test.go`, `migration_test.go` and `internal/canon`'s three named no claim shape at all. So the corrected document went on condemning, on a technicality of its own making, the whole tier it had just been rewritten to sanction — the same failure mode as the original defect, one turn of the screw later. **Closed at the repair round (2026-08-01) by making the tree satisfy the rule rather than by softening it:** all six headers now cite this section and name, per test or per group, which claim shape they hold and what the invariant would cost to lose. Doing that turned up one test whose claim shape could not honestly be written down — `TestAMigrationThatCannotApplyToThisDatabaseFailsTheOpen` asserted a refusal that reaches a caller through `icelake.Open` and that nothing in this document held end to end — so the missing half was written instead, as the `StagingErrorMigrate` case in the root package's `errors_test.go`. That is the order this rule is meant to force: a test that cannot name its claim shape is a test whose claim is not where it should be, and the answer is to put the claim where it belongs rather than to widen the rule until the test fits.

**And that closure miscounted the tree, which is the third time in this section that a survey has been wrong about its own subject, so it is recorded here with the others rather than quietly fixed.** The paragraph above says "`internal/canon`'s three" and "all six headers". `internal/canon` has four test files, not three: `batch_test.go` was not looked at, and it had no header citing either category while three of its six tests are not golden calculations at all — two assert that changing a component of the hash input changes the key, which is an inequality rather than an independently derived exact output, and the third asserts a typed `errdef.EncodingError` for an empty batch. `internal/schemamap/adapt_test.go` was missed in a different way, which is why counting files would not have caught it either: it did have a header, and the header was wrong. It said "the tests in this file are the sanctioned unit-test category from `TESTING.md`: a calculation whose exact output matters", which is true of the three sign-extension and timestamp tests and false of `TestAdaptColumnRefusesEveryOtherTypePair` — a six-case typed refusal asserting `errdef.CrossCheckError` with its table and column, which is not a calculation and is not on the closed list. A file that claims the wrong category is worse than one that claims none, because it reads as settled. **Corrected at the audit's third round (2026-08-01):** `batch_test.go` now separates its three golden-hash tests from its three second-category ones and names the claim shape of each; `adapt_test.go`'s header now names the second category for its refusal test, its claim shape, and what the invariant costs to lose, and leaves the other three where they belong. The count that is actually true is eight, not six, and here it is spelled out so the next survey can be checked rather than believed: `internal/schemamap/declare_test.go` and `adapt_test.go`; `internal/staging/store_test.go` and `migration_test.go`; and all four of `internal/canon`'s — `record_test.go`, `descriptor_test.go`, `remap_test.go`, `batch_test.go`. (`internal/flush/retry_test.go` cites this section too and is a ninth file, but it is first-category only — the backoff schedule, on the closed list — and the claim-shape rule is the second category's, so it is not one of the eight.) The lesson this section keeps re-learning is that a survey which reports "clean" is a claim like any other, and this document has now been wrong about the state of its own tree at three consecutive rounds — once about the whole internal tier, once about the headers, and once about the count of the files it had just finished amending.

**Make that four consecutive rounds.** The third-round survey named the right eight files and then did not read every test inside them, which is the same error one level down from the round before it. `internal/canon/descriptor_test.go`'s amended header disposed of its seven non-golden tests with the words "every one of them holds its second claim shape", and three of the seven did not: two are first-category outputs derived from the format specification rather than captured (an exact field list in field-id order, and a fingerprint compared against the golden fixture's own across a round trip), and `TestFingerprintDistinguishesEveryMaterialDifference` holds the *first* claim shape, not the second — it is structurally the same test as `batch_test.go`'s `TestBatchHashDependsOnEveryComponentOfItsInput`, which the very same repair round had classified the opposite way in the file next door. **Corrected at the audit's fourth round (2026-08-01)** by making that header enumerate rather than generalise, every test placed by name. The pattern across all four rounds is one pattern, and it is worth naming plainly now that it has repeated this many times: each survey checked the level it had just been corrected about and took the level below it on trust. A blanket quantifier — "every one of them", "all six headers", "internal/canon's three" — is where that trust hides, which makes it the thing to distrust first in the next round rather than the last.

**Make it five, in two headers this time, and the fourth round's lesson was written down before the fifth round proved it again on the two files that round had not read.** `internal/canon/remap_test.go` said its tests "hold its first claim shape throughout: the caller-facing half of every one of them is already proven end to end through the public API", and that was false of two of them. The `StagingSchemaError` kinds `field_required` and `field_retyped` were asserted there and nowhere else: the only end-to-end assertions on that error's `Kind` anywhere in the tree — scenario 2's `TestStagedRowsUnderAnUnknownFieldRefuseTheOpen` and `reconcile_test.go`'s `TestOpenWriterRefusesStagedRowsItCannotRepresent` — both catch `field_removed`, so two of the three kinds a caller can be handed had no caller-facing half at all. `internal/staging/store_test.go` was wrong twice inside one header: it accounted for fourteen of its fifteen tests, leaving the atomicity test (`TestSealRollsBackEveryRowWhenOneIsRefused`, which defends the seal being all-or-nothing rather than merely that a bad row is refused) named nowhere; and it said of its durability group that "every one of them closes the store and opens the file again", when eleven of the file's fifteen tests do and one of the four that do not — `TestCountersAgreeWithTheReplayScan`, whose claim is that two query paths agree and not a durability claim at all — was inside the group being quantified over.

**Closed at the fifth round (2026-08-01) in the order this section requires, which is worth watching because the tempting order is the other one.** The missing caller-facing halves were written rather than the header softened: `TestOpenWriterRefusesStagedRowsUnderAChangedColumn` in `reconcile_test.go` drives both remaining kinds to a caller through `OpenWriter`, against the real substrate, with real records left in a real staging file, exactly as the migration test's missing half was written into the root package's `errors_test.go` at the repair round. Both headers now place every test by name, and where a test's caller-facing half is proven at a coarser grain than its own shape pair, the header says so instead of rounding it up. Two things about how this one was found are worth keeping. The first is that "unreachable" was very nearly written into the tree in place of the hole: reading the code, both kinds look unreachable through the public API, because reconciliation runs before the staged-shape check and refuses most declaration changes first — they are in fact reachable, but only through the changes reconciliation accepts, which is why no one had ever stumbled into them and why relabelling the header would have buried a real gap under a false sentence. The second is that the reopen sentence in `store_test.go` was found by the round's review of its own findings and by none of the passes that had read the file, one level below the header the round before had just corrected. That is the fifth consecutive round in which the defect was one level below the last correction, and it is now less a warning than a description: assume it is there, and go looking one level down from wherever the previous round stopped.

**And that figure was taken one level too high as well, which is recorded here rather than edited away because it is the sixth instance of the same shape and the first one to occur inside a sentence about miscounting.** The paragraph above first read "ten of the file's fifteen tests do and one of the five that do not", and so did the header in `store_test.go` that it describes. The count was arrived at by matching the `reopen` helper's name inside each test function, which counts uses of a helper rather than the behaviour the sentence claims — closing the store and opening the same file again. `TestScanRefusesAPartlyQuarantinedBatch` does exactly that behaviour by hand: it closes the store, writes a state into the database that this package's own API cannot produce, and opens the file again to hand that state to `Scan`. Counting helper calls made it invisible. The true figures are eleven of fifteen closing and reopening, four not — `TestCountersAgreeWithTheReplayScan`, `TestSealRefusesARowAnotherBatchAlreadyOwns`, `TestSealRefusesRowsFromAnotherTable` and `TestRowsFailsLoudlyWhenAStagedRowIsGone` — and two of the five refusal tests reopening rather than one. **Corrected at the fifth round's repair pass (2026-08-01)** in this paragraph and in the header it describes, by enumerating every test function and every close/open in the file instead of grepping for a name. The rule this yields is narrower than "distrust blanket quantifiers" and worth stating on its own: when a sentence claims a behaviour, the check that verifies it has to look for the behaviour, because a check that looks for the usual *spelling* of the behaviour will silently exclude every place the behaviour was written some other way.

**The correction rule this document writes under is scoped, and the scope is a rule rather than a preference.** Six rounds of auditing measured its cost: six of the last eight confirmed findings were caused by correction prose rather than by the thing it corrected. So — a substantive reversal gets a dated correction that names the mistake and states the true behaviour: a design decision that changed, a guarantee that was overstated, a claim about behaviour that was wrong. Bookkeeping does not: a stale count, a mislabelled section title, a sentence pointing at the wrong file, a typo, are fixed silently and completely. Never write a correction about a correction — collapse it and state what is true now, once. Cite by name — a test function, a type, a section title — never by file and line, because line numbers go stale on the next edit.

**Three things this second category does not cover, named so that the map has no blank corners.** The MinIO harness's own single round-trip test (`internal/testsubstrate`) is not a test of icelake at all: it starts the container, puts one object, gets it back, and asserts the bytes, which is the harness proving it hands every scenario a working bucket. It is eligible for none of the four rules above because it is not making a claim about this library, and it is worth exactly one test for the reason its own comment gives — a harness that silently did not work would look like a library bug in every storage-facing test in the tree. The three `apps/` commands are the second: their tests are package-internal by construction, since a `main` has no public API, so "drive it through the public API" is not a form available to them at all, and what they hold is the command's own claims — that it builds, that its usage text is reachable and documents its flags, that it refuses on its arguments before it can reach any bucket, that asking for help does not print back the credential it was handed, that a flag it does not define ends the run as a failure and not as the help request the flag package reports it as — for the rebuild command, non-zero out of the built binary and with the credential still unprinted; for the R2 check command, with no report written — and (for the R2 check command, added at the repair round on 2026-08-01) that its preflight, its record-before-write ordering and its cleanup behave as documented against a real bucket, and that a run cancelled part-way is reported as cancelled rather than as a verdict about the bucket. That last clause was added at the fifth round (2026-08-01), where the fuller enumeration in "Real R2 verification" below was found to be one short and is corrected in its own words there. Nothing is stood in for in any of them — the substrate-backed ones drive the command's own entry points against the same MinIO container every scenario uses — so the mock ban is honoured here as everywhere; what makes them fall outside the second category is only that the category is about *layers below the public API*, and these are programs beside it. The third command, `apps/icelake`, holds the same shape of claim with one difference of substance: it is configured by environment rather than by flags, so "refuses on its arguments before it can reach any bucket" is refused on its *environment*, and the claim that its documentation cannot drift is held by iterating the command's own table of environment variables and requiring every name in it to appear in both the help output and the embedded manual. Its substrate-backed half — a real daemon, a real pipe, a real bucket read back through DuckDB — is a scenario rather than a command test, for the reason every other end-to-end claim here is. Scenario 3 below sanctions the rebuild command's own two tests in its own text; scenario 13 sanctions the `icelake` command's; the R2 check command's tests are named in "Real R2 verification" below, where the procedure they belong to lives.

**The third is a test that used to be in the tree and is not any more, recorded here because the paragraph above claims to leave no blank corners and this was one.** `internal/flush/retry_test.go` held `TestAttemptBudgetIsNeverBelowOne`, which called the unexported `(Retry).attempts` with a budget of zero and required it to resolve to one. It was refused three times over by the text above and there was no honest way to bring it inside: `internal/flush` is not an eligible layer under the first rule, because that layer reaches the object store; calling an unexported helper to assert what the helper computes is what the second and fourth rules forbid in those words; and the closed list in the calculation category names "the retry backoff schedule (exact delay sequence and jitter bounds)", which is the schedule, not the budget. The input it pinned was unreachable as well — `Config` refuses a negative `FlushMaxAttempts` and maps zero to the documented default — so no caller could ever meet the refusal it described. **It was deleted at the repair round (2026-08-01) rather than the closed list being widened to admit it**, because widening a closed list to fit a test that was already written is the failure mode this whole section exists to avoid, and because the claim it appeared to hold — that the budget is bounded and a stuck table heals — is really proven end to end in scenario 8. The clamp in the code stays as the cheap in-code defence it always was; what went is the test that dressed an unreachable line up as a proven claim. The rest of that file is untouched: the backoff schedule is on the closed list, and its tests derive every expected delay from `ARCHITECTURE.md` rather than from the code.

**Explicitly banned, rejected in review on sight:**

- Tests that restate the code: asserting a function called another function, asserting a struct has a field, asserting a constant equals its own value, mock-choreography tests of any kind. If deleting the implementation line would make the test's purpose vanish, the test is a duplicate of the code, not a test of it.
- String-inclusion assertions: no matching substrings of error messages, log lines, or any human-readable text. Error assertions use `errors.Is`/`errors.As` against exported sentinel or typed errors. This is itself a design requirement flowing back into the implementation: every fail-loudly path in `ARCHITECTURE.md` and `SCHEMA.md` must return a matchable error type or wrapped sentinel, never a bare `fmt.Errorf` a test would have to grep.
- Mocks or fakes of the storage substrate: no mocked S3 client, no in-memory SQLite stand-in, no fake catalog, no stubbed Iceberg layer. The real substrate runs locally and cheaply; a test against a mock proves the mock.
- Coverage-driven tests: a test exists to prove a claim from the design documents, never to raise a coverage number.

**One seam is explicitly allowed and is not a mock: time.** Tests drive timer-dependent behaviour (the flush interval, the flush floor, retry backoff) through the injected clock decided in `ARCHITECTURE.md` ("Clock injection"), stepping it forward deterministically instead of sleeping for real or asserting loose latency bounds. A fake clock controls an *input*; it does not fake the storage substrate, which stays real in every test. The no-mocks rule above is about the substrate, and this exception is stated here precisely so nobody relitigates it in review.

**A second thing is not a mock either, for a different reason, and it is written down beside the clock so that the same argument does not have to be had twice: local-only mode.** A store can be opened with `LocalOnly` set — decided at M10, built at M11 — which reaches no bucket and opens no catalog by design (`ARCHITECTURE.md`, `Config`). A test that runs one, on a machine with no container running, is not standing anything in for MinIO — it is exercising a mode a user really runs, whose whole definition is that there is no substrate in it. Nothing is faked because nothing has been replaced: the storage substrate is absent from the *feature*, not from the test. That distinction is also the boundary, and it is the direction a reviewer refuses. Using local-only mode to test a claim about the **bucket** path — reading a spool file and calling it the upload, asserting a batch "committed" against a mode that never commits — is standing in for the substrate as squarely as an in-memory S3 would be, and is refused by the rule above with no exception available. So every claim about uploading, committing, the catalog, Iceberg, or retention's eviction rule is proven in bucket mode against the real container, as always; what local-only tests may prove is what local-only does. Scenario 12 below is the library scenario that runs with no container, and it asserts that fact rather than merely relying on it; scenario 13's local-only run of the built binary is the command's version of the same thing.

## Test substrate: Chainguard MinIO, not real R2

Automated tests run against a local **Chainguard-published MinIO container image** as an S3-compatible stand-in for Cloudflare R2. This means:

- No real Cloudflare account, bucket, or credentials are needed to run the test suite.
- The Chainguard image is preferred over a generic MinIO image for the usual reasons Chainguard images are chosen elsewhere: minimal attack surface, no shell/package manager baggage, suitable for CI.
- Tests spin the container up per test run via `testcontainers-go`'s official MinIO module (`testcontainers-go/modules/minio`), which takes the container image as a parameter — swapping in the Chainguard image in place of the module's community default is a one-line change — started and torn down by the test binary itself rather than a pre-existing docker-compose the developer has to remember to run.
- Everything icelake itself does — batching, Parquet encoding, upload, Iceberg commit, catalog rebuild — is exercised against this local MinIO exactly as it would be against real R2, since both speak the same S3 API. DuckDB, used only for read-side validation (see below), points at the same local MinIO endpoint.

### A second container, from M17: a pinned ClickHouse server

The ClickHouse mirror (`ARCHITECTURE.md`, "The ClickHouse mirror") needs a real server for the same reason the write path needs a real bucket, and it is started the same way: `testcontainers-go`, one container per test that asks for one, torn down by the test binary, over whichever container runtime the machine has — the rootless Podman socket counts, exactly as it does for MinIO, and the detection is the same shared code rather than a second copy of it.

**The image is `clickhouse/clickhouse-server`, referenced by digest and never by tag,** for the reason the MinIO pin gives: a tag that moves underneath a suite turns an unrelated upstream release into a mystery failure. Pinned at `26.7.2.59`, the current stable release, resolved from the registry on 2026-08-04 as the multi-arch index covering `linux/amd64` and `linux/arm64`. The exact digest lives in `PLAN.md`'s pin table beside the MinIO one.

**Why the version number matters more here than it does for MinIO, stated so a future bump is done deliberately.** This mirror's idempotency rests entirely on `insert_deduplication_token`, and the settings around insert deduplication have moved repeatedly through the 26.x line — `system.settings_changes` on the pinned server records changes at 26.1, 26.2, 26.6 and 26.7, including `deduplicate_insert` moving from `backward_compatible_choice` to `enable` at 26.2. So the behaviour this design depends on is a property of a server version rather than of ClickHouse in general, and the pin is what makes the claim checkable. What was measured on the pinned server, by hand, before the pin was chosen: three identical inserts under one token produce **three copies** of the batch into a plain `MergeTree` and **one** into the same table created with `non_replicated_deduplication_window = 1000`. That is the whole argument for the setting appearing in the generated DDL, and a bump of this pin re-runs that measurement rather than assuming it.

**One thing the mirror's tests do not do, and it is the same shape as the MinIO/R2 boundary above:** they run against a single-node, non-replicated server, which is what the generated `MergeTree` DDL and the `non_replicated_deduplication_window` setting are for. A `ReplicatedMergeTree` deployment deduplicates through a different window with different settings, and nothing here proves anything about it.

## DuckDB's role: validation tool, not a dependency

Per `ARCHITECTURE.md`, querying is explicitly out of icelake's scope — DuckDB is used here purely as an independent, already-trusted reader to prove that what icelake wrote is actually correct and queryable, without needing icelake to also contain its own query/verification logic. It is a test-time dependency only.

The Go-side binding for driving DuckDB from the test binary is `github.com/duckdb/duckdb-go/v2` — the actively maintained package as of 2026, not the older `marcboeker/go-duckdb`, which is being retired. The `/v2` suffix is load-bearing: `github.com/duckdb/duckdb-go` without it is not importable at all, because that path's `go.mod` still declares the pre-rename module name (verified at M0; see `PLAN.md`'s pin table).

## Crash injection: how a test actually kills the process

Scenario 2 needs the process to die at exact moments — including "after the Parquet file uploaded, before the Iceberg commit." An in-process "simulated crash" is not one: deferred cleanup still runs, in-memory state drains gracefully, and the test proves recovery from a tidy shutdown rather than a crash. Two mechanisms, both designed in from the start rather than bolted on:

- **Subprocess execution.** Crash tests run the write path in a child process — the standard Go pattern of re-executing the test binary with an environment flag selecting a helper `main` — and the parent kills it with SIGKILL. Only a hard kill of a real process proves the staging layer's durability claims.
- **Named crash points.** The flush path exposes internal, test-only hooks at the moments that matter — at minimum `after-seal-before-encode` and `after-upload-before-commit` — selected by an environment variable read only by the test-helper path, causing an immediate `os.Exit(1)` at that point. (M5 added a third, `after-commit-before-prune`, because this scenario's "must not double-count an already-committed batch" clause is unreachable from the first two — at both of them nothing has been committed yet. A fourth, `after-spool-before-upload` — the `PointAfterSpoolBeforeUpload` constant — is decided at M10 and built at M11, and sits in the new seam the spool opens between encoding and uploading: at that moment a Parquet file exists on local disk that no bucket has ever seen and no row in `spool_files` may or may not yet describe, which is the only window in which the spool's file-first-database-second ordering is observable at all.) These hook sites are part of the flush code's design from day one; retrofitting them later is exactly the kind of invasive change that gets skipped, leaving the crash variants untestable.

Stated scope: killing a process proves recovery from a *process* crash. It does not prove recovery from power loss — that guarantee is delegated to SQLite's own `synchronous=FULL` semantics, per `ARCHITECTURE.md`, and is accepted on SQLite's decades of fault-injection testing rather than re-proven here.

**The same delegation covers the spool's own durability, and is written down here at M11 so the crash tests are not read as proving more than they do.** The spool writes a batch's bytes to a temporary file, fsyncs it, renames it into place and fsyncs the directory, and the property that buys — a file under its final name is a whole file, because a rename cannot half-happen — is a POSIX guarantee about rename and fsync, accepted on the same terms as SQLite's. A test that kills a process at `after-spool-before-upload` proves what a *process* crash leaves behind and no more: it cannot exercise a torn write, because the kernel has the bytes whether or not the process does. Power-loss behaviour of the file system underneath is delegated, not demonstrated, exactly as it is for `staging.db`. What the crash test does prove is the part icelake owns: that a file with no row naming it, or a row whose file the bucket never saw, is recovered by an ordinary retry.

## Example schemas

Two data shapes cover the structurally distinct cases surfaced by the motivating cases (not identical to any real adopting service's schemas — representative analogues, so tests aren't coupled to any one service's actual code):

### Case A — pure structured facts ("fill" table)

Modeled loosely on the motivating trade-decoding case: fully typed/scalar columns, no blob payload, genuinely immutable once written (a fact never edited after the fact).

Representative columns: `symbol` (string), `side` (string, application-level enum of `buy`/`sell`), `price` and `quantity` (**DECIMAL(18,9)**, declared as `int64` unscaled values per `SCHEMA.md`'s column-type decisions — deliberately not `float64`), `sequence_id` (integer, per-venue monotonic), `venue_timestamp_ms` (**TIMESTAMP(millis, UTC)**, declared as `int64` epoch millis, not a bare integer column), `order_id` (string), `source` (string, identifying which upstream provider supplied the record). Dedup/identity key: `(order_id, sequence_id)`. The exact declaration struct for this table is the `Fill` example in `SCHEMA.md`, tags included; this test uses that struct rather than a second, drifting copy of it.

This case validates: pure-append write/commit correctness; that a DECIMAL column survives the round trip *exactly*, asserted by comparing the value DuckDB reads back against the exact decimal string written, not against a tolerance (a tolerance-based assertion would pass even if the column had silently been a float, which is precisely the failure this type decision exists to prevent); that a TIMESTAMP column comes back as a real timestamp type in DuckDB rather than as an integer the test has to reinterpret; and a schema-evolution scenario, described next.

**Schema evolution: add a new optional column mid-test.** Partway through the test run — after several batches have already been written and committed under the original schema — the test restarts the writer against a declared struct with one extra field appended: an optional `*string` `venue_order_type` carrying a fresh, never-used `fieldid`. This must exercise the real reconciliation path in `SCHEMA.md`: the field is absent from the live table, is optional, and therefore results in a real `AddColumn` call against a real Iceberg table with real committed data behind it. The test then writes further batches carrying the new field and asserts, via DuckDB, that the table reads back as one table across the boundary — rows written before the change return `NULL` for the new column, rows written after return their value, total row count still matches everything written, and no already-written Parquet file was rewritten (assert the pre-existing data files are byte-identical, by size/hash, to what they were before the change). That last assertion is the actual claim being proven: schema evolution here is metadata-only.

**One clarification, settled at M9, when this clause was completed.** The evolution scenario is proven by the reconciliation test built at M4 (`TestReconcileAddsAnOptionalColumn`), which already made the real `AddColumn` call against a table with committed data and already asserted the whole read-back — rows before the change null, rows after valued, the total unchanged, and every pre-existing data file byte-identical by size and entity tag. What that test did not do, and what this clause asks for in its first sentence, is put *several* committed batches either side of the boundary: it wrote one batch before and one after, which passes every assertion while saying nothing about a table that had been collecting for a while, and that is the only kind of table anyone evolves. The counts were raised to three batches before and two after, and one row from each side is now read back whole rather than only counted. The clause is proven there rather than a second time in scenario 1's own file, for the same reason scenario 7 names where per-table isolation lives instead of re-asserting it: a second copy of a passing test is not a second claim.

**The other two arms of the reconciliation loop are proven beside it, and are named here rather than written up as scenario steps of their own — added at the post-M9 completeness audit's second round (2026-08-01), because they were on no map at all.** This clause is about adding a column, which is the evolution an adopting service does most often; `SCHEMA.md`'s loop has two further arms, and both are covered by `TestReconcileRenamesAndWidensColumns` in the same file, each against a table that already holds committed data. The rename subtest writes a row, reopens the table under a declaration that keeps a column's field ID and changes its name, and reads *both* rows back through DuckDB under the new name — including the one written before the change, which is the whole claim: a rename moves the name and not the data, and is recognizable as a rename at all only because identity is the permanent ID rather than the name. The widening subtest does the same for an `int32`→`int64` change, asserting that the column now reads back as `BIGINT`, that the value written before the change is still 7, and that a value written afterwards which no `int32` could have held (2^40) comes back intact. Those two plus the added column above are the three changes `SCHEMA.md` describes as verified end to end through the two-commit chain; that document said "verified end to end" and this document named only one of the three, which is the kind of gap that turns a claim into a rumour.

**What a table icelake creates *is*, before any of that machinery runs, is held by `TestCreatedTableHasTheDecidedCreationProperties`, in `reconcile_test.go` beside the tests above.** `SCHEMA.md`'s Branch A and `ARCHITECTURE.md`'s 2026-07-30 decision both say the same three things about the one `CreateTable` call in the code base, made with no partition-spec and no sort-order option: an unpartitioned spec, the unsorted sort order, and format version 2, with nothing extra passed to get any of the three. The test opens a writer against a table that does not exist and reads those properties out of the table's own metadata file in the bucket rather than out of the catalog, at two points in its life — the metadata file creation produced, and then the one a real commit wrote, since a library that reset a default while rebuilding that document would leave a creation-time assertion perfectly happy. It is a test rather than a comment because all three are a library's defaults, and none of the three would fail anything else here: a partitioned table still reads back correctly, so does a sorted one, and so does a format-version-3 table until the day it meets a reader that only speaks 2.

**This replaces an earlier version of this scenario that would have proven nothing.** That version widened `source`'s set of allowed values — adding a new permitted source string — and described it as a schema-evolution test. It is not one. Iceberg has no native enum or allowed-values concept for a plain string column: `source` is simply a `string`, and "the allowed values are A, B, C" is an application-level convention held in the caller's own code. Adding a fourth allowed value requires **no schema change at all**, so the scenario would have exercised nothing but writing a different string, while appearing to validate the evolution machinery. Worth being precise about, because the original pain point it was drawn from is real but lives one layer down: in the motivating service the allowed values were enforced by a SQL `CHECK` constraint, and widening *that* required a full table rebuild. The genuine Iceberg win is that the constraint has nowhere to live in the first place — not that Iceberg evolves it cheaply.

### Case B — raw-payload archive ("event archive" table)

Modeled loosely on the motivating archival case: structured metadata columns plus a raw payload column carrying the full original event body — this is the case that proves icelake can absorb what today requires a hand-rolled separate `.msgpack.zst` file next to a database (see `ARCHITECTURE.md`'s "Unifying the hot store + separate cold archive split" section).

Representative columns: `source_id` (string, e.g. a source-stream identifier), `event_kind` (string, application-level enum of `created`/`edited`/`deleted`), `sequence_ordinal` (integer), `observed_at_ms` (**TIMESTAMP(millis, UTC)**), `payload` (**`[]byte` → plain Parquet BYTE_ARRAY, no logical annotation** — the full raw original event body as received), `payload_sha256` (string, content hash for round-trip verification). Identity key: `(source_id, sequence_ordinal)`. The declaration struct is the `EventArchive` example in `SCHEMA.md`.

The payload column is deliberately untyped bytes rather than a JSON-annotated column, per `SCHEMA.md`'s decision: the test should fill it with msgpack bytes specifically (not JSON), so that the round-trip assertion proves format-agnostic byte fidelity rather than accidentally proving only that JSON survives a JSON-annotated column.

This case validates: that a raw/blob-bearing column round-trips byte-for-byte (compare `payload_sha256` before and after), and that Parquet+ZSTD compression on this column is competitive with the manual msgpack+zstd approach it's meant to replace (a rough size comparison, not a strict benchmark gate).

Both cases are written by a single-writer-per-table harness throughout — no test attempts a concurrent-writer scenario, matching the topology decision in `ARCHITECTURE.md`.

## Configuration used in tests

Per `ARCHITECTURE.md`'s configurable-settings section, test runs use:

- A low/fast ZSTD compression level (e.g. level 1), never the production-target high/max level — tests should be fast to run, not representative of production compression ratios.
- Small batch flush size and time thresholds, deliberately small enough that a test writing a modest number of records triggers multiple flushes (multiple Parquet files / multiple Iceberg snapshots) rather than one — the volume test below depends on there being several snapshots to query across, not just one.
- A staging ceiling (`StagingMaxRecords`/`StagingMaxBytes`) set high enough not to interfere with the volume tests, and deliberately set *low* in the guardrail scenario below, which exists to prove the ceiling actually refuses writes.
- A short retry policy (`FlushMaxAttempts` of 2, `RetryBaseDelay` in the tens of milliseconds), so a test that forces a flush failure does not spend half a minute backing off. This is the one place a test overrides a default rather than a production-shaped value, and it is worth noting that doing so is only possible because the retry policy is configuration rather than a constant.
- An `OnFlushError` callback that records every invocation into a slice the test can assert on — the same hook a production caller would wire into its own logging or metrics.
- The MinIO container's endpoint and credentials supplied as explicit `AccessKeyID`/`SecretAccessKey` values, with `Region` set to whatever the MinIO module expects rather than R2's `"auto"`. Tests should cover the `Credentials` provider form at least once as well (a static provider is enough), since it is a supported input shape and an untested one would rot.
- One `staging.db` and one `catalog.db` per test, in the test's own temp directory, matching the one-file-per-process decision in `ARCHITECTURE.md` — including the tests that open two tables, which deliberately share the single staging file. A local-only test has no `catalog.db` at all, and scenario 12 asserts its absence rather than merely not using it.
- A `CacheDir` in the test's own temp directory wherever the spool is under test, and no `CacheDir` at all everywhere else, so that the default configuration every other scenario runs on is still the one without a cache. Retention bounds are set deliberately tiny in scenario 11's eviction clause for the same reason the flush thresholds are small everywhere — a bound that never trips proves nothing — and are left unset in the clauses about files that must survive.

## Test scenarios

### 1. End-to-end volume / round-trip test

For both Case A and Case B: run the icelake writer through many batches over simulated time (i.e., call the write path repeatedly with small delays/thresholds so multiple flushes occur), producing several Parquet files and Iceberg snapshots per table against the local MinIO bucket. Then, using DuckDB pointed at the same MinIO endpoint (via its S3/httpfs support), query the resulting table(s) and assert:

- Total row count matches total records written.
- Spot-checked individual records match what was written, including exact match on `payload_sha256` for Case B (proving the raw payload round-trips byte-for-byte through Parquet/ZSTD).
- Querying succeeds and returns consistent results regardless of how many underlying files/snapshots exist — proving the "collect over time in many small batches, query it all later as one table" story actually holds, not just for a single write.

### 2. Crash recovery / write-ahead staging test

Validates the write-ahead durability layer added to `ARCHITECTURE.md` (2026-07-27 decision): write a batch of records for Case A or B, but stop the process (or simulate a crash by killing the writer mid-run) *before* the batch's size/time flush threshold trips — i.e., before any Parquet file is written to MinIO or any Iceberg commit happens. Restart the writer against the same local staging store and the same bucket, and assert:

- The records accepted before the simulated crash are recovered from the local staging store on restart, not lost.
- Those recovered records end up correctly flushed and committed (eventually appearing in the Iceberg table, verifiable via the same DuckDB validation queries as scenario 1) exactly once — replay must not double-count a batch that had, in some other run, already been confirmed committed before a crash.
- Records staged by *two different tables* into the one shared `staging.db` are both recovered and routed to the right table on replay, with neither table's rows appearing in the other's. This is the direct test of the shared-staging-file decision; the single ordered replay scan is what makes it worth checking explicitly.

**Variant 2 — crash after upload, before commit.** A second variant crashes *after* a Parquet file has been uploaded to MinIO but *before* the Iceberg commit is confirmed, proving the retried upload + commit is idempotent rather than producing a duplicate data file or a duplicate snapshot. Under the 2026-07-30 batch-identity decision in `ARCHITECTURE.md`, this variant's guarantee now rests on two specific mechanisms, and the test should assert both rather than just the end state:

- **The batch was sealed durably before it was encoded.** On restart, the recovered rows still carry the `batch_key` stamped on them at seal time, so replay reassembles *exactly* the same batch with exactly the same membership and order — not a differently-bounded batch that merely happens to contain the same records. Assert this directly, two ways: the re-upload's object key is the *stored* `batch_key` (per `ARCHITECTURE.md`'s stored-key decision, a sealed batch's key is read back, never recomputed), and — since this variant keeps the schema unchanged across the restart — independently recomputing the hash from the replayed rows yields that same stored key, proving the hash is deterministic. Without the seal step this would be the weak point of content-hash keying, since a re-batching that split at a different record would produce a different, non-colliding hash and orphan the uploaded file.
- **The hash is over the canonical in-memory batch, not the encoded bytes.** The test should make this non-vacuous by having the restarted writer run with a *different ZSTD level* than the crashed one. The re-uploaded object's key must be unchanged (the logical batch is identical), even though its bytes are not — which is exactly the property that would break if the key were a hash of the compressed Parquet output. This is a cheap way to prove the decision holds rather than merely assuming the encoder is deterministic.

Then assert the end state as before: exactly one data file under the table's `data/` prefix for that batch (the retry overwrote the same key, it did not add a second), one snapshot for it, and a DuckDB row count with no duplicates.

**Variant 3 — crash, then restart under a changed schema.** This is the direct test of the schema-fingerprint decision in `ARCHITECTURE.md` — the case where replay meets rows encoded under a shape the current binary no longer declares. Crash leaving both a sealed-but-uncommitted batch and several unsealed staged rows, then restart with a declared struct carrying one extra optional field (a fresh `fieldid`, as in Case A's evolution scenario). Assert:

- The sealed batch re-uploads under its **stored** key, unchanged — even though recomputing the hash under the new schema would give a different answer, which is exactly why the stored key is authoritative.
- The unsealed rows are re-encoded under the new fingerprint at seal time, and `staging_schemas` no longer carries the old descriptor once no live rows reference it.
- Every record across both groups commits exactly once; DuckDB shows the pre-change rows with `NULL` in the new column.
- The fail-loudly side: separately stage a row whose recorded shape contains a field id **absent** from the current declaration, and assert `OpenWriter` for that table fails with `StagingSchemaError` (matched via `errors.As`) rather than opening and silently dropping the staged column's values.

### 3. Catalog rebuild test

Using the data produced by scenario 1 (or an equivalent fresh setup): stop the writer, then **delete `catalog.db` entirely** (the SQL catalog's own file — `staging.db`, kept as a separate file per `ARCHITECTURE.md`'s decision, is untouched by this test), simulating total loss of local catalog state. Run icelake's rebuild tool **without providing it any table list or other hint** — calling the library function `Rebuild(ctx, RebuildOptions{...})` directly rather than shelling out, since per the 2026-07-30 packaging decision in `ARCHITECTURE.md` the CLI binary is a flag-parsing wrapper with no logic of its own (two small tests are sufficient coverage for the wrapper itself: one that builds the binary and runs it, both for `--help` and for a flag it does not define, and one on the seam inside it that tells those two endings apart). Per the 2026-07-27 decision, it must discover which namespaces and tables exist purely by listing the configured warehouse prefix (per the two-level `<namespace>/<table>` layout convention), then, for each table it finds, scan that table's metadata directory, determine the latest valid metadata file, and repopulate the catalog's records from that scan alone.

Then re-run the same DuckDB validation queries from scenario 1 against the rebuilt catalog and assert **identical results** to before the deletion — including that both Case A and Case B tables were actually rediscovered, not just successfully read once told about.

**One mechanical clarification, settled at M6, because without it this scenario would prove nothing.** Scenario 1's validation queries reach a table by *listing the bucket* for its current metadata file — deliberately, so that read-back validation never depends on icelake's own state. Run that way here, the queries would return identical results whether or not the rebuild had done anything at all. So this scenario takes the metadata location it hands DuckDB **out of the catalog database**, read directly from the file with plain SQL, both before the deletion and after the rebuild: the comparison is then between what the original catalog pointed at and what the rebuilt one points at, with DuckDB proving that what is pointed at is a correct, complete table. The safety refusals get their own tests against typed errors, as does the interruption hazard: a rebuild is cancelled mid-run, and another is blocked at its final rename after every row has been written, and both assert the catalog path holds either the complete previous file or nothing — never a partial catalog, which would silently fork a table's metadata chain. One further test goes beyond this scenario's text on purpose — it appends more records **through** the rebuilt catalog and asserts the commits land on the same table. Read-equivalence is the headline claim, but a catalog an operator can read from and never commit through again would still have cost them the table, and whether the registered row is the row the next commit's compare-and-swap reads is not something read-back can show. This is the concrete proof for `ARCHITECTURE.md`'s central claim: the catalog is a disposable, rebuildable cache, not irreplaceable state. Explicitly note in this test's documentation/comments that this is valid *because* it runs with the writer stopped (no concurrent commit racing the rebuild scan) — this test does not, and is not meant to, prove anything about safety under concurrent writers, nor about R2's list-consistency behavior under concurrent writes (a separate, still-open verification item per `ARCHITECTURE.md`).

### 4. Startup migration test

Validates the "`goose`, run automatically, fail loudly" requirement in `ARCHITECTURE.md`'s write-ahead durability section:

- Starting icelake against a fresh (or older-schema) `staging.db` applies all pending `goose` migrations automatically, with no separate manual migration command run by the test — confirmed by checking the resulting schema/version, not by any row-level data check.
- Starting icelake with a migration deliberately made to fail (e.g. a broken statement) causes startup itself to fail with an error, rather than starting up against a database in an unknown state.

**Where this one lives, and one honest limit on it — recorded at the post-M9 completeness audit's second round (2026-08-01).** This is the one numbered scenario proven entirely at the package-internal tier described in the philosophy above, in `internal/staging/migration_test.go`, and the tier fits it: every claim here is about a local SQLite file and the layer that owns it, each test runs against a real file on a real disk opened by the real startup path, each reads the result back through a second, independent SQLite handle rather than through the store that wrote it, and each refusal is matched as a typed `StagingError` with its `Kind`. The second claim can only be made there — reaching it needs a deliberately broken migration substituted for the shipped set, which no public API can express — and it is made twice on purpose: once with a broken migration appended to a copy of the real shipped files, which also proves the failed migration rolled back whole rather than half-applying, and once with the real shipped migrations run against a foreign database that already has a table called `staging`, which is the same claim with nothing substituted anywhere. The limit is on the first claim: "starting *icelake* against a fresh `staging.db` migrates it automatically" is asserted of `staging.Open` and not of `icelake.Open`, so what holds it end to end is only the fact that every storage-facing scenario in this document would fail if migrations had not run. That is real but indirect, and it is written down here as a known gap rather than left to look like coverage.

### 5. `cache_httpfs` demonstration

A documented example (not necessarily a hard pass/fail CI gate, since it's demonstrating a downstream consumption pattern rather than icelake's own correctness) showing DuckDB with the `cache_httpfs` community extension enabled, pointed at the same local MinIO bucket, running an identical query twice and showing the second run is served from local disk cache rather than re-issuing requests against the bucket. This exists to prove out, concretely and locally, the "long exploratory analysis session should not re-fetch from the bucket on every query" pattern from `ARCHITECTURE.md`'s query-side section — even though `cache_httpfs`/DuckDB usage itself remains outside icelake's own scope and ownership.

**Three mechanical clarifications, settled at M9, when this was built.** First, "is served from cache" is measured *outside* DuckDB: every request the reader makes passes through a counting proxy in front of the same real MinIO, so the claim is about requests that never reached the bucket rather than about a counter the extension keeps on itself. (The extension's own hit/miss table reads zero in the pinned version unless profiling is turned on, which is a second reason not to have rested on it.) Second, "twice" is twice *across two readers*, not twice down one connection: measured within one connection the repeat costs almost nothing even with no cache extension at all, because DuckDB's own caching absorbs it — and that cache is memory-only and dies with the process, which is exactly the gap the extension fills and the exploratory-session pattern needs filled. So the demonstration runs the query in a fresh reader each time and compares two pairs: without the extension the second reader pays full price, with it the second reader pays a fraction, and the cache directory has real bytes in it. That contrast is the assertion; a bare "the second run was cheaper" would have proven DuckDB rather than the extension. Third, it skips rather than fails when the community extension cannot be installed, since that needs DuckDB's community repository over the network and this is a demonstration by design.

### 6. API contract: concurrency, non-blocking flush, and drain

Validates the 2026-07-30 public-API decisions in `ARCHITECTURE.md`. These are cheap tests of promises that would otherwise only exist in prose:

- **`Insert` is safe from concurrent goroutines.** Many goroutines insert into one `Writer` while flushes trip repeatedly; the suite runs under `-race`, and the final row count must equal the total inserted. Note explicitly in the test that this validates the *single writer object, many goroutines* promise — it is not a multi-writer-per-table test, which remains out of scope.
- **A flush does not block inserts.** With a deliberately slowed upload path (a proxy or a MinIO container paused briefly), `Insert` calls issued while a flush is in flight must return promptly rather than waiting on the upload. The assertion is a latency bound loose enough not to be flaky, since the point is "did not stall on network I/O," not a benchmark.
- **`Close(ctx)` force-flushes below the threshold.** Write a handful of records — fewer than `FlushMaxRecords`, and well inside `FlushInterval` — then `Close`. Every record must be committed and queryable afterwards, with nothing left in `staging`.
- **`Flush(ctx)` flushes without closing.** Same setup, but the writer keeps accepting records afterwards, and `Flush` returns only once the data is actually committed (assert it is visible to DuckDB immediately on return, with no polling).
- **Sealed batches survive a shutdown that times out.** `Close` with an already-expired context returns an error and leaves the records intact in `staging`, recoverable by the next run — the drain is bounded, but not at the cost of the durability guarantee.
- **One writer per table, enforced inside the store.** A second `OpenWriter` for a table that already has a live writer in the same `Store` is refused with `ErrTableInUse`, matched with `errors.Is` against the exported sentinel — `TestSecondWriterForOneTableIsRefused`, which also proves the rule is per table rather than per store (a second, different table opens and commits normally) and that closing a writer releases its table, so a service that reopens one deliberately, to change its declaration, is not blocked by the writer it just closed. The harder half is `TestReopenDuringADrainIsRefusedUntilCloseReturns`: with the upload path stalled so the drain cannot possibly finish inside its budget, every open attempted while `Close` is still running is refused, and only once `Close` has returned does an open succeed — whereupon the reopened writer inherits exactly the records the failed drain left staged and commits them, checked through DuckDB as the right count with no duplicates. That test is a regression test for a real bug two individually-correct changes made between them, where a writer opened during a drain claimed the batch already in flight and was left, once the first writer committed and pruned, holding row IDs that no longer existed and failing every attempt for the rest of the process's life. This is the in-process half of `ARCHITECTURE.md`'s single-writer rule; the two-process half is undetectable from inside either process and is disclaimed in "What these tests are not trying to prove" below.

**One addition, made at the post-M9 completeness audit's second round (2026-08-01).** The `ErrTableInUse` bullet above is new to this document, not to the suite: the sentinel was added at M4 with the enforcement `ARCHITECTURE.md` describes, both of the tests it names were written before this document mentioned either of them, and `README.md` has been promising the behaviour to callers the whole time. This document is the map of which test proves which claim, so a public sentinel that appeared in two other documents and in none of these scenarios was a hole in the map rather than a gap in the suite. It is recorded as an addition rather than folded in silently, because "which claims were never written down" is itself worth being able to read off the history.

### 7. Fail-loudly guardrails

Every "fails loudly" claim in `ARCHITECTURE.md` and `SCHEMA.md` is a claim about behaviour, and an unenforced one rots quietly. Each of these asserts a specific rejection, with an error, before any data is written:

- **Config validation.** `Open` with a zero `FlushMaxRecords`, a negative `FlushInterval`, a `ZSTDLevel` of 0 or 23, both credential forms supplied, neither supplied, and a `StagingMaxRecords` below `FlushMaxRecords` — each rejected. One case supplies several bad fields at once and asserts, via `errors.Is`/`errors.As` against typed per-field violation errors inside the joined error (never message-substring matching, per the test philosophy above), that every violation is present — proving the joined-error decision rather than first-error-wins.
- **Namespace/table name validation.** `OpenWriter` rejects a name containing a slash, a dot, a hyphen, an uppercase letter, a leading underscore, an empty string, and one over 63 characters. The slash case is the load-bearing one: it is the input that would silently break the rebuild tool's two-level discovery.
- **Staging ceiling.** With a deliberately tiny ceiling and uploads blocked (MinIO stopped), insert until `Insert` returns `ErrStagingFull`; assert the refused record is *not* in `staging` (the caller still owns it), that the error is `errors.Is`-matchable, and that the writer recovers and accepts records again once MinIO returns and the backlog commits — `TestStagingCeilingRefusesThenRecovers`. The other half of the ceiling's definition needs a second table to be visible at all and is `TestStagingCeilingIsProcessWideAcrossTables`: one `Store`, two writers, the whole ceiling filled by `market.fills` alone, and `archive.events` — which has staged nothing — refused, with nothing of its record in `staging` and its `Pending` at zero. Then the same claim read backwards: once `market.fills` drains, the headroom that releases is what lets `archive.events` accept the very record it was refused, which no per-table accounting would ever hand over. Both tables' rows are read back through DuckDB at the end, each holding exactly what it was allowed to accept.
- **Poison records.** A `string` field containing invalid UTF-8, and a decimal value that does not fit the declared precision, are both rejected by `Insert` itself with an error naming the field — not accepted and then discovered at flush. Assert nothing entered `staging`.
- **Two-derivation cross-check.** A declared struct where the two tag namespaces disagree (e.g. mismatched names, or a field with an `arrow:"-"` skip that the parquet side keeps) fails `OpenWriter` with an error naming the column, before any table is created. This is the test that keeps `SCHEMA.md`'s adapter/cross-check honest.
- **Nested struct rejection.** A declared struct containing a nested group is rejected at `OpenWriter`, per the flat-only scoping decision — proving the limitation is enforced rather than merely documented.
- **List-of-groups rejection.** A declared struct carrying a slice of structs is rejected at `OpenWriter` too, by the same flat-only check and with the same typed error naming the list column. `SCHEMA.md` records the two limits as differing in lifetime rather than in which line stops them today, and that is the difference this bullet exists for: if the flat-only check were ever lifted, the plain sub-struct above would simply be supported, while a list of groups would still be refused one call later, because the list's synthesized element node is given no field ID and no tag can supply one. The sub-struct case was tested from the beginning and this one was not, which left this half of `SCHEMA.md`'s nesting paragraph resting on prose.
- **Decimal precision ceiling.** A declaration asking for precision 19 on an `int64`-backed decimal column is refused at `OpenWriter`, before any table is created, with a typed `DeclarationError` that names the table and keeps the derivation library's own error reachable underneath it. The cap lives entirely at this seam: icelake writes Arrow `Decimal128` columns, which would carry a nineteenth digit happily, so nothing further down the write path would notice if the refusal went away. The ceiling from both sides — 18 still accepted, an `int32`-backed decimal refused at any precision — is pinned in `internal/schemamap`, which can declare a schema without a substrate to open it against.
- **Per-table reconciliation isolation.** Open two tables from one `Store` where the first table's declaration is deliberately invalid (a new *required* field against an existing table). The first `OpenWriter` returns an error; the second returns a working writer that writes and commits normally. This is the concrete proof of `SCHEMA.md`'s "one table's failure blocks that table only" decision.

**Three mechanical clarifications, settled at M7, when this scenario was completed.** First, the ceiling clause says "MinIO stopped", and what the test does is reject every connection at the proxy already sitting in front of the same real MinIO for the flush-failure tests. What reaches icelake is identical — connections that fail immediately — the substrate behind it is unchanged and still real, and the endpoint comes back without a container restart the writer would have no way to observe. Stopping and starting a container would have made the same claim more slowly and less deterministically, not more strongly. Second, the per-table isolation clause was already proven, word for word, by the reconciliation refusals built at M4: one store, a first table whose declaration adds a required field to a table that already has rows (refused, typed), and a second table that opens, writes and commits normally, checked with DuckDB. Scenario 7's own file names where that lives rather than asserting it a second time — a second copy of a passing test is not a second claim. Third, a disclosure about the poison clause: `ARCHITECTURE.md` names three poison cases and `Insert` enforces all three, but only the two this scenario names are tested. The third — a string or binary value longer than the encoder's four-byte length prefix can address — is untested on purpose, and the reason is this document's own rule rather than any difficulty. End to end it is unreachable without allocating 4 GiB, which would be a memory test wearing a guardrail test's clothes. Below that, the boundary is trivially assertable against the length check directly, and that is exactly the test the philosophy above bans: the allowed unit-test category is a closed list of calculations whose exact output matters (the canonical encoding and its hashes, the decimal adapter, the backoff schedule), and "a comparison against a constant returns what the comparison says" restates the implementation line rather than proving anything about behaviour. So it is implemented and reviewed rather than proven, and this sentence exists so the gap is a recorded decision rather than an oversight a reader has to find.

**One addition, made at the post-M9 completeness audit's repair round (2026-08-01) and recorded here at the round after it, which is a gap worth naming rather than smoothing over.** The ceiling bullet above described only the single-table arc, because until that round only the single-table arc existed. `ARCHITECTURE.md` has always said the bound is on "the total staged-but-not-yet-committed volume across all tables in the process", `Config`'s own documentation says it, and `Store.accept` has always charged one pair of counters rather than a map keyed by table — but every test that had ever reached `ErrStagingFull` opened one writer on one table, and a process-wide bound and a per-table bound are indistinguishable when only one table exists. The audit confirmed that by keying those counters by table and watching the whole suite still pass, which is a change that turns a stated limit on total local disk and total memory into no limit at all for a service that opens tables in a loop. `TestStagingCeilingIsProcessWideAcrossTables` is what fails under it now. This document is the map of which test proves which claim, so the map was updated a round late: the test landed in one round and was named here in the next, and the reason it is written down that way is that "which claims were never written down" is exactly what this map is for.

### 8. Flush failure, retry, and self-healing

Validates the 2026-07-30 failure-handling decisions. With a short retry policy configured (above), stop the MinIO container mid-run and assert:

- `Insert` keeps succeeding while the table cannot flush — the records are durable in staging, which is the whole point — until the ceiling is reached, at which point it refuses.
- Retries are bounded, not infinite: after `FlushMaxAttempts`, the `OnFlushError` callback fires exactly once for that cycle, carrying the table identity, batch key, record count, and underlying error.
- Nothing is lost or dropped: the sealed batch is still in `staging` with its `batch_key` intact.
- The table self-heals. Restart MinIO without restarting the writer; the next flush trigger retries the same batch with a fresh attempt budget and commits it, and DuckDB then sees every record written across the whole episode, in order, with no duplicates and no gaps.
- Ordering holds through the failure: no batch sealed *after* the stuck one committed ahead of it, checked by comparing the table's snapshot sequence against the order records were written in.

**Six mechanical clarifications, settled at M8, when this scenario was built.** First, "stop the MinIO container" is done the same way scenario 7's ceiling clause does it and for the same reasons: every connection is rejected at the proxy already sitting in front of the same real MinIO, so what reaches icelake is identical, the substrate behind it is unchanged and still real, and the endpoint comes back without a container restart the writer would have no way to observe. Second, the clock seam does two different jobs here and both are worth naming. For the schedule, the injected clock records the delay the worker asks for and returns immediately: the delays are the only evidence the schedule reached the worker at all, and waiting them out for real would trade that evidence for a slower suite. Recording them is not enough by itself, and the correction is worth keeping: full jitter draws each delay from a *window*, so a recorded delay can only ever be checked against the window it came from, and a schedule that had lost its doubling entirely would satisfy every such check. The jitter draw is therefore pinned at its maximum through a test-only package variable — the same mechanism the crash points use, and just as deliberately not part of the public configuration — so the delays observed end to end are the ceilings themselves and can be compared against the exact sequence. For the *interruption* claim — a shutdown must not wait out a backoff — the injected clock instead makes the sleep last until its context is done, because real backoff is jittered and a test that used the real clock would be asserting against a delay that might have been milliseconds, proving nothing on those runs. Both are inputs; the storage substrate stays real in both. Third, "fires exactly once for that cycle" is asserted as a ratio rather than as an absolute count, because how many cycles run during an outage depends on how many triggers arrive: with an attempt budget of two, every cycle sleeps exactly once, so the number of delays the worker asked for *is* the number of cycles it ran, and the assertion is that the callback fired exactly that many times. A callback that fired per attempt would fail it immediately. Fourth, the ordering clause is checked by reading the table back at **every metadata version it ever had** rather than by parsing manifest lists: each commit writes a new metadata file, records carry their write position as `sequence_id`, and batches are contiguous runs of them, so a table that committed in seal order shows an unbroken prefix `0..n-1` at every version — and a batch that overtook another leaves a gap at whichever version it landed in. Fifth, quarantine has no numbered scenario of its own and is proven alongside this one, because it is the other half of the same decision: the test corrupts a staged payload with plain SQL while no writer is running (a genuinely damaged database, not an error injected into the path under test), and asserts the whole batch is marked, the queue behind it moves again, the marked rows never replay, and they keep occupying the staging ceiling. The exhausted-budget case deliberately does *not* quarantine — that distinction is `ARCHITECTURE.md`'s, and the two tests assert the two different endings. The reporting contract is asserted the same way round as it actually happens: the test waits for the quarantine to have already occurred, with no caller waiting on it, *before* calling `Flush`, because "a call that arrives afterwards is still told" is the clause that matters and a test that raced the writer to it would prove only that it sometimes holds. The second `Flush` and the `Close` after it assert the other half, that it is reported once and not forever. Sixth, one path in this area has no honest test and is implemented and reviewed instead: the double fault where a batch cannot be encoded *and* the staging write that would mark it also fails. Reaching it needs two independent failures at the same instant, one of them inside a local SQLite file that the same test is relying on to observe everything else, and every way of forcing it either fakes the staging layer — which this document's philosophy bans outright — or proves only that the fake failed. Its behaviour is stated in `ARCHITECTURE.md`: the batch keeps its place, the callback is told, and the next trigger tries the marking again.

**A seventh clarification, added at the post-M9 completeness audit's second round (2026-08-01), because the containment half of this hook's contract appeared in no scenario.** `OnFlushError` is notification and nothing else, and unlike `OnAccept` it runs on a background goroutine the caller cannot see — so the two ways a caller's own callback could take the writer down with it are icelake's problem rather than the caller's, and both are held by `TestFlushErrorCallbackCannotBreakTheFlushPath`. The first subtest wires a callback that panics, forces a flush failure by rejecting connections at the proxy, waits for the notification to have happened, and then lets the store answer again: the panic is contained, the writer is unharmed, the same batch commits on the next trigger, `Close` succeeds, and DuckDB shows every record — a broken callback costs the table nothing. The second wires a callback that blocks forever, and the assertion is that `Close` returns at all: it returns the flush failure inside its budget rather than hanging on a caller who never comes back, with every record still in staging for the next run, and the callback is still parked inside itself when the test ends. Both are one edit away from being false, neither would fail anything else in this scenario, and both are promises the hook's own documentation makes to callers, which is the reason they are tested rather than asserted in prose. This is the deliberate opposite of scenario 9's ruling on a panicking `OnAccept`, which is *not* contained because it runs on the caller's own goroutine where the caller's own `defer` can catch it — the two hooks differ in whose goroutine they occupy, so they have to differ here too.

### 9. Mirroring, status, and the flush floor

Validates the 2026-07-30 "Mirroring and visibility" additions in `ARCHITECTURE.md`:

- **`OnAccept` fires exactly once per accepted record, synchronously, before `Insert` returns.** Wire a callback that appends to a slice; assert its contents exactly match every row inserted, in order, checked after every individual `Insert` call rather than only at the end — proving it is not buffered or deferred to flush time.
- **An `OnAccept` error surfaces from `Insert`, but the record is still archived.** Configure a callback that fails for a specific subset of rows; assert `Insert` returns an error for exactly those rows, and separately assert, via the same DuckDB validation as scenario 1, that every row — including the ones whose callback failed — is still fully committed. This is the concrete proof that a failing mirror never costs icelake's own durability.
- **`Status()` numbers agree with reality.** After a known sequence of inserts and flushes, assert `RecordsAccepted` and `FlushesCommitted` match exactly, `RecentFlushTimes` has the expected length and ordering, and `RecentRecords` contains exactly the most recently inserted rows, by value, once more than five have been written.
- **The flush floor coalesces a burst instead of splitting it.** Configure a floor well above a test-friendly `FlushInterval` (inverted from every other scenario's configuration, deliberately, to make the floor the binding constraint) and insert a burst of records that would otherwise trigger several flushes in rapid succession. Assert fewer flushes happened than trigger events, `Status().FlushFloorEngaged` is greater than zero, and no record was lost or duplicated across the coalesced flushes.

**Seven mechanical clarifications, settled at M9, when this scenario was built.**

First, the floor test freezes time through the injected clock rather than configuring a floor large enough to outlast a burst against the real one. The floor is a comparison between two instants, so against a real clock the test would be asserting on how long a hundred fsynced inserts happen to take on the machine running it — true on a developer's laptop, a coin flip in CI. Only `Now` is controlled; the timers stay real, so what is being watched is the writer's own timer loop rather than a substitute for it, and the retry sleep returns immediately as it does in scenario 8.

Second, "fewer flushes than trigger events" is asserted as `FlushesCommitted` against `FlushesCommitted + FlushFloorEngaged`, because a trigger event is not otherwise observable from outside the writer. That sum is the trigger count *in this test's own arrangement* and not in general — `FlushesCommitted` also counts a batch an explicit `Flush` or `Close` sealed and a batch replayed from a previous run, neither of which happens here — and `ARCHITECTURE.md` states the general form.

Third, the counter's definition needs a test of its own and now has one, because the burst test cannot catch the failure the definition exists to prevent. `ARCHITECTURE.md` pins "engages" to a trigger that actually held records back; the timer nudges the worker on every tick whether or not there is a batch, so a counter that also incremented on those would climb on an *idle* table — and in the burst test inflation only makes an already-large count larger, which its lower-bound assertion tolerates. The dedicated test is two phases against a frozen clock: many ticks with nothing inserted, where the count must stay at zero, and then a single record behind the same unelapsed floor, where the same tick stream must move it. The second phase is what makes the first phase's zero mean "the ticks were arriving and were deliberately ignored" rather than "nothing was happening". (Confirmed by mutation: moving the empty-batch guard below the floor check — the exact bug — leaves every other test in the suite passing and fails this one.)

Fourth, the burst test proves the *other* half of the floor's promise in the same run, because without it the first half is satisfied by a bug: a floor that never released anything would coalesce perfectly and lose everything. So time is advanced past the floor and the very next interval trigger — no `Flush`, no `Close`, nothing but the writer's own timer — commits one batch containing every record of the burst, read back through DuckDB with no duplicates.

Fifth, the status clause also asserts the shape of a writer that has done nothing (zero counts, no commit time, empty windows) and that the returned snapshot's slices are the caller's own; the record window is checked after far more than five records so that what is proven is the window dropping the earlier ones rather than never having had them. What is *not* asserted, because it is not true, is that the snapshot is deep: for a declaration type with a reference field the records share memory with what the caller inserted, which `ARCHITECTURE.md` and the godoc both now say outright rather than leaving to be discovered.

Sixth, the two containment promises the hook's documentation makes are tested rather than asserted in prose, since both are one edit away from being false and neither would fail anything else here: one goroutine's `Insert` completes while another sits parked inside its callback (the callback holds no lock), and an `Insert` whose callback calls `Status`, `Pending` and `Flush` returns rather than deadlocking (re-entry is allowed, unlike `OnFlushError`'s). Calling `Insert` from inside the callback is documented as forbidden — it is unbounded recursion — and deliberately has neither a test nor a runtime check: a check would cost every insert something to catch a mistake whose first run is an immediate stack overflow.

Seventh, two things are implemented and reviewed rather than proven, in the same spirit as scenario 7's disclosure about the third poison case. A panicking `OnAccept` is untested: the decision is that it is *not* contained — it runs on the caller's own goroutine, where the caller's own `defer` can catch it — so a test would be asserting Go's own semantics for a callback icelake makes no promise about, which is the restate-the-code shape this document bans. And the crash window in the hook's ordering is untested: a process that dies between the staging commit and the callback leaves a record that replay commits with the mirror never told, since replay deliberately does not fire the hook. That is a property of the ordering rather than a bug — the alternative ordering trades it for telling a mirror about records that were never archived — and it is now stated in `ARCHITECTURE.md` and in the godoc, where a caller deciding whether their mirror needs its own reconciliation will actually meet it. Proving it would need the crash harness to assert the *absence* of a callback in a subsequent run, which restates the replay rule rather than testing it.

### 10. Runtime schema: the dynamic writer end to end

Validates `SCHEMA.md`'s "A second source of a declaration". The shape of this scenario is scenario 1's, run through the other front door: a schema document instead of a tagged struct, `InsertJSON` instead of `Insert`, and the same DuckDB read-back holding the same exactness to the same standard. Against the real substrate:

- **A document declaring two tables opens two writers and round-trips.** The document declares Case A's fill shape and a payload-bearing shape, and the records go in as JSON lines carrying every awkward form the coercion table admits: decimals as strings, decimals as exact JSON numbers, both accepted timestamp spellings (integral epoch millis and an RFC3339 string at whole-millisecond precision), `null` and absent keys in optional columns, and a base64 payload. DuckDB then asserts what scenario 1 asserts and for the same reasons — the decimal against its exact decimal string rather than a tolerance, the timestamp as a real timestamp type, the payload against its `payload_sha256`.
- **Twin equivalence, which is the one test that pins the whole derivation.** A struct covering every one of the nine kinds and both optionalities, and the document that declares the same table, must produce equal Arrow schemas *including the `PARQUET:field_id` metadata*, equal Iceberg schemas, and equal canonical descriptor fingerprints. Everything else in this scenario would still pass if the twin drifted in some way DuckDB cannot see; this is the assertion that would not.
- **Evolution through a document is the same evolution.** Adding a field with a fresh `fieldid` and `"optional": true` and reopening produces a real `AddColumn` against a table with committed data behind it, and the pre-existing data files are byte-identical afterwards — the same claim Case A's evolution clause makes, made from the runtime path, because the reconciliation loop cannot tell the two sources apart and this is what proves it.
- **The two APIs cross on one table.** A table written by a struct writer is reopened by a dynamic writer declared from the equivalent document, and it writes and commits normally; records staged by one and replayed by the other commit exactly once. That is the caller-facing consequence of equal fingerprints — replay decodes by the recorded descriptor, so if the two paths disagreed by a byte, this is where it would surface as a refusal.
- **The coercion matrix, table-driven, one row per refusal in `SCHEMA.md`'s table.** Each asserts a `RecordError` matched with `errors.As`, checked on its `Kind` and its `Field`, driven through `InsertJSON` on an open writer, with nothing entering `staging` — the same standard the poison clause in scenario 7 holds. The two rows worth naming because they are the ones a reviewer will want to delete as pedantic: a `float64` above 2^53 into a `long`, and a `float64` into a `decimal` at all.

**Where each clause landed, recorded at M12 the way scenario 12's `DrainSpool` addendum is.** `TestDynamicWriterRoundTripsThroughADocument` is the round trip, with the two decimal spellings, both timestamp spellings, the optional column present, null and absent, and the base64 payload checked against its `payload_sha256`. `TestDocumentEvolutionIsTheSameEvolution` is the evolution, asserting every pre-existing data file byte-identical by size and entity tag. `TestTheTwoAPIsCrossOnOneTable` is the crossing: a struct writer accepts records against a refusing endpoint, a dynamic writer declared from the equivalent document opens the same table, replays them and commits them exactly once — which also puts the two codecs on opposite ends of one batch, since rows bound by the struct binder are built into an Arrow record by the dynamic one. `TestDynamicWriterRefusesEveryRowTheCoercionTableRefuses` is the matrix — the refusals one row each, and the *acceptances* beside them, because half of that table is about what is taken and a matrix listing only refusals would be satisfied by a writer that refused everything — ending by proving the poison check still runs underneath the coercion table. `TestDynamicWriterWritesInLocalOnlyMode` puts the runtime schema and local-only mode together with no container, because that combination is the five-minute start the command in scenario 13 is built for.

**The twin-equivalence clause is held in two places, and the split is forced rather than chosen.** `TestStructAndDocumentAgreeOnOneShape` holds it through the public API with no container: a struct writer and a dynamic writer declared from the real JSON document, opened on one local-only store under two table names, must record the same schema fingerprint on disk — the fingerprint being the thing the equality is *for*, since it keys `staging_schemas` and is hashed into every batch key and therefore into every object name. The rest — equal Parquet schemas (the one comparison that catches a wrong physical type or timestamp unit, which the fingerprint cannot see), equal Arrow schemas including their `PARQUET:field_id` metadata, and equal Iceberg schemas — is not observable from outside the library at all, so it is held by `TestStructAndFieldsDeriveOneSchema` in `internal/canon`, under the second category above, with a header that names its claim shape. It lives in that package rather than in `internal/schemamap` because it needs both sides at once and `canon`'s tests may import `schemamap` while the reverse is a cycle.

### 11. The local Parquet spool, and retention

Validates `ARCHITECTURE.md`'s "The local Parquet spool" and its retention decision. Bucket mode throughout, against the real substrate, with `CacheDir` configured:

- **The spool file is the object.** After a flush, `<CacheDir>/<namespace>/<table>/data/<batch-key>.parquet` exists, and its bytes are compared against the object fetched from the bucket under the mirrored key — the whole bytes, not the length, because "byte-identical" is the claim and a length check would pass for two files that differ.
- **DuckDB reads the cache and the table and gets the same rows.** `read_parquet` over the cache directory returns exactly what an `iceberg_scan` of the same table returns. This is the "DuckDB readability is a property" claim, held once, so that it does not have to be repeated as a promise anywhere else.
- **Retention evicts committed files, oldest first, on the injected clock.** With deliberately tiny caps and time advanced past `CacheMaxAge`, the oldest committed file is gone from disk and the newest is not; the bucket is untouched; and the table still reads back complete through DuckDB, which is what makes eviction visibly free.
- **Uncommitted files are protected by the shape of the query, and this is the assertion that matters most in this scenario.** With uploads rejected at the same proxy scenario 7 and 8 use, records keep flowing and spool files keep landing while nothing commits. The cache goes far over both bounds, sweep after sweep, and not one file is deleted — that is the documented behaviour rather than a bug, and it is asserted as such. Then the endpoint answers again, the backlog commits, and a later sweep evicts exactly the files that just became committed. A version of the sweeper that filtered uncommitted files in Go rather than in the statement would pass every other bullet here and fail this one.
- **A file icelake did not write is never touched.** An unrelated file placed in the cache directory survives every sweep, including sweeps that evict.
- **Crash safety at the new seam.** A crash at `after-spool-before-upload` leaves a Parquet file no bucket has seen; the restarted writer rebuilds the identical batch, rewrites the identical file, uploads it under the stored `batch_key`, and commits once — one data file under the table's `data/` prefix, one snapshot, no duplicate rows, and the spool file byte-identical to the one the dead process wrote. A crash at `after-commit-before-prune` is asserted for its spool consequence too: the file is left with a null `committed_at`, the next run finds it already committed and marks it rather than committing a second time, and it becomes evictable from then on.

### 12. Local-only mode, and the transition to a bucket

Validates `ARCHITECTURE.md`'s local-only decision and the transition drain beside it. **This is the one *library* scenario whose first half runs with no container at all** — scenario 13's hermetic tests and its local-only run of the built binary are the other no-container work in this document — and it asserts that rather than relying on it: the local-only tests do not call the container-runtime helper, and their comment says why — local-only mode has no substrate in it, so there is nothing to skip on and nothing being stood in for (see the note beside the mocks ban above).

- **The configuration matrix.** Every rule of the local-only matrix is a case: `LocalOnly` with no `CacheDir`; `LocalOnly` with each of `CatalogPath`, `Endpoint`, `Bucket`, `WarehousePrefix`, `AccessKeyID`, `SecretAccessKey` and `Credentials` set; `LocalOnly` with either retention bound; a retention bound with no `CacheDir`; a `CacheDir` in bucket mode with neither bound. Each asserts its own `ConfigFieldError` inside the joined `ConfigError`, and one case sets several at once and requires every violation to be present, exactly as scenario 7's config clause does.
- **A local-only store writes, prunes, and is readable.** Two tables, records inserted, `Flush`, then: `staging` holds nothing (the rows were pruned against the spool file, which is the mode's whole durability story), one file per batch is in the cache, no `catalog.db` exists anywhere on disk, and DuckDB `read_parquet` over the cache returns every record with scenario 1's exactness assertions on the decimal and the timestamp. `Store.DrainSpool` returns `ErrLocalOnly`, matched with `errors.Is`.
- **The transition, which needs the container.** The local-only run above writes under two shapes — a second local-only run reopens with an added optional column — and then the same `StagingPath` and the same `CacheDir` are opened in bucket mode. Assert: the drain runs inside `OpenWriter` and runs *before* the table is loaded or reconciled against the current declaration, in file creation order; the table is created from the **oldest** file's persisted descriptor, and each file is committed against the shape its own descriptor records, the table being walked forward one file at a time; the reconciliation to the current declaration happens after the last file, not before the first; every batch commits exactly once; DuckDB through the Iceberg table returns every record written during the local-only period, with the pre-change rows reading `NULL` in the added column; and the spool files are now all marked committed. A drain that ran after the table had been reconciled forward would still satisfy the row counts and the read-back whenever the two shapes happen to be compatible, which is exactly why the ordering is asserted directly rather than inferred from the data.
- **Re-running is a no-op, and a crash mid-drain is not observable.** A second bucket-mode open commits nothing further and adds no snapshot. A run killed part-way through a drain and restarted produces the same final set of snapshots and one data file per batch — the same idempotency claim scenario 2 makes about a single flush, made about a backlog.
- **A table no writer reopens is drained by `Store.DrainSpool`**, with the same assertions, which is the only path that covers a table whose declaration is no longer in the process.

**`Store.DrainSpool`'s own contract is held by three further tests, added at M11 and named here rather than written up as scenario steps, because they are claims about that one method rather than about the transition it serves.** They are recorded the way the reconciliation arms are recorded under Case A above: the claim, and where it lives.

- **The slot exclusion is `TestDrainSpoolSerializesAgainstWriters`.** A table has exactly one owner — a writer being opened, that writer's own open-time drain, or this call — from the first moment either path touches it. The test drives a real backlog with a live writer on one of two tables, then races an `OpenWriter` against a `DrainSpool` on a second backlog that is genuinely uncommitted, and requires the loser to be told either nothing (this call skips a held table) or `ErrTableInUse` (a writer cannot skip its drain and carry on), with one data file and one snapshot per backlog file however the race fell. **The reason it exists as a test rather than as a comment is worth keeping: the first two attempts at the exclusion both passed a weaker version of this test.** The first left `OpenWriter`'s drain unclaimed altogether and failed four runs in four; the second claimed the drain but released the slot before loading the table, and failed about one run in fifteen, because the drain that slips into that gap still creates the namespace and loads the table against the same local catalog on its way to finding it has nothing to do. Both failures surfaced as a raw SQLite `UNIQUE constraint` error, which is precisely the shape of failure the error taxonomy exists to make impossible, so the test asserts the sentinel rather than merely a non-nil error — and it is run many times, because a 7% flake passes once.
- **Continuing past a failure is `TestDrainSpoolReportsOneTableAndDrainsTheRest`.** This is a process-wide recovery call, so one table's failure must not decide what happens to every other table's backlog: the first error is kept and returned once every table has been attempted, which is `Store.Close`'s recorded shape for draining many writers. The failing table is deliberately the one the walk meets *first*, since a test whose failure came last could not tell "carried on" from "stopped".
- **The refusal order is `TestDrainSpoolRefusesAClosedStore`.** A closed store answers `ErrClosed` before it touches anything, including a closed store that is also local-only — the store's own state outranks the mode's, exactly as it does for every other entry point, and a caller who shut a store down and then called this deserves to be told which of the two problems came first.

### 13. The `icelake` command

The daemon (`apps/icelake`) is a thin wrapper — env in, `OpenDynamicWriter` and `InsertJSON` under it, stdin as the only input — so what it holds is the command's own claims, in the sense of the "three things this second category does not cover" paragraph above, plus one end-to-end run that proves the wrapper is wired to the library at all.

Hermetic, needing no container:

- **It builds, and its documentation cannot drift from its configuration.** `icelake usage` prints the embedded manual; every environment variable in the command's own table is required to appear both there and in the help output, with the names iterated from that table rather than retyped, so a variable added without documentation fails the suite.
- **Nothing printed for a human ever carries a secret.** Help, usage and the resolved-configuration line the daemon prints at startup are asserted not to contain the credential the test itself put in the environment. This is the same claim, and the same open question about substring assertions, that the `--help` test in "Real R2 verification" below already flags; it is not a second decision. One thing about this command's tests *is* a decision and is recorded here so the ban above is not read as silently violated: a command's printed text is its contract — exit messages naming the offending variable, the line number of a refused line, the staging-full and reading-resumed announcements — so scenario 13's tests match stderr substrings for exactly those claims, and only there. The library's errors stay matchable by type alone, and no library test may do this.
- **The refusal matrix, by `t.Setenv`.** Missing data directory; missing schema file; local-only set alongside bucket configuration; neither local-only nor a complete bucket configuration; a partial bucket configuration; a malformed boolean, duration and byte size; a ZSTD level of 0 and of 23; and a case violating several at once, which must report all of them in one refusal rather than the first. Each is matched against the command's own refusal sentinel rather than merely being non-nil, for the reason the R2 check command's argument test gives: a network failure satisfies a non-nil check while proving the opposite.
- **The byte-size parser is exact.** Powers of 1024, no fractions, no silent rounding. This is sanctioned as a command claim and deliberately *not* as an addition to the closed list of calculations in the philosophy above — that list is about the library's durable formats and is still closed; this is a `main`'s own argument handling, in the tier that paragraph describes.
- **`icelake rebuild` tells a help request from a parse error**, the same seam scenario 3 names for the rebuild CLI, and refuses outright in local-only mode, where there is no catalog to rebuild.
- **Exit codes are part of the contract**: zero for a clean end of input, two for a configuration or usage refusal, one for a runtime failure. A supervisor distinguishes "restart me" from "restarting will not help" by exactly this, so each is asserted on a real run of the built binary.

Substrate-backed, against the same MinIO container as every other scenario:

- **A real pipe, two tables, a real bucket.** NDJSON envelopes for both tables are piped into the built binary, stdin is closed, the process exits zero, and DuckDB validates both tables against the bucket exactly as scenario 1 does.
- **A signal drains rather than drops.** `SIGTERM` mid-stream ends the run within the shutdown timeout with exit zero, and every record the daemon had accepted is committed and queryable afterwards.
- **A malformed line dies loudly and loses nothing.** The run exits one, naming the line number; a second run against the same staging file replays every record accepted before the bad line, exactly once, checked through DuckDB. This is the claim the whole design rests on for a pipe: what was accepted is durable, and what was still in the pipe was never icelake's.

And one run that sits between the two, because it reaches a real disk and no container: **a local-only run of the real binary** pipes records in, writes its cache, and has DuckDB read it back — the command's own version of scenario 12's first half, through the binary an operator actually installs.

**Where each clause landed, recorded at M13 the way scenarios 10 and 12 record theirs.** `TestBinaryBuildsAndDocumentsItsConfiguration` builds the command, runs `usage` and `help`, and requires every variable in the command's own table to appear in both — iterating that table rather than retyping the names, so a variable added without documentation fails the suite the moment it is added — and requires neither output to contain the credential the test put in the environment. `TestStartupLineReportsTheConfigurationWithoutTheSecret` holds the same claim for the third thing this command prints for a human, the resolved-configuration line, which reports the secret as set or unset rather than truncated: a redaction that shows a prefix leaks a prefix. `TestConfigurationRefusalMatrix` is the matrix, thirteen cases, each matched against the command's own sentinel *and* required to name the variables it is about — a refusal that reported a different problem than the case made would pass a bare sentinel check. `TestByteSizeParserIsExact` states the rule rather than the outputs: every expected value is written as the arithmetic that produces it. `TestRebuildTellsAHelpRequestFromAParseError` and `TestRebuildRefusesInLocalOnlyMode` hold the two claims about that subcommand, and `TestRebuildDoesNotRequireASchemaFile` records the one place the two subcommands' configurations deliberately differ. `TestExitCodesAreThreeDistinctAnswers` asserts all three on real runs of the built binary, which is the only place an exit code is visible — against the literals 0, 2 and 1 rather than against the command's own constants, because a test that compared a code with the constant that produced it would pass with all three set to the same number, and what a supervisor's configuration is written against is the numbers. Two tests hold dispatch claims no scenario clause names, and they are named here so the map stays a complete inventory rather than a sample: `TestUnknownSubcommandsAreRefused` (a typo'd subcommand exits 2 rather than starting a daemon), and `TestVersionAndUsageAnswerWithoutConfiguration` (the two informational subcommands need no environment at all, because asking what a tool is must not require configuring it first).

**Three further claims of the daemon's own loop are held by tests added when the reviewer found them unheld, and they are named here because each one is a rule that reads as a detail until it is broken.** `TestOnlyAnEnvelopeIsAccepted` holds the line grammar from both ends: a bare row — valid JSON, a correct row of a declared table, simply not wrapped — dies at its line rather than being guessed at, and an envelope carrying one mistyped key beside two good ones is refused rather than written with the extra key silently dropped. It is the test a future convenience of accepting bare rows would have to delete before it could land. `TestTheLineBoundIsTheConfiguredNumber` holds both ends of `ICELAKE_MAX_LINE_BYTES`, at a bound far below the buffer size a default would have used: the obvious implementation enforces neither end, because a scanner refuses a token only when it has to grow past its maximum — so a generous starting buffer silently raises the bound for every value below it — and a maximum that does not allow for the line terminator — one byte for LF, two for CRLF, neither part of the line — makes a line of exactly the configured length depend on whether the input ended there or on how the producer ends its lines. The test's table holds all four ends: exactly-at-bound and one-over, each with LF, with CRLF, and with no terminator at all. `TestBackpressureHoldsStdinAndResumes` holds the one loop in this command that answers an error by not giving up. It is scenario 7's ceiling clause moved out of the library and into a process: a deliberately tiny ceiling, a gate in front of the bucket that stops answering and then answers again, and all three parts of the claim asserted — the daemon does not exit, it says so on stderr, and everything it was holding is committed exactly once when the bucket comes back. The gate is the same kind of seam as the slow proxy scenarios 7 and 8 use and stands in for nothing: the store behind it is the same real MinIO, and what it controls is the network.

**Two more were added at M15, when this command stopped writing one line at a time, and both exist because chunked reading has a failure mode that no test handing the daemon its whole input at once can reach.** `TestABlankLineOnALiveStdinDoesNotEndTheRun` writes to a real pipe in three separate writes with real pauses between them — a good line, a blank line on its own, then more good lines — and requires every record to arrive. A blank line with nothing queued behind it is the one case that produces an empty chunk while the input is still open, and reading that as the end of input exits zero and silently drops the rest of the pipe; that defect was in the first version of the chunked loop and the whole suite stayed green over it, because every other test here writes its input in one go and the next line is therefore always already queued. `TestAStreamedBadLineWritesTheGoodPrefixOfItsChunk` holds the promise chunking puts under the most pressure: a line the *library* refuses, mid-chunk, on a stream interleaving two tables, and every line of that table before the bad one still durable — which only happens because the daemon writes the refused group a second time, cut at the bad line, and nothing else in the suite would notice if that second write disappeared. It also asserts the message names the operator's line number and not the library's row index, and it states the documented residue as the two outcomes the design permits rather than as one, because which of them happens depends on where the chunk boundary fell and that is a property of how the producer wrote.

The substrate half is `TestDaemonWritesTwoTablesToABucket` (a real pipe, two tables, blank lines skipped, DuckDB validating the decimal at its exact digits and the payload through base64), `TestSignalDrainsRatherThanDrops` and `TestMalformedLineDiesLoudlyAndLosesNothing`. The last two share a technique worth naming: both read the daemon's own `staging.db` to turn "every record it had accepted" into a number the test knows rather than a guess about timing, since a record is accepted exactly when it is durable there. The signal test also asserts that *nothing* was committed before the signal — the flush thresholds are left at their production defaults, so the drain is the only thing that can have written those rows. And `TestLocalOnlyRunWritesACacheDuckDBCanRead` is the run between the two halves: the real binary, a real disk, no container, and the exact five-minute start the embedded manual opens with, which is what keeps that page honest.

### 14. Batch ingest, and the fsync amortization it exists for

Validates the three M15 decisions in `ARCHITECTURE.md`: that `InsertBatch` is durable at the granularity of the call and atomic within it ("Local write-ahead durability"), that a batch is charged against the staging ceiling all-or-nothing (`Config`), and that the batching layer the M4 measurement told a caller to build for itself now lives in the library instead ("Scope, schema, and pragmas of the staging store"). The shape is scenario 1's, run through the batch door, plus a refusal matrix and one regression tripwire.

Substrate-backed, against the same MinIO container as every other scenario:

- **A batch round-trips.** Records inserted as slices rather than one at a time are batched, encoded, uploaded and committed exactly as scenario 1's are, and DuckDB reads back every row with its exact values. This is the clause that proves the new door is the same pipeline and not a parallel one.
- **A batch is one transaction, so a cancellation part way through leaves none of it.** A batch is inserted under a deadline derived from how long that same batch has just been measured to take, halved until a call actually fails, and whatever the outcome staging holds either the whole batch or nothing — never a prefix. Deriving the deadline is the part that matters and it was not there at first: a deadline that lands *before* the first record leaves nothing staged under any implementation, including one that opens a transaction per record, so the first version of this clause passed against the very mutation it names. Cutting half way into a batch this machine has already timed is what makes it discriminating.
- **A crash inside a batch leaves none of it either, and that is a different claim.** The M15 decision says the batch is atomic across a crash between any two of its rows, and no in-process test can make that statement. A child process accepts a few records one at a time — which `Insert`'s own contract says are durable — then enters one batch of a quarter of a million, and the parent watches the staging file while it runs before killing it with `SIGKILL`. What is asserted during the watch is the whole difference between the two designs: the staged count may be what was there before the batch or all of it, and never anything between. What is asserted after the kill is that the file holds exactly the records from before it, that the surviving records are picked up by the next run, and that a fresh batch through the same door commits alongside them exactly once. Watching rather than timing the kill is deliberate and was forced by mutation: a kill placed by a clock lands wherever the machine happened to get to, and against a per-record transaction it lands early enough to look like a pass.
- **A bad row refuses the whole batch and says which one it was.** A slice with one unrepresentable value is refused with a `BatchError` whose `Index` is that row's position and which unwraps, through `errors.As`, to precisely the `PoisonError` the same row earns from `Insert`. Nothing from the batch is in staging afterwards, asserted against the staging file's own counters rather than inferred from a later read.
- **The ceiling refuses a batch whole.** Against a deliberately tiny ceiling, a batch that does not fit returns `ErrStagingFull` and leaves the staged count exactly where it was — the atomic-charge decision, asserted as the absence of a partial write rather than as the presence of an error. A batch that fits exactly is accepted, so the test cannot pass by refusing everything.
- **The refusal order is the documented one.** A closed writer handed a batch whose first row is poison answers `ErrClosed`, not the row's error: the same ordering promise `Insert` makes, at batch granularity.
- **An empty slice is a no-op.** It returns nil, stages nothing, and leaves the counters untouched, so a caller looping over a partition that happened to be empty needs no special case.
- **`OnAccept` fires once per row, in order, after the batch is durable**, and an error from it comes back as a `MirrorError` — the one refusal-shaped answer that does not mean the batch was refused.
- **The dynamic door decodes each line strictly and names the index.** `InsertJSONBatch` applies exactly `InsertJSON`'s decode to every line, and a line that is not a JSON object is a `BatchError` at that line's index wrapping the same `RecordError` the single-line door returns, with nothing staged.

**Where each clause landed, recorded at M15 the way scenarios 10, 12 and 13 record theirs.** `TestBatchInsertRoundTripsThroughTheBucket` is the round trip, five hundred records in batches of a hundred, read back through DuckDB with the decimal asserted at its exact digits and the spot checks placed either side of a call boundary. `TestABatchIsRefusedWholeOrAcceptedWhole` is everything else, one subtest per clause against one container: the bad row and its index, the ceiling met from both directions — a batch one record too large for an empty store, then one that fits exactly, then one record too many for the store that now holds it, so the test cannot pass by the writer having stopped working — the closed writer answering `ErrClosed` for a batch whose first row is poison *and* for an empty one, the empty batch, the mirror hook seen once per record in batch order with the staging file read from inside the callback to prove the whole batch was already durable when the first one ran, the failing mirror that is not a refusal, the bad JSON line followed by two good ones, and the cancelled context. Every one of them counts the rows in the real `staging.db` rather than asking icelake what it believes happened, because "nothing was accepted" is a statement about a file. `TestACrashInsideABatchLeavesNoneOfItBehind` is the crash clause, driving the `batch-crash` child script through the same machinery scenario 2's variants use. **Corrected at M16 (2026-08-04), in the test rather than in anything it tests.** That test has two arms — the kill landed inside the batch, or the batch finished first and the poll is what held the claim — and only the first of them was carried through to the recovery half: the three assertions after the kill read "the twenty records that were there before the batch" where the second arm leaves a quarter of a million. So on any machine fast enough to finish that batch inside the watch window, the test failed at the recovery clause while the atomicity clause it exists for had passed, which reads as a durability failure and is not one. It was reproduced at the commit that introduced it before being changed, so it is a branch that had never run on the machines it was written on rather than a regression. The assertions now read what is actually on disk, and the re-sent batch is numbered past everything the crashed run could have staged so the exactly-once count cannot be flattered by a collision. `TestBatchedIngestStaysManyRecordsPerTransaction` is the tripwire, and it needs no container.

And one regression tripwire, which is a test rather than a benchmark, needs no container, and runs in the ordinary suite:

- **A batch is still many records to a transaction.** The signal is a ratio between the two doors — the cost of one record through `Insert` against the cost of one record through `InsertBatch` — measured on the same machine, with the same records, in the same run. It is deliberately not a rate: a rate is a property of the disk, would have to be recalibrated for every machine it ever ran on, and would be flaky on a slow runner. The ratio needs no calibration at all, because the regression this milestone is exposed to makes the two doors into the same code doing the same work and therefore drives the ratio to one, wherever it is run. The assertion is that the batch door stays at least twice as cheap, and the bound is set against the least favourable machine rather than the comfortable one: on an ordinary disk the measured figure is in the tens with the race detector on and the hundreds without it, and on a filesystem whose sync costs nothing — a tmpfs, or a disk that does not honour barriers, where batching genuinely saves less — thirty-five consecutive runs measured between 4.1 and 6.2. Getting that spread down to something a bound could sit under took two changes worth naming, because the obvious form of this measurement is not stable: the two doors are measured in interleaved rounds and the ratio is taken *per round* before the median is taken of the ratios, so a round in which the machine was busy inflates both of its figures and cancels; and the single-record door is given many records per round, because on a nearly-free sync one `Insert` costs tens of microseconds and SQLite's automatic WAL checkpoint lands inside one round out of several and triples it. Mutating the staging store to open a transaction per row puts the same figure at 1.0 to 1.6. The disk's own sync cost is measured alongside and reported rather than asserted on, because it is what makes the other two figures readable: on a millisecond disk the ratio is the fsync being amortized, and on a microsecond one it is what a transaction costs apart from its sync.

**How the benchmarks are run and read.** `mise run bench` runs the Go benchmarks in the root module and in `internal/staging`; they are ordinary `testing.B` functions, so `mise run check` never runs them and the gate stays as fast as it was. The figures are meant to be read together, top to bottom. `BenchmarkDiskFsync` is the machine's floor, one `fsync` per iteration and nothing else, and everything below it is bounded by it. `BenchmarkStagingAppend` is one record per transaction, which should land within noise of the fsync figure and is the M4 behaviour kept so the comparison stays measured rather than remembered. `BenchmarkStagingAppendBatch` runs at each of the transaction sizes `ARCHITECTURE.md`'s M15 table reports, so that table is something anyone can re-run rather than a set of numbers to be believed. And `BenchmarkWriterInsertBatch` and `BenchmarkDynamicInsertJSONBatch` are the same work end to end through the public API, the second including the per-line JSON decode the `icelake` command pays, so the gap between them is what a runtime-declared table and a stream of bytes cost. The two run the *same eight-column table*, declared as a struct on one side and as a schema document on the other, which is what makes that reading true rather than merely stated: an earlier pair ran five columns against eight and had the door doing strictly more work measuring faster, which reads as a finding and was an artefact of the fixture. Every one of them reports nanoseconds per *record*, so any figure can be compared with any other. A run where the single-record figure is much *better* than the raw fsync figure means the pragmas are not what the store thinks they are, which is worth more attention than a run where the last figure is slower than expected.

**Four benchmarks were added at M16 for the second encoding, and what they measured is not what they were added to measure.** `BenchmarkDynamicInsertCBORBatch` sits beside `BenchmarkDynamicInsertJSONBatch` — same eight columns, same records, same batch size — and the two are indistinguishable. On the development machine, across ten runs of a hundred to two hundred thousand records each, JSON measured between 12.1 and 19.7 microseconds a record and CBOR between 12.3 and 18.5: two overlapping ranges and not a difference. That is the honest reading and it is the *expected* one once the figures above are read in order — a staging transaction is between one and two orders of magnitude larger than either decode, so a benchmark that puts a decode next to one is measuring the disk. So `BenchmarkDynamicDecodeJSONBatch` and `BenchmarkDynamicDecodeCBORBatch` were added to measure the decode alone, and there the two separate. As M16 first shipped they separated the wrong way — about 2.9 microseconds a record for JSON against 3.4 for CBOR, ten to fifteen percent *slower* for the binary format — and that sign was a defect, not a property of the format: the decode read every record twice to keep its refusals sharp, and a profile priced the second read at a fifth of the whole. `SCHEMA.md`'s tag-rule consequence records the correction: valid records are now decoded once, and the two-step read is only the error path's wording pass. Measured after the correction on the same machine, **CBOR decodes at about 2.3 to 2.5 microseconds a record against JSON's 2.8 to 3.3 — fifteen to twenty percent faster, with fewer allocations**. The wire is also 17.6% smaller for the same records — 171 bytes against 141 on the benchmark's fixture — so the second encoding buys decode time, bytes on the pipe, exactness for integers past 2^53, and bytes into a `binary` column with no base64 step. Anyone quoting these figures should re-run them: the durable points are that the end-to-end pair cannot show a decode difference at all, and that a decode which measures slower than JSON is a defect worth profiling rather than a fact worth recording.

**The reason it is slower is a design decision and not an accident, and it is recorded so nobody optimises it away without knowing what they are removing.** `SCHEMA.md`'s M16 tag decision explains it in full: the row is decoded in two steps, its fields' raw bytes first and then each field on its own, because a one-step decode into a map hands back a tagged value with the tag already applied and the field it came from already forgotten, and `undefined` indistinguishable from `null`. The two-step decode is what makes every tag refusable *by shape* and `undefined` distinguishable at all. Roughly four hundred nanoseconds a record is what that costs, and the exactness is what it buys.

**The technique the two decode benchmarks use is worth naming, because it looks like a seam and is not one.** Both JSON and CBOR batch doors decode every item *before* the writer's lifecycle check — a documented ordering, matching the single-record doors — so a *closed* writer runs the whole decode and then answers `ErrClosed` without touching staging. That makes a public-API benchmark of a private step possible with no seam added for it, and it fails loudly if the ordering ever changes, because the error stops being `ErrClosed`.

### 15. The ingest entry point, and the second encoding

Validates the three M16 decisions in `ARCHITECTURE.md` — that the ingest pump is a library entry point rather than something each program writes for itself, that the input is one grammar with per-record dispatch on the first byte and no setting anywhere, and that a refusal names the record always and the line only when the record is not CBOR — together with `SCHEMA.md`'s CBOR column of the coercion table.

**Where this scenario runs, and why it is not where scenario 13 runs.** Everything here is local-only and needs no container, for the reason scenario 12's first half needs none: what these clauses are about is the path from a caller's bytes to a durable row in `staging.db`, and that path is the same objects doing the same work whether or not a bucket exists behind it. That is a deliberate reversal of where the same claims lived at M15, when the pump was in a `main` and the only way to reach any of it was to start a binary and write to a pipe — which is why most of the rows below had no test at all until this milestone. Scenario 13's streaming clauses stay exactly where they are and are now the proof of the *translation*: that the command hands its pipe to this call and adds nothing.

Hermetic, needing no container:

- **A stream is read in chunks and every record is durable when the call returns**, in both spellings, asserted by counting the real `staging.db` rather than by asking the library what it believes happened.
- **A blank line is skipped, is counted as a line, and is not counted as a record.** Three good records with three blank lines among them and then a record the writer refuses: the refusal has to say record 4 and line 7. A loop that counted only the lines it kept says line 4; one that counted blank lines as records says record 7. Both numbers are asserted, because the two failures are different and each looks correct against the other's assertion.
- **A refused record stages the good prefix and names its absolute position**, in both spellings, on a stream interleaving two tables with the *other* table's group written first. This is the clause that fails if the truncate-and-rewrite is ever dropped: a row the writer refuses is refused with its whole group, because the group is one transaction, so the records before it are durable only because the group is written a second time cut at the bad one. It also asserts what the error deliberately does *not* carry — the batch's own row index is unreachable through `errors.As`, because it counts from the start of a slice the library built and an operator counts from the start of their stream.
- **The stream's own refusals are typed and name the record**, one case per kind: a line that is not JSON, a bare row, an envelope with an unknown key, an envelope with no row, a table with no writer, and the same set again in CBOR — plus the four the grammar itself owns: a first byte that starts neither kind of record, a stream opening with a byte-order mark, an indefinite-length CBOR map, and a truncated CBOR item at the end of the stream. Each asserts the `Kind` and the record number and that nothing was staged.
- **A record over the size bound is refused rather than truncated, and the record before it is still durable**, in both spellings, with the bound set above the first record and below the second so the clause cannot pass by refusing everything.
- **A group the staging ceiling refuses is halved rather than held for good.** The chunk is five times the whole ceiling, which is the case a loop that only slept and retried could never get past — no amount of draining makes an identical over-sized group fit — and the assertion is that every record still arrives. The context is bounded so that a regression here fails with every record accounted for instead of hanging.
- **A cancelled context is a clean stop rather than a failure**, in both of its arms. One lands between chunks and is seen by the loop's own select; the other lands while a chunk is being written and comes back from the staging store wearing a failure's clothes, and reading *that* as a runtime failure would make a clean shutdown fail whenever the signal happened to arrive inside a chunk. The second arm is reached by starting with an already-cancelled context and an already-full reader, so which arm runs is a select over two ready channels — that is, random — and twenty rounds reach both. The assertion is the same for both, which is the point.
- **Options are refused before a byte is read**, in the shape `Config` refuses one.

- **The two spellings mean exactly one thing.** The same hundred and twenty records of two tables go through three runs — all JSON, all CBOR, and a stream alternating between them record by record — and what is compared afterwards is the canonically encoded payload of every staged row, byte for byte, together with the schema fingerprint it was recorded under. Those payloads are what the batch hash is taken over and therefore what every object name in the warehouse derives from, so equal payloads mean the three runs produce the same table, the same files and the same names. Comparing the Parquet the runs write would be a weaker test that looked stronger: it would pass on any two encodings that happen to round-trip to the same values, where this fails the moment one encoding's decode admits a value the other's does not. The third run is the one no format setting could have expressed at all.
- **A mixed stream numbers records and lines separately.** A stream of JSON, CBOR, CBOR, JSON, a blank line and then a bad JSON record must report record 5 on line 4 — the two CBOR records consumed no newline, so the line counter did not move for them — and a CBOR record refused in the same stream must report a record number and *no* line, with the word "line" absent from the message entirely. This is the clause that would have been impossible under a format setting, and it is where the two numbers visibly stop being the same number, which is why `IngestError` carries both rather than one relabelled.
- **The CBOR coercion matrix**, one case per row of `SCHEMA.md`'s CBOR column, asserted on the typed error's `Kind` and `Field` and never on its message. It mirrors the JSON matrix in scenario 10 case for case where the two share a rule, deliberately, because the whole claim of the second encoding is that it has no rules of its own — a matrix listing only the CBOR-specific refusals would leave "the shared rows still hold here" untested. The rows that exist only here are the ones a format that can express more than JSON makes reachable: a byte string offered to a string column and to a decimal column, an integer past the int64 range, an integer past 2^53 *accepted* because a CBOR integer never travelled through a float, all four tags named individually, `undefined` in both an optional and a required column, an indefinite-length item, a duplicate key, a non-text map key, and a text string that is not valid UTF-8. The acceptances are asserted in the same table and for the same reason scenario 10 gives: a matrix of refusals alone is satisfied by a door that refuses everything. The declared shape is the JSON matrix's eight columns plus one `double`, because CBOR has three float widths where JSON has one spelling and the float rows need somewhere to land.
- **The CBOR batch door names the index of the item at fault and stages none of the slice**, which is `InsertJSONBatch`'s contract asserted again rather than assumed to transfer.

Through the built binary, in scenario 13's file because they are claims about the command:

- **A CBOR stream is written like a JSON one, with nothing configured at all.** A real pipe carrying CBOR records with no newlines in them, two tables interleaved so a framing error of one byte in either direction would fail to decode the second record, and DuckDB reading back the decimal at its exact digits and the payload as the bytes that were sent rather than as base64. "Nothing configured" is the claim: the command has no input-format setting and no code that decides one.
- **One stream carries both spellings.** Twenty records of each table in each spelling, alternating, with a blank line thrown in, through one pipe into one running daemon. Every record arrives and every price is distinct, so a spelling that had been mangled rather than refused shows up as a collision. It is here rather than only at library level because "no configuration" is a claim about this program: a version of this feature with an environment variable in it would pass every library test and fail this one.
- **A refusal in a CBOR stream names a record and not a line**, asserted on the process's own stderr, which is where scenario 13 already records that a command's printed text is its contract.

**Where each clause landed.** `TestIngestStreamIsTheWholeIngestLoop` is the loop, one subtest per clause. `TestTheTwoFormatsMeanExactlyOneThing` is the three-run payload comparison. `TestAMixedStreamNumbersRecordsAndLinesSeparately` is the numbering. `TestCBORCoercionMatrix` is the matrix. `TestACBORStreamIsWrittenLikeAJSONOne` and `TestOneStreamCarriesBothSpellings` are the two through the binary. The M15 streaming tests — `TestABlankLineOnALiveStdinDoesNotEndTheRun`, `TestAStreamedBadLineWritesTheGoodPrefixOfItsChunk` and `TestBackpressureHoldsStdinAndResumes` — are unchanged and still pass against a `run` that is now four lines of translation, which is the acceptance test for the move: the behaviour did not move, only the address did.

### 16. The ClickHouse mirror, end to end

Validates the M17 decisions in `ARCHITECTURE.md` — the opt-in mirror, the encode-seam tap, the doorbell-not-queue failure shape, the `_batch_key` column, the add-only reconciliation and its refusal — together with `SCHEMA.md`'s two-door type mapping. It runs against the pinned ClickHouse container above; the clauses that also need a bucket run against MinIO beside it, and the clause that is about local-only mode deliberately has no bucket in it at all.

- **Rows written through icelake arrive in ClickHouse with the right values.** Records go in through the public API, a flush is forced, and the mirror table is read back through the driver: the row count, and every column of a sampled row compared against what was inserted — the decimal at its exact digits and the timestamp to the microsecond through `toUnixTimestamp64Micro`. The binary byte-for-byte readback and null-versus-zero in an optional column are scenario 17's clauses, where every type appears in both required and optional form against a real load from the file. The types the table was actually created with are read out of `system.columns` and compared against `SCHEMA.md`'s mapping, because a column that was created as the wrong type still accepts every value this clause writes.
- **Every row carries its `_batch_key`, and it is the batch's real key.** Not merely non-empty: the distinct `_batch_key` values in the mirror are compared against the object names in the warehouse `data/` prefix, which is the join the design promises a user can reconcile on. In the local-only clause below the same comparison is against the spool file names, which are the same strings.
- **Replay does not duplicate.** The process is killed at `after-spool-before-upload` — after the mirror insert has happened and before anything reached the bucket — and restarted; the batch replays under its stored key, the tap fires again with the same rows and the same token, and the mirror's row count is *unchanged*. The count is the assertion rather than a log line, because the count is the only thing that distinguishes a token that worked from one that was accepted and ignored. A control run with the deduplication window removed from the table is not part of this scenario: that measurement is recorded against the pin above, where it belongs, and repeating it here would be testing ClickHouse rather than icelake.
- **ClickHouse being down never costs the lake anything.** The container is stopped mid-run. Records keep being accepted, the flush commits, the object appears in the bucket and DuckDB reads the rows back — and the failure arrives at `OnClickHouseError` as a `ClickHouseError` whose `Kind` is `connect`, `insert` or `schema` — which of the three depends on where in the batch's round trips the stop landed — matched with `errors.As` and never by message. `Flush` and `Close` both return nil, which is the sharp end of the doorbell decision: a mirror failure that reached either of them would be ClickHouse blocking the lake.
- **The writer is unaffected by a mirror that is down at open time.** (The daemon inherits this by being the library's caller; no separate daemon clause exists or is needed.) `OpenWriter` succeeds against an unreachable server, the notification fires, and the writer accepts and commits records normally. This is the reachability half of the open-time split; the configuration half is the next clause.
- **A declared `MirrorTTL` is created, enforced, and reconciled, and the lake never notices.** The expiry test runs the dial in both directions because of a server behaviour worth recording: ClickHouse applies TTL whenever it writes a part, an insert's own part included, so a fixture whose aged timestamps were already past a short TTL would be dropped by the insert itself and prove nothing about expiry. So the table is created under a TTL far longer than the fixture's age — `engine_full` carries the declared clause, and every row survives its own insert — and then a second open declares a shorter one: reconciliation moves the live table to it (`MODIFY TTL`, the one overwriting reconciliation the mirror has, argued in `ARCHITECTURE.md`), `OPTIMIZE ... FINAL` forces the merge that applies it, and the count goes to zero while the spool still holds every batch. A companion clause proves the refusals need no server at all: a TTL naming an undeclared column, a non-timestamp column, or a zero duration is a conflict from `OpenWriter` against an unreachable address. The daemon's `ICELAKE_CLICKHOUSE_TTL` syntax — the one channel expiry reaches the command through, because the schema document carries shape and never configuration — has its parse-and-refuse matrix in `TestClickHouseTTLEntriesParseAndRefuse`.
- **A live table icelake will not reconcile is a refusal, not a notification.** A ClickHouse table is pre-created with one column at the wrong type, and `OpenWriter` returns a `ClickHouseError` with `Kind` `conflict` naming that column, and no writer. Beside it, the case that must *not* refuse: a table pre-created with the operator's own `ORDER BY` and an extra column of their own is accepted and written into, because icelake verifies the columns it writes and nothing else. And the add-only arm: a table missing one optional column gains it by `ALTER`, and rows written after that carry it.
- **A name that cannot be mapped is refused before anything is created.** A namespace or table containing a double underscore returns a `conflict` and no writer, since `<namespace>__<table>` would not be injective over such names.
- **Local-only mode plus the mirror works, with no bucket anywhere.** A store opened with `LocalOnly` and a `ClickHouse` config writes rows, the spool file lands, and the same rows are in ClickHouse with the same `_batch_key` — which is the clause that proves the tap is at the encode seam rather than after the commit, because in this mode there is no commit at all. It is the only scenario-16 clause with no container but ClickHouse's own in it.
- **Configuration is refused the way every other configuration is.** A `ClickHouse` config with no `Addr`, or with no `Username`, is a `ConfigError` carrying a `ConfigFieldError` per violation with the field named as a caller spells it in Go, joined with the rest of the matrix in one error — asserted through the existing scenario-7 machinery rather than a second copy of it, and in both modes, because the mirror is valid in both.

### 17. Two-door identity: the live insert and the file the lake holds

Validates the property `ARCHITECTURE.md` names and rests the whole "disposable and reproducible" story on: inserting a batch through the live mirror, and loading *the same Parquet file* into a table with the same DDL through ClickHouse's own Parquet reader, produce the same rows. It is the milestone's most important test and it is the one whose value depends entirely on it being able to fail, which is why the mutations below are part of the scenario rather than an appendix to it.

**The table under test carries all nine declared types twice** — once required and once optional — plus a required `long` that is the row's ordinal, so that both sides can be compared in a fixed order. The optional columns are populated on odd rows and null on even ones, so every column of every type has real nulls in it and a mutation that turned nulls into zeros has something to be caught by.

**The two doors.** Door one is the live mirror: records go through the public API, a flush is forced, the tap fires. Door two is the same batch's spool file — which is byte-for-byte the object in the bucket, by the spool's own decision — copied into the ClickHouse container and read with `file(..., Parquet, '<structure>')`, inserted into a twin table created from the identical DDL. The structure is stated explicitly rather than inferred, because an inferred structure would quietly accept whatever the file happened to contain and there would be nothing left to prove. Both strict settings are set on the read: `input_format_null_as_default=0`, so a null landing in a non-`Nullable` column is a refusal rather than a zero, and `input_format_parquet_allow_missing_columns=0`, so a column the file does not have is a refusal rather than a column of defaults.

**What is compared, per column, in a fixed row order.** Counts first, on both sides and against what was written. Then every column, as an ordered list of exactly rendered values: a timestamp through `toUnixTimestamp64Micro`, so the comparison is an integer count of microseconds and not a formatted string whose precision could hide the difference; a decimal through `toString`, which is exact digits; a binary column through `hex`; and every nullable column wrapped so that a null renders as something no value can render as, which is what makes "null preserved as null, not as zero" an assertion rather than an assumption. Then the null counts themselves, per optional column, on both sides — because two columns that were both zeroed the same way would compare equal to each other and be wrong together. And **last**, the two tables' column types out of `system.columns`, because "a table with the same DDL" is the other half of the property. The order of those two is deliberate and is not cosmetic: a schema check running first would short-circuit the one mutation below whose whole point is that the load succeeded and the data is wrong.

**Three mutations, each of which must make this fail.** They run as subtests against the same live data, each building the twin from a deliberately wrong DDL or a deliberately loosened read, and each is required to fail either at the twin's own insert or at the comparison. Which of the two it fails at is not asserted — pinning it would make the test brittle about ClickHouse's error surface — but what each one actually did on the pinned server is recorded here, because a mutation whose failure mode is not understood is a mutation that could start passing for the wrong reason.

- **`DateTime64(3, 'UTC')` in place of scale 6.** Caught by the schema comparison, and the reason is worth stating rather than leaving as a surprise: icelake's declared `timestamptz` is milliseconds, widened to microseconds by `FileSchema`, so every value in the file is a whole number of milliseconds and scale 3 truncates *nothing about these particular values*. The mutation is still the right one and the scale is still load-bearing — a reader that took the file's microseconds for milliseconds would be wrong by a factor of a thousand, and any future column carrying real sub-millisecond precision would lose it — but what catches it today is the type disagreement and not a wrong number. Recorded so nobody later "improves" the test by dropping the schema check.
- **A non-`Nullable` column where the declaration says optional.** Caught at the load: with `input_format_null_as_default=0` the server refuses with "Cannot convert NULL value to non-Nullable type", naming the column. This is the hazard `SCHEMA.md`'s mapping table records, arriving as a failure rather than as a data-loss bug.
- **The same non-`Nullable` mutation with the strict settings dropped.** Caught by the values: the load now *succeeds* and the comparison reports the column differing at the first row, live null against twin `0`. This is the mutation that proves the two settings are load-bearing rather than decorative, and it is the reason the pair is written down in `SCHEMA.md` as a hazard rather than as a test detail.

After the mutations, the unmutated comparison runs once more, so the scenario ends having demonstrated that the thing it just made fail three ways still passes when nothing is wrong.

### Coercion and DDL, at the package-internal tier

Two things about the mirror are pure computation over values the rest of the suite cannot easily vary, and they sit in the second category this document's philosophy section sanctions, in `internal/chmirror`, with the comment each of those tests is required to carry. The generated `CREATE TABLE` text for a declaration covering all nine types, both nullabilities and a decimal, compared against an expected string derived from `SCHEMA.md`'s mapping table rather than from the generator — which is the "exact calculation asserted against an independently derived expected value" shape the closed list names. And the name mapping: `<namespace>__<table>` for the cases that map, and the refusal for the cases that would collide, which is a local decision about a string with no substrate anywhere near it. Everything else about the mirror — the connection, the DDL actually running, the reconciliation diff, the insert — is end-to-end against the container above, because all of it is a claim about what a real server does.

## Real R2 verification: a one-off manual procedure, never CI

Everything above runs against MinIO, and two behaviours this design leans on are R2-specific — MinIO passing them proves nothing about R2. This is handled as a **one-off, operator-run, manual procedure**: a standalone check program (`apps/icelake-r2check`) that is pointed at a real bucket with real credentials and run by hand. **That run — a real bucket, real credentials — is what is never wired into CI, and it is the only part of this procedure that says anything about R2.** The program's own code is a separate matter and is exercised in CI; the paragraph beginning "The third kind is the substrate-backed one" below says exactly how much, and what that costs. It is a procedure with a checklist, not a test:

1. **The checksum workaround holds.** An upload through icelake's exact client construction (region `auto`, request/response checksum calculation disabled) succeeds — proving the documented R2 `501 Not Implemented` behaviour is correctly worked around by the SDK configuration icelake actually uses.
2. **List-after-write is consistent enough for rebuild discovery.** Create objects under fresh `<namespace>/<table>/metadata/` prefixes, then immediately perform the same two-level delimiter listing the rebuild tool uses, and confirm every just-created prefix appears — the property auto-discovery depends on. **Extended at the repair round (2026-08-01) to the third level rebuild also uses**, because the two delimiter listings only ever return `CommonPrefixes`, which a provider may well be able to materialise before the object underneath them is returned by an ordinary listing: for one of the tables, `<root>/<namespace>/<table>/metadata/` is listed with no delimiter and the key it returns is fetched. That is the branch whose failure is severe rather than survivable — rebuild treats a table whose metadata directory lists empty as a fatal error for the whole warehouse, not as one table to skip.
3. **Same-key overwrite behaves as an overwrite.** Upload the same key twice with different bytes and confirm the key reads back as the second body — the property retry idempotency depends on. **Corrected at the repair round (2026-08-01):** this used to say "confirm a single object with the second body", and the program implemented that with a `ListObjectsV2` count requiring exactly one entry, which cannot fail — that call returns at most one entry per key by construction, so a provider that had kept the first body as well would have been reported as passing. The count is now over `ListObjectVersions`, which can tell the two apart, and where an endpoint does not answer that listing the check says so and claims only the read-back it really performed.
4. **The bucket is one this program may write into at all** — a preflight added at the repair round (2026-08-01), before any of the three above. The prefix it was given must list empty, which is what distinguishes a disposable prefix from a warehouse prefix and is the only thing standing between a mistyped flag and a leaked `run-<hex>` directory that would abort every future catalog rebuild of that warehouse; and the bucket must have versioning off, because this program deletes without a version id, so on a versioned bucket every object it wrote would survive as a non-current version and go on being billed. A refused run writes nothing and reports that it wrote nothing.
5. **Cleanup measures rather than asserts.** Every key the run may have created is deleted — recorded before the upload, so an upload whose response was lost is still on the list — and then the run root is listed, by version where the endpoint answers a version listing and by object otherwise, and the step fails unless nothing is left. What it reports when it cannot tell is deliberately weaker than what it reports when it can, and keys it could not account for are named as ones to check by hand rather than asserted to be stranded.

The program prints a pass/fail per step and touches only keys under a disposable prefix it deletes afterwards.

**Corrected at the post-M9 completeness audit's repair round (2026-08-01): this section's opening paragraph used to call that program "a small standalone check program (`apps/icelake-r2check`, a thin `main` in the same spirit as the rebuild CLI)", and it is not one.** `ARCHITECTURE.md` says of the rebuild CLI that its binary is "a `main` that parses flags and calls it, with no logic of its own", so putting `icelake-r2check` "in the same spirit as" it asserted the same thing of a program made of provider checks, its own S3 calls, a preflight that decides whether a bucket may be written into at all, and an ordered cleanup that deletes out of a real paid bucket and then lists it to check. The mistake was caught on the same day as the equivalent one in `AGENTS.md` and was missed by that pass, which surveyed the other documents, concluded this file was clean and said so in its own correction — a survey claim that was wrong about the one document a reviewer of this program would actually consult for its requirements. It matters because of what "thin `main`" buys a reviewer: permission to skim. Two reviewers had it, and the defects the repair round found in that program — a cleanup that printed "nothing left under <root>" without ever looking, a prefix flag whose "deliberately not a warehouse prefix" promise nothing enforced, an overwrite count that could not fail — are exactly the kind that survive a skim. `AGENTS.md` has been amended to record that this document carried the claim too.

**And a number inside that correction was itself wrong, and has been removed rather than updated at the completeness audit's fifth round (2026-08-01).** The sentence above used to size the program at "a little over five hundred lines". That figure was already false when it was written into this file: `apps/icelake-r2check/main.go` was 523 lines at the commit before the repair round and 892 at the commit that carried this very correction, because the same change that gave the program its substrate-backed test is the one that added the preflight and the measured cleanup that test exists for. It reads exactly like what it is — a count taken from the program before that round's own changes to it and never taken again afterwards, which is the ordinary way this happens, since nobody recounts a file to write a sentence that is about something else. What replaced it is what the program *contains* rather than how long it is, and deliberately not today's count, because a line count written into prose is a fact about one commit that goes on being read as a fact about the file. This one stood in three documents at once — here, `AGENTS.md` and `PLAN.md` — copied forward each time rather than recounted; the other two were corrected in this same round, and each of them closed by naming this file as the copy still outstanding, which is how this one came to be found at all. The argument never needed the number: what makes "thin `main`" the wrong description is the four kinds of logic listed above, not their length.

**The program itself has two hermetic tests, named here because nothing else in this document mentions them (recorded at the post-M9 completeness audit's second round, 2026-08-01):** one builds the binary and runs `--help`, asserting it exits zero and does not print back the secret access key it was given in the environment — the mistake it guards is binding `os.Getenv` as a flag's default, which puts a credential into the block `flag` prints for `-h` and for every parse error; the other empties the credential environment and asserts that a run with no endpoint, bucket or credentials is refused on its arguments, matched against the command's own usage sentinel rather than merely being non-nil, since a network failure would satisfy a non-nil check while proving the opposite. Neither reaches a bucket, which is what makes them safe to have in a suite that runs everywhere, and the second is really a test of icelake's standing rule that nothing here ever falls back to the ambient AWS credential chain — a tool that writes throwaway objects into whichever bucket it can reach would be that rule's worst exception.

**Both of those grew at the repair round (2026-08-01), and a third kind of test was added that this section previously argued against having.** The `--help` test asserted only an exit status and the absence of the secret, so it passed identically if `--help` printed *nothing at all* — the usage block it exists to prove is reachable was never asserted to have been produced. It now requires a non-empty output and requires every flag the command defines to appear in it, with the flag names taken from the command's own flag set through `VisitAll` rather than retyped, so the claim is "this command's arguments are documented in the block an operator is shown" and not a restatement of a sentence. The argument test gained the prefix cases, because the run root is built with `path.Join`, which cleans as it joins: `-prefix warehouse/..` would have collapsed to nothing and scattered the run's objects across the top level of the bucket while every printed line still said PASS, and that is now refused on the arguments, in the same one place as the credential rule and before a client exists. It has since gained the mistyped-flag case as well: the `flag` package reports a flag the command does not define exactly as it reports `-h`, so a comparison inside the command is the whole of the difference between a question answered and an argument refused, and the test requires the refusal *and* an empty report, which is how it says nothing reached a bucket.

The third kind is the substrate-backed one, and the reasoning that had excluded it was a category error worth naming. "It needs real credentials, costs real money and verifies a vendor's behaviour" is a true and sufficient argument for not running *the three provider checks* in CI. It is not an argument for leaving the program that performs them untested, and treating it as one left roughly two hundred and fifty lines — the preflight, the record-before-write invariant, the ordered cleanup — with no test of any kind, which is how a cleanup that never looked at the bucket survived a milestone and a review. Those are claims about icelake's own code, they cost nothing against the MinIO container the rest of this suite already runs, and they are now held there, behind the same container-runtime skip helper as every other storage-facing test: a successful run leaves the prefix listing empty afterwards; a prefix that already holds an object is refused and *nothing is written*; a versioning-enabled bucket is refused and nothing is written; a bucket that cannot be inspected at all — the name is a typo, the endpoint is unreachable, the token cannot list — is reported as that and not as a judgement about a prefix and a versioning setting the run never learned anything about (added at the audit's third round, 2026-08-01, because until then every preflight failure closed with the advice for the other one, on the most common way a first run against a new account fails); cleanup against a bucket that retains what it deletes reports failure rather than success (the case that is unreachable through the program precisely because the preflight refuses it first, and therefore the one worth pinning at the layer that must be right the day the preflight cannot tell); a run cancelled part-way is reported as cancelled rather than as a verdict about the bucket; and a key whose upload failed outright is still on the delete list.

**That enumeration listed six of the seven, and the seventh is the cancellation one just added to it — recorded at the audit's fifth round (2026-08-01) rather than slipped in.** `TestACancelledRunIsReportedAsCancelled` was written in the same round as the other six, is gated by the same container-runtime helper, and drives the same `check` procedure against the same MinIO container; what it holds is a defect the program was rewritten to fix. Every step turns a cancelled context into its own FAIL, so a run stopped with Ctrl-C used to end "N of M checks failed. Do not treat this bucket as verified." with nothing anywhere saying it had been interrupted — and this program's own closing line instructs the operator to write the outcome into `ARCHITECTURE.md`'s ledger. That is how a keystroke becomes a false statement about a storage provider, recorded as fact, in the one place this project keeps evidence about R2. It earns its own line because what it holds is not a verdict about a bucket but the program's refusal to issue one, which is a different kind of claim from the rest of this list.

**And one branch added in that same round is held by nothing at all, which is written down here rather than left to be assumed from the test sitting next to it.** The cleanup step used to sit inside the program's "not refused" branch while the cancelled verdict told the operator, with nothing conditioning it, that "cleanup still ran, on its own budget" — so a run cancelled during the preflight printed a statement about someone's bucket that no code had made true. The fix gates both the step and the sentence on the list of keys the run actually recorded, and `TestACancelledRunIsReportedAsCancelled` drives precisely that path: a context already cancelled, a preflight whose listing fails, a refusal, no cleanup. What that test asserts is the returned error, and the returned error is identical with the fix and without it. So is everything else observable from outside the program. The obvious substrate assertion — count the `DeleteObject` requests through a proxy and require none — passes just as contentedly against the unfixed version, because the unfixed version did not run cleanup on that path either: the defect was never that cleanup ran when it should not have, it was that the program *said* it had. That was checked rather than reasoned about: with the old gate put back and nothing else touched, this command's whole test suite still passes. The two gates select the same runs on every path a run can reach, and it is worth writing out why, because "equivalent" is the sort of claim this document keeps catching itself asserting: `put` is the only thing that appends to the key list, the three provider checks are the only callers of `put`, and the first of those checks reaches `put` before anything that can fail except a `crypto/rand` read, so "the list is non-empty" and "the preflight did not refuse" are the same condition on every path a run can actually take. The one path where they differ is a `crypto/rand` failure, which no test can produce and which the old gate handled by announcing a cleanup of zero keys. What differs between the two versions is four printed lines, and asserting on printed lines is what the banned list above forbids in its own words. Making the branch assertable would mean giving `check` a seam that hands its step list back to its caller — a testability-shaped change to a program whose entire output is a printed report — and that trade has not been made. So this is a stated hole rather than an assumed one, in the same spirit as scenario 9's seventh clause and scenario 7's disclosure about its third poison case: the cleanup-announcement branch is reviewed and not proven, and the honest reason is that once message text is off the table this document's own rules leave nothing about it to assert.

**Corrected the same day, at the audit's third round (2026-08-01), and the sentence being corrected is one this paragraph had just written.** The paragraph above used to end "The three provider checks themselves are still never run in CI and never will be", and that was false the moment it was written, made false by the code the same round added a few lines above it. The first substrate test in the list — "a successful run leaves the prefix listing empty afterwards" — calls the program's whole `check` procedure, which is the preflight, the checksum workaround, list-after-write, same-key overwrite and cleanup in that order, and requires it to return nil. All three checks run, every time the suite runs, wherever a container runtime exists. No charitable reading rescues the sentence, because it draws precisely the distinction the code crosses: the program that performs the checks on one side, correctly said to be tested, and the checks themselves on the other, wrongly said not to run. `PLAN.md` carried the same claim in four words and `apps/icelake-r2check`'s own package comment carried it in a clause; both have been amended, and the correction is recorded here rather than in any of them because this is the document that owns the decision. That paragraph's opening move is wrong in the same way and is left standing above rather than quietly rewritten: it calls "it needs real credentials, costs real money and verifies a vendor's behaviour" a *sufficient* argument for not running the three provider checks in CI, when what that argument is actually sufficient for is not running them **against a real bucket**. Running them against a container that starts on a developer's laptop needs no credentials and costs nothing, and what it produces is not evidence about a vendor — which is the whole point of the two paragraphs below.

**What is true is this.** The program's own code — including the happy path of all three provider checks — runs in CI against the MinIO container, behind the same container-runtime skip helper as every other storage-facing test. What is never in CI, and never will be, is the run this section exists for: against a real bucket, with real credentials, by hand. That is the only run that says anything about R2, and it is the only run recorded in `ARCHITECTURE.md`'s ledger. A green CI here is not evidence about Cloudflare and must never be written down as though it were; MinIO answering "yes" to a question about a provider is MinIO answering a question about MinIO.

**And there is a consequence to own rather than to footnote: a change in MinIO's behaviour can now fail this repository's gate on a check whose subject is a storage provider.** Concretely, check 3 requires `ListObjectVersions` to report exactly one version and no delete marker for a key written twice on an unversioned bucket, and check 2 requires the two delimiter listings and the non-delimited listing to return objects written moments earlier. If MinIO ever stops answering either the way it does today, `mise run check` goes red on a claim this project does not make about MinIO. **That is accepted, deliberately, and the reasoning is worth stating because the manual-procedure decision exists to avoid exactly this kind of coupling.** Three of the four behaviours are already load-bearing for the rest of this suite, and were long before this program had a test: every scenario uploads an object and reads it back, scenario 3 rebuilds a catalog from the very delimiter listings check 2 performs, and scenario 2's crash between the upload and the commit requires the replayed batch to re-upload over a key the dead process had already written and to leave one data file rather than two, which is check 3's read-back property under another name. A substrate that stopped honouring list-after-write or same-key overwrite would fail those first and would fail them far less legibly than a step whose printed name is `list-after-write`. The one genuinely new coupling is the version count, and its blast radius is bounded by the check's own degraded branch: an endpoint that will not answer a version listing is not a failure, it is a weaker claim honestly stated, so for that assertion to redden the gate MinIO would have to answer the listing *and* answer it wrongly — a bug in the substrate every other test in this tree already trusts with more than this.

**The narrower alternative was considered and rejected, and it is written down here so the next reviewer does not have to re-derive it.** The substrate test could have been cut back to the preflight, the record-before-write ordering and the cleanup — the three claims it was added for — leaving the whole-procedure run untested. But a happy-path test that runs `check` while tolerating a FAIL from the three provider steps would pass just as contentedly on the day icelake's own client construction, its own listing code or its own key handling broke them, and a test that cannot fail for the reason it exists is the coverage-shaped test the philosophy above bans. If a MinIO change ever does fail this gate on check 2 or check 3, the repair is to give the substrate test a way to run the procedure with the provider steps stood down — not to weaken the checks themselves, which have to stay strict, because they are the ones that run against a bucket someone is paying for.

**One thing about the `--help` test is flagged here rather than settled, and the repair round made it two things rather than one:** asserting that a given byte string is *absent* from a program's output, and asserting that six others are *present*, are both substring assertions against human-readable text, which the banned list above forbids in its own words. The ban's target is identifying behaviour by what a message says, and neither of these identifies behaviour that way — the absent string is a credential the test itself made up and handed to the program, and the present ones are the command's own flag names read off its own flag set, which is an interface rather than a message. But the ban has deliberately not been reworded to carve either out, because a rule bent to fit a test it did not anticipate is exactly how the philosophy above came to need correcting. It is an open question for whoever next reviews that file: either the ban gains a stated, general exception for proving that a secret is not printed and that a program's own flags are documented, or the tests do, or the tests go.

The manual run's results — date run, `aws-sdk-go-v2` version, outcome — get recorded in `ARCHITECTURE.md`'s open questions, which is the ledger of whether this procedure has been run yet. Re-run the procedure on any major SDK bump, before first production use of a new account or bucket, and never otherwise. **That run — the one against a real bucket, whose result goes in the ledger — is deliberately excluded from CI**: it needs real credentials, costs real (if tiny) money, and verifies a vendor's behaviour rather than icelake's own code. (Both pronouns in this paragraph have now been corrected, one round apart, and the second was introduced by the fix for the first. The original bare "It" read as the whole program once the program acquired a substrate test, and was narrowed at the audit's third round; that same edit moved the sentence in front of it up the page and left this one welded to the end of the `--help` paragraph above, so "Its results" and "Re-run it" took the `--help` test as their nearest antecedent until the fourth round split them apart. ## CI requirements

CI must be the same workflow a developer runs locally, or the two drift apart:

- CI runs the `mise` tasks (`fmt-check`, `build`, `test`, `vet`, `lint`, `tidy-check`, `generate-check` — `mise run check` runs them all), not raw `go` commands — `AGENTS.md` mandates mise as the execution path, and CI is not exempt.
- `go test` always runs with `-race` (scenario 6 requires it, and there is no reason any run should skip it) and an explicit `-timeout` well above the suite's normal runtime, since container startup makes hangs otherwise slow to surface.
- The runner must provide Docker, for the testcontainers-driven MinIO. This is a stated requirement, not an assumption. **A machine with no container runtime skips each storage-facing test individually, and says so** (settled at M4): every such test calls a helper that checks for a runtime and calls `t.Skip` with the reason. Skips are visible in the output and countable, which is the property that matters — a package that printed `ok` while having run none of its real assertions would be reporting a pass it did not earn. An earlier version of this did exactly that, by checking once in `TestMain` and exiting zero; it was replaced. CI is required to provide a runtime, so this path is a developer's machine and never the gate.
- **The README quickstart is compiled everywhere and run where there is a substrate.** A testable example gets no `*testing.T` and so cannot skip itself, which is why the example carries no `// Output:` comment: the testing package compiles it and does not run it, and the compile guarantee — that the documented sequence is real, current Go against the real API — holds on every machine. A normal test alongside it runs the same sequence against the substrate and asserts the record reads back, under the same skip rule as every other storage test. Two mechanisms, because the two guarantees have different reach.
- The runner needs a C toolchain: the DuckDB validation library requires cgo. This is confined to the *test* dependency graph — icelake's own runtime remains pure Go (`modernc.org/sqlite` was chosen for exactly that) — and this line exists so the cgo appearance in test builds is understood as deliberate, not scope creep.
- `generate-check` regenerates sqlc output and fails on any diff, keeping committed generated code honest with its SQL sources.

## What these tests are not trying to prove

- Not a concurrency/multi-writer stress test — single-writer-per-table is a standing design assumption, not something being validated here.
- Not a production-scale volume or performance benchmark — thresholds and compression levels are deliberately tuned low/small for fast test iteration, not representative of production behavior (see the configurable-settings note above). The benchmarks scenario 14 adds do not change this and are deliberately not part of any gate: they are run by hand through `mise run bench`, on a machine somebody is looking at, and no number they print is asserted anywhere. The one performance-shaped thing inside the gate is scenario 14's rows-per-fsync ratio, and it is in the suite precisely because it is not a rate: it compares the library against the disk it is running on, so it means the same thing on a laptop and on a slow runner.
- Not a substitute for validating iceberg-go's row-delta/equality-delete path — these scenarios only exercise the append path, since that's the only path either motivating case's data actually needs today. Mutating-projection support (`ARCHITECTURE.md`'s "harder fit" case) will need its own dedicated test design if/when an adopting service actually takes that path.
- Not a test of nested (non-flat) schema evolution — that path does not exist, by decision, and the only thing tested about it is that a nested declaration is rejected rather than half-supported (`SCHEMA.md`'s flat-only scoping, carried in `ARCHITECTURE.md`'s open questions).
- Not a test of snapshot expiration, small-file compaction, or orphaned-data-file cleanup. None of those exist yet. The volume test deliberately produces many small files and never cleans any of them up, which is realistic for the initial implementation and is exactly why those items are recorded as open questions rather than as solved. Scenario 11's retention clauses are **not** coverage of any of the three, and should not be read as such: they exercise deletion of *local* copies of files that are already committed, and nothing they assert touches the bucket, a snapshot, or a data file's existence in the table.
- Not a test of any claim about a bucket made from local-only mode. Scenario 12's first half runs with no substrate because there is no substrate in the feature; every claim about uploading, committing, the catalog or Iceberg is proven in bucket mode against the real container, and the note beside the mocks ban above is what a reviewer cites if that boundary is ever blurred.
- Not a test that `OnAccept` correctly implements any particular hot-store or caching pattern — icelake only proves the hook fires correctly, exactly once, and never compromises its own durability; what an app does inside the callback (indexing, retention, its own storage engine) is entirely out of scope, per `ARCHITECTURE.md`'s "Mirroring and visibility" section.
- Not a test of two processes writing the same table. `ARCHITECTURE.md` now describes concretely what breaks if that assumption is violated; describing it is not the same as defending against it, and no test here asserts any behaviour under that condition.
- Not proof that R2's list operations are read-consistent enough for the rebuild tool's bucket-listing discovery to be trusted in production — MinIO's list-consistency behavior locally is not a stand-in for R2's. That verification exists, but as the one-off manual procedure above ("Real R2 verification"), run by hand against a real bucket — deliberately not as part of this automated suite.
