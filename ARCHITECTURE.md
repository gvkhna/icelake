# icelake — architecture

## Problem this exists to solve

Across the private projects this library was designed to serve, the same pattern keeps recurring: a service collects a large, continuously-growing volume of data and has nowhere principled to put it. The default has been "shove it into a local SQLite file," which works until it doesn't — either the file grows past the point where routine operations (integrity checks, restarts, migrations) scale linearly with its size, or the append-only archival layer next to it degrades into thousands of tiny, uncompacted files. Two concrete, independently-investigated cases motivated this project:

- **An archival service** whose canonical SQLite file had grown past a hundred gigabytes, where a startup integrity check (`PRAGMA quick_check`, run on restart) scales linearly with file size — measured in the tens of minutes and closing in on the service's deploy timeout, projecting a hard deploy failure at a size the file was on course to reach. Its append-only archive writer also had no batching: several code paths wrote one independent compressed frame per single record, so archive files were an ever-growing pile of small, never-compacted frames.
- **A batch-decoding service** with a much smaller file but a structurally similar problem: a decoder that fully regenerates a canonical derived table from raw archives, already hitting a named pain point where widening an enum-like column (`CHECK` constraint) requires a full table rebuild — exactly the kind of schema change a table format with real schema evolution makes free.

Both cases wanted the same thing: collect large amounts of data cheaply, write it in large infrequent batches instead of many small ones, park it in object storage instead of an ever-growing local file, and query it later, lazily, without needing to reconstruct a bespoke pipeline every time. Building that generically, once, is the point of this project.

## What icelake is

A **Go library** (not a service, not a managed platform) that gives any Go program a generic path from "batch of typed records" to "queryable table in Cloudflare R2," using Parquet+ZSTD as the file format and Apache Iceberg (via `apache/iceberg-go`) as the table format. Any caller that can describe its own record schema gets, for free: in-memory batching with size/time flush thresholds, Parquet encoding, upload to R2, and Iceberg table commits (append, and eventually schema evolution) — without hand-rolling any of that per service, which is the failure mode this project exists to end.

It is deliberately **not**:
- A query engine. Reading is DuckDB's and PyIceberg's job — both already read Iceberg tables natively off R2 directly. icelake's job ends at "the table is committed and queryable by anything that speaks Iceberg."
- A managed platform dependency. Cloudflare's own R2 Data Catalog + Pipelines solve a similar problem, but as a hosted control plane — ruled out specifically because depending on a Cloudflare-managed service for the core write path was considered an unacceptable coupling for this project's purposes.
- A multi-language ingestion service (yet). It is Go-native, and calling it *as a library* from another language remains an open problem, addressed under "Multi-language story" below rather than solved here. What the CLI decided at M10 and built at M13 changes is narrower and is stated there too: a non-Go program that can write lines to a pipe can now use all of this without a Go compiler, which covers the common shape without making icelake callable from anywhere.

This repo also carries a command, `apps/icelake` — decided at M10, built at M13 — which embeds the library and reads records on stdin. That does not make icelake a service in the sense this section rules out: it has no listener, no request, no API surface over a wire, and no tenant but the one process that started it. It is a writer fed by a pipe, and everything it does is a library decision it passes along — the rule `AGENTS.md` states for every app in this tree.

## Core write path

1. **Caller declares a schema explicitly.** Each table's shape is defined by the calling service as one explicit, hand-written declaration — see `SCHEMA.md`, which is the authoritative design for this step. (An earlier version of this document said the declaration must *not* be a tagged Go struct, on the grounds that a struct could silently change shape between deployments. `SCHEMA.md` supersedes that: the declaration is a tagged struct, and the objection is answered by mandatory permanent `fieldid` tags, which make a silent shape change impossible — a field's identity is a number a human had to write down, not its position or name. Correcting the contradiction here rather than leaving two documents disagreeing.) What matters architecturally is unchanged: the declaration is explicit and per-table, and it is what makes the write path data-shape-agnostic — the same staging/batching/flush/commit machinery serves an event-archive-like schema and a trade-fact-like schema identically.
2. **Durable local staging.** A record is not considered accepted until it is durably written to a local staging log, independent of the in-memory batch it will eventually belong to. See "Local write-ahead durability" below — this exists specifically so a process crash between accepting a record and flushing its batch does not lose that record.
3. **Batching.** Records accumulate in memory until a **size threshold or a time threshold** trips, whichever comes first — replacing the "one write = one tiny compressed frame" anti-pattern observed in the archival case, where low-traffic paths forced a frame per single record with no coalescing.
4. **Flush.** One batch becomes one Parquet file, ZSTD-compressed, written to R2 as an Iceberg data file, keyed deterministically by a content hash of the batch's canonical *pre-encoding* form — never a sequence number, never a fresh UUID per attempt — so a retried upload after a crash is naturally idempotent. See "Batch identity: content hash over the canonical batch" below, which settles what this document previously left as two open alternatives. Parquet encoding uses `apache/arrow-go`'s `parquet`/`pqarrow` packages — the same library `iceberg-go` itself depends on, so no second Parquet implementation is introduced — with ZSTD compression built into arrow-go's own codec support (no direct dependency on a ZSTD library needed). The upload to R2 goes through `aws-sdk-go-v2`, the same SDK `iceberg-go`'s own S3 FileIO uses internally; it must be constructed with region forced to `auto` and request/response checksum calculation disabled, since newer SDK versions default to sending checksum headers R2 returns `501 Not Implemented` for. When a local Parquet spool is configured, the encoded bytes are written to a local file first and the upload sends those same bytes — see "The local Parquet spool" below.
5. **Commit.** The new data file is registered via an Iceberg append (or, later, an append + equality-delete for tables that need row-level mutation) against the table's catalog, making the new data visible in a new snapshot. Once a batch's commit is confirmed, its records are pruned from the local staging log from step 2. In local-only mode there is no step 5 and no upload in step 4: the spool file is the durable record, and a batch's records are pruned from staging once that file is on disk — see "Local-only mode" under `Config` below.

Large chunks, infrequent writes, cheap storage, lazy query later — the shape asked for from the start of this design process.

**Decision (2026-07-30): tables are created unpartitioned, with no sort order, as Iceberg format version 2.** These three creation-time properties were previously unstated, which meant they would have been decided silently by whatever `iceberg-go`'s `CreateTable` defaults happen to be. Verified against the pinned library, all three are exactly what `CreateTable(ctx, ident, schema, opts…)` produces when passed neither `catalog.WithPartitionSpec` nor `catalog.WithSortOrder`: the spec comes back unpartitioned, the sort order comes back as `table.UnsortedSortOrder`, and the metadata's format version is 2, which is the library's own `table.DefaultFormatVersion`. So the decision and the default coincide, and icelake gets all three by passing nothing — but the decision is recorded here so it stays a decision if a future release changes its default. (Format version is overridable through a `format-version` entry in `catalog.WithProperties`; 1, 2 and 3 were all confirmed to be honoured, and 3 is the highest the pinned version supports. One trap worth recording, since icelake should never rely on this property and a future maintainer might reach for it: a **non-numeric** value is swallowed silently and falls back to 2, contradicting the library's own doc comment, which promises an error if the property "exists and is not a valid version number." Verified — `"banana"`, `""`, `"2.0"` and `" 2"` all produce a version-2 table with no error, because the parse failure assigns the default rather than returning. Out-of-range *numeric* values do fail loudly: `0`, `4` and `99` are all rejected with `invalid format version: N`. So the dangerous input is a typo'd string, not a wrong number — `"3.0"` would quietly give you a v2 table when you asked for v3.) Unpartitioned is the deliberate choice, not a shrug: an Iceberg partition spec forces every write to split its rows into one data file per partition value touched, and this write path's batches span arbitrary rows (a time-partitioned table would turn one sealed batch into a file per day touched) — multiplying small files is the exact anti-pattern this project exists to end, in exchange for partition pruning this workload's lazy, infrequent query pattern does not need. Format version 2 is the current ecosystem standard, and it is what the eventual equality-delete path for mutating projections requires — creating v1 tables now would buy a format migration later for nothing. If a future read-heavy consumer genuinely wants time-based pruning, adding a partition spec to an existing table is a real, supported Iceberg evolution — recorded in the open questions below, to be designed against a real case rather than speculatively.

## Public API surface

Until now this design described a write path without ever writing down the surface a caller actually touches. This section fixes that. Everything below is illustrative call shape, not a frozen signature list — the decisions are the semantics, not the exact spelling.

**Decision (2026-07-30): two handles opened in two steps — one process-level `Store`, then one generic `Writer[T]` per table.**

```go
// Process-level. Validates cfg, opens staging.db, runs goose migrations against
// it, and takes one ordered pass over staging: it seeds the ceiling counters,
// and it refuses a staging database left in a state this build will not replay.
// In bucket mode it also opens catalog.db and the R2 client, exactly once, and
// starts the retention sweeper when a cache is configured; in local-only mode it
// opens neither and starts no sweeper. The index that pass builds is a local
// variable, discarded when Open returns — see the M4 decision under "Local
// write-ahead durability". Illustrative shape.
func Open(ctx context.Context, cfg Config) (*Store, error)
func (s *Store) Close(ctx context.Context) error

// Bucket mode only. Uploads and commits every spool file the cache still holds
// that was written in local-only mode and has never reached a bucket. A writer
// drains its own table when it opens; this is for a table no writer reopens.
// See the local-only decision under Config below.
func (s *Store) DrainSpool(ctx context.Context) error

// Per-table. T is the caller's tagged declaration struct (see SCHEMA.md).
// Validates the namespace/table names, derives the declared schema from T,
// drains any spool backlog this table has (bucket mode only, and before the
// table is loaded — see the local-only decision under Config), runs the schema
// reconciliation loop for this one table, and takes its own fresh ordered pass
// over staging to claim that table's pending rows.
func OpenWriter[T any](ctx context.Context, s *Store, tc TableConfig[T]) (*Writer[T], error)

func (w *Writer[T]) Insert(ctx context.Context, row T) error
// One transaction for the whole slice: all of it is durable when this returns
// nil, none of it is when it returns an error. See the M15 decisions under
// "Local write-ahead durability" and Config's staging ceiling above.
func (w *Writer[T]) InsertBatch(ctx context.Context, rows []T) error
func (w *Writer[T]) Flush(ctx context.Context) error   // force a flush, do not close
func (w *Writer[T]) Close(ctx context.Context) error   // drain, then stop accepting
func (w *Writer[T]) Pending() (records int, bytes int64)
func (w *Writer[T]) Status() WriterStatus[T]          // see "Mirroring and visibility" below

// Per-table, declared at runtime instead of at compile time. The declaration
// comes from a schema document rather than a tagged struct and a row is parsed
// JSON rather than a Go value; everything after the declaration —
// reconciliation, staging, sealing, batching, replay, flush — is the same
// machinery, run by the same Writer. SCHEMA.md owns the document format, the
// derivation and the coercion rules.
type Record = map[string]any

// A parsed table entry from a schema document: the field specs a declaration is
// derived from, and nothing else. ParseSchemaDocument builds these; a caller can
// also build one itself and never touch a document.
type TableSchema struct{ /* field specs, in declaration order */ }

type DynamicTableConfig struct {
    Namespace string
    Table     string
    Schema    *TableSchema
    Flush     *FlushPolicy          // nil means inherit Config's batching fields
    OnAccept  func(row Record) error // optional; same contract as TableConfig's
}

// DynamicWriter is a defined struct embedding *Writer[Record], deliberately not
// an alias for it: Go does not allow a method to be declared on an instantiated
// generic type, so InsertJSON cannot hang off Writer[Record] under any spelling.
// Embedding promotes Insert, InsertBatch, Flush, Close, Pending and Status
// unchanged, so there is still exactly one writer implementation and this
// wrapper adds the two JSON doors to it rather than duplicating any of them.
type DynamicWriter struct{ *Writer[Record] }

// One DynamicTableConfig per table in the document, carrying its namespace,
// table and schema; Flush and OnAccept are left zero for the caller to fill in.
func ParseSchemaDocument(doc []byte) ([]DynamicTableConfig, error)
func OpenDynamicWriter(ctx context.Context, s *Store, tc DynamicTableConfig) (*DynamicWriter, error)
func (w *DynamicWriter) InsertJSON(ctx context.Context, line []byte) error
// Per-line strict decode exactly as InsertJSON does it, then one InsertBatch:
// a line that will not decode names its index and refuses the whole slice.
func (w *DynamicWriter) InsertJSONBatch(ctx context.Context, lines [][]byte) error

// The same two doors in the other encoding, added at M16. One CBOR data item
// per record, decoded through the same coercion table into the same Record, so
// the two encodings reach staging as identical bytes.
func (w *DynamicWriter) InsertCBOR(ctx context.Context, item []byte) error
func (w *DynamicWriter) InsertCBORBatch(ctx context.Context, items [][]byte) error

// The whole ingest loop, added at M16 and moved out of apps/icelake: framing,
// chunking, per-table grouping, the truncate-and-rewrite that keeps "everything
// before the bad record is durable" exact, and the halving retry against the
// staging ceiling. Returns nil for the two ordinary endings — end of input, and
// a cancelled ctx — and an IngestError naming the record otherwise. writers is
// keyed by the envelope's own `table` field. There is no format option: the
// grammar reads each record's encoding off its own first byte.
func IngestStream(ctx context.Context, writers map[string]*DynamicWriter, r io.Reader, opts IngestOptions) error

type IngestOptions struct {
    MaxRecordBytes  int                  // longest record; 0 means 16 MiB
    ChunkMaxRecords int                  // records per staging transaction; 0 means 4096
    ChunkMaxBytes   int                  // record bytes per chunk; 0 means 8 MiB
    ReadAhead       int                  // records queued ahead of the writer; 0 means 1024
    BackoffMin      time.Duration        // 0 means 100ms
    BackoffMax      time.Duration        // 0 means 5s
    OnNotice        func(IngestNotice)   // optional; staging held, and reading resumed
}
```

**Decision (2026-08-04, M16): the ingest pump is a library entry point, `IngestStream`, and not something each program that pipes records into icelake writes for itself.** M15 put that loop in `apps/icelake`, and `AGENTS.md`'s placement rule — rewritten at M15's review precisely because the descriptive version had failed — says a CLI may contain exactly four translations and nothing else. The loop was not one of them. What settles it is not the rule's letter but what the loop is made of: chunking, the size of a chunk, what happens to the records before a bad one, whether a group the staging ceiling refuses is retried or halved, and whether a staging failure caused by the caller's own cancelled context means "you were told to stop" or "something broke". Every one of those is a statement about durability, which is this library's entire subject; and every one of them was, in `main`, unreachable by the crash tests and the substrate tests that hold every other durability claim in this repository. The rejected alternative was to leave the loop where it was and write the missing tests around the binary. It is rejected because the tests are the smaller half of the problem: a second program that embeds this library — and the whole reason `apps/icelake` is not the product is that there will be others — would have had to arrive at the same five answers by reading a `main` it does not import. The cost accepted is a wider public surface: one function, one options struct, one notice type and one error type, all of which are now promises. `run` is a translation again, and it names the call, which is the mechanical test that rule states.

**Decision (2026-08-04, M16): one input grammar with per-record dispatch on the first byte, and no setting anywhere that selects an encoding.** A record is an envelope; an envelope is a map with the two keys `table` and `row`; and the map may be written as JSON or as CBOR. Which it is, is read off that record's own first byte: `{` (0x7b) begins a JSON envelope that runs to the next newline, and a definite-length CBOR map header (0xa0 to 0xbb) begins a CBOR envelope that is one self-delimiting data item (RFC 8742). Whitespace between records is skipped, which is what keeps a blank line a blank line. Any other first byte is refused at that record, naming its position — including a UTF-8 byte-order mark, which is refused rather than skipped, because it is not whitespace and a stream carrying one was written by a tool that believes it is producing text for a person.

**The two first-byte sets cannot collide, and that is what makes this a dispatch rather than a sniff.** In CBOR, 0x7b is the header of a text string with an eight-byte length, and a top-level text string is not a map and can therefore never be an envelope. In JSON, no encoding of any value begins with a byte in 0xa0 to 0xbb at all. So the sets are disjoint by construction, one byte decides, and nothing anywhere guesses, scores, or tries one parser and falls back to the other. The rejected alternative was the obvious one and was built first: an `ICELAKE_INPUT_FORMAT` environment variable translated into an `IngestOptions.Format` field. It is rejected because it buys nothing the dispatch does not already give and costs the one thing the dispatch is for — a process-wide setting makes the encoding a property of the daemon, so two producers writing into one pipe must agree on it, and changing it is a restart. Under the dispatch they need not agree and there is nothing to change: one producer writes JSON into a running stream and the next writes CBOR into the same one, interleaved record by record, with nothing configured. The cost accepted is that the grammar is now a promise about bytes rather than about a setting — a future third encoding has to begin with a byte neither of these two can, or it does not get in — and that a stream can no longer be described by naming one format, which every document that describes it has had to be rewritten to say.

An indefinite-length CBOR map (0xbf) is refused rather than accepted, and so is an indefinite-length item anywhere inside a record. RFC 8949's deterministic-encoding rules exclude them, and this library's posture on input is that a value has exactly one spelling — the same argument the binary column's single base64 encoding and the decimal's single digit grammar already rest on. Two encodings of one map are one thing two producers can disagree about while both believing they are right.

**Decision (2026-08-04, M16): a refusal names the record number always, and the line number only when the record is not a CBOR one.** A stream that can change encoding per record has no single coordinate: "line 41" means nothing about a CBOR item, which is not on a line, and a byte offset names a position no producer can count to without a decoder of its own. So `IngestError` carries both, `Record` counting records from one and `Line` carrying the physical line, and the rule for `Line` is one sentence: it is zero exactly when the record is known to be CBOR. A JSON record reports the line it is on; so does a byte the grammar does not recognise as either start, because somebody meeting that refusal is looking at a file and the line is the only handle they have. In a stream of nothing but JSON the two numbers coincide apart from blank lines, which are lines and are not records — so a file with two blank lines before its third record reports record 3 on line 5, and the message reads `record 3 (line 5)`.

**Corrected at the completeness audit's fifth round (2026-08-01): the two comments in the sketch above described the staging replay as one snapshot taken at `Open` and handed out a table at a time, and that design was reversed at M4 — in this same document, in full, and then never carried back up to here.** `Open`'s comment used to say it takes "the single ordered pass over staging that both seeds the ceiling counters and indexes which rows are pending for which table", and `OpenWriter`'s used to say it "claims that table's pending rows from the replay index built by `Open`". Neither has been true since M4. The code that ships does what the M4 decision says: `Open` scans once, reads the counters off the result and lets the index go — `Store` has no field to hold one — and `Store.pendingFor` makes its own fresh `staging.Scan` on every `OpenWriter`, keeping the index local to that call. The reasoning is all in "Decision (2026-07-31, M4)" under "Local write-ahead durability" below and is not repeated here, but the short form is that a snapshot taken at process start cannot contain rows staged during a writer's own life, so the natural response to a `Close` that returned with records undrained — reopen the table and try again — was handed nothing, and those records sat in staging, accepted and undelivered, with nothing anywhere saying so.

**The mechanism of this defect matters more than the defect, because it is the one a reader of this document is most likely to meet again.** Nothing was concealed and nothing was hurried: the reversal was recorded at the time, in the section that owns the staging design, at the length that decision deserved. What did not happen is the propagation back to the summary two hundred lines above it, and a summary near the top of a design document is exactly what a new reader reads and a hurried reader trusts. So the two statements sat in one file contradicting each other from M4 through M9, with the correct one buried and the stale one in the position of authority. The rule to take from it: when a decision reverses an earlier one, the reversal is not finished when it is written down where it was made — it is finished when every earlier statement of the thing it reversed has been found and changed, and in this document the earliest statement of almost anything is the API sketch here. The same superseded sentence had also been copied into `Open`'s and `OpenWriter`'s own Go doc comments, both corrected in this round.

**Amended at that round's repair pass (2026-08-01), because the deferral this paragraph closed with was wrong about its own reach and did not need to exist.** It said "the same wording still survives in `internal/staging`'s package and generated-query documentation, which this round did not own", and named that so a sixth round would meet it as a known item. Two things were wrong with it. It described the remainder by category — package documentation, generated-query documentation — where the remainder was eight sentences across five sources of which those two categories reach four, so a reader could not tell whether they were being handed two leftovers or ten, and following the categories literally would have found half of them. And it flattened a difference that mattered: seven of the eight were stale, describing a design that had been replaced, while one was flatly false about the code beside it. `internal/staging/index.go` told the reader "An `Index` is a snapshot taken at startup, before any writer exists", when one `Index` is built per `OpenWriter` by `Store.pendingFor` at whatever moment a caller opens a table — a sentence that, believed, says the M4 bug is still there. All eight were corrected in the repair pass rather than carried into a sixth round, and the enumeration and the correction live on `internal/staging`'s `Index` type, next to the sentence that was false. The general lesson is the one this document has been collecting all day, arriving this time in the shape of a deferral rather than a claim: a deferral is a survey too, and naming what is left over by category rather than by member conceals both how much of it there is and which member is the one that cannot wait.

**Why two steps rather than a single `Open[T](ctx, cfg)`.** Go does not allow a method to introduce its own type parameter, so the per-table constructor has to be a package-level generic function — `store.OpenWriter[T](...)` is not expressible. Given that, the real choice was between a single `Open[T](ctx, cfg Config)` that internally deduplicates process-wide resources (the staging file, the catalog file, the S3 client) behind a hidden registry keyed by file path, and an explicit two-step. The explicit version wins on the project's own stated terms: shared resources are shared *because the caller passed the same `*Store`*, not because a map somewhere matched two path strings. It also makes the per-table failure isolation decided in `SCHEMA.md`'s lifecycle section fall out for free rather than needing a rule — one table's `OpenWriter` returning an error is just an error from one call.

**Decision (2026-07-30): `Insert` is safe for concurrent goroutines on the same `Writer`.** A single mutex per writer guards the in-memory batch and the staging insert. This is the least surprising default — the alternative (documenting the writer as caller-synchronized) saves a mutex the workload will never notice and buys a data race for anyone who doesn't read the docs closely. The only thing *not* promised is ordering between concurrent callers: rows are ordered by arrival at the mutex, nothing more. A caller that needs a specific order per key must impose it itself, exactly as it would with any other concurrent sink.

**Decision (2026-07-30): a flush never blocks `Insert`.** When a threshold trips, the current batch is sealed (see "Batch identity" below), a fresh empty batch is swapped in immediately, and the sealed batch is encoded, uploaded and committed on a background goroutine. Callers never stall on R2 or network I/O. Flushes for one table are strictly serialized — one in flight at a time, in seal order — so snapshot order matches insert order and a stuck batch is visibly stuck rather than being quietly overtaken by later ones. Sealed-but-uncommitted batches are bounded by the staging ceiling below, not by a separate queue-depth knob, because their records are still staged (nothing is pruned until commit is confirmed — until the batch's spool file is on disk, in local-only mode) and therefore already counted.

**Decision (2026-07-30): `Close(ctx)` force-flushes everything regardless of thresholds; `Flush(ctx)` does the same without closing.** `Close` stops accepting new records (subsequent `Insert` returns `ErrClosed`), seals whatever is in memory even if it is one row, drains every pending batch through upload + commit, and returns the first error encountered. `Flush` is the same drain without the shutdown, and unlike a threshold-driven flush it is synchronous — it returns only once every batch sealed at the moment of the call has been committed, which is what makes it usable as a checkpoint in tests and in a caller's own shutdown sequence. Both are bounded by their `ctx`: if the context expires mid-drain, the call returns an error and the undrained records stay safe in staging for the next run. `Store.Close` closes every writer it opened (draining each), stops the retention sweeper if one is running, and then closes the SQLite handles it opened — two in bucket mode, one in local-only mode, which opens no catalog; it is the one call an embedding service needs in its shutdown path.

### Config

```go
type Config struct {
    // Local state (see "Local write-ahead durability" and "Catalog design")
    StagingPath string // path to staging.db — one file per process, all tables; required
    CatalogPath string // path to catalog.db — iceberg-go's SQL catalog; required in
                       // bucket mode, and must be empty in local-only mode

    // Object storage (required in bucket mode; every one of them must be empty
    // when LocalOnly is set — see the local-only decision below)
    Endpoint        string // e.g. https://<account>.r2.cloudflarestorage.com
    Bucket          string
    WarehousePrefix string // the <configured-prefix> of the key layout below
    Region          string // optional; defaults to "auto", which is what R2 wants
    AccessKeyID     string
    SecretAccessKey string
    Credentials     aws.CredentialsProvider // optional alternative to the two above

    // The local Parquet spool (see "The local Parquet spool" below)
    CacheDir      string        // enables the spool; empty disables it, except in
                                // local-only mode, where it is required
    CacheMaxBytes int64         // retention: total size bound over committed files
    CacheMaxAge   time.Duration // retention: age bound over committed files
    LocalOnly     bool          // no bucket, no catalog; explicit opt-in

    // The ClickHouse mirror (optional; nil means off — see "The ClickHouse
    // mirror" below). It works in both modes, because the seam it fires at is
    // one local-only runs too.
    ClickHouse *ClickHouseConfig

    // Batching (required, per table unless overridden in TableConfig)
    FlushMaxRecords int
    FlushMaxBytes   int64
    FlushInterval   time.Duration
    ZSTDLevel       int // 1..22

    // Resource bounds (required)
    StagingMaxRecords int64
    StagingMaxBytes   int64

    // Failure handling (optional; zero means the documented default)
    FlushMaxAttempts int           // default 5
    RetryBaseDelay   time.Duration // default 1s
    RetryMaxDelay    time.Duration // default 60s
    OnFlushError     func(FlushError)

    // The mirror's own notification channel, deliberately separate from
    // OnFlushError — see "The ClickHouse mirror" below for why the two cannot
    // be the same callback (optional)
    OnClickHouseError func(ClickHouseError)

    // Flush floor (optional; zero means the documented 1s default — see
    // "Mirroring and visibility" below)
    MinFlushInterval time.Duration

    // Time source (optional; nil means the real clock — see "Clock injection" below)
    Clock Clock
}

type TableConfig[T any] struct {
    Namespace string
    Table     string
    Flush     *FlushPolicy      // nil means inherit Config's four batching fields
    OnAccept  func(row T) error // optional; see "Mirroring and visibility" below
}
```

`FlushPolicy` is those four batching fields plus `MinFlushInterval` grouped so they can be overridden together. It exists because two tables in one process can have wildly different row sizes — a scalar fact table and a raw-payload archive table are the two examples in `TESTING.md` — and forcing both onto one byte threshold would mean picking a number that is wrong for one of them. A nil pointer meaning "inherit" is unambiguous in a way a zero-value field would not be, given zero is otherwise a rejected value.

**Decision (2026-07-30): R2 credentials are either two explicit strings or one `aws-sdk-go-v2` provider, never both, never implicit.** `AccessKeyID`/`SecretAccessKey` cover the common case (an R2 API token pasted into a config file or read from the environment by the *caller*, not by icelake). `Credentials` covers anyone with a real credential-sourcing story already — environment chains, an assumed-role provider, a secrets manager — by handing icelake a built provider directly. Supplying both, or neither, is a config error — **in bucket mode; the local-only decision below reverses the "neither" half of that rule for the one mode that reaches no bucket at all, where both forms must be empty and supplying either is the config error.** icelake never silently falls back to the ambient AWS default credential chain: an ingestion library quietly picking up whatever credentials happen to be lying around in the environment is exactly the kind of "works until it writes to the wrong bucket" behaviour this project is trying not to have. `Region` defaults to `"auto"` because that is what R2 requires; it stays overridable only so the MinIO-based test substrate can pass its own value.

**Decision (2026-07-30): config is validated at construction and fails loudly with every problem at once.** `Open` rejects, before any file is touched or any network call is made: an empty `StagingPath`; an empty `CatalogPath`, `Endpoint`, `Bucket` or `WarehousePrefix` in bucket mode, and a *non-empty* one of those four when `LocalOnly` is set (the local-only decision below owns the whole matrix and is where each of those violations is spelled out); a zero or negative `FlushMaxRecords`, `FlushMaxBytes`, `FlushInterval`, `StagingMaxRecords` or `StagingMaxBytes`; a `ZSTDLevel` outside 1..22; both or neither of the two credential forms in bucket mode, and either of them in local-only mode; a negative `FlushMaxAttempts`/`RetryBaseDelay`/`RetryMaxDelay`/`MinFlushInterval`/`CacheMaxBytes`/`CacheMaxAge`; a retry schedule whose base delay exceeds its cap once the documented defaults have been filled in; a retention bound set with no `CacheDir` to bound, a `CacheDir` in bucket mode with neither retention bound set, a `LocalOnly` store with no `CacheDir`, and a `LocalOnly` store carrying either retention bound; and a `StagingMaxRecords` below `FlushMaxRecords` or a `StagingMaxBytes` below `FlushMaxBytes`, which is nonsensical rather than merely small — a batch could never fill before the ceiling refused it, so the writer would be dead on arrival. All violations are collected and returned as one joined error (`errors.Join`), not just the first one found: a caller fixing a config file should learn everything wrong with it in one run. There are no "sensible" fallbacks for the required fields — a zero threshold is a bug in the caller's config, and silently substituting a default would hide it.

**Corrected at the post-M9 completeness audit (2026-08-01): the retry-schedule rule in that list used to read "a `RetryBaseDelay` greater than `RetryMaxDelay`", stated against the literal fields a caller types, and read literally it gets a real case backwards.** `Config{RetryBaseDelay: 0, RetryMaxDelay: 500 * time.Millisecond}` is rejected, and zero is not greater than five hundred milliseconds, so a caller checking this document against what `Open` actually did would conclude icelake had a bug. What the code compares is the *resolved* schedule — the two zero-means-default fields are filled in first, a zero base becoming the documented one-second `DefaultRetryBaseDelay` and a zero cap the one-minute `DefaultRetryMaxDelay`, and only then are the two put side by side. The code is the correct side of this disagreement and the document has been changed to match it, because the property worth enforcing is about the schedule the store will really run on rather than about the shape of the caller's literal struct: a schedule whose first sleep is already longer than its own ceiling cannot make progress in the way the backoff design describes, and it is exactly as broken whether the caller wrote the one-second base or merely left it blank and got it. Validating the literal fields instead would let a cap below one second through with no base set, and the store would then run a schedule quietly flattened to the cap — a silent substitution, which is the one thing the rest of this decision refuses to do.

The surprising part is worth stating plainly rather than leaving for a caller to hit, because it is the part that costs someone an afternoon: the `ConfigFieldError` this raises names `RetryBaseDelay`, which in the case above is a field the caller never set. That is deliberate and it stays. The base is the value that is too large, so naming it points at the number the resolved schedule is actually complaining about; naming `RetryMaxDelay` instead would report a field the caller *did* set as the offender when the fault is the relationship between the two, and the fix is genuinely either one — raise the cap above the resolved base, or set a base below the cap. The rule text the error carries ("must not exceed `RetryMaxDelay`") is what makes the pair legible from the field alone. One further detail of the check exists for the same reason the whole section does: it is skipped entirely when either field is already negative, so a single mistake produces one violation rather than two, and the joined error a caller prints stays a list of distinct problems.

**Decision (2026-08-01, M10): a store can be opened in local-only mode, where there is no bucket, no catalog and no upload — and that reverses two stances stated above, "Object storage (required)" and the credential rule that a store must always carry exactly one of the two forms.** Until now `Endpoint`, `Bucket` and `WarehousePrefix` were required fields rejected at empty like any other, and a store supplying neither credential form was refused before it touched a file. Both were right while the only reason to open a store was to fill a bucket. What changed is that the first five minutes of using this library now involve no bucket at all: with a schema and a stream of records, a person wants to watch rows land in files they can query before they go and create an object-storage token, and the spool decided below already writes the exact Parquet bytes to local disk on the way to the upload. Local-only mode is that path with the upload removed, so it costs a branch rather than a second write path. `LocalOnly` is an explicit boolean and is deliberately not inferred from an empty `Endpoint`: a config file that lost its endpoint would otherwise become a local-only store that looks like it is working, which is the silent-substitution failure the validation decision above refuses everywhere else.

**The matrix, stated as rules because each one is its own `ConfigFieldError` inside the single joined `ConfigError`.** `LocalOnly` requires `CacheDir` — there is nowhere else for the data to go. It requires `CatalogPath`, `Endpoint`, `Bucket`, `WarehousePrefix`, `AccessKeyID`, `SecretAccessKey` and `Credentials` to be empty, each named separately, because a store told to reach no bucket while holding a bucket's credentials is a caller who thinks they configured something they did not. And it requires `CacheMaxBytes` and `CacheMaxAge` to be zero, which follows from the retention rule below rather than being a second policy: retention only ever evicts a file that has been uploaded *and* committed, nothing is uploaded in this mode, so a retention bound here is a knob that cannot turn. Independently of the mode, a retention bound set with no `CacheDir` is rejected, and a `CacheDir` in *bucket* mode with neither bound set is rejected too — an unbounded local cache has to be asked for by name, through `LocalOnly`, rather than fallen into by leaving two fields blank.

**What local-only actually skips is everything that touches a network, and nothing else.** `Open` builds no S3 client and opens no `catalog.db`; `OpenWriter` and `OpenDynamicWriter` skip the table load, the creation and the whole reconciliation loop, because there is no live schema to reconcile against; no retention sweeper runs. Everything else is the same code: name validation, the two-derivation cross-check, the declared descriptor, staging, the ceiling, the seal, the batch hash, the crash points, replay, quarantine, `Flush`, `Close`. A flush ends one step earlier than it does in bucket mode — the spool write is the last durable act, and the batch's rows are pruned from staging against the spool file rather than against a commit. That is the one place the durability story changes shape and it is worth saying plainly rather than leaving in the exchange rate: in bucket mode a pruned record exists in an Iceberg snapshot, and in local-only mode it exists in a Parquet file on one local disk. The record is still durable; it is no longer redundant. Every `Store` method that genuinely needs a bucket returns the sentinel `ErrLocalOnly` rather than a confusing failure from a client that was never built, and `Store.DrainSpool` is the only such method. Catalog rebuild is deliberately *not* on that list and never produces this sentinel: `rebuild.Rebuild` takes its own options, opens its own client and has never heard of a `Store`, so there is no local-only store for it to be refused by. "You cannot rebuild a catalog this configuration never had" is a refusal the `icelake` command makes against its own environment, and it is described where that command is (`PLAN.md`'s app bullet, `AGENTS.md`, and `TESTING.md`'s scenario 13) rather than here.

**Decision (2026-08-01, M10): a local-only store's backlog is drained by reopening it in bucket mode, per table, at `OpenWriter` time, and the drain is idempotent for the same reason a crash-recovered upload is.** This is the half of the feature that makes it more than a demo: a person tries icelake locally for a week, then puts an endpoint, a bucket, a prefix and credentials into the same configuration and restarts against the same `StagingPath` and the same `CacheDir`. Every spool file whose `committed_at` is null is a batch that exists on disk and in no table. **The order inside `OpenWriter` is the load-bearing part, and it is not the obvious one.** A table with a backlog is drained *before* the table is loaded, created or reconciled against the current declaration — not after it. The reason is the risk the whole drain turns on: `AddFiles` re-reads the file it is handed and checks it against the live table, so committing a file written under an old shape to a table that has already been moved forward to today's declaration is the one step in this design that might simply be refused. Reversing the order removes the question. So a writer whose table has uncommitted spool files walks them in creation order first and, for each: skips it if the batch's rows are still staged, since replay owns those and would otherwise upload the same batch from both ends; brings the table to *that file's own* recorded shape, from the descriptor the spool stored beside it and through `DeclareFromDescriptor` rather than through any struct or document the current process happens to hold — creating the table from that descriptor if it does not exist yet, which is the ordinary case, since local-only mode never created one; uploads it; asks the live snapshot whether that data file path is already referenced, which is the same `alreadyCommitted` check the crash path already makes; commits it with `AddFiles`; and marks it committed. Only then does the ordinary lifecycle run: `OpenWriter` loads the table it has just brought up to the newest file's shape and reconciles it to the current declaration, which is one more forward step of the same loop the reconciliation design already describes, followed by replay as usual. A table the current process never opens is covered by `Store.DrainSpool`, which does the same walk for every table with a backlog and stops there, since there is no declaration to reconcile to.

The idempotency argument is not new machinery, which is the point of drawing it out. A spool file's name is its batch key, the batch key is the content hash decided under "Batch identity" below, and the object key it uploads to is the same key that batch would have had if the bucket had been configured from the first day. So a drain interrupted anywhere re-uploads byte-identical bytes over the same key on the next run, exactly as a crashed flush does, and the two orderings that could double-count are both closed the same way they already are: the snapshot check before the commit, and marking the file committed *after* the commit lands. A crash in that last window leaves a committed file the sweeper will never evict, which is the harmless direction — a file kept too long costs disk, and a file evicted too early costs the drain a batch it would then re-upload from nothing. The rejected alternative here was a local Iceberg warehouse — writing a real `file://` table locally and migrating it to the bucket at transition. Beyond being unavailable in the pinned library (see "Catalog design" below), it would produce a table whose every manifest records a local path, and rewriting those paths on transition is a metadata surgery Iceberg does not offer and icelake would have to own. The cost of the design that was taken is stated rather than buried: there are now two modes to reason about and to test, a first-run-after-transition code path that runs once per file and is exactly the sort of path that rots unwatched (`TESTING.md` gives it a numbered scenario for that reason), and a local-only store whose data lives on one disk with no second copy anywhere.

**Decision (2026-07-30): the staging store has a hard, configurable ceiling, and `Insert` refuses records once it is hit.** `StagingMaxRecords` and `StagingMaxBytes` bound the total staged-but-not-yet-committed volume across all tables in the process. Once either is reached, `Insert` returns `ErrStagingFull` immediately and the record is *not* accepted — it never enters staging, so the caller knows precisely which records it still owns. This is the direct answer to the failure mode that motivated the whole project: the archival case did not fail loudly when its file was already unmanageably large, it just kept growing until an unrelated operation (a startup integrity check) hit a timeout months later. Refusing is deliberately chosen over blocking: a blocking `Insert` turns a storage problem into an invisible latency problem in the caller's own hot path, and can deadlock a caller that inserts from the same goroutine that would otherwise drain something. `Pending()` exists so a caller can throttle itself *before* it gets refused; the ceiling is the backstop, not the intended flow-control mechanism. The counters backing the check are held in memory and seeded once at startup off the totals the single ordered pass `Open` already makes over `staging` accumulates as it goes — cheap precisely because the table that pass reads is itself bounded by this ceiling.

**Corrected at the completeness audit's fifth round (2026-08-01): the seeding clause above said "seeded once at startup by a single aggregate query over `staging`", and there is no such query on that path.** What `Open` does is one ordered pass over the staging table — the replay scan it has to make anyway, to group staged rows by table and to refuse a database this build will not replay — and that pass accumulates the record count and the payload-byte total as it walks, so the two numbers the ceiling needs are already in hand when it finishes and nothing else is asked of the database. The mistake is small in its consequences and specific in its cause, which is why it is worth a dated entry rather than a quiet edit: it describes a second query that a reader looking for the cost of startup would go looking for and not find, and it invites the opposite change to the one that is right, because the obvious way to "restore" the described behaviour is to add the aggregate call to the write path. There *is* an aggregate query with exactly that shape — `Counters` on the staging store, a direct `SELECT` over the same table — and it exists for a different purpose: it is the second, independent way of obtaining the numbers the in-memory counters carry, which is what makes it useful for checking them against the database. Nothing in the write path calls it and nothing should; its only caller anywhere in the tree is `TestCountersAgreeWithTheReplayScan` in `internal/staging/store_test.go`, which is the test that puts the two paths side by side. Two code comments carried the same wrong clause and were corrected the same day, in the same round: the `accept` comment in `store.go`, which is where the ceiling is charged, and `internal/staging/store.go`'s doc comment on `Counters` itself, which had gone further and called that function "the aggregate that seeds the in-memory ceiling counters" while its own next sentence explained that startup never calls it. This document was not looked at by either of those corrections, and neither claimed to have surveyed the documents, so nothing false was written when they landed — but the design document is the copy a reader consults first, and it was left saying what the code comments had just stopped saying.

**Decision (2026-08-04, M15): a batch is charged against the ceiling atomically and all-or-nothing — if the whole batch does not fit, `InsertBatch` returns `ErrStagingFull` and not one of its records enters staging.** The counters are checked once, for *n* records and the batch's total payload bytes together, under the same hold of the lock that then charges them, so there is no window in which half a batch is charged and the rest is being decided about. The property this preserves is the one the paragraph above puts the whole ceiling there to deliver — "the caller knows precisely which records it still owns" — read at the granularity the caller actually used: a refused batch is a refused slice, entire, and the caller re-sends exactly what it handed over. The rejected alternative was to fill the remaining headroom and refuse the tail, which is the more accommodating behaviour and the worse one to reason about: it turns one refusal into a number the caller has to be told and then trusted to act on, it makes `ErrStagingFull` mean "some unspecified prefix of your slice was accepted", and it re-introduces at batch granularity exactly the partial-acceptance state the atomic transaction below it was built to remove. The cost accepted is a small quantity of wasted headroom — a batch that would have fitted all but its last few records is refused whole, and those bytes sit unused until a flush commits — which is a bounded, self-correcting inefficiency, where an unclear ownership boundary is neither.

Because sealed-but-uncommitted batches remain in staging, the ceiling also bounds icelake's in-memory footprint: a table that cannot reach R2 accumulates at most the ceiling's worth of records in RAM and staging together before it starts refusing. Pick the ceiling with that in mind — it is a memory bound as much as a disk bound.

### Clock injection

**Decision (2026-07-30): every read of time inside icelake goes through one small injected clock, supplied in `Config`, nil meaning the real clock.** That covers all of it: the flush-interval timer, the flush floor, retry backoff sleeps, `staging.created_at`, `LastCommitAt`, and `RecentFlushTimes`. Illustrative shape:

```go
type Clock interface {
    Now() time.Time
    NewTimer(d time.Duration) Timer            // resettable, like time.Timer
    Sleep(ctx context.Context, d time.Duration) error // returns early on ctx cancel
}
```

This exists for exactly one consumer — the test suite — and is not a general extension point. Timer-driven behaviour (the interval trigger, the floor coalescing a burst, the backoff schedule) cannot be exercised deterministically against a real clock; without this seam the tests either sleep for real (slow) or assert loose bounds (flaky under CI load), and the flush-floor scenario is close to unwritable. A fake clock is deliberately *not* considered a violation of `TESTING.md`'s no-mocks rule: it controls an input, it does not fake the storage substrate — see the philosophy section there, which states the same exception from the other side. Production callers leave the field nil and never think about it again.

### Mirroring and visibility: small additions, not a second storage system

This section exists because of a real, separate question: should icelake help with a common pattern that otherwise lives entirely outside it — an app keeping its own local "hot" copy of recent data, indexed for its own fast queries, alongside the permanent archive? The answer to *that* question is unchanged and firm — a hot-data cache is exactly the query-serving, operational-state shape this document already rules out by name, twice over ("What icelake is," "Data classification"), and building one here would be real scope creep. But two narrower, real problems came out of that question, and both are small enough, and specific enough to what only icelake itself can see, to be worth a few lines of API rather than being waved off with the rest. A third, larger one arrived later and is the one this section's own refusal has to be read against: the local Parquet spool, decided in the section immediately after this one, keeps the bytes icelake uploads on local disk as well, and although a reader could reasonably call the result a cache, it is a write-side artifact rather than a query-serving system. The decision there says exactly which half of the refusal above it reverses and which half it does not.

**Decision (2026-07-30): `TableConfig[T]` takes an optional `OnAccept func(row T) error`, called synchronously inside `Insert`, immediately after the staging write commits and before `Insert` returns.** This exists to answer the "dual-write problem" directly, not to soften it: if an app also keeps its own local mirror of recent data, the standard failure mode (well known enough to have a name) is two independent write decisions in the app's own code slowly disagreeing with each other — a field added to one path and not the other, a row written to one and not the other after a partial failure, an agent quietly deciding to batch locally for a few days "for convenience" before archiving. `OnAccept` removes the second decision point rather than trying to keep two of them in sync: the app's mirror write happens inside the same call that already durably accepted the record for icelake's own purposes, so there is exactly one place in the caller's code where "this record now exists" gets decided, even though it lands in two physical stores. If `OnAccept` returns an error, `Insert` returns it too — visibly, on the caller's own hot path, exactly like any other error in code the caller wrote — but the record's durability inside icelake is not conditioned on it: staging already committed before `OnAccept` ran, so a failing mirror callback never costs icelake's own guarantee, only tells the caller their mirror fell behind. icelake does not retry it, does not store what it returned, and has no idea what the app did inside it — indexing, retention, and querying that mirror stay entirely the app's problem, per the original scope boundary.

**Decision (2026-07-30): `Writer[T].Status()` returns a small, read-only snapshot of what a table is actually doing, so a person or a separate process can check it without trusting the writer's own caller.** The concrete motivation is not general observability — that stays out of scope, see below — it's the specific, real cost shape of this project: Cloudflare R2 bills every write operation, and the entire premise of batching is keeping that operation count low. A bug that silently causes far more, or far smaller, flushes than a table's configuration intends is a direct cost problem this design otherwise has no way to catch.

```go
// Illustrative shape. Corrected at M9: the type is generic, WriterStatus[T],
// because RecentRecords below is a slice of the caller's own declaration type
// and a non-generic struct cannot hold one. The line in the API surface above
// says so too.
type WriterStatus[T any] struct {
    PendingRecords    int           // already backs Pending()
    PendingBytes      int64
    RecordsAccepted   uint64        // cumulative since this Writer was opened
    FlushesCommitted  uint64        // cumulative since this Writer was opened
    LastCommitAt      time.Time
    LastFlushErr      error
    RecentFlushTimes  []time.Time   // fixed-size ring buffer, last 20 commits
    RecentRecords     []T           // fixed-size ring buffer, last 5 accepted rows
    FlushFloorEngaged uint64        // see the flush-floor decision below
}
```

`RecordsAccepted` and `FlushesCommitted` are cumulative counts whose ratio approximates a table's average batch size — the number worth watching against its configured threshold, since a table whose average is far below its threshold is either misconfigured or hitting the flush floor constantly. **Corrected at M9, when the counters were built: "approximates" rather than "is".** The two are not counted over the same set of batches. A batch replayed from a previous run is committed by this writer without ever having been accepted by it, and an explicit `Flush` or `Close` commits a batch no threshold asked for, so the ratio is a signal to watch and not an identity to compute with. It is stated that way here rather than being fixed by making the counters agree, because both counts are individually the honest answer to their own question. `RecentFlushTimes` is a small fixed-size ring buffer a caller can use to compute a real recent flush rate without icelake building any time-series machinery of its own. `RecentRecords` is a small fixed-size ring buffer of the last few accepted records, by value — a deliberately tiny, in-memory-only window that answers "what is this table actually storing right now" by direct inspection, not by trusting a claim about it. **The copy it hands back is shallow, stated here at M9 rather than left to be discovered:** the slice belongs to the caller, but a declaration type with a reference field (a `[]byte` payload column is the obvious one) shares that memory with the value the caller inserted, in both directions, and the window keeps up to five records' worth of it alive until five more displace them. Copying an arbitrary `T` deeply is not something a library can do, so the promise is worded to what is actually true rather than to what would be nicer. Nothing about this can reach what was *staged* — the record is encoded to canonical bytes before this window ever sees it — so the exposure is confined to what a later `Status` displays. It is not a query surface: it is bounded, it is not indexed, it is not persisted, and it does not survive a restart — it exists purely so a person debugging a table can see real, current records without standing up DuckDB or an R2 client, the same way a developer might `tail -f` a log. Scoped honestly: everything `Status` reports is about operations icelake itself issues — flush uploads and catalog commits, plus the infrequent metadata reads `OpenWriter` performs. It has, and can have, no visibility into read costs from DuckDB, PyIceberg, or anything else querying the same bucket directly, since none of those go through icelake at all.

**Decision (2026-07-31, M9): an `OnAccept` error crosses the boundary as its own typed error, `MirrorError{Namespace, Table, Err}`, and the callback runs outside every lock the writer holds.** Two things were left to the implementation by the decision above and neither should stay implicit. First, the error: `Insert` already answers three refusals — `PoisonError`, `ErrStagingFull`, `ErrClosed` — and every one of them means *the record is still yours*. A mirror failure means the exact opposite, that the record is icelake's now and only the caller's own copy fell behind, so a caller treating the two alike and re-inserting would write the record twice. Passing the callback's own error straight back would have made those two answers indistinguishable without knowing which errors the callback can produce, which is precisely the kind of thing the error taxonomy exists to stop; `MirrorError` wraps it with `%w`, so the caller's own sentinels stay reachable through `errors.Is`. Second, the containment, which is deliberately *not* `OnFlushError`'s. That callback runs on a background goroutine the caller cannot see, so a panic in it is recovered and a callback that never returns is abandoned at shutdown. `OnAccept` runs on the caller's own goroutine, inside the caller's own call, so a panic there travels up the caller's own stack where the caller's own `defer` can catch it, and recovering it here would swallow a bug in code icelake did not write. What *is* contained is the lock: the callback fires after the writer's mutex is released, so a slow callback delays only the goroutine that called `Insert`, and a callback that calls back into the writer — `Pending` and `Status` being the useful ones — cannot deadlock against it. `Insert` from inside it is the one re-entry that is forbidden rather than merely useless, since it is unbounded recursion; it is documented and deliberately not detected, because a check on the caller's own hot path would cost every insert something to catch a mistake whose first run is an immediate stack overflow.

**Consequence, recorded at M9 because the decision above argues only one direction of it: there is a window in which a record is archived and the mirror was never told.** The ordering is staging first, callback second, and the decision above justifies that from one side — a mirror write that happens before the record is durable would tell the mirror about records that were never archived, which is the worse failure. The other side follows and should be stated plainly: a process that dies between the staging commit and the callback leaves a record that replay will flush and commit, with no callback ever having fired for it, because replay deliberately does not fire the hook (the records were accepted by a previous run, and firing again would double-tell a mirror that may not be idempotent). So `OnAccept` removes the *decision* point, not every failure mode: it guarantees that a record the callback was told about is archived, and not that every archived record was one the callback was told about. A mirror that cannot tolerate a missing record needs its own reconciliation against the table — which is a query, and querying is the caller's side of the boundary this whole section is drawn around.

**Decision (2026-07-30): a minimum flush interval is enforced internally, as a hard floor beneath whatever `FlushInterval`/`FlushMaxRecords` a caller configures.** This is the one place this design actively guards against, rather than only reports on, a runaway operation-count/cost scenario: if a bug or a misconfiguration ever caused a table to trip its flush trigger far more often than intended, the natural failure mode is exactly the anti-pattern this whole project exists to end — a flood of tiny, expensive write operations against R2 (see "Reference cost model" below for what that actually costs). The floor is `MinFlushInterval` in `Config`, overridable per table through `FlushPolicy` (zero means the 1-second default, deliberately far below any sane production `FlushInterval`); validation rejects a negative value but deliberately does *not* require the floor to sit below `FlushInterval`, since `TESTING.md` scenario 9 inverts the two on purpose to make the floor the binding constraint. The floor does not drop or delay-forever anything: if a flush trigger fires before the floor has elapsed since the table's last flush, the current batch simply keeps accumulating until the floor passes, producing one larger batch instead of several tiny ones back-to-back — the exact correction this project was built around applying in the first place. Each time the floor actually engages is counted in `WriterStatus.FlushFloorEngaged`, so a table that is hitting it constantly — a real signal that its configured thresholds don't match its actual traffic — is discoverable rather than silently invisible.

**Decision (2026-07-31, M9): "engages" means a trigger the floor held records back from, and nothing else.** The counter was built here and the definition had to be pinned, because the obvious implementation counts something useless. The timer loop fires on every interval whether or not there is anything to seal — that is deliberate, and is what lets a stuck table heal — so a counter incremented whenever a trigger arrives before the floor has elapsed would climb steadily on an *idle* table, where the floor is holding back nothing at all, and the number an operator is supposed to read as "your thresholds no longer match your traffic" would instead mean "this table has been running a while." So a trigger that finds an empty batch is not counted, and the count is exactly the number of times a batch that could have been sealed was left to keep accumulating. Two things follow that are worth stating. An explicit `Flush` or `Close` never touches the counter, because the floor never applies to a caller who asked. And the counter is what makes "fewer flushes than trigger events" checkable at all, since a trigger event is otherwise invisible from outside the writer — but only alongside knowing what else committed: `FlushesCommitted` also counts batches an explicit `Flush` or `Close` sealed and batches replayed from a previous run, so `FlushesCommitted + FlushFloorEngaged` is the count of threshold-driven triggers that had something to do *only* for a table where nothing else committed anything. That is a condition a test can arrange and an operator generally cannot, which is why the operator-facing signal is the counter's own trend rather than any arithmetic between the two.

### The local Parquet spool

**Decision (2026-08-01, M10): when `CacheDir` is set, a flushed batch's Parquet bytes are written to a local file *before* they are uploaded and kept there until retention evicts them — which reverses this section's own refusal, quoted above, that "a hot-data cache is exactly the query-serving, operational-state shape this document already rules out by name."** The refusal is reversed on one clause and left standing on the rest, and the distinction has to be held precisely or the sentence above stops meaning anything. What is no longer true is the blanket part: icelake does now keep a local copy of recent data. What is still true, and is the whole of the original objection, is that icelake serves no query, builds no index, keeps no operational state, and never reads this data back to answer anything. The spool is a **write-side artifact**: the same bytes, on their way somewhere, written down twice.

Three properties make that framing a fact rather than a manner of speaking. **The bytes are the uploaded bytes** — the identical buffer, not a re-encoding, not a projection, not a second compression pass — so the local file and the bucket object are byte-for-byte equal and a difference between them is a bug rather than a version skew. **The name is the batch key**, so the layout mirrors the warehouse layout exactly: `<CacheDir>/<namespace>/<table>/data/<batch-key>.parquet` against `<warehouse-prefix>/<namespace>/<table>/data/<batch-key>.parquet`. An operator comparing the two needs no lookup table, and a retried batch overwrites the same local file for the same reason it overwrites the same object — the key is a content hash, decided under "Batch identity" below and reused here rather than invented. **And DuckDB can `read_parquet()` the directory**, which is a property of having written Parquet files into a directory tree and is deliberately not a service icelake offers. There is no manifest, no snapshot, no schema resolution across files, no deletes; two files written under two shapes are two Parquet files with two schemas, and reconciling them is the reader's problem (`union_by_name` is the usual answer). The Iceberg table remains the queryable artifact. The spool is bytes on a disk that happen to be readable, and if a future reader wants more than that, the answer is to query the table.

**Why it earns its place, given the refusal it partly reverses.** Three uses, all real and none of them a query engine. The local-only mode decided above has nowhere else to put data at all, and it is the reason this landed now. A person spending a day on analysis can read the recent window off local disk without issuing a single request against the bucket — which is the same pattern the query-side section below already recommends `cache_httpfs` and a bulk `rclone` sync for, arrived at from the write side, for free, and without a second copy having to be fetched back down. And during the window between "the batch was encoded" and "the catalog confirmed it," the spool file is a second durable copy of exactly the bytes at risk.

**Decision (2026-08-01, M10): retention evicts a file only after it has been uploaded *and* committed, and the protection for everything else is the shape of the query rather than a rule in the sweeper.** `spool_files.committed_at` is null until both of those have happened; the eviction statement carries `WHERE committed_at IS NOT NULL`. So a never-uploaded file is not defended by policy code that could be edited wrong — it is not visible to the statement that does the deleting. That distinction is the entire reason to record the decision: a size cap enforced by a loop that skips uncommitted files is one refactor away from being a size cap that deletes the only copy of a day's records, and this design has spent enough words on silent data loss to prefer the version where the mistake is unrepresentable. It follows, and is stated so nobody reports it as a bug, that **a cache can sit far over its configured bound**: a bucket that has been unreachable for a day leaves a day of uncommitted files that no sweep will touch, and the cache shrinks by itself once the backlog commits. Within the committed set, eviction is by age first and then by size, oldest first. Two smaller rules travel with it: a file already gone from disk is not an error (`ENOENT` is tolerated — a committed spool file is disposable and an operator who deleted one by hand has done nothing wrong), and a file in `CacheDir` that icelake did not write is never touched, because eviction deletes exactly the paths its own table names and never lists the directory to decide.

**The write is file-first, database-second, and both halves are idempotent.** The bytes go to a temporary file, are fsynced, renamed into place, and the directory is fsynced; then one transaction records the batch's schema descriptor and its file row. A crash between the two leaves a file no row names, which is precisely what a retry of the same batch overwrites and re-records, since the key is a content hash over rows that are still staged. The crash point `PointAfterSpoolBeforeUpload` exists at that seam (`TESTING.md`, "Crash injection"). The two alternatives were both considered and are worse for the same underlying reason. **Uploading first and downloading the object back into the cache** would make this a read-through cache of the bucket — the actual hot-data cache the refusal above rejects — at the cost of a full download per flush, and would leave local-only mode with nothing at all. **Keeping the Parquet in a second SQLite table** would put gigabytes into the one local file whose whole virtue is being small enough to back up, and would take away the property that makes the spool useful, which is that a reader can point at a directory. The costs of what was chosen are three and are all stated in the caller's own terms: disk, bounded by the caller's caps in bucket mode and by nothing at all in local-only mode; a second durable artifact per batch that has to stay consistent with the staging database, which is why the two spool tables are in the same file as staging rather than beside it; and one background goroutine per store, which the next decision owns.

### The ClickHouse mirror

**Decision (2026-08-04, M17): when `Config.ClickHouse` is set, every batch icelake encodes is also inserted into a ClickHouse table, and this lands as a capability of the one existing module rather than as a separate or nested one.** The owner's call, and it is the expensive half of the decision, so it is stated with numbers rather than waved at. `github.com/ClickHouse/clickhouse-go/v2` enters the root module's `require` set and therefore every consumer's dependency graph, whether or not that consumer ever sets the field. Measured the way the `io/gocloud` entry below was measured, on the same minimal-consumer program that imports `github.com/gvkhna/icelake` and calls `Open`: the module graph goes from 144 modules to 151, `go.mod` from 188 requirements to 195, `go.sum` from 708 lines to 721, and a `CGO_ENABLED=0 -trimpath -ldflags=-s -w` binary from 85,311,650 bytes to 90,534,050 — **seven modules and 4.98 MiB, a 6.1% increase**. The seven are the driver, `ClickHouse/ch-go` (its low-level protocol half), `go-faster/city` and `go-faster/errors` (that half's hashing and error wrapping), `segmentio/asm` (its base64), `shopspring/decimal` (the only honest Go type for a `Decimal(P,S)` column), and `paulmach/orb`, which arrives because the driver supports geospatial column types this library will never declare. None of them registers anything in an `init` that dead-code elimination cannot see past, which is the specific property that made the `io/gocloud` cost 37MB rather than five.

**The rejected alternative is a second module — `github.com/gvkhna/icelake/clickhouse`, or a nested `mirror/` module — and it was rejected by the owner on what it would cost the feature rather than on what it would save the graph.** A separate module makes the mirror a plugin: it would have to reach the flush path through an exported seam, which means the seam becomes public API, which means the record's lifetime, the `FileSchema`'s widening and the batch key all become promises to strangers rather than internal arrangements this repository can change in one commit. The whole argument of the next decision is that the mirror gets *the same Arrow record the Parquet file is written from*; a module boundary between those two facts is a boundary the identity property has to be re-proven across every time either side moves. The accepted cost is the 4.98 MiB above, carried by consumers who will never set the field. It is accepted because the alternative trades a real correctness property for a size number, and because a consumer who cares about five megabytes has the `io/gocloud` stopgap to remove first, which is worth seven times as much.

**What the mirror is, and the sentence everything else here follows from: ClickHouse is a disposable local index, the lake is the truth, and nothing about ClickHouse may ever block, slow or lose lake data.** The Parquet collection in the bucket is the record; the ClickHouse table is a reproduction of it that exists to be queried quickly and to be thrown away. That is not a disclaimer, it is the design constraint that decides every question below — what happens when ClickHouse is down (nothing, to the lake), what happens when its schema disagrees (the operator rebuilds it), and what icelake will never do (retry, queue, buffer, or reconcile on the mirror's behalf). It also reverses nothing in "Mirroring and visibility" above: that section refuses to build a hot-data cache *of icelake's own design*, and this is icelake filling somebody else's, on their explicit opt-in, with no query surface, no index decision and no retention policy of its own.

**Decision (2026-08-04, M17): the tap fires at the encode seam — in the flush worker's `process`, beside the spool write, after the Parquet bytes exist and before they are uploaded — and not after the catalog commit.** This is the design's spine and the reason it is worth building at all. At that instant the Arrow record the data file was just written from is still alive, and it is the record built at `FileSchema`, so the millisecond-to-microsecond widening Iceberg's `timestamptz` requires has already happened *to the values the mirror is about to insert*. The rows ClickHouse gets are therefore not a re-derivation of the rows Parquet gets; they are the same in-memory columns, adapted once, consumed twice. Nothing between the two can drift, because there is no "between".

The two rejected alternatives both break that. **Tapping after the catalog commit** would put the mirror insert where the record no longer exists — it is released the moment the Parquet buffer is built — so the mirror would either hold the record alive across an upload and a commit, adding a batch's worth of Arrow memory to the window `FlushMaxBytes` is planned against, or re-read the rows from staging and rebuild them, which is a second derivation and exactly the drift this design is buying its way out of. **Tapping at `Insert`, beside `OnAccept`,** would put a network write on the caller's own hot path, which every other decision in this document exists to avoid, and would lose the batch key, which is what makes the insert idempotent. The accepted cost of the encode seam is that the mirror can be told about a batch the lake never commits: a crash after the ClickHouse insert and before the catalog commit leaves rows in the mirror for a batch that is still staged. That is not a leak, because of the next decision, and it is the direction that is safe — the mirror's contents are reproducible from the lake, and the lake's are not reproducible from the mirror.

**Why that crash window closes by itself, which is the argument the batch key is carrying.** A batch's rows stay in staging until the lake commit is confirmed, so a process that dies in that window replays exactly those rows, under exactly the stored batch key, and re-encodes them onto the same shape — the identical batch, by construction, because the key *is* the content hash over it. The re-fired tap inserts the same rows again with the same `insert_deduplication_token`, and ClickHouse collapses the second insert to nothing. So the crash window is not repaired, it is made unobservable: the mirror ends up with each batch exactly once whether the process survived or not, and the same mechanism covers an ordinary retry of a failed upload, a failed commit, and a flush cycle that spent its whole attempt budget.

**Decision (2026-08-04, M17): the mirror is a doorbell, not a queue. A ClickHouse failure never fails a flush and never keeps anything for later — it is reported through `Config.OnClickHouseError` and the flush proceeds.** What a failure *can* cost a flush is time, and the amount is stated rather than rounded to zero: the mirror insert is synchronous on the flush worker and bounded at thirty seconds per batch, so a server that accepts the connection and then stops answering delays each flush — and each batch of a closing writer's drain — by up to that bound until the outage is noticed by the operator or the connection starts refusing outright, at which point the cost drops to nothing. The bound is the design's price for having no queue; an async hand-off would hide the same thirty seconds inside an unbounded buffer instead, which is worse in every way that matters here. This is `OnFlushError`'s containment applied to a callback that means the opposite thing, which is precisely why it is a second callback rather than a widening of the first. `FlushError` says *the batch is still in staging and will be tried again*; a mirror failure says *the batch is on its way into the lake exactly as it should be, and only the disposable index fell behind*. The two travel different routes as well: `Flush` and `Close` return `FlushError` synchronously to the caller who asked, and a mirror failure must not reach either of them, because a `Close` that returned an error because ClickHouse was down would be ClickHouse blocking the lake — the one thing this design forbids. Reusing `FlushError` would also have made `Attempts` and `Records` lie, and would have put a second meaning inside the callback whose documentation enumerates its three events. The rejected alternative is a bounded in-process retry queue for failed mirror inserts; it is rejected because a queue is state, state has a size, a size has a bound, and a bound has a policy for what happens when it is reached — all of which is the beginning of icelake owning the mirror's contents, which it does not. What replaces the queue is the flush path's own self-healing: the next flush trigger re-fires the tap for the next batch, and a batch the mirror missed is recovered by rebuilding the mirror from the lake, which is what a disposable index is for.

**Decision (2026-08-04, M17): two-door identity is a named property of this design and is proven by test, not asserted by argument.** The property: for any batch, inserting it through the live mirror and loading the *same Parquet file* into a table with the same DDL through ClickHouse's own Parquet reader produce the same rows, column by column, value by value — timestamps to the microsecond, decimals exactly, nulls as nulls. It is worth naming because it is the only thing that makes the mirror trustworthy without a reconciliation tool: if the two doors agree, then rebuilding the mirror from the bucket produces what the live mirror would have produced, so "disposable and reproducible" is a fact rather than a hope. `TESTING.md`'s scenario 17 is the proof, and it includes the part that matters more than the assertion — three mutations, each of which must make the test fail.

**Decision (2026-08-04, M17): every optional icelake column is `Nullable(T)` in the mirror, always, and the two-door test runs with `input_format_null_as_default=0` and `input_format_parquet_allow_missing_columns=0`.** This is a hazard rather than a preference, and it is the one place ClickHouse's defaults will quietly destroy data if nobody writes this down. `input_format_null_as_default` defaults to *true*: a null read out of a Parquet file into a non-`Nullable` column is silently written as that type's zero value — `0`, `''`, the epoch — with no error, no warning and no way to tell afterwards which rows were null and which were genuinely zero. A mirror that declared an optional column as plain `Int64` would therefore look correct in every count and be wrong in every value that mattered. So: optional means `Nullable(T)` with no exception, and the identity test turns both settings off so that a mismatch is a refusal rather than a coercion. The second setting is the same hazard from the other side — a column missing from the file must fail the read rather than arrive full of defaults.

**Decision (2026-08-04, M17): the mirror's engine is `MergeTree` with `ORDER BY tuple()`, and the generated `CREATE TABLE` sets `non_replicated_deduplication_window = 1000`.** The window is not a tuning knob here, it is the thing that makes the batch key work at all, and the fact is measured rather than assumed: on the pinned server, three identical inserts of one batch under one `insert_deduplication_token` produce three copies of the batch without that setting and one with it. Plain `MergeTree` has insert deduplication *off* by default — the window is what turns it on for a non-replicated table — so a mirror created without it would duplicate a batch on every retry and on every replayed crash, which is the failure the whole tap-point argument above is built to avoid. `ORDER BY tuple()` is the default rather than a recommendation: icelake does not know what the operator will query by, an arbitrary sorting key is a guess that costs merges forever, and an operator who does know keeps their own — see the reconciliation rule below.

**Decision (2026-08-04, M17): materialized views are out of scope at this layer, permanently.** icelake delivers data and a schema; what is built on top of them is the user's layer. This is not a scheduling statement — there is no milestone in which icelake grows a view definition — and the reason is that a view is a query, querying is out of scope by the section below that says so, and a library that owned view definitions would own their schema evolution, their backfill and their failure modes as well. There is a second, sharper reason specific to this mechanism: ClickHouse's insert deduplication and materialized views interact in ways that depend on server settings an operator controls (`deduplicate_blocks_in_dependent_materialized_views` among them), so a view icelake defined would make icelake responsible for a dedup story it cannot see the whole of. The user's views are the user's, and the `_batch_key` column below is what they can reconcile against.

**Naming: one configured database, one table per icelake table, named `<namespace>__<table>`.** `ClickHouseConfig.Database` defaults to `icelake`. The rejected alternative is a database per namespace with the table keeping its own name, and it is rejected on the operation that matters most for a disposable index: rebuilding it. One database means `DROP DATABASE icelake` is the whole of "throw the mirror away and rebuild it", and one `GRANT` is the whole of the permission surface; a database per namespace makes both an N-step operation over a set of names icelake mints at runtime and the operator has to discover. The accepted cost is that the separator is ambiguous — a namespace `a__b` with table `c` and a namespace `a` with table `b__c` would want the same ClickHouse table — so a namespace or table name containing a double underscore is **refused when the mirror is configured**, loudly, at the call that would have created the table. Refused rather than escaped, for the reason every name rule in this project gives: rewriting a caller's table name is how two services end up sharing a table.

**The `_batch_key` column, and why the token alone is not enough.** Every mirrored row carries `_batch_key String`, the same content hash that names the batch's Parquet object and its spool file. The deduplication token is server-side state with a window: it answers "have I seen this insert recently" and it forgets. The column is data: it answers "which batch is this row from" forever, from a query, which is what makes a user's own reconciliation against the lake possible at all — the batch keys in the mirror and the object names in the warehouse are the same strings. It is the one column icelake adds, it is not `Nullable`, and it is why the insert names its columns explicitly rather than positionally.

**Decision (2026-08-04, M17): the mirror's schema is created and reconciled add-only, and any other disagreement is a refusal that tells the operator to rebuild.** On the first flush-path use of a table, icelake issues `CREATE DATABASE IF NOT EXISTS` and `CREATE TABLE IF NOT EXISTS` with the DDL derived from the table's declared schema (`SCHEMA.md` owns the type mapping). If the table already exists, its columns are read from `system.columns` and diffed: a column the declaration has and ClickHouse does not is added, by `ALTER TABLE ... ADD COLUMN`, and only when it is optional — which is the only kind of column icelake's own schema evolution ever adds. Everything else is refused: a required column missing, a column whose type differs, a `_batch_key` that is not there. The operator's fix is one `DROP TABLE`, and that is an acceptable instruction *only* because the thing being dropped is reproducible from the lake — which is the same sentence this section opened with, now doing work. Two consequences are stated rather than left to be discovered. A widening the lake accepts, `int32` to `int64`, is a type disagreement here and therefore a rebuild; the mirror is disposable and the lake is not, so the asymmetry is the right way round. And **an operator who pre-created the table with their own `ORDER BY`, their own `PARTITION BY`, or extra columns of their own keeps all of it** — icelake verifies the columns it writes and nothing else, because the sorting key is exactly the kind of decision that depends on queries icelake cannot see. An extra column icelake does not write is left alone; if it has no default, every insert will fail and say so through the doorbell, which is the operator's own arrangement failing loudly rather than icelake guessing at it.

**Decision (2026-08-04, M17): a mirror failure at open time blocks the table only when it is a statement about configuration, never when it is a statement about reachability.** Two things can go wrong while a table's mirror is being prepared and they mean opposite things. A name that cannot be mapped injectively, and a live table whose columns disagree in a way the add-only rule refuses, are the operator asking for something icelake will not do: they cannot heal by themselves, they are discovered before a single record has been accepted, and they are returned from `OpenWriter` exactly as a `ReconcileError` is, blocking that one table and no other. A ClickHouse that is unreachable, or a `CREATE TABLE` that failed because the server is unwell, is not that: refusing to open the writer would mean a ClickHouse outage stops the lake from accepting records, which is the one thing this section forbids by name. So that failure is reported through `OnClickHouseError`, the writer opens, and the whole preparation is re-attempted at the next flush — the same self-healing shape a failed flush cycle already has. The accepted cost is that a process can start with a mirror that is silently behind if the caller wired no callback; it is accepted because the mirror is opt-in, the callback is documented beside it, and the alternative is worse in the direction that loses data.

**What is not in this milestone, named so the map has no blank corners: backfill and verification tooling.** There is no call that rebuilds a mirror from the Parquet collection, and no call that compares a mirror against it. Both are real and both are the next milestone's; what M17 owes them, and delivers, is the property they rest on — two-door identity, proven now, so that a backfill written later is known in advance to produce what the live mirror produces.

## Local write-ahead durability

A deliberate decision (2026-07-27): icelake accepts the added complexity of a local write-ahead staging layer rather than accepting bounded data loss on crash, given this system is meant to eventually hold irreplaceable data — the motivating archival case collects data that cannot be re-fetched if lost.

Mechanically: every record passed to icelake is durably appended to a local staging store before the call returns success, independent of whatever in-memory batch it will eventually be flushed as part of. On restart after a crash, the process replays the staging store to recover any records that were durably accepted but never made it into a committed Iceberg snapshot, and resumes normal batching from there. Once a batch's flush + catalog commit is confirmed, its constituent records are pruned from the staging store — or, in local-only mode, once the batch's spool file is durably on disk, which is the whole of what a confirmed flush means where there is no bucket (see the local-only decision under `Config` above).

This is real, acknowledged new complexity, not a free win: there are now three persisted things per table to reason about and keep consistent — the local staging store, the spool's files and rows where a cache is configured, and the committed Iceberg snapshots — rather than just one. (Two of the three when there is no `CacheDir`, and two again in local-only mode, where there are no snapshots; three is the bucket-plus-cache case, which is the one to design against.) The staging store's own crash-recovery correctness (does a crash mid-append leave a torn/corrupt record? does replay correctly avoid double-counting an already-committed batch?) needs its own explicit test coverage, not an assumption — see `TESTING.md`. **Decision (2026-07-28): reuse the same SQLite technology already required for the catalog (see below) for the staging store too, but as a second, separate database file — not the same file as the catalog** (`staging.db` next to `catalog.db`). A plain `staging` table (row per record — table name, payload, monotonic id) gives every property this layer needs for free: durable-accept-before-return via an `INSERT` inside a transaction, replay-on-restart via `SELECT ... ORDER BY id`, and prune-on-commit via `DELETE ... WHERE id IN (...)`. SQLite's own journal/WAL already solves torn-write recovery — decades of fault-injection testing behind it, not something icelake has to prove itself. This removes a candidate dependency (`bbolt`) and an entire class of hand-rolled crash-recovery code without weakening the durability guarantee. The tradeoff is SQLite's per-transaction overhead versus a raw fsync'd append, which is acceptable since records are already being batched downstream rather than written one at a time.

**Decision (2026-08-04, M15): durability is promised at the granularity of the call that asked for it, and `InsertBatch` is one call — when it returns, every row it was handed is durable, atomically; when it returns an error, none of them is.** `Insert`'s promise is untouched and is not weakened by a second door existing beside it: hand over one record, and that record is on the disk before the call returns. What the batch door adds is a second *granularity*, not a second guarantee. The whole batch is written inside one transaction, so it is either entirely in the staging store or entirely absent — on a refusal, on a failure part way through, on a context cancelled mid-transaction, and on a crash between two of its rows. There is no state in which a caller is holding a slice and does not know which end of it icelake took. The rejected alternative was the obvious one, and it is worth naming because it is what a caller writes by hand: loop `Insert` over the slice and call that a batch. It reads identically right up until something goes wrong, at which point it is not a batch at all — a failure at row *k* leaves rows 0 through *k*-1 durable, the caller cannot re-send the slice without writing those rows a second time, and the fsync per row that motivated the whole thing is still being paid once per row. The cost accepted in exchange is that partial success is not expressible through this door: one unrepresentable value refuses the batch it is in, and a caller who wants the other rows accepted splits the batch itself and says so. That is the same shape of answer `Insert` already gives about one record — the caller is told exactly what it still owns — moved up to the unit the caller actually handed over.

### Scope, schema, and pragmas of the staging store

**Decision (2026-07-30): one `staging.db` per process, shared by every table, not one file per table.** The concern with sharing is real and worth stating rather than waving off: SQLite allows exactly one writer at a time per database, so two tables' inserts in the same process serialize against each other. For this workload that does not matter. Inserts are single-row appends into a table with one index (its primary key). **Measured at M4, and the number is two orders of magnitude worse than this paragraph originally guessed: about 3.35ms per insert, roughly 300 records per second**, because `synchronous=FULL` means every insert is a real fsync and this design deliberately pays for that rather than risking the last transactions on a power loss. The reasoning survives the correction — the thing that actually takes time here is still the flush to object storage, which is seconds and does not hold the SQLite write lock at all, so two tables' inserts serializing against each other costs a few milliseconds against an upload measured in seconds. What the real number does change is the shape of the ceiling a caller should expect: a single writer accepts hundreds of records a second, not tens of thousands, and a caller that needs more than that is asking for a batching layer of its own in front of this one. Nothing here is latency-sensitive — the entire premise is "collect for a while, then upload in a big chunk." Against that non-cost sit three real benefits: one file to back up (and per the disposability discussion below, this is the file an operator *must* back up — one file rather than "one file per table, and remember to add the new one when a service adds a table" is a genuine safety property, and it stays one file under the spool decided at M10, since the spool's own tables are in this same database and the only other thing needing a backup is a spool file the bucket has not confirmed), one `goose` migration run at startup instead of N, and one replay pass at startup instead of N. A per-table file would also make the staging ceiling above either per-table or awkwardly aggregated across handles, when the thing an operator actually cares about bounding is total local disk.

**Decision (2026-08-04, M15): the batching layer the paragraph above sends a caller away to build is now part of this library, as `InsertBatch`, and `synchronous=FULL` does not move to buy the throughput.** The M4 measurement stands exactly as it is recorded above — about 3.35ms per insert, roughly 300 records a second — and so does its diagnosis: one transaction per row at `synchronous=FULL` is one real fsync per row, and the disk's fsync rate is the entire number. What is withdrawn is the sentence that measurement ended on, that "a caller that needs more than that is asking for a batching layer of its own in front of this one". A caller building that layer would be building it on the wrong side of the durability boundary: to make groups worth a transaction it would hold records in its own memory, unstaged, for as long as it took to fill one — which is precisely the bounded loss on crash that the decision opening this section refuses to accept. The layer belongs *below* the boundary, where the records it groups are already icelake's to lose and the transaction it groups them into is the same transaction that makes them durable. So the answer to "I need more than a few hundred records a second" is no longer "write your own buffer", it is "hand the slice to `InsertBatch`", and the fsync is amortized across the batch instead of being paid per row.

Measured at M15 on the development machine, through this package's own `Append` and `AppendBatch` against a real staging file with the real pragmas — the same figures `mise run bench` prints, so the table is re-runnable rather than merely recorded. Absolute figures are a property of the disk and will differ on other hardware; the shape is the point, and the shape is that above a certain size everything except the number of fsyncs stops mattering.

| rows per transaction | rows per second |
| --- | --- |
| 1 — the M4 behaviour | 267 |
| 100 | 24,400 |
| 1,000 | 121,500 |
| 10,000 | 202,100 |
| 50,000 | 227,700 |

The disk under those numbers manages 327 fsyncs a second on its own, which is what the first row of the table is: one record per transaction is one record per fsync, and no amount of work anywhere else in this library could have moved it.

Three further measurements are recorded because each closes off a plausible alternative explanation. `synchronous=NORMAL` with one transaction per row reaches about fifteen thousand rows a second — a fifty-fold improvement over the M4 behaviour, and still slower than grouping a hundred rows into one transaction at `FULL`, which is why the pragma never had to be touched: the rejected option is both less durable *and* slower than the accepted one, so there is no trade to weigh. The descriptor upsert every append performs alongside its insert costs nothing measurable per record — a few rows a second either way, which is noise in both directions — so statement *count* inside the transaction was never the thing to attack, and the batch path deliberately keeps the same single-row insert statement in a loop rather than hand-building a multi-row `VALUES` clause that would earn nothing and owe sqlc an explanation. What it does do once instead of per row is the descriptor upsert, once per *distinct* fingerprint in the batch, because the loop had no reason to repeat it.

**Decision (2026-08-04, M15): the staged-row insert returns its id as the statement's last insert rowid rather than through a `RETURNING` clause, and every statement in the staging package is prepared once at open rather than parsed on each execution.** Both are consequences of the same fact about the pure-Go driver, found by profiling the batch path rather than guessed at: given SQL as a string it parses that string every single time, and given a `RETURNING` clause it must open, step, scan and close a result set for a statement that is otherwise a write. Inside one transaction, at M15, dropping `RETURNING` took an insert from about 43 microseconds a row to about 14, and preparing the statement once took it from 14 to about 7.7; the flush path's per-row payload read fell from 15.5 microseconds to 7.2 on the second change alone, which is why it is applied to the whole package rather than to the insert. Neither changes what any statement means: for a single-row insert the last insert rowid *is* the id the row was given, and a prepared statement is the same statement. What is accepted in exchange is that `staging.Open` now does work proportional to the number of queries in the package before it returns — a dozen prepares against a database whose schema has just been migrated — and that `Store.Close` has one more thing to release. The alternative considered and rejected was to leave the generated code alone and hand-build a multi-row `INSERT`, which measured *worse* than the prepared single-row statement (about 13.5 microseconds a row at a hundred rows per statement) while owing an explanation for leaving sqlc behind.

TESTING.md's rows-per-fsync scenario is the regression tripwire for this decision, and it is deliberately a ratio rather than a rate: a rate would have to be tuned per machine and would be flaky on a slow runner, and the failure this decision is exposed to — someone reinstating a transaction per row — collapses the ratio to one wherever it is run.

**Decision (2026-07-30): WAL mode and a busy timeout are set explicitly at open, as a stated requirement, not left to whatever `modernc.org/sqlite`'s defaults happen to be.** On opening `staging.db`, icelake issues `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=FULL` and `PRAGMA busy_timeout=<a few seconds>` (concretely five seconds, fixed at M3 and deliberately not configurable — a caller has no way to know a better number than "longer than an insert into a ceiling-bounded table can take", and exposing the knob would invite tuning a symptom), and asserts the results rather than firing them and hoping. Two mechanical details were settled at M3 and are recorded because getting either wrong would silently un-do the paragraph above. The pragmas travel as DSN parameters rather than as statements issued after opening, because `database/sql` owns a *pool* of connections and hands out whichever is free: a pragma set once, on one connection, would leave every other connection running on the driver's defaults, and `synchronous` and `busy_timeout` are per-connection settings. And every transaction this layer opens takes its write lock at `BEGIN` (`_txlock=immediate`) rather than deferring it, because a deferred transaction that upgrades to a write lock mid-way is the one contention case a busy timeout cannot absorb — SQLite returns `SQLITE_BUSY` immediately there rather than waiting, since waiting could deadlock. WAL is what makes a reader (the replay/flush path) coexist with the insert path without either blocking the other, and is the mode SQLite's crash-recovery story is best exercised in. `synchronous=FULL` rather than WAL's usual `NORMAL` is deliberate and is the one place this design pays for durability rather than speed: `NORMAL` in WAL mode can lose the last transactions on a *power* loss (not on a process crash), and "the record is durable once `Insert` returns" is the entire reason this layer exists. The busy timeout turns the brief lock contention between two tables' inserts into a short wait inside the driver instead of an `SQLITE_BUSY` error surfacing to a caller.

The schema, in full — this is migration `00001`, the first `goose` applies to a fresh `staging.db`; migration `00002` adds the spool's two tables and is set out after it:

```sql
CREATE TABLE staging (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    namespace  TEXT    NOT NULL,
    table_name TEXT    NOT NULL,
    batch_key  TEXT,             -- NULL until the record's batch is sealed
    schema_fp  TEXT    NOT NULL, -- fingerprint of the schema the payload was encoded under
    payload    BLOB    NOT NULL, -- the canonical record encoding (see "Batch identity")
    byte_len   INTEGER NOT NULL, -- payload length, so the ceiling needs no length() scan
    created_at INTEGER NOT NULL, -- unix millis; diagnostic only, never read by the write path

    quarantined_at   INTEGER,    -- NULL normally; set if the batch could not be encoded
    quarantine_error TEXT        -- the encoder error, kept for an operator to read
);

CREATE TABLE staging_schemas (
    fp         TEXT PRIMARY KEY, -- hex hash over the descriptor below
    descriptor BLOB NOT NULL     -- serialized (field id, name, type, nullability, and
                                 -- precision/scale for a decimal) list, ascending
                                 -- field-id order, icelake's own canonical form
);
```

**Decision (2026-08-01, M10): the spool's durable state lives in `staging.db` too, as goose migration `00002`, in two tables of its own — and `spool_schemas` is deliberately a separate table from `staging_schemas` rather than a reuse of it.**

```sql
CREATE TABLE spool_files (
    batch_key    TEXT PRIMARY KEY, -- the content hash; also the file's name and the object's
    namespace    TEXT    NOT NULL,
    table_name   TEXT    NOT NULL,
    schema_fp    TEXT    NOT NULL, -- the shape these bytes were written under
    byte_len     INTEGER NOT NULL, -- the file's size, so the size bound needs no stat() walk
    created_at   INTEGER NOT NULL, -- unix millis; the age bound and the drain order read this
    committed_at INTEGER           -- NULL until the file is uploaded AND catalog-committed
);

CREATE TABLE spool_schemas (
    fp         TEXT PRIMARY KEY, -- hex hash over the descriptor, exactly as staging_schemas
    descriptor BLOB NOT NULL     -- icelake's own canonical descriptor form
);
```

Putting them in `staging.db` rather than in a third file is the same decision as putting staging and the catalog in two files, applied the other way: these rows and the staging rows are written and pruned in step with each other, they have the same disposability rules, and a spool row that disagreed with a staging row across two files would be a consistency problem with no transaction available to fix it. The one thing that could have argued for separation — that the spool is about the cache directory and the cache directory is disposable — is exactly wrong, since the rows that matter most here are the ones describing files that are *not* disposable because they have never been uploaded.

**Why `spool_schemas` is its own table is the part worth recording, because sharing one looks obviously right until it destroys data.** `staging_schemas` is pruned: the flush path drops a fingerprint's row once no staged row references it, which is correct there because a descriptor exists to decode staged payloads and there are none left to decode. A spool file outlives its staged rows by design — in bucket mode its rows are pruned the moment the commit is confirmed, and in local-only mode they are pruned as soon as the file is on disk — so a spool file's shape would be pruned out from under it within seconds of being recorded. That descriptor is not decoration: the transition drain reads it to decide whether the live table has to be reconciled forward before this file can be committed, and to create the table at all when the drain is the first thing that ever touched the catalog. Sharing the table and teaching the prune to check both references was the alternative, and it is rejected for the reason this document rejects most sharing: it makes a delete in one subsystem depend on a condition owned by another, and the failure mode is a file on disk whose shape nothing in the world can state. Two tables, two lifetimes, one prune each.

**Decision (2026-07-30): every staged row records the schema fingerprint its payload was encoded under, and replay decodes each row by its *recorded* shape, never the current one.** This closes what was previously a real hole. The canonical payload encoding is positional — field values in ascending field-ID order, with no per-field framing — so the bytes alone cannot say which schema wrote them. The failure sequence without this: rows are staged, the process crashes, a new build deploys with one more field (or a widened type), the restart replays old rows by decoding them against the *new* declared shape, and either fails or silently misreads values. The fingerprint is a hash over the **full serialized descriptor** — (field id, name, type, nullability) for every column, in ascending id order — not over a reduced (id, type, nullability) projection, which is what an earlier draft of this paragraph said and which contradicted the schema above it (`fp TEXT PRIMARY KEY, -- hex hash over the descriptor below`). **Decision (2026-07-31, M2): the descriptor comment wins and the column name is part of the fingerprint.** The reason is not that decoding needs the name — decoding is by field id, so a rename cannot change how a payload is read — it is that `staging_schemas` is a content-addressed table: `fp` is its primary key and `descriptor` is its value, so a hash that did not cover the whole stored value would let two genuinely different descriptors collide onto one row, and the descriptor that came back for a given fingerprint would be whichever was written first. A rename therefore produces a new fingerprint and a new row, which is also the honest answer for an operator reading that table by hand. `staging_schemas` keeps the full descriptor for every fingerprint that still has live rows, so decoding an old row depends only on what staging itself recorded — not on the old struct still existing anywhere in the current binary. Replay decodes a row via its descriptor into values keyed by field id, then maps them into the current declaration by id: a field the current declaration added since is simply nil (it is optional by the evolution rules in `SCHEMA.md`, so nil is exactly right). The one unmappable case fails loudly: a recorded shape containing a field id **absent** from the current declaration means staged data exists that the current struct cannot even represent — `OpenWriter` for that table returns a typed error (see "Error taxonomy" below) telling the operator to drain the table with the previous binary first, rather than half-opening and quietly dropping a column's staged values. Rows whose fingerprint matches the current one — the overwhelmingly normal case — skip all of this and decode directly.

Two consequences are part of the decision rather than implementation detail. First, **at seal time, any row in the batch whose fingerprint differs from the current schema's is re-encoded under the current schema, in the same transaction that stamps `batch_key`** — so a sealed batch is always fingerprint-homogeneous, and the batch hash below is always computed over payload bytes that agree with the schema portion of its own hash input. Second, **a batch that is already sealed uploads under its stored `batch_key`, which is never recomputed** — recomputing would silently produce a *different* key if the declared schema changed between seal and replay (the schema is part of the hash input), stranding the previously-uploaded object as an orphan and breaking the retry-hits-the-same-key guarantee at exactly the moment it matters. The stored key is authoritative from the moment of sealing; recomputing the hash and comparing is a valid integrity check only when the fingerprints match, which is how `TESTING.md` scenario 2 uses it.

**Decision (2026-07-31, M3): a staged row and the descriptor its fingerprint names are written in one transaction, so no window exists — not even a crash-sized one — in which a payload exists whose shape is unrecorded.** This was previously left to whoever wrote the code: `staging_schemas` is described above as content-addressed and read by replay, but nothing said *when* a row lands in it. Registering the descriptor once per table at `OpenWriter` and then inserting rows would be cheaper by one trivial statement per insert, and would be wrong: a crash between the two leaves staged payloads that no binary can decode, including the one that wrote them, because decoding is driven by the recorded descriptor and there would be none. The staging insert already pays an fsync, so the extra `INSERT … ON CONFLICT DO NOTHING` is free in the only currency that matters here. The same rule applies at seal time: the shape a batch is sealed under is recorded in the sealing transaction, which matters precisely in the case where no row was ever *staged* under that shape — a replay after a schema-changing deploy, where every row in the batch is being re-encoded into a shape this database has not seen.

**Decision (2026-07-31, M3): sealing refuses a row that is already sealed or already quarantined, rather than restamping it.** The seal statement carries `WHERE id = ? AND batch_key IS NULL AND quarantined_at IS NULL` and the update is required to match exactly one row. Without the guard, a bug one layer up that put one record into two batches would silently change both batches' contents *without changing either's stored key* — which is the one way content-hash keying can lie, since the key would then name bytes that are no longer what it was computed over. The refusal is a typed error (below); nothing is repaired automatically, because every path to this state means some assumption about who owns which rows has already been violated.

**Decision (2026-07-31, M3): a batch belongs to exactly one `(namespace, table)`, and sealing enforces it.** This was assumed everywhere and stated nowhere, which is how it came to be unenforced: the batch key's own hash input begins with the namespace and the table name, and the object it names lives under `<prefix>/<namespace>/<table>/data/`, so a batch containing two tables' rows has a key that is wrong for at least one of them and an object under a prefix half its contents do not belong to. The seal statement therefore carries the table identity alongside the primary key (`WHERE id = ? AND namespace = ? AND table_name = ? AND …`), so a row from another table simply does not match and the seal fails with the same typed refusal as a row that is already sealed.

**Decision (2026-07-31, M3): a sealed batch is quarantined whole or not at all, and a database that already contains a half-quarantined batch is refused at startup rather than replayed.** Quarantine is described above as a *batch*-level action — "a batch that cannot be encoded is quarantined in place" — but nothing enforced that, and the gap reopens the exact hole the seal guard closes, through a different door: marking some of a sealed batch's rows and not others leaves a batch whose stored key no longer names its bytes, so replay would offer a *shorter* batch under the key computed over the longer one and the retry would overwrite a correctly uploaded object with a truncated one. Silent data loss under a key that still looks right. Both sides are closed. Marking refuses any row carrying a `batch_key` unless every row of that key is named in the same call, for the same reason and with the same typed error as the seal refusal. And the startup scan refuses outright — rather than skipping the marked rows, as it does for an unsealed quarantine — if it ever meets a sealed batch with some rows quarantined and some live, which this build cannot produce but an older or buggier one could have left behind.

**Decision (2026-07-31, M3): the startup scan reads `quarantined_at` too, and descriptor cleanup is its own call rather than part of the delete-on-commit path.** The single ordered scan named above selects `id, namespace, table_name, batch_key, schema_fp, byte_len, quarantined_at` — the extra column is what lets one pass honour both halves of the quarantine decision at once, since a quarantined row is excluded from the replay index but still counted toward the ceiling. Separately, dropping `staging_schemas` rows nothing references any more cannot be done by primary key — it has to look across the whole staging table to know a fingerprint has no rows left — so it is a separate operation the flush path calls after a commit, not something folded into the prune. That keeps the commit path purely primary-key, as the indexing rule below requires, and a descriptor that lingers a while longer is harmless: it costs a few bytes and nothing reads it.

`AUTOINCREMENT` (rather than a plain `INTEGER PRIMARY KEY`) is deliberate: it guarantees a monotonically increasing id that is never reused after a delete, which matters here because rows are continuously deleted on commit and replay order must remain insert order.

**The no-secondary-index rule from below still holds, and the shared-file decision does not break it.** Nothing here does one filtered scan per table. Each ordered pass is a single `SELECT id, namespace, table_name, batch_key, schema_fp, byte_len, quarantined_at FROM staging ORDER BY id` — no payloads — from which pending row ids are grouped in memory by `(namespace, table_name)` and, within that, by `batch_key`. What the pass at startup does with that result is the two things only it does: seed the ceiling counters before any writer exists, and refuse a staging database this build will not replay. Which rows are pending for which table is answered per writer, by the decision immediately below, and the payloads of whichever rows a writer claims are read back by primary key.

**Decision (2026-07-31, M4): that ordered pass is made once per `OpenWriter`, not once per process, and the index it builds is local to the call that made it.** The original design had one snapshot taken at `Open` and consumed a table at a time, which is cheaper and is wrong in a way that only shows up in the one flow an operator is most likely to take. A snapshot describes the moment the process started, so it cannot contain rows staged *during* a writer's own life — and `Close` is explicitly allowed to return with records undrained and safe in staging, which makes "close, then open the table again and try once more" the natural response to a failed shutdown. That reopened writer inherited nothing: its records were in the file, accepted and undelivered, and no writer, no counter and no error said so for the rest of the process's life. Rescanning per open closes it, and closes the same hole for every future same-process flow, because the answer comes from the durable file rather than from a memory of it. It also makes a failed open incapable of stranding anything, which a shared consumable index could not promise: the index is a local variable, so an open that fails discards it and the next open reads the same rows again. The costs are exactly two and both are acceptable: one bounded scan per writer opened instead of one per process, paid at startup where a table's whole point is that it is small; and no change at all to the indexing rule, since the pass is still a full ordered scan by primary key. The startup pass stays, because it still does two things nothing else does — seed the ceiling counters before any writer exists, and refuse a staging database left in a state this build will not replay. One ordered scan of a bounded table, then primary-key lookups; no index on `(namespace, table_name)` is needed for either. The delete-on-commit path is `DELETE ... WHERE id IN (...)` and the sealing path is `UPDATE staging SET batch_key = ? WHERE id IN (...)`, both of which are the primary key. No access pattern in this design needs an index on `(namespace, table_name)`, and none should be added until a measured query proves otherwise.

**Corrected at the completeness audit's sixth round (2026-08-01): the paragraph above the decision used to end "Each `OpenWriter` takes its own table's group and reads those rows' payloads back by primary key", which is the pre-M4 design — one index built at startup and handed out a table at a time.** The decision reverses exactly that, and the code has followed the decision since M4: `Open` reads the counters off its scan result and lets the index go, `Store` has no field to hold one, and `Store.pendingFor` makes a fresh scan on every `OpenWriter`. The mechanism is the part worth carrying away, because it is the same one the fifth round met in the API sketch near the top of this document: the reversal was written as a new paragraph *beside* the sentence it reversed rather than replacing it, so the stale claim and its correction sat two lines apart in the section that owns the staging design, and the M4 commit that added the decision edited that paragraph without touching the clause it superseded. Replacing the sentence a reversal supersedes is part of making the reversal, not a follow-up to it.

Rows belonging to a table that no `OpenWriter` claims in a given run stay in staging untouched and keep counting toward the ceiling. That is deliberate rather than an oversight: those rows are accepted, undelivered data, and quietly discarding them because this run's code no longer declares that table would be a silent data loss. A service that genuinely retires a table must drain it (open it once more and let it flush) or delete its rows knowingly.

**Decision (2026-07-30): a batch is sealed durably before it is encoded, by stamping `batch_key` on exactly its rows in one transaction.** This is what makes crash recovery reproduce the *same* batch rather than a differently-bounded one, which is what makes the content-hash file key idempotent in practice rather than only in theory — see "Batch identity" below, and `TESTING.md` scenario 2. On replay, rows that already carry a `batch_key` are reassembled into exactly that batch, in id order, before any newly-staged rows are batched — and per the schema-fingerprint decision above, a sealed batch's upload key is read from `batch_key`, never recomputed.

**Decision (2026-07-30): a batch that cannot be encoded is quarantined in place, never retried forever.** The two nullable columns in the schema above carry this: on an encode failure, the batch's rows are marked instead of deleted, excluded from all future replay, and reported through `OnFlushError`. Quarantined rows deliberately keep counting toward the staging ceiling, so a quarantine that grows eventually stops the writer loudly rather than silently eating headroom forever. They are plain SQLite rows an operator can inspect, export, or delete by hand. See "Failure handling" below for when this can actually happen, which is rarer than it sounds.

**Why a separate file, not a shared one with the catalog:** the two databases have opposite disposability rules, and a separate file makes that a physical fact rather than something that has to be remembered in code. The catalog (below) is explicitly rebuildable from the bucket at any time and needs no backup. The staging store is the opposite — it is, by definition, holding data not yet copied to the bucket, so it is **not** reconstructable if lost, and whoever operates icelake needs their own backup story for it (e.g. whatever host-level snapshot mechanism they already use for other local state). **The spool, decided at M10 and built at M11, splits that story in two without changing its principle, and the split is what an operator has to get right:** the thing to back up is `staging.db` *plus any spool file that has never been uploaded*, which is to say any file whose `spool_files` row still has a null `committed_at` — in local-only mode, that is every file there is. The cache's committed files are the opposite and are as disposable as `catalog.db`: they are byte-identical to objects that are already in the bucket and referenced by a committed snapshot, so losing one costs a re-download at worst and the sweeper is going to delete it anyway. The rule reduces to the same sentence it always was, with one clause added: back up what has not reached the bucket. This is an operational requirement to document, not something icelake's own code solves — consistent with the "observability out of scope" decision below, which draws the same boundary between what the library does and what the operator is expected to already handle.

**Schema ownership and migrations: `goose`, run automatically on startup, fail loudly on error.** The `staging` table's schema belongs to icelake, and is managed with `goose` (`github.com/pressly/goose`) migrations embedded directly in the binary (`//go:embed`), not the Iceberg catalog's schema — that is entirely internal to `catalog/sql` and out of icelake's hands (see below). Requirements, stated strictly:
- Pending migrations run automatically every time icelake starts, against `staging.db`. There is no separate manual migration step or CLI invocation for an operator to remember.
- If a migration fails, startup fails loudly and stops immediately. Icelake must never start serving writes against a database it isn't sure is in the expected schema state.
- "Validate" here means exactly one thing: confirming `goose`'s own migration call returned no error. It does **not** mean a data scan, an integrity check, or any row-level validation of existing content — that would reintroduce the same "slow startup check that scales with data size" failure mode from the archival case this whole project exists to avoid. Trust `goose`'s own result; do not re-verify it independently.

Query code against `staging.db` is generated with `sqlc` (`github.com/sqlc-dev/sqlc`, SQLite engine) from hand-written SQL, rather than hand-written `database/sql` scanning code — sqlc's generated code only depends on the generic `database/sql` interfaces, so it runs against `modernc.org/sqlite` at runtime with no cgo driver needed at either generation or run time.

**Decision (2026-07-30): the code-generation workflow is pinned down, not left to convention.** The SQL sources live inside the library module: migrations at `internal/staging/migrations/NNNN_*.sql` (embedded via `//go:embed`, which is what lets `goose` run them with no files on disk at runtime) and queries at `internal/staging/queries.sql`, with `sqlc.yaml` checked in at the module root (which is the repo root, per `PLAN.md`'s layout). Generated code is **committed to the repo** — a plain `go build` must never require the generator to be installed — and regenerated only through `mise run generate`, with the `sqlc` binary version pinned in `mise.toml` so every machine generates identical output. CI runs the generator and fails on any diff against the committed output, so generated code can never silently drift from its SQL sources. `goose` is used strictly as a library; there is no goose CLI in the workflow anywhere.

**Indexing: none beyond the primary key, added only when measured, never speculatively.** The `staging` table's entire access pattern is insert a row, read rows back in id order, delete rows by id — the primary key already covers all three. No secondary index should be added up front. If a future access pattern needs one, it should be added only after a real, measured slow query proves it, not in anticipation of one — over-indexing has a real, ongoing cost (slower writes, more disk) for a benefit that, for this table's known access pattern, doesn't exist.

No job queue (e.g. `River`) sits in front of any of this — see "Alternatives considered and explicitly rejected" below.

## Batch identity: content hash over the canonical batch, not a sequence number

The write path above needs every data file to have a name that is a pure function of what is in it, so that a retry after a crash rewrites the same object instead of creating a second one. This document previously offered two candidates and picked neither.

**Decision (2026-07-30): the file key is a content hash, and the hash is taken over the batch's canonical *in-memory* representation — never over the final encoded/compressed Parquet bytes, and never a sequence number.**

Against the sequence number: it requires durably persisting a counter and then correctly recovering *the same* value after a crash rather than skipping ahead, which is a small amount of code with a genuinely fiddly failure mode (a counter that advances before the batch it names is committed produces gaps; one that advances after produces reuse). It also fails badly in the exact scenario this design does not enforce against: two accidental concurrent writers on the same table both produce `...-000173.parquet`, and one silently overwrites the other's data. A content hash needs no persisted counter at all, and two accidental concurrent writers almost certainly produce *different* hashes, because their batch boundaries will differ by even one record — a real safety margin obtained for free rather than designed for.

Against hashing the final Parquet bytes: the whole scheme depends on "same logical batch ⇒ same key," and that would make the property hostage to a third-party encoder's determinism. Parquet writers routinely embed a `created_by` string, and any future arrow-go version bump, ZSTD level change, or dictionary-encoding heuristic change would silently produce a different hash for identical data — silently breaking idempotency at precisely the moment it is needed. Hashing something icelake fully controls removes that dependency entirely.

Concretely, the hashed input is a deterministic byte string built from, in order: the namespace and table name; the full serialized schema descriptor — (field id, name, type, nullability) per column in ascending field-ID order, which is the same canonical form `staging_schemas` stores and `schema_fp` is taken over; the record count; and each record's canonical encoding, in batch order. (An earlier version of this sentence said the schema component was only "the declared schema's field IDs and types". It is the whole descriptor, decided at M2 and set out under "The encoding, the descriptor, and the two hashes" below: a superset, chosen so exactly one canonical schema form exists anywhere in the codebase rather than two that have to be kept in step.) A record's canonical encoding is its field values written in ascending permanent field-ID order, each length-prefixed or fixed-width by declared type — the same permanent-ID-based identity that governs schema change everywhere else in this design, reused here so that two structurally different tables, or two schema versions of one table, can never collide. That encoding is not a new artifact invented for hashing: it is exactly what is already stored in `staging.payload`, so the batch's hash is computed over bytes that were durably written before the batch ever existed.

Deliberately *not* used for this: `encoding/gob` or JSON. Both are convenient and neither promises canonical output — gob's stream carries type descriptors and is documented as unstable across type changes, and JSON has no guaranteed number formatting or field ordering. Determinism here has to be icelake's own property, not something inherited.

**The decoder is icelake's own code too, and it was previously implied rather than designed.** Replay needs the inverse of the canonical encoding: payload bytes back into a typed row, so recovered records can be batched and encoded to Parquet. It is hand-written, symmetric to the encoder, and driven by the schema descriptor recorded in `staging_schemas` (see the fingerprint decision above) rather than by the current declaration — decode produces values keyed by field id, which are then mapped into the current struct by id, with pointer fields handling nulls the same way they do everywhere else in this design. Its correctness contract is the round-trip property — decode of encode returns the identical row — and, per `TESTING.md`'s philosophy, the encoder/decoder/hash trio is the canonical example of the one place unit tests are wanted: golden-byte fixtures checked into the repo, because file-key idempotency rests on these exact bytes never drifting across releases.

### The encoding, the descriptor, and the two hashes — exact forms

Everything above pins *what* is hashed and in what order, but left the byte-level details and the hash algorithm itself unstated. They are settled here, at M2, because all four artifacts are durable: a payload staged today is decoded by a build that does not exist yet, a fingerprint keys a row in `staging_schemas`, and a batch key is the name of an object in a bucket that is never renamed. The authoritative reference is the `internal/canon` package doc, which carries the same layouts next to the code that implements them; this section is the decision record.

**Decision (2026-07-31): the hash is SHA-256, from the Go standard library, rendered as lowercase hex, never truncated.** No algorithm had ever been named, which meant it would have been chosen silently by whoever wrote the code first. SHA-256 is in the standard library (so this adds no dependency to a project that otherwise pins every one deliberately), is hardware-accelerated on every platform icelake will run on, and produces a 64-character key that is comfortably short inside an object path. Truncation is deliberately declined: the digest costs nothing to carry and shortening it would trade a real, if remote, collision margin for cosmetics. Both hash inputs begin with a distinct ASCII domain tag (`icelake/schema-fp/v1\n` and `icelake/batch/v1\n`), so a schema fingerprint and a batch key can never be the same 32 bytes whatever their remaining inputs happen to be.

**Decision (2026-07-31): both byte formats carry a leading one-byte format version, and an unfamiliar version is refused rather than guessed at.** The record encoding is still positional with no per-field framing, exactly as decided above — a single leading version byte is a format tag, not framing, and it costs one byte per staged row. It buys the thing durability actually needs: a future format change takes the next version number and leaves every previously written byte readable and identifiable from the bytes alone, without a join against anything. The descriptor and the record payload version independently, because a new column type changes how a shape is described without changing how an existing value is written.

The record payload: one version byte, then each column's value in ascending field-ID order.

- An **optional** column's value is preceded by one presence byte — `0x00` null (no value bytes follow), `0x01` present. A **required** column has no presence byte at all, which makes "a null in a required column" unrepresentable rather than merely forbidden.
- Fixed-width values are big-endian: `boolean` one byte (`0x00`/`0x01`), `int` four bytes, `long`/`decimal`/`timestamptz` eight bytes two's-complement, `float`/`double` four and eight bytes of IEEE-754. A decimal's value is the unscaled int64 the caller already scaled; a timestamp's is the caller's own epoch milliseconds, untouched — the microsecond upcast Iceberg wants happens later, in the Parquet write path, not here.
- `string` and `binary` values carry a **four-byte big-endian length prefix**, then that many bytes. A fixed-width prefix rather than a varint was chosen because exactly one encoding exists per length (a varint admits non-minimal forms), and because a golden fixture is read by a human. Big-endian for the same second reason: a big-endian integer reads left to right in the order its digits are written.
- **`MaxUint32` is therefore the concrete meaning of "longer than the encoder's addressable limits"** in the poison-record decision below.
- A nil `[]byte` and an empty `[]byte` are the same value: both encode to a zero length and both decode back to a non-nil, zero-length slice. A required binary column has no null to round-trip to, and this is what the Arrow and Parquet sides of the write path do with it anyway.

The descriptor: one version byte, a four-byte big-endian column count, then per column in ascending field-ID order — four-byte field id, one-byte type tag, one-byte flags (bit 0 set means required, every other bit reserved and required to be zero), two bytes of decimal precision and scale for a decimal column only, a four-byte name length, and the name. Exactly one byte string can describe a given shape, and that is enforced structurally rather than by a list of rules: parsing re-serializes what it read and requires the result to be identical to its input. That is what lets the fingerprint simply be a hash of these bytes.

**Decision (2026-07-31): the batch hash's schema component is the full serialized descriptor, not a reduced list of field IDs and types.** This is a superset of what this document pinned above, chosen so that exactly one canonical schema form exists anywhere in the codebase — the same bytes that are stored in `staging_schemas`, that the fingerprint is taken over, and that the batch key depends on. A second, reduced form would be a second thing to keep canonical, for no gain. So the batch key is SHA-256 over: the domain tag; the namespace, the table name, and the descriptor, each behind a four-byte big-endian length; an eight-byte big-endian record count; and then each record's payload behind its own four-byte length, in batch order. The length prefixes are load-bearing rather than decorative — without them a batch boundary could move without the key changing, which is precisely the property replay depends on. A batch with **no** records is refused outright: a key must name real bytes, and hashing nothing would hand back a valid-looking name for an empty file.

**Decision (2026-07-31): the canonical encoding supports a closed set of nine Iceberg primitive types, and `SCHEMA.md`'s declaration path is given a matching closed whitelist of Go field types, so that the mapping between the two is one-to-one.** The nine Iceberg types are `boolean`, `int`, `long`, `float`, `double`, `decimal(P,S)`, `timestamptz`, `string` and `binary`. `date`, `time`, `uuid`, `fixed`, a timestamp with no zone, and every nested type are unreachable through the declaration path (each is rejected earlier, by the tag parser, by the two-derivation cross-check, or by the flat-only scoping rule), so giving them a speculative encoding would mean shipping a durable format for shapes nothing can write. Decimal precision is capped at 18 here for the same reason the declaration path caps it: the unscaled value is an int64. If a future declaration path unblocks one of these types, it takes the next unused type tag — tag numbers are permanent and are never reused or renumbered, for the same reason a field ID is not.

The Go-side half of that decision is the part worth writing down, because the gap it closes was found the hard way. An earlier version of this paragraph claimed the nine-type set had been established by enumerating every candidate Go field type through the real derivation; it had not, and a review that actually ran the enumeration found the hole. **A plain `int` field derives perfectly cleanly, and derives to a *different Iceberg type depending on the word size of the build*** — `arrow-go`'s reflection branches on the type's bit width, so an `int` column becomes `long` on a 64-bit target and `int` on a 32-bit one. Nothing downstream objects, because both are valid columns. But the column type is recorded in the schema descriptor, the descriptor is hashed into `schema_fp`, and `schema_fp`'s descriptor is hashed into every batch key — so the same source compiled for two architectures would produce two different fingerprints and two different object keys for identical data, and a staged row written by one would be unreadable-as-written by the other. `uint` and `uintptr` carry the same hazard. Separately, `int8`, `int16`, `uint8`, `uint16` and `uint32` all derive cleanly to an Iceberg `int` column, and `uint64` to a `long`, but the canonical encoding carries those columns as a Go `int32` and `int64` respectively — so an unsigned value above the signed ceiling would wrap silently once rows were staged.

So `Declare` now enforces a closed Go whitelist — `bool`, `int32`, `int64`, `float32`, `float64`, `string`, `[]byte`, plus a pointer to any of them for an optional column — and refuses everything else with a `DeclarationError` of kind `unsupported_go_type` naming the field and its Go type. The platform-dependent case is thereby unrepresentable rather than documented-around, which is the standard this project holds elsewhere and should have held here. The whitelist deliberately judges scalar column types only: a nested struct, a slice of structs or an array is not a wrong column type but not a single column at all, and the flat-only scoping rejection and the derivation chain already refuse those by name.

The resulting object key is `<warehouse-prefix>/<namespace>/<table>/data/<hex-hash>.parquet`. Since sealing durably records which rows belong to which batch (above), a crash between upload and commit is recovered by rebuilding the identical batch, producing the identical hash, and re-uploading to the identical key — a byte-for-byte overwrite, not a duplicate. Before re-committing, the flush path checks whether the live table's current snapshot already references that data file path and, if so, skips the commit and prunes staging directly.

**The call path for that check, verified against the pinned `iceberg-go`.** There are two public routes from a loaded table to the list of data-file locations in its current snapshot, and icelake uses the first:

```go
snap := tbl.CurrentSnapshot()                    // *table.Snapshot, nil if the table has no snapshots
fio, err := tbl.FS(ctx)                          // iceberg-go's own io.IO for the table's storage
manifests, err := snap.Manifests(fio)            // []iceberg.ManifestFile
for _, m := range manifests {
    for e, err := range m.Entries(fio, true) {   // iter.Seq2[ManifestEntry, error]; true = discard deleted
        df := e.DataFile()                       // iceberg.DataFile
        _ = df.FilePath()                        // the data file's location, e.g. s3://…/data/<hash>.parquet
        _ = df.ContentType()                     // must be filtered: Data vs the two delete-file kinds
    }
}
```

(**Corrected at M4:** this loop previously read `m.FetchEntries(fio, true)`, which returns a `[]ManifestEntry` and is deprecated in the pinned version in favour of the streaming `Entries` above — the two answer the same question, and the streaming form does not have to hold every entry of every manifest in memory to answer a yes/no. The deprecation is real enough that the project's own linter refuses the older call, which is how it was found.)

The second route is `tbl.Scan().PlanFiles(ctx)`, which returns `[]table.FileScanTask` whose `.File.FilePath()` gives the same set. Both were run against a real table with two appended data files and returned the same two paths. The manifest route is preferred here because it is a pure metadata walk with no scan planning, no expression evaluation and no partition pruning in the way — this check needs "does the current snapshot reference this exact key," not a query plan. `ContentType()` filtering is not optional: the same manifest machinery also carries positional- and equality-delete files, which are irrelevant to this check today and would be actively wrong to treat as data files once the equality-delete path exists. (`Table.AllManifests(ctx)` also exists and walks every snapshot in the table's history, not just the current one — the wrong tool for this check, but the right starting point for the orphaned-file enumeration recorded in the open questions.)

### Committing the uploaded file, and the file IO that makes it possible

**Decision (2026-07-31, M4): a data file is registered with `Transaction.AddFiles`, by location, and the library reads the file back to derive its own statistics.** Two routes exist in the pinned version. `AddDataFiles` takes fully-built `iceberg.DataFile` values and reads nothing — but every piece of machinery that *builds* one (the statistics aggregator, the metrics plan, the Parquet-metadata-to-bounds conversion) lives in `table/internal`, which is unreachable from outside the module, so taking that route means icelake hand-rolling column bounds, value counts and null counts for every column of every batch. `AddFiles(ctx, []string{location}, nil, ignoreDuplicates)` gets all of that from the library, and gets the library's own schema-compatibility check against the live table with it. The cost is stated plainly rather than hidden, with the numbers measured at M4 rather than guessed. **The file icelake has just uploaded is downloaded and parsed again on every flush**, and it is not one read: a Parquet reader needs the footer before it needs anything else, so the observed traffic is **three ranged GETs against the data file** (footer, then column metadata), for a per-flush total of **four Class A operations and four Class B operations** at the pinned versions. On R2's price list that is small money.

The real cost is not the operation count, and this is the argument that should decide the question later. It is latency and memory, and both scale with the batch: one batch is built whole in memory as an Arrow record, encoded whole into a Parquet buffer, uploaded whole, then *downloaded again* and re-parsed, and all of it happens on the single worker that serializes this table's flushes — so nothing behind it commits until it finishes. At the 167KB batches the test suite writes that is invisible. At the 128MiB batches the production configuration in the README targets, it is a whole extra transfer and parse of 128MiB inserted between one commit and the next. That is the case for eventually replacing `AddFiles`, and it is stronger than the billing one.

`ignoreDuplicates` is passed as `true`, which skips a full walk of the current snapshot's manifests on every single commit — an O(table size) cost paid per flush, forever. The duplicate case it would have caught is instead checked deliberately, using the manifest walk above, and only where a duplicate is actually possible: a batch being re-committed after a crash or a failed attempt. A batch sealed once in one process cannot collide with anything.

**Decision (2026-07-31, M4): icelake imports `iceberg-go/io/gocloud` for the S3 file IO — as a stopgap with an owner and a deadline, not as a settled choice.** Every table's own metadata — the `metadata.json` written on each commit, the manifest and manifest-list files, and the data-file footer `AddFiles` reads — is read and written by iceberg-go through its own `io.IO`, resolved from a global registry keyed by URL scheme. There is exactly one seam, and it is that registry: nothing about a table living in a bucket is reachable without something registered for `s3://`, and the only implementation the library ships is that package.

The cost, measured at M4 rather than estimated: **55 new modules in the graph, and a consumer binary 37MB larger — a 43% increase** on a minimal program that opens a store and writes one record. The Azure and Google Cloud SDK symbols are confirmed present in the linked binary, and dead-code elimination cannot remove them: the package registers all three schemes from one `init`, which is a live reference to each driver. So a service that writes to R2 and has never heard of Azure links the Azure Blob SDK, permanently, because of an import icelake made on its behalf.

Two arguments were originally recorded for taking it and both are weaker than they looked, which is worth writing down so the decision is not re-defended on bad grounds. "A library should not write to a process-global registry" cuts both ways: importing this package writes to the same registry, and writes *three* schemes into it instead of one, so the choice is not between mutating global state and not mutating it — it is between mutating it a lot and mutating it a little. And "the design documents assume iceberg-go's own S3 FileIO" is not load-bearing at all: these documents are ours, and a sentence in them is not a constraint on us.

What survives is the honest reason: at M4 the write path did not exist yet, and standing up a bespoke file IO — `Open`/`Remove` plus `Create`/`WriteFile`, over objects that are all small except the footer read above — at the same time as the write path itself would have meant debugging two new things against each other. That is a sequencing argument, not a design one, and sequencing arguments expire. **This is therefore an owned pre-release item in `PLAN.md`, not an open question: an S3-only file IO over `aws-sdk-go-v2`, which icelake already depends on, lands before the first tagged release.** Nothing about the public API depends on which implementation answers `s3://`, so it is a change with no caller-visible surface.

**Decision (2026-07-31, M4): everything about reaching the bucket travels on the context, except path-style addressing, which travels as a table property.** iceberg-go builds its S3 client from a `*aws.Config` stored on the context when there is one (`utils.WithAwsConfig`), and icelake puts its own there — the endpoint, the region, the caller's credentials, and the disabled request/response checksum calculation R2 requires. That covers every call, including the commit-time metadata write, which the catalog performs with a file IO built from the *table's* properties rather than the catalog's. The single exception is bucket addressing, which iceberg-go resolves from properties alone and from nothing else: `s3.force-virtual-addressing=false` is set on every table icelake creates, and topped up on reconciliation for a table that predates it. Storing that one flag durably is acceptable in a way storing the endpoint would not be — it says "address this bucket path-style", which is true of every endpoint icelake writes to, whereas an endpoint baked into a table's metadata would be a table remembering where it was first written and trying to go back there.

## Failure handling: what fails loudly, what retries, and what stops

**Decision (2026-07-30): a failed staging write fails the `Insert` call, synchronously, immediately.** Staging is the fast, local, reliable part of this system. If a single-row insert into a local SQLite file fails after the busy timeout has already absorbed ordinary lock contention, something is genuinely wrong — a full disk, a corrupt file, a revoked permission — and there is no honest way to keep pretending records are being accepted. `Insert` returns the error, the record is not accepted, and the caller decides what to do with a record it still owns. There is no in-memory fallback buffer for this case: an in-memory buffer for "the durability layer is broken" would be a silent downgrade of the exact guarantee the durability layer exists to provide.

**Decision (2026-07-30): a failed upload or commit retries with bounded exponential backoff, then stops and reports — but the batch is never dropped and is retried again on the next flush trigger.** Concretely: up to `FlushMaxAttempts` attempts (default 5), starting at `RetryBaseDelay` (default 1s), doubling, capped at `RetryMaxDelay` (default 60s), with full jitter — roughly half a minute of trying at the defaults. When the budget is exhausted, the batch stays sealed in staging with its `batch_key` intact, the table is marked stuck, and `OnFlushError` fires. The stuck batch remains at the head of that table's flush queue: nothing later commits ahead of it, so a table's snapshots never interleave out of order and a stuck table cannot half-progress. Each subsequent flush trigger starts a fresh attempt budget against the same batch, which the flush *time* threshold guarantees will arrive even if inserts stop entirely — so a table stuck on an R2 outage heals by itself when R2 comes back, without ever spinning hot against a dead endpoint. Nothing is lost in any of this: the records are in staging until a commit is confirmed, by construction.

**Built at M8, with the schedule stated exactly and one arithmetic correction to the paragraph above.** The delay *ceiling* after attempt n is `RetryBaseDelay` doubled n−1 times and capped at `RetryMaxDelay`; the delay actually slept is drawn uniformly from zero up to that ceiling, which is what "full jitter" means. A budget of N attempts therefore sleeps N−1 times, between the attempts and never after the last one — sleeping once more before reporting would delay the caller's error and the callback for nothing. At the defaults that is ceilings of 1s, 2s, 4s and 8s: **at most fifteen seconds of waiting per cycle, and around seven on average**, not the "roughly half a minute" this decision originally claimed. That number was the sum of five un-jittered delays, 1+2+4+8+16, which counts a sleep after the final attempt and ignores the jitter that halves the rest; correcting it here rather than leaving a wrong number in a design document. Nothing about the behaviour changes — the cycle was never the last chance a batch gets, only the last before the next trigger. Three consequences are part of the decision. `FlushError.Attempts` counts the attempts of the cycle it ended, not the batch's whole life, because each trigger starts a fresh budget and a number that only ever grew would say nothing about the budget it was measured against. The jitter's random source is a parameter of the schedule rather than a package-level call, precisely so the delay sequence is a calculation with an expected output — `TESTING.md` puts the backoff schedule on its closed list of assertable calculations, and a schedule whose only randomness came from the global generator could not be on that list. That parameter is what the unit test uses. It is not enough on its own for the layer above it, and the gap is worth recording because the first version of this work missed it: a test that watches the delays a *worker* asks for can only assert that each fell inside its own window, and every wrong schedule sharing the same cap passes that. So the source is also replaceable through a test-only package variable, exactly as the crash points are, and the end-to-end test pins the draw so the delays it observes are the ceilings themselves. Neither mechanism is public: jitter is not a knob on `Config`, because a caller has no use for one and a retry schedule that varies by deployment is a support problem rather than a feature. And `Flush`/`Close` absorb the retries *inside* a cycle and return only when the whole cycle has failed: reporting the first transient attempt to a caller would be a lie whenever the retry a moment later succeeded. The retry knobs are process-wide and deliberately not part of `FlushPolicy` — a per-table override exists because two tables genuinely batch differently, while how long to keep trying is a property of the endpoint every table in the process shares.

**Decision (2026-07-30): flush failures surface through an optional `OnFlushError` callback in `Config`, and the staging ceiling is the backstop for callers who ignore it.** This is deliberately the smallest thing that can work, and it is consistent with the observability decision below: icelake does not ship metrics, but a caller cannot be expected to notice that a table has quietly stopped committing for six hours. The callback hands over a small struct (`Namespace`, `Table`, `BatchKey`, `Records`, `Attempts`, `Err`) and the caller does whatever it already does with errors — log it, count it in its own Prometheus registry, page someone. It is invoked from a background goroutine, so it must not block and must not call back into the writer (the writer's lock is held on that path; re-entering it deadlocks). A caller who supplies no callback still cannot be silently starved forever: sustained flush failure fills staging and `Insert` starts returning `ErrStagingFull`, which is a hard, synchronous, unmissable signal on the caller's own hot path. `Flush(ctx)` and `Close(ctx)` also return flush errors synchronously, which is the path tests and shutdown sequences use.

**Built at M8, with the two things the paragraph above left to whoever wrote the code: when it fires, and what it is protected against.** It fires on exactly two events — a cycle that spent its whole attempt budget, and a batch that was quarantined — and on nothing else. In particular a cycle cut short by shutdown does *not* fire it: the budget was not spent, the table is not stuck, and the error is already travelling back to whoever called `Close` synchronously. Firing there too would page someone about a clean shutdown. The safety demands are met three ways, none of which asks the caller to be careful. The failure is recorded *before* the callback runs, so a slow callback cannot delay the error reaching a `Flush` or a `Close`. A panic inside it is recovered rather than taken as the process's last act — a caller's logging bug must not be able to kill a writer on a goroutine the caller cannot see — and swallowed, because there is no caller left to hand it to and the flush path has nothing to do differently. And the worker stops waiting for the callback as soon as the store's context is done, so a callback that never returns cannot hold a shutdown open; the goroutine it occupies is its own, which is the one thing icelake cannot take back. What is deliberately *not* absorbed is how long a well-behaved callback takes: the worker waits for it before looking at its queue again, so a callback that takes a second delays that table's next flush by a second. That is the whole content of the must-not-block rule above, and it is a stall the caller controls; the alternative, dispatching the notification and moving on, would trade it for notifications that could arrive out of order and outlive the writer they describe. **One correction to the sentence above:** re-entering the writer from the callback does deadlock, but not because "the writer's lock is held on that path" — no icelake lock is held while the callback runs. The reason is that the callback runs on the flush worker's own goroutine, which is exactly the goroutine `Flush` and `Close` wait for. **A second correction, made at the post-M9 completeness audit (2026-08-01), because an operator writing a monitoring runbook from the "exactly two events" sentence at the top of this paragraph would have been missing a page:** the callback fires on *three* events, not two, and this document contradicted itself two paragraphs apart — the quarantine decision immediately below has always described the third and has always said it is reported through `OnFlushError`, `Config`'s own doc comment has always named all three, and the code has always fired on all three. So the defect was this paragraph's opening summary and the places that had copied it — `PLAN.md`'s M8 bullet, and the `FlushError` doc comment in `internal/errdef`, which the review pass caught after an initial sweep had missed it because it phrased the same two-event list in different words. Nothing was changed in the code, and the "and on nothing else" flourish is what made a merely incomplete sentence into a wrong one. The `errdef` comment is not a fourth copy of the corrected list either: the enumeration now lives in exactly one place, `Config.OnFlushError`'s own doc comment, and the other sites point at it — a list that appears once cannot drift from itself, which is the real lesson of an error this document had already written down correctly two paragraphs below and still got wrong up here. The third event is the double fault: a batch that cannot be encoded, in a staging database that then refuses to record the quarantine. It is worth saying why that is genuinely a third case rather than a shading of the other two, since the whole value of the enumeration is that an operator can tell from the notification what state the table is in. Its batch was *not* quarantined — the mark did not take, so the quarantine flag is false and the rows are still ordinary sealed staged rows, which is exactly why the batch keeps its place at the head of the queue for the next trigger rather than leaving it. And its cycle did *not* spend its attempt budget: an unencodable batch is never retried inside its cycle, so the `Attempts` it reports is the attempt that met the encode failure rather than the whole budget, as the decision below already pins. The `Err` it carries is the *marking* failure, not the encode failure, and that is the distinction the runbook needs: this is the one flush error that says the local staging database is in trouble rather than the record or the network. Exactly one of its two halves can heal by itself, and which one is the part a runbook has to get right. The encode half never heals: the same rows, decoded by the same recorded shape, refuse to encode on every future trigger for as long as they exist, which is the whole premise of quarantining them. The *marking* half often will, because marking is an ordinary write to the local staging database under the worker's own context — a store context already canceled by a shutdown, or any transient failure of that database, is enough to produce this notification. So the batch holds the head of that table's queue only until the first trigger whose mark succeeds, and at that trigger the double fault collapses into an ordinary quarantine: the rows are marked, the batch leaves the queue, the table drains again, and nobody was involved. What always requires a person is the *rows*, not the table: no future trigger will ever commit them, and the notification that finally names the encode failure itself is the ordinary quarantine one, which only arrives once the mark takes. The one thing the original sentence got right is the exclusion it was drawing: a cycle cut short by shutdown still does not fire the callback, for exactly the reasons given above.

**Decision (2026-07-31, M8): quarantine is for batches that fail to *encode*, and an exhausted attempt budget never quarantines anything.** These are the two halves of failure this document assigns different endings, and it is worth saying plainly which is which, because "give up" could reasonably have meant either. An exhausted budget leaves the batch exactly where it was — sealed, staged, at the head of the queue, retried with a fresh budget by the next trigger — because the failure was about something outside this process and outside things come back. A batch that cannot be encoded is marked and taken out of the queue, because the same rows, decoded by the same recorded shape, fail identically forever, and a queue whose head can never succeed is a table that has stopped. Concretely, the encode side is: decoding a staged payload by the shape recorded for it, remapping or re-encoding it onto the current shape, hashing the batch, building the Arrow record, and writing the Parquet bytes. Everything else — reading staging, the durable seal, the upload, the catalog commit, the prune — is transient and retried. Three details follow from marking a batch rather than dropping it. The queue moves on immediately, rather than waiting for the next trigger as an exhausted budget does, because there is nothing left to wait for. The rows keep counting toward the staging ceiling, exactly as the quarantine decision above says, but they stop counting toward `Pending()`: they will never be flushed, and reporting them forever would turn a handful of unencodable records into a backlog that never drains — an operator finds them by their quarantine columns instead. And if the *marking itself* fails, the batch stays queued and the failure is reported like any other — `OnFlushError` included — because a batch that could not be marked has not been dealt with; its `Attempts` is the attempt that met the encode failure rather than a budget nothing spent, since an unencodable batch is never retried inside its cycle.

**Decision (2026-07-31, M8): a quarantine is reported to `Flush`/`Close` exactly once, to the first wait that covers the batch, even if the quarantine happened long before that call.** This is the half of quarantine that the decisions above left implied and that got it wrong in the first implementation, so it is written down as its own rule. A quarantined batch leaves the queue exactly as a committed one does, and the flush-error state a waiter reads is otherwise *generational* — a caller that arrives after a failed attempt is answered by its own attempt, which is right for a failure a retry can undo. Applied to a quarantine, that combination is a lie: the normal case is a background trigger meeting the bad batch with nobody waiting, and the next `Flush` would then return nil about records that will never be committed, contradicting what `Flush` promises. So the quarantine is held separately from the generational failure, survives every later success, and is handed to the first `Flush` or `Close` whose sequence covers it — the one already in flight if there is one, the next one otherwise. It is reported once and then cleared: the queue is healthy again, and failing every later call for the rest of the process's life over records no retry can save would turn a bounded loss into a permanently broken writer. A caller who wants the event rather than the timing wires `OnFlushError`, which is told independently and does not consume it.

### Background worker lifecycle

**Decision (2026-07-30): each `Writer` runs exactly two goroutines — a timer loop and a flush worker — both owned by the `Store`'s lifetime, and no goroutine icelake owns outlives `Store.Close`'s return.** (The qualifier "icelake owns" was added at M8, when the one exception appeared and it is the caller's own code: `OnFlushError` runs on a goroutine of its own so that a callback which never returns cannot hold a shutdown open, and such a callback keeps that goroutine after `Close` returns. Every goroutine icelake itself runs is gone; a callback that will not return is the one thing this library cannot take back, and pretending otherwise in this sentence would be worse than naming it.) The count is per *writer* and stays exactly two; a store with a cache configured in bucket mode also runs one goroutine of its own, which is the companion decision below and is deliberately not counted here — a sentence about what a writer runs would be wrong either way if it silently absorbed a goroutine no writer owns. This was previously implied by the non-blocking-flush and serialized-flush decisions above without ever being specified, which is exactly the kind of gap that gets improvised into shutdown hangs and goroutine leaks. Concretely:

- **The timer loop** owns the flush-interval trigger and the flush floor, driven by the injected clock. It is the "flush trigger will arrive even if inserts stop" guarantee the retry decision below leans on.
- **The flush worker** drains a queue of sealed batches in seal order, one at a time. Flush serialization is therefore a structural property of there being one worker — not a lock discipline someone has to maintain.
- **Background flushes run under a store-level context** created at `Open` — never under any `Insert`'s context, which has long since returned. That context is canceled only after `Close`'s drain completes or `Close`'s own `ctx` expires.
- **Retry backoff sleeps select against that store context** (via `Clock.Sleep`), so a shutdown interrupts a sleeping retry immediately rather than waiting out a 60-second backoff; the batch stays sealed in staging, safe for the next run, per the drain-timeout behaviour already decided in the API section.
- **`Writer.Close` in order:** under one hold of the writer's lock, reject further inserts (`ErrClosed`) and seal whatever is in memory; release the lock; stop the timer loop; wait for the worker to drain the queue bounded by `ctx`; then the worker exits. `Store.Close` closes every writer this way, then stops the retention sweeper, then closes the SQLite handles it opened — two in bucket mode, one in local-only mode — in that order, because staging is never closed while a worker might still prune it or a sweep might still be reading it.
- `OnFlushError` and the retry path run on the worker goroutine (hence the existing must-not-block, must-not-reenter rule); `OnAccept` runs on the caller's goroutine inside `Insert`, as already decided.

**Corrected at the post-M9 completeness audit (2026-08-01): the `Writer.Close` bullet above named the right steps in an order the code cannot have, and the bullet has been rewritten to the order the code actually runs.** It used to read "stop the timer loop, reject further inserts (`ErrClosed`), seal whatever is in memory, wait for the worker to drain the queue bounded by `ctx`, then the worker exits" — the timer stopped first. It is stopped third. Two of those steps are not separable and one of them cannot join them. Rejecting inserts and sealing have to happen under a single hold of the writer's lock, because a record accepted between them would land in a batch that nothing afterwards ever seals — `Close` has already sealed, and the timer is about to stop. Stopping the timer cannot be inside that same hold, because stopping it means closing its stop channel and then *waiting for the goroutine to exit*, and a tick already in flight is on its way to taking the very lock the closing caller would still be holding. Written the way the bullet described it, that ordering is a deadlock rather than a stylistic preference, and the fact that it can only be reached by an interleaving is what makes it worth writing down rather than leaving to be rediscovered by whoever next tidies this function.

The deeper reason the code's order is right, rather than merely the only one that runs, is that the timer is already inert before its goroutine is ever asked to stop. Every tick re-reads the closed flag under the same writer's lock before it seals or triggers anything, so the instant `Close` publishes that flag the timer can no longer produce a batch — including a tick that has already passed its own select and is queued on the lock, which is precisely the case a stop request cannot catch. Stopping the goroutine afterwards is therefore reclamation of something that has already stopped mattering, and doing it first would have moved the moment the timer stops *acting* later rather than earlier, since that same in-flight tick would then run to completion before `Close` reached the lock at all. What a caller needs from this sequence is not the order of its steps: it is that once `Close` has taken the writer's lock nothing further is accepted and nothing further is sealed except by `Close` itself, that the sequence number `Close` snapshots for its drain therefore covers everything this writer will ever produce, that the timer goroutine is provably gone before the drain begins, and that the drain is bounded by `ctx`. All four hold under the order the code runs, and the first two hold *because* of it.

**Decision (2026-08-01, M10): a store with a cache configured in bucket mode runs one further goroutine — the retention sweeper — owned by the `Store`'s lifetime rather than by any writer's, and the "exactly two goroutines" count above is per writer and is untouched by it.** The two numbers describe different things and it is worth saying which is which rather than leaving a reader to reconcile them: a writer runs a timer loop and a flush worker because both read one table's own state, and the sweeper reads no table's state at all. It enforces a bound on a directory every table in the process shares, so per-writer sweepers would be N goroutines enforcing one global size cap from N partial views of it — the same argument the staging ceiling already settled in the other direction, that the thing an operator wants bounded is total local disk. It is started by `Open` and stopped by `Store.Close` *before* the staging database is closed, for the same reason the writers are drained first: a sweep reads and deletes rows in that database, and a sweep still running against a closed handle is a shutdown-ordering bug rather than a race the code can absorb. It ticks on the injected `Clock` like every other timer here, at a fixed unexported interval, deliberately not configurable — a caller who wants a tighter bound sets a tighter bound, and a sweep interval is a symptom knob of the kind the busy-timeout decision above already refused. It does not run in local-only mode, where nothing is ever evictable, and it does not run without a `CacheDir`, where there is nothing to sweep. The "no goroutine icelake owns outlives `Store.Close`'s return" promise above now covers one goroutine more than it did.

**Decision (2026-08-01, M10): a sweep that fails reports to nobody, and that is the design rather than an omission.** The two things it could have done are both worse. Routing it through `OnFlushError` would break that callback's two most useful properties at once: its event list is exactly three, enumerated in one place precisely so an operator's runbook can be written from it, and it fires on the flush worker's own goroutine, which is what makes "must not block, must not re-enter" a rule with a reason behind it. A fourth event from a fourth goroutine would cost a documented enumeration and a documented contract to report something none of the other three resemble. Adding a second callback — an `OnCacheError` beside it — would put a whole new notification surface in `Config` for a failure with exactly one possible consequence. And that consequence is the argument: **an eviction that fails means the cache is larger than it was asked to be, and nothing else.** The file it could not delete is committed, so its records are in the table and in the bucket; nothing is at risk, nothing is stuck, no batch is waiting, and the next tick tries again. A failure that persists — a read-only disk, a permission that was changed underneath the process — ends as a full disk, which is a condition the operator's own host monitoring already owns and has always owned better than a library callback could. So the documentation says exactly that, in those words, and the sweeper stays silent.

**Decision (2026-07-31, M4): the trigger seals a batch *logically* — it hands the batch to the worker and swaps a fresh one in under the writer's lock — and the worker performs the durable seal, as the first thing it does with that batch.** This was left ambiguous by the decisions above, which say both "when a threshold trips, the current batch is sealed and a fresh empty batch is swapped in immediately" and "a batch is sealed durably before it is encoded, by stamping `batch_key` on exactly its rows in one transaction". Doing the durable half inside `Insert` would put a second fsync, plus a read of every payload in the batch, inside the caller's hot path and under the lock that orders every other insert — for no gain, because a batch that dies before its durable seal is simply replayed as unsealed rows and re-batched, which is a case the replay path has to handle anyway. What the trigger must do immediately, and does, is stop the current batch from growing: the boundary is decided at the trigger, and the worker records that same boundary durably a moment later. Everything downstream of the durable seal — the stored key's authority, the identical-batch rebuild after a crash — is unchanged, because all of it starts from `batch_key` being in the database.

**Decision (2026-07-31, M4): the timer loop lives beside the writer rather than in the flush package.** The decision above says "each `Writer` runs exactly two goroutines — a timer loop and a flush worker", and that is exactly what runs. The interval trigger and the flush floor both read the in-memory batch state — how long the current batch has been accumulating, when this table last sealed — which is the writer's own state under the writer's own lock, so the loop sits with it and the flush package is told what to flush rather than deciding when. Every tick also nudges the worker whether or not there was anything to seal, which is what turns "the time threshold guarantees a trigger arrives" into "a batch whose previous attempt failed gets a fresh attempt", without anything spinning against an endpoint that is down in between.

**Decision (2026-07-30): poison records are rejected at `Insert`, not discovered at flush.** They can genuinely happen — records are typed Go values, but not every value of a Go type is representable in the declared Parquet column. The real cases are narrow and known: a `string` field carrying bytes that are not valid UTF-8 (Parquet's String logical type requires validity), a decimal-typed field whose value does not fit the declared precision, and a string or binary value longer than the encoder's addressable limits (concretely `MaxUint32` bytes, per the canonical encoding's four-byte length prefix — see "The encoding, the descriptor, and the two hashes" above). So `Insert` validates exactly those constraints, per field, against the declared schema, before writing to staging, and returns an error naming the offending field. The record is refused at the boundary by the caller who supplied it — where the context to fix it exists — rather than poisoning a batch that then fails to encode forever. The batch quarantine described above is the belt-and-braces second line for anything this check misses: the batch is marked, excluded from replay, reported, and the writer moves on, so a doomed batch can never become an infinite retry loop. Both mechanisms are needed; the first makes the second almost never fire. **Corrected at M7, because this sentence overstated the second line and a wrong claim about a safety net is worse than no claim:** quarantine catches a batch that fails to *encode*, which is a strict subset of what this check catches. An invalid-UTF-8 string and an out-of-precision decimal both encode perfectly well, so for those two — the two cases a caller is actually likely to produce — the `Insert` check is the only thing standing between a bad value and a committed data file. Quarantine is a second line for the over-long case and for shapes the encoder itself refuses, and nothing more.

**Built at M7, with two details this decision left open.** *Where* the check runs: on the bound row, between reading the declaration struct into canonical values and encoding them — the last point at which a value is still associated with the column it was declared as, and the last point at which there is a caller holding the record. *What is underneath it*, stated correctly here because an earlier draft of this paragraph got it wrong: for two of the three cases there is nothing underneath it. The canonical encoding validates no value's domain by design, and the column adapter documents that it assumes this check already ran, so an invalid-UTF-8 string or an out-of-precision decimal that got past `Insert` would encode, stage, upload and commit in silence and sit in the data file as a value the column's own type says it cannot hold. Only the over-long case is refused a second time, by the encoder's four-byte length prefix. That asymmetry is deliberate — pushing UTF-8 validation or a precision check down into the encoder would put per-value policy inside the one component whose entire contract is that it moves bits deterministically — but it means this check is load-bearing rather than belt-and-braces, and has to be exhaustive rather than best-effort. And *what the check does not do*, stated so the three cases above are the whole contract rather than a starting point: it says nothing about a value's meaning — a wild timestamp, an unknown value in a string column an application treats as an enum, a negative quantity are all perfectly representable in their declared columns, and a library that guessed at them would be enforcing the caller's business rules from the wrong side of the boundary. Scale is not checked either, because a decimal's value is the unscaled integer the caller already scaled and only its digit count can be wrong.

## Error taxonomy

**Decision (2026-07-30): every error that crosses the public API boundary is matchable with `errors.Is`/`errors.As`; no bare `fmt.Errorf` string ever crosses it.** This is forced, deliberately, by `TESTING.md`'s ban on string-matching assertions: a fail-loudly promise that can only be tested by grepping a message is a promise the test suite cannot hold. Wrapping always uses `%w`, so underlying library errors (SQLite, aws-sdk, iceberg-go) stay reachable through the chain. The catalog, written down once so it is designed rather than accreted:

**Sentinels** (`errors.Is`): `ErrClosed` (insert after `Close`), `ErrStagingFull` (ceiling reached, record not accepted), `ErrTableInUse` (a second writer for a table that already has a live one in the same store — added at M4 with the enforcement described under "Catalog design" below), `ErrCatalogExists` (rebuild target exists and `Replace` unset), `ErrLocalOnly` (a `Store` method that requires a bucket, called against a store opened with `LocalOnly`; `Store.DrainSpool` is the only one, and catalog rebuild is deliberately not among them, per the local-only decision above — the store never built a client, so the honest answer is the mode rather than whatever a nil client would have said).

**Where each name lives.** Every type and sentinel in this taxonomy is declared once in the internal `errdef` package and re-exported as an alias by each public package that returns it — an alias is the same type, so `errors.Is`/`errors.As` behave identically whichever name a caller reaches for. The two public packages overlap rather than partition: four names are on `rebuild` alone (`ErrCatalogExists`, `RebuildPrefixKind` with its three constants, `RebuildPrefixError` and `RebuildStorageError`), deliberately *not* on the root package, because only rebuild returns them and a name on the root package should promise something the root package can deliver; and three names are on both, because both packages really do return them — `ConfigError` and `ConfigFieldError`, since rebuild's credential rules are deliberately identical to `Config`'s and a parallel pair saying the same thing about the same fields would be a second thing to keep in step, and `CatalogError`, since a rebuild that cannot open, write or move the catalog file it is rebuilding fails in exactly the way the write path fails against the same file. No other name in the catalog below appears on `rebuild` at all.

**Corrected at the completeness audit's fifth round (2026-08-01): the paragraph above used to read "that public package is the root one for all but four names" and then mention only `ConfigError`/`ConfigFieldError` as shared, which quietly asserted a clean split that does not exist.** `rebuild/errors.go` aliases `CatalogError` too, and has since the package was written, so the shared set is three names rather than two and the arrangement is an overlap rather than a partition. Nothing about the code is wrong and nothing needed to change there: an alias is the same type, `errors.As` matches through either name, and a caller importing only `rebuild` can match a `CatalogError` without importing the root package, which is precisely what the aliasing is for. What was wrong was the shape of the sentence, and the shape is what a reader builds on — someone auditing the taxonomy against the source would have counted the names, found one more on `rebuild` than the document allows for, and had to work out from scratch whether the extra alias was an oversight or a decision. It is a decision, so it is now written as one. One asymmetry inside that decision is worth naming while it is being written down, because it is the kind of thing that reads as an oversight later: `rebuild` aliases the `CatalogError` type but not the `CatalogKind` type or its constants, so a caller that has matched one and wants to branch on `.Kind` still has to import the root package for the constant names. Matching works from `rebuild` alone; naming the kinds does not.

**Typed errors** (`errors.As`), each carrying the identifiers a caller or test needs:

- `ConfigError` — wraps the `errors.Join` of one `ConfigFieldError{Field, Rule}` per violation, which is what makes the "all violations at once" decision testable per field rather than per message.
- `NameError{Kind, Value}` — namespace/table name validation, `Kind` saying which.
- `PoisonError{Table, Field, Reason}` — the per-field `Insert` rejection. `Field` is the declared column name, matching `EncodingError`'s. `Reason` was made a small exported enumeration at M7 rather than the free-form string this line originally implied — `invalid_utf8`, `decimal_range`, `too_long`, exactly the three cases the poison decision names — because a reason a test could only assert on by matching a prose fragment is a fail-loudly promise the test suite cannot hold, which is the same constraint that produced this taxonomy in the first place. Which value it was is carried in the message only, as with `CrossCheckError` and `EncodingError`.
- `DeclarationError{Table, Field, Kind, Err}` — a declaration struct icelake cannot turn into a table schema at all, refused before the two derivations can even be compared. `Kind` distinguishes five cases: a declaration type that is not a struct; one that derives to **zero columns** (which nothing downstream refuses — an empty schema creates a zero-column table, successfully and uselessly); one carrying an **unexported field** (the declared side turns it into a real column the caller has no way to tag, so left alone it surfaces as a misdirecting `FieldIDError` about a missing tag no tag can supply); one carrying a field whose **Go type is outside the declarable whitelist** (`unsupported_go_type`, added at M2 — see the type-set decision under "Batch identity" above, where a plain `int` deriving to a platform-dependent column type is the case that forced it); and any failure inside the three-call derivation chain itself — a malformed logical type, a non-numeric `fieldid`, an unknown `arrow` tag option — with `Err` carrying the wrapped arrow-go/iceberg-go error so it stays reachable through `errors.Is`/`errors.As`. `Field` names the offending Go field where one field is at fault and is empty when the problem is the struct as a whole. Added at M1: these were real fail-loudly paths that had been returning bare `fmt.Errorf`, which the testing policy's ban on message-substring assertions makes untestable.
- `CrossCheckError{Table, Column}` — the two-derivation startup check in `SCHEMA.md`, including its nested-struct rejection. Those two fields are the entire assertable surface **by deliberate choice**: which of the disagreements it was (name, nullability, unadaptable type, nested group, column present on one side only) is carried in the error message via an unexported field, and is not exported, precisely so that no test can come to depend on that wording. A test that needs to distinguish them should be distinguishing them by the column and the declaration under test, not by prose.
- `FieldIDError{Table, Field, FieldID, WantID}` — a declared field ID that violates the rules in `SCHEMA.md`'s "Field IDs at creation": a missing `fieldid` tag, or, when creating a table, an ID that does not equal that field's position in a **pre-order traversal** of the declared schema (`WantID` carries the number the traversal expects). Added because `iceberg-go` renumbers a new table's fields itself, in pre-order, and does so *silently* — a declaration that disagrees creates a table with no error raised whose IDs the declaration can then never match again. Pre-order rather than "declaration order" because a nested group's children consume IDs between the group and its next sibling; flat-only scoping means only flat structs reach this check today, where the two orders coincide.
- `ReconcileError{Table, Err}` — any failure of one table's startup lifecycle: creating it, loading it, diffing the declared shape against the live one, or committing the resulting change. `Err` wraps the underlying iceberg-go error, so a change the library itself refused as unsafe stays reachable through `errors.Is`/`errors.As`. It blocks exactly one table, which is what the per-table constructor makes free. Added at M4 alongside the loop it reports on; the field list previously named only `Table`.
- `CatalogError{Path, Kind, Err}` — a failure of the local `catalog.db` itself, added at M4 because it was a real hole: the staging database had a typed error for opening and closing it and the catalog database had none, so "the catalog file would not open" could only have crossed the boundary as a bare `fmt.Errorf`. `Kind` distinguishes `open`, `close` and — added at M6 with the rebuild path that produced the first one — `write`. It deliberately goes no further: a failure that concerns one *declared* table is a `ReconcileError`, because it must block that table alone rather than read as a broken catalog. `write` exists because rebuild is the one thing that writes rows into this file directly, from a bucket scan, with no declaration anywhere in sight, so its failures are about the file rather than about a table. Unlike `StagingError`, this one is never about lost data — the file it names is rebuildable from the bucket, so an operator meeting it has lost a cache.
- `StagingSchemaError{Table, FieldID, Kind}` — replay found staged rows whose recorded shape cannot be mapped into the current declaration by field id (see the fingerprint decision above). `Kind` was added at M2, because the documented case turned out not to be the only unmappable one and the three call for different operator actions: `field_removed` is the documented case (the recorded shape has a field id the current declaration lacks — staged data exists the current struct cannot represent); `field_required` is a field the current declaration requires that the staged row has no value for, either because the recorded shape never had it or because it recorded a null there (reachable when a table's first flush never succeeded, so no live schema existed to refuse the required column at reconciliation time); and `field_retyped` is a field id whose type differs between the two shapes, where reinterpreting the staged bytes would silently misread them. All three are refusals rather than best-effort mappings, because the only alternative to refusing is inventing data. Unlike `CrossCheckError`, whose discriminator is deliberately unexported, this one is exported: an operator's next action differs per kind, so a test asserting the right refusal fired has a real claim to make. **One correction to what that next action is, at the completeness audit's fifth round (2026-08-01), because the error's own message says the same thing for all three kinds and for one of them it is not available.** The message tells the operator to drain the table with the previous binary. For `field_retyped` reached through a widening that reconciliation *accepts* — the declaration goes from int32 to int64 while rows staged under the narrow shape are still waiting — opening a writer reconciles and commits the widening before it looks at what is staged, so by the time the caller holds the refusal the live column is already the wider type and the previous binary's narrower declaration is refused as a narrowing. Neither binary opens the table. The refusal itself stays right, since the alternative is reading the staged bytes as a type they were not written under; what changes is only the advice, and the way out on that path is the staging file, the same place `README.md` already sends an operator for rows that cannot be encoded. The other two kinds leave the live column untouched, so rolling back reconciles cleanly and the advice holds. `StagingSchemaError`'s doc comment in `errors.go` carries this note too, which is where a caller reading the godoc meets it; it is recorded and deliberately not asserted anywhere, because the claim is about what an operator should be told rather than about what the code does.
- `EncodingError{Table, Field, FieldID, Kind}` — a failure in icelake's own canonical record encoding, added at M2 alongside it. `Kind` distinguishes four: `unsupported_type` (a declared column whose type the encoding has no representation for), `value` (a value it cannot write for its declared column — the wrong Go type, a null in a required column, or a string or binary longer than the four-byte length prefix can address), `format` (stored bytes that do not conform — an unknown format version, a truncated or non-canonical payload or descriptor, an unknown type tag), and `empty_batch` (an attempted content hash over zero records). `Field` and `FieldID` name the column where one column is at fault and are empty when the problem is the payload or descriptor as a whole. Which malformation it was is carried in the message only, exactly as with `CrossCheckError`, so no test can come to depend on that wording. These reach a caller wrapped inside a `FlushError` when a batch cannot be encoded and is quarantined, which is why they are a typed part of the taxonomy rather than an internal detail.
- `StagingError{Path, Kind, Err}` — any failure of the local staging store, added at M3. This was a real hole: the write path's own durability layer had no typed error anywhere in this list, even though two decisions above promise loud failures from it — "a failed staging write fails the `Insert` call, synchronously, immediately" and "if a migration fails, startup fails loudly and stops immediately" — and neither promise was testable without grepping a message, which the testing policy bans. `Path` is the `staging.db` the failure is about, which is the file an operator has to have a backup story for — alongside any spool file the bucket has not confirmed, per the split recorded under "Why a separate file, not a shared one with the catalog" above. `Kind` distinguishes six, because the operator's next action differs for each: `open` (the file would not open, one of the required pragmas did not take effect — the durability guarantee rests on those, so a pragma that silently did not apply is a failure, not a warning — or the configured path is one the SQLite driver would misread, concretely a path containing `?`, which the driver reads as the start of DSN parameters and would silently truncate; that is refused rather than mangled, because a staging database opened at the wrong path is an empty one and an empty staging database is indistinguishable from a clean start with nothing to replay), `close` (the database did not close cleanly, which is its own kind because it means the opposite of an open failure to an operator: work *was* served and the final flush of it is in doubt), `migrate` (a migration failed; goose rolls it back and never records it, so the database is left exactly as the previous binary left it and stays usable by it), `read` and `write` (an ordinary query failure against an open, migrated database — a full disk, a revoked permission, a corrupt file), and `state` (the database is not in the state the operation requires: a row to be sealed is already sealed into another batch or quarantined, a row read back by id is gone, or a staged row names a fingerprint with no recorded descriptor). `Err` wraps the underlying SQLite, goose or query error so it stays reachable through `errors.Is`/`errors.As`.
- `FlushError{Namespace, Table, BatchKey, Records, Attempts, Err}` — already decided; the one that also travels through `OnFlushError`. `Attempts` was pinned at M8 to the attempts of the *cycle* the error ended rather than of the batch's whole life, since each flush trigger starts a fresh budget. `Err` is the underlying cause with nothing of icelake's own in between: a quarantined batch's `EncodingError` and a failed upload's SDK error are both reachable through `errors.As` from the error a caller was handed.
- `MirrorError{Namespace, Table, Err}` — added at M9 with the `OnAccept` callback it reports: the callback returned an error, and the record it concerns *was accepted*. It is in this list rather than being the caller's own error passed straight back because it is the one thing `Insert` can return that does not mean "this record is still yours", and a caller that could not tell it from `PoisonError` or `ErrStagingFull` would re-insert a record already on its way to the table. `Err` is what the callback returned, wrapped, so the caller's own values stay reachable.
- `RebuildPrefixError{Prefix, Kind}` — a prefix catalog rebuild refuses: the configured warehouse prefix itself, or one discovered beneath it. `Kind` was added at M6, alongside the two refusals the original one-case field could not express, because the operator's next action differs for each: `unparseable` is the documented case (a discovered prefix that does not parse as `<namespace>/<table>` — fix or remove the stray prefix), `no_metadata` is a discovered table prefix with no metadata file that parses (investigate a table whose metadata is gone), and `empty` is a warehouse prefix that yielded no tables at all (point the tool at the right prefix). All three are refusals rather than smaller answers, per the decision above.
- `RebuildStorageError{Bucket, Key, Err}` — a read against the warehouse bucket that rebuild could not complete: a listing, or a fetch of a metadata file it had just listed. Added at M6 because it was a real hole with no home: rebuild reads object storage directly and never opens a table, commits, or uploads, so a bucket that answered with an error — a wrong endpoint, a rejected credential, a missing bucket — had nothing in this list to be reported as. `Key` is a prefix for a listing and an object key for a fetch; `Err` is wrapped, so the SDK's own error stays reachable.

- `SpoolError{Kind, Dir, Path, BatchKey, Err}` — a failure of the local Parquet spool, owned by `internal/spool` and surfaced by the flush worker and the transition drain — the two paths that have a caller to answer. `Kind` distinguishes four, because the operator's next action differs for each and because they mean very different things about what is at risk: `write` (the bytes could not be put on disk — a full disk, a bad path, a permission; in bucket mode the flush fails and the batch stays staged, in local-only mode this is the only durable act there is and its failure is the whole flush's failure), `record` (the file landed but its row did not, so a file exists that no sweep will evict and no drain will find until the batch's own retry rewrites both), `mark` (the upload and the commit both succeeded and `committed_at` could not be set — the safe direction, since the file is merely unevictable), and `drain` (a backlog file could not be uploaded, committed or reconciled to, which blocks that one table's open exactly as a `ReconcileError` does). **There is deliberately no `evict` kind**, and the absence is recorded so it reads as a decision rather than a gap: a retention sweep has no caller to return to and, per the decision under "Background worker lifecycle" above, reports to nobody, so an `evict` kind would be a name in this taxonomy that no `errors.As` anywhere could ever match. This list is of errors that cross the public boundary, and that one does not cross it. `Dir` is the `CacheDir` and `Path` the file, so an operator meeting one is looking at a real path; `Err` is wrapped.
- `RecordError{Namespace, Table, Field, Kind, Detail}` — a JSON row the dynamic writer refuses, owned by the root package's dynamic codec and returned from `InsertJSON` and `Insert` on a `DynamicWriter`. It is the runtime-schema counterpart of `PoisonError`, and it is a separate type rather than a reuse because the two answer different questions: `PoisonError` says a well-typed Go value cannot live in its declared column, while this says the caller's JSON does not describe a row of this table at all — an unknown key, a missing required field, a null in a required column, a number that is not exactly representable in the declared type. `Kind` is a small exported enumeration for the reason `PoisonError.Reason` is one: the testing policy bans asserting on message text, so a refusal a test can only recognise by its prose is a promise the suite cannot hold. `Detail` carries what was seen, in the message only, exactly as `CrossCheckError` and `EncodingError` do. `SCHEMA.md` owns the full coercion table this enumerates the refusals of.
- `SchemaDocError{Table, Field, Kind, Err}` — a schema document `ParseSchemaDocument` will not accept: unknown keys, a duplicate namespace/table pair, a table with no fields, a duplicate column name, an unknown type spelling, a malformed `decimal(P,S)`. Field-ID violations inside a document are *not* this type and deliberately reuse `FieldIDError`, since the rule being broken is the same permanence rule a struct declaration breaks and a caller matching on it should not have to know which of the two declaration sources produced the table.

- `BatchError{Index, Err}` — added at M15 with `InsertBatch` and `InsertJSONBatch`: one row of a batch was refused, and this says which one. `Err` is the refusal that row earned on its own — a `PoisonError`, a `RecordError`, an encoding failure, a decode failure on a JSON line — wrapped, so every assertion a caller already writes about a single-row refusal keeps working through `errors.Is` and `errors.As` on the batch's error. It carries an index rather than the row itself because the caller still has the slice it passed in and the index is what turns "one of these is bad" into "this one is bad". It is deliberately *not* returned for the refusals that are about the batch as a whole rather than about any row in it: `ErrClosed`, `ErrStagingFull` and a staging failure come back unwrapped, exactly as `Insert` returns them, because there is no index to name and inventing one would say something false about which row was at fault.

- `IngestError{Kind, Record, Line, Table, Err}` — added at M16 with `IngestStream`: which record of a caller's stream the ingest loop stopped at, and why. It exists because a stream has a coordinate system nothing underneath it can supply — a `RecordError` is about a column, a `BatchError` is about a row of a slice the ingest layer itself built, and neither can say which record of the operator's own input that was. `Kind` distinguishes seven, because the next action differs for each: `grammar` (the bytes are not an envelope, or are not the start of a record at all), `envelope` (a decoded envelope with no table or no row), `unknown_table` (an envelope naming a table the caller opened no writer for, with `Table` carrying the name it asked for), `too_large` (a record over `IngestOptions.MaxRecordBytes`, refused rather than truncated), `read` (the caller's reader failed, with no record at fault), `refused` (the table's own writer refused the row, with that refusal in `Err`), and `write` (a failure about neither the record nor the stream — a staging store that failed, a writer that closed — reported against the record the failing write started at, because that is the only position there is). `Record` and `Line` are the two coordinates the format decision above records the rule for. `Err` is wrapped, so every assertion a caller writes about a single-record refusal keeps working through it.

- `ClickHouseError{Namespace, Table, Target, Column, BatchKey, Records, Kind, Err}` — added at M17 with the ClickHouse mirror it reports on, and it is a separate type from `FlushError` for the reason the mirror's own decision above gives: the two mean opposite things about what a caller should do next. A `FlushError` says the batch is still in staging and will be retried; this says the batch is on its way into the lake exactly as it should be and only the disposable index fell behind, so a caller that treated the two alike would be acting on a problem that is not theirs. `Kind` distinguishes four, because the operator's next action differs for each: `connect` (the server could not be reached or would not answer — wait, or fix the address; nothing is lost and the next flush tries again), `schema` (a `CREATE DATABASE`, a `CREATE TABLE`, an `ALTER ... ADD COLUMN` or the `system.columns` read failed — the same instruction, since the server is the thing that is unwell), `conflict` (a live table's columns disagree with the declaration in a way the add-only rule refuses, or a namespace or table name cannot be mapped to a mirror table injectively — the operator rebuilds the mirror or renames, and this is the one kind that is a statement about configuration rather than about reachability, which is why it is also the one kind `OpenWriter` returns), and `insert` (the batch insert itself failed — the flush proceeded, the lake is unaffected, and the mirror is missing that batch until it is rebuilt). `Target` is the ClickHouse object the failure is about, spelled as the operator would type it — `<database>.<table>`, or the database alone — so an error is about a real name rather than about a Go field; `Column` names the column for a `conflict` and is empty otherwise; `BatchKey` and `Records` identify the batch for an `insert` and are empty and zero otherwise. `Err` is the driver's own error, wrapped, so a rejected credential or a refused connection stays reachable through `errors.Is` and `errors.As`. It travels through `Config.OnClickHouseError` on the flush path and is returned from `OpenWriter` for the `conflict` kind only.

New failure modes must extend this list in the same commit that introduces them — an error type is part of a feature's surface, not a follow-up. That rule is why the three types and the sentinel above are in this list from M10, before any of them exists in code: the milestone that writes them is the milestone that would otherwise be free to return a bare `fmt.Errorf` and leave the taxonomy to a follow-up that never comes.

## Catalog design: local, real, and disposable — not stateless, not a server

The original instinct behind this project was that the catalog (whatever tracks "which metadata file is current" for a table) shouldn't be a durable dependency at all — ideally derivable purely by reading the bucket, so that losing the catalog is a non-event.

That instinct turned out to be half right. Investigated directly against `apache/iceberg-go`'s source:

- iceberg-go **does** ship a catalog mode that determines "current" purely by listing a table's `metadata/` directory and picking the highest version-numbered `metadata.json` — no external database at all (its Hadoop/filesystem catalog, `catalog/hadoop`).
- But in the pinned version it **cannot be pointed at object storage at all.** Re-verified at M0, and this is a correction to an earlier draft of this document: there is no `allow-unsafe-commits` escape hatch and no "not atomic and can lose data with concurrent commits" warning anywhere in `catalog/hadoop` — the catalog simply rejects any warehouse whose URL scheme is not `file://` (or a bare local path) with `hadoop catalog: unsupported warehouse scheme %q, must be file:// or a local path`, and its whole implementation is built on `os.ReadDir`/`os.Rename`. The underlying reason the ecosystem avoids this pattern on object storage is unchanged and still worth recording — rename emulation there is a check-then-act race under concurrent commits, which is why REST catalogs backed by a real compare-and-swap database became the recommended path — but as far as icelake is concerned the question is settled harder than the earlier draft suggested: this is not an unsafe option to be declined, it is not an option. A proposal exists upstream (Iceberg dev mailing list, July 2026) to build a real object-storage-native catalog using conditional `If-Match`/`If-None-Match` PUTs — which R2 does support — but it is proof-of-concept only, not shipped in any implementation as of this writing.

**Decision (2026-08-01, M10): local-only mode opens no catalog at all — which reverses the reach of the sentence above, "this is not an unsafe option to be declined, it is not an option," without reversing its content.** That sentence is about a `file://` Iceberg warehouse and it is still exactly right on its own terms: the pinned Hadoop catalog refuses any scheme but `file://` and is built on `os.ReadDir`/`os.Rename`, so it cannot be pointed at a bucket — and pointing it at a local directory, which is what a "no-bucket mode" would naively reach for, produces a real Iceberg table whose every manifest records a local path, which is not movable to a bucket afterwards without metadata surgery Iceberg does not offer and icelake would then have to own. What the sentence was carrying by implication, and what is now false, is the broader reading: that a store reaching no bucket is out of the question. Local-only mode is exactly that store, and it works by having **no table**, not by having a local one. No `catalog.db` is opened, no `metadata.json` is written, no snapshot exists, and the first catalog commit those records ever see is the one the transition drain makes after a bucket is configured; until then the spool file is the durable record and staging prunes against it. The cost is the one to be blunt about rather than to discover: **a local-only store's data is not an Iceberg table**, so none of schema evolution, snapshot isolation or engine portability applies to it yet, and a reader pointed at the cache directory is reading Parquet files rather than a table. That is a real downgrade, taken deliberately, in exchange for not maintaining a second catalog implementation and not inventing a path-rewriting migration.

**Decision: use iceberg-go's built-in SQL catalog backend directly** (`catalog/sql`, `database/sql` + `uptrace/bun`), backed by an embedded SQLite file, `catalog.db` (preferring a pure-Go driver such as `modernc.org/sqlite` to avoid a cgo dependency where practical) — kept as its own separate file from the staging store's `staging.db` (see "Local write-ahead durability" above), since the two have opposite disposability rules. This was revised away from an earlier draft of this design that proposed a custom `bbolt`-backed `Catalog` implementation — once it was clear iceberg-go already ships a working SQL catalog backend, writing and maintaining a second, custom one against a KV store bought nothing: it's strictly more new code to own for no capability gained. Use what iceberg-go already gives you.

`catalog/sql` manages its own schema entirely on its own — it creates its tables itself (via its `init_catalog_tables` property, which defaults to true, or the explicit `CreateSQLTables`/`DropSQLTables` calls it exposes) — so `catalog.db`'s schema is never touched by `goose` or any migration tooling icelake owns; that's internal to iceberg-go, not icelake's concern.

Construction was verified at M0 and both routes work. The direct one, which icelake uses because it lets icelake own the `*sql.DB` handle and therefore its lifecycle: `sql.NewCatalog(name string, db *sql.DB, dialect sql.SupportedDialect, props iceberg.Properties) (*sql.Catalog, error)`, with `dialect` set to `sql.SQLite` and `db` opened against `modernc.org/sqlite` under its registered driver name `sqlite`. The registry route also works — `catalog.Load(ctx, name, props)` with `props["type"]="sql"`, plus the package's own `sql.driver` and `sql.dialect` keys and a `uri` (an optional `sql://` prefix is stripped) — but it opens the database itself, which is the reason icelake does not use it.

This is genuinely correct and fast for icelake's actual topology, which is single-writer-per-table everywhere it has been examined (a long-running archival collector, a batch trade-decoder) — there is no concurrent-commit race to worry about in normal operation, because there is never a second concurrent writer to a given table. Concurrency safety in this design's tests and reasoning is scoped to single-writer only; it is not a goal to make icelake safe under concurrent writers to the same table.

**What actually breaks if that assumption is violated — stated plainly, since nothing enforces it.** Real distributed locking stays out of scope, but "out of scope" should not mean "undescribed." Two processes writing the same table, each with its own `catalog.db`, have no shared compare-and-swap anywhere: each one's SQL catalog does a correct CAS against *its own file*, which the other has never heard of. Both therefore load a table state, append a snapshot, and write a new `metadata.json` derived from a base the other has already moved past. The last writer to write a given metadata version wins and the other's snapshot is gone from the table's history — silent data loss at the metadata layer, with no error raised by either process. The content-hash file keying above changes the shape of that loss in one specific, useful way: because the two writers' batch boundaries will almost certainly differ, their data files get different names, so the *bytes* survive in the bucket as orphaned data files even when the snapshot referencing them is lost. That is recoverable by hand in principle (the objects are there and are valid Parquet), but icelake ships no tool that does it, and reconstructing which orphans belonged to a lost snapshot is not something this design describes — see the orphaned-file entry under "Open questions" below. In the one case where the two writers stage *identical* batches (two processes replaying the same `staging.db`, which is itself a misconfiguration), the identical hash makes the duplicate upload a harmless overwrite of the same key — the single case where content-hash keying actively saves you rather than merely limiting the damage. A shared `staging.db` between two processes is separately unsafe regardless of the catalog: both would replay the same rows and commit them twice. The practical rule this reduces to is unchanged and worth stating as an operational requirement: one process, one `staging.db`, one `catalog.db`, one writer per table.

**Decision (2026-07-31, M4): the last clause of that rule is enforced within a process, because there it is a map lookup.** Everything above is about two *processes*, which is genuinely undetectable from inside either one. Two writers on one table inside a single `Store` are not: the store already holds every writer it opened, so `OpenWriter` refuses a table that already has a live writer with `ErrTableInUse`. This is worth enforcing rather than documenting because the failure is nastier than the two-process one and arrives sooner. Both writers claim the same table's replayed rows and batch newly staged ones independently; both commit through the *same* catalog, so the compare-and-swap works exactly as designed and one of them loses — and having lost, it keeps trying to commit against a base the other has already moved past, on every attempt, for the life of the process. A table that can never commit again, with its records accumulating in staging behind it, from a mistake as small as opening a writer twice in two subsystems of one program. Closing a writer releases its table, so deliberately reopening one — to change its declaration, say — still works.

**Disposability, not statelessness, is the actual property being preserved — and it applies to the SQL catalog file exactly as it would have to bbolt.** The catalog database is not treated as a precious, must-never-lose asset — it is treated as **rebuildable**: a deliberate, explicit recovery tool mirrors the same approach iceberg-go's own Hadoop catalog uses for reading (list each table's `metadata/` directory, parse the version number out of each filename, pick the highest) to reconstruct "what's current" per table from R2 alone, then repopulates the SQL catalog's rows from that scan. "Mirrors" rather than "reuses": as noted above, `catalog/hadoop` is local-filesystem-only in the pinned version, so its code cannot be pointed at a bucket — but its filename parsing is the specification worth copying. Verified against a real table written through the SQL catalog: metadata files land at `<table>/metadata/NNNNN-<uuid>.metadata.json`, with `NNNNN` a zero-padded five-digit sequence starting at `00000` and incrementing on every commit, which is the same pattern `catalog/hadoop` already recognizes as the Java/PyIceberg naming form. No `version-hint.text` is written on this path, so the rebuild tool must not depend on one. The distinction that makes this safe where the live listing-based catalog mode is not: rebuild is an operator-invoked, writer-stopped recovery action, not a live concurrent-commit mechanism — there is no race to lose, because nothing else is writing while it runs. **This property must not be taken on faith — it needs an explicit end-to-end test that deletes the catalog database and proves the rebuild tool restores correct, queryable state from the bucket alone.** See `TESTING.md` for how this is validated.

**Decision (2026-07-27): rebuild discovers tables by listing the bucket, not from a caller-supplied list.** The rebuild tool does not ask the caller "which tables should exist" — it lists the warehouse prefix itself and infers namespaces/tables from the directory structure, so that no side-channel state about "what should exist" lives anywhere outside the bucket. This is the more automatic, more generic option, chosen deliberately over the simpler "caller tells the tool its own table list" alternative, and it has two direct consequences: the warehouse key layout (below) becomes load-bearing correctness, not just a naming nicety, and R2's list-operation consistency guarantees (read-after-write behavior for newly created prefixes/objects) need explicit verification before this recovery path is trusted, rather than assumed — now specified concretely as the one-off, manual, never-in-CI procedure in `TESTING.md`'s "Real R2 verification" section, whose results get recorded in this document's open questions once run.

**Decision (2026-07-30): the rebuild tool ships as both an importable Go function and a thin CLI binary that wraps it.** The real implementation is a library function; the binary is a `main` that parses flags and calls it, with no logic of its own. This is the ordinary Go convention and it costs almost nothing, while covering both consumers that actually exist: an operator recovering a host by hand wants a command, and a service that wants to self-heal on startup (or a test — `TESTING.md` scenario 3 is exactly this) wants a function call, not to shell out to a binary it then has to locate. Per this repo's layout (`PLAN.md`), the library is the repo's root module and the binary lives under `apps/` as its own nested module, rather than in a `cmd/` directory inside the library module.

```go
// Illustrative shape.
func Rebuild(ctx context.Context, opts RebuildOptions) (*RebuildReport, error)

type RebuildOptions struct {
    Endpoint        string
    Bucket          string
    WarehousePrefix string                  // the prefix to list; discovery starts here
    Region          string                  // defaults to "auto", as in Config
    AccessKeyID     string                  // or…
    SecretAccessKey string
    Credentials     aws.CredentialsProvider // …a pre-built provider, same rule as Config
    CatalogPath     string                  // target catalog.db to write
    Replace         bool                    // required if CatalogPath already exists
    DryRun          bool                    // discover and report, write nothing
}
```

`RebuildReport` carries what was found, what was chosen, and what was passed over — the namespaces that yielded at least one table; per table, the metadata file selected for it, the sequence number parsed out of its name, how many snapshots it lists and whether its row was actually written; and a list of everything discovery stepped over with a reason for each. It also echoes back the bucket, prefix and catalog path it acted on, and whether the run was a dry one, so a report pasted somewhere else is self-describing. All of that exists so an operator can eyeball the result before trusting it, and so `DryRun` has something to return. The credential rules are deliberately identical to `Config`'s (exactly one of the two forms, no ambient fallback, region defaults to `auto`), because a recovery tool reaching for the wrong bucket's credentials is a worse version of the same problem. Two safety behaviours are part of the decision rather than implementation detail: the tool refuses to overwrite an existing `catalog.db` unless `Replace` is set, and it fails loudly on any prefix under the warehouse that does not parse as a valid `<namespace>/<table>` pair (see the naming rules below) instead of skipping it silently — a table that discovery cannot see is exactly the failure this tool must never have.

**Decision (2026-07-31, M6): a table is registered by writing the catalog's row directly, because the SQL backend has no other route that does not damage the table.** This was the one mechanical unknown left in the paragraphs above — "repopulates the SQL catalog's rows from that scan" says what must end up true without saying which call makes it true — and the answer, checked against the pinned `iceberg-go`, is that no call does. `catalog/sql` exposes no `RegisterTable`; the method exists on the Glue, Hive and REST backends and simply is not on this one, nor on the `Catalog` interface. Of what it does expose, `CreateTable` and `CommitTable` both *write a new metadata file* before touching a row — which would discard the table's history in the first case and add a commit to a table nobody is writing to in the second, and both would mean a recovery tool modifying the very bucket it is recovering from. So rebuild writes the row: one parameterized `INSERT` into `iceberg_tables` naming the catalog, the namespace, the table, the type and the metadata location it discovered. `previous_metadata_location` is left null deliberately — it is the catalog's record of what the last commit replaced, and a rebuild replaced nothing; inventing a value would claim a history this database never saw, and the compare-and-swap the next commit performs reads `metadata_location` only. This is a real coupling to a library's internal storage shape, taken knowingly and confined to a single statement in `internal/catalogdb` so that an upgrade which changed that shape breaks in one obvious place. Two things make it acceptable rather than merely necessary: the catalog still owns its own schema (the tables are created by iceberg-go's own constructor, exactly as before, and nothing icelake owns migrates this file), and the claim is verified end to end rather than by inspection — the rebuilt catalog is proven both readable *and writable*, by a test that appends further records through it and watches the commits land on the same table.

**Decision (2026-07-31, M6): the catalog name, the catalog open path and the S3 client construction move into internal packages shared by the writer and the rebuild tool.** `internal/catalogdb` holds the catalog name — which is part of every row's primary key, so a rebuild that wrote a different one would produce a database the writer opens and finds empty, the failure mode most likely to look like success — plus the DSN pragmas and the row insert above. `internal/s3cfg` holds the `aws.Config` construction and the credential-form rule. The rule being identical between the two entry points is already a decision above ("the credential rules are deliberately identical to `Config`'s"); one implementation is how that stays true rather than being re-asserted. Nothing about this is visible to a caller: `Config` and `RebuildOptions` keep their own fields and their own godoc.

**Decision (2026-07-31, M6): the whole catalog is built in a temporary file beside its destination and moved into place by one rename.** This is a correctness requirement, not tidiness, and the hazard it closes is the nastiest one in this milestone. Each row insert is its own transaction, so a rebuild that died partway — a signal, a full disk, a lost connection — would otherwise leave a catalog holding some of its tables and not the rest, which is *worse than having no catalog at all* and worse in a way nothing reports. The next writer finds the missing table absent, creates it, and starts a **second metadata chain** for it under the same prefix, numbered from `00000` — below the surviving chain's sequence. A later rebuild, doing exactly what it is supposed to do, then picks the higher-numbered *old* chain, and every record written since the fork becomes unreachable with no error raised anywhere. This is the same class of silent loss the empty-prefix refusal above exists to prevent, arrived at from inside the tool rather than from a mistyped argument. A rename is the one filesystem operation that cannot half-happen, so the partial state is made unrepresentable rather than detected. Wrapping the inserts in a single transaction was the other candidate and is weaker: it closes the crash case but not a write that fails after the catalog is already in place. The destination's write-ahead siblings are removed just before the rename — a rename replaces the database file and nothing else, and a stale log left beside a fresh database is the same recovery hazard by another route — and the destination file itself is never removed, so there is no moment at which the path holds nothing. It follows that a failed or interrupted run leaves either the complete new catalog, the old one, or nothing, and that is asserted directly by tests that cancel a run and that block its final rename. One clause of honesty about "the old one": a run that dies in the narrow window *between* removing those sidecars and completing the rename leaves the previous catalog minus a write-ahead log. That is a real ordering gap and it is stated rather than glossed, but it is harmless for the same reason the temporary file is self-contained — every catalog this code writes is closed cleanly, which checkpoints the log into the database and deletes it, so the sidecars are absent in the normal case and carry nothing the database does not already have in any case this build can produce. Nothing about the writer's own catalog handling changes; it opens WAL mode as it always did. The CLI wires `SIGINT`/`SIGTERM` to context cancellation for the same reason: an operator's Ctrl-C should end the scan promptly, and it is safe to do so at any point.

**Decision (2026-07-31, M6): three refusals, and the exact interaction between `DryRun` and the existing-catalog check.** The two safety behaviours above are joined by a third, and one of them is narrowed. A warehouse prefix that yields **no tables at all** is refused rather than reported as an empty success: it is almost always a mistyped prefix or the wrong bucket, and the alternative is handing back an empty catalog that reports success, after which the next writer would create fresh tables over tables that already exist — the same silent snapshot loss the concurrent-writer discussion above describes, arrived at by a different road. A discovered table prefix with **no metadata file that parses** is refused for the same reason: registering nothing would silently leave a table out. Everything genuinely incapable of being a table is reported instead of refused, and the report says so — an object sitting directly at the warehouse or namespace level (a table is always a prefix with more beneath it), and a namespace prefix with no table prefixes under it. "Latest **valid**" is enforced by stepping down: the highest-numbered metadata file that does not parse is recorded in the report and the next-highest is tried, so a half-written file at the top of the sequence is recoverable rather than fatal. And `DryRun` deliberately does **not** trip the existing-catalog refusal: that refusal exists to protect a file from being overwritten, a dry run writes nothing, and making it refuse would break the one sequence an operator actually wants — look at what would be registered, then decide whether to replace. `Replace` means replace: a whole new catalog is built from the scan alone and moved onto the path, never merged, because a merge would keep rows for tables the bucket no longer has and the bucket is the only authority here. Setting `Replace` alongside `DryRun` is accepted and inert, since there is nothing for permission-to-overwrite to permit.

### Warehouse key layout

Given discovery depends on it, the layout must be a single, strict, consistently-applied convention across every adopting service — not a per-service choice: `<configured-prefix>/<namespace>/<table>/...`, exactly two path segments (namespace, then table) between the configured warehouse prefix and each table's own Iceberg-managed `metadata/`/`data/` directories. Listing the prefix with a delimiter yields namespaces; listing one level deeper within a namespace yields its tables — generically, for any adopting service, with no per-service special-casing in the discovery logic. Namespace naming should map to whatever a service already calls itself, so two services' tables can never collide by construction.

**Decision (2026-07-30): icelake validates namespace and table names itself, at declaration time, and fails loudly on an invalid one.** Leaving this as an undocumented convention would mean every adopting service independently rediscovers that a slash in a table name silently creates a third path segment and makes the table invisible to the rebuild tool's two-level discovery. The rule: each of `Namespace` and `Table` must match `^[a-z0-9][a-z0-9_]*$` and be at most 63 characters. Lowercase letters, digits and underscores only; must start with a letter or digit; no slashes, dots, spaces, hyphens or uppercase. The check runs in `OpenWriter` before anything is derived, opened, created, reached for over the network, or changed in the store, and rejects with an error naming the offending value — never normalizes it, since silently rewriting a caller's table name is how two services end up sharing a table. The same rule is applied in reverse by the rebuild tool when parsing discovered prefixes.

**Corrected at the post-M9 completeness audit (2026-08-01), because the sentence above used to claim the check "runs in `OpenWriter` before anything else happens" and that is literally false.** Two refusals do run ahead of it. `OpenWriter` first asks whether a writer can be opened at all — the store is closed, or this table already has a live writer — and then validates any per-table flush policy it was handed. Neither of them opens a file, derives a schema, loads a table, issues a request, or writes anything down: the first is a map lookup and a flag read under the store's own lock, the second is arithmetic over configuration values the process already holds. So the property the original sentence was reaching for is intact and is now stated as what it actually is, which is also the only part of it a reader can build on: an invalid name is judged before anything exists that would have to be cleaned up, so a rejected name leaves behind no namespace, no Iceberg table, no staging row, no registered writer and no network call. The overreach has been dropped rather than repaired in the code, because the two checks that precede it are in front of it on purpose and moving them would be a regression. A closed store has to answer `ErrClosed` and a busy table has to answer `ErrTableInUse` — the sentinels a caller matches on — instead of answering with whatever the first resource they touched happened to say, which is the whole reason that check exists and is documented at its own definition; a caller that shut its store down and then made a typo is better served by being told the store is shut down. The ordering is only observable at all when a call is wrong in two ways at once, which is exactly the case where naming the more fundamental fault first is the more useful answer.

**Amended at M11, because the first of those two refusals stopped being a question and became a claim, and the sentence above says "writes anything down" about it.** `OpenWriter` now *takes* the table's slot in the store's writer registry at that first step rather than looking at it, holds it across the spool drain and the table's whole startup lifecycle, and hands it to the writer at the end without ever letting go — so the table has exactly one owner from the first line of the call. The reason is in the spool decisions above: a writer's open drains that table's backlog, `Store.DrainSpool` drains the same backlog, and the two must not both be walking it. Merely checking left every step after the check unguarded, and the version that claimed only the drain left a gap between releasing it and loading the table that a concurrent drain fell into about one run in fifteen — both times surfacing as a raw SQLite constraint error rather than a sentinel, which is the shape of failure the error taxonomy exists to prevent. What that costs the paragraph above is one clause: the first step does now write something down, in memory, in this process. Everything else it claimed survives exactly — no file is opened, no schema derived, no table loaded, no request issued — and a rejected name still leaves behind no namespace, no Iceberg table, no staging row, no registered writer and no network call, because a failed open releases the slot on its way out.

The reasoning behind each restriction is mechanical, not aesthetic: slashes and dots break the two-segment key layout that discovery depends on; case is excluded because object keys are case-sensitive while much of what surrounds them (developer file systems, some SQL identifiers, human memory) is not, so allowing both `Fills` and `fills` creates two tables that look like one; hyphens are excluded because they are not valid unquoted SQL identifiers in most engines that will query these tables; 63 characters matches the identifier limit most SQL engines already impose and keeps the composed object key comfortably short.

## Unifying the "hot store + separate cold archive" split that motivated this project

A clarification worth stating explicitly, since it changes what "migrating a service to icelake" actually means: in the motivating archival case, event data lives in two separate places today — a SQLite projection table (queryable, "hot") and a parallel `.msgpack.zst` archive file per source (the full raw payload, kept *outside* the database purely for compression and to avoid keeping cold bulk data on the hot path). The trade-decoding case has the same shape — a decoded trade table in SQLite, plus separate `.msgpack.zst` archives of the raw provider responses.

icelake is meant to collapse that split, not replicate it. A Parquet/Iceberg table can hold a raw-payload column (JSON, text, or binary/blob) directly, alongside its structured/typed columns, and Parquet's own per-column ZSTD compression already delivers the "don't keep this hot and uncompressed" property that the manual separate-archive-file pattern exists to provide today. Adopting a service into icelake should be evaluated as replacing *both* of its current storage mechanisms (the typed SQLite table and the hand-rolled archive files) with one Iceberg table, not just the typed part. This is reflected in the test schemas in `TESTING.md`, which deliberately include a raw-payload-bearing example table alongside a pure-scalar one.

## Configurable settings

The following must be explicit, caller-supplied configuration, not hardcoded constants, specifically so the same code path can run cheaply in tests/dev and correctly in production:

- **ZSTD compression level.** Low/fast (e.g., level 1, well below the zstd default of 3) for local development and test runs, where iteration speed matters more than ratio; a high/max level (e.g., 19+) for production, where storage cost and compression ratio matter more than CPU spent compressing. This is a pure parameter change, never a code-path change.
- **Batch flush size threshold** (e.g., max buffered records or max bytes before a flush is forced).
- **Batch flush time threshold** (maximum time a batch may sit un-flushed even if the size threshold hasn't been hit — i.e., a "minimum upload cadence" / "time to sync" setting).
- **Staging ceiling** (max staged-but-uncommitted records and bytes before `Insert` refuses new records).
- **R2 endpoint, bucket, warehouse prefix, region, and credentials** — either two explicit key strings or a pre-built `aws-sdk-go-v2` provider.
- **Local file paths** for `staging.db`, `catalog.db`, and the spool's `CacheDir`.
- **Retry policy** (max flush attempts, base and max backoff delay) and the optional flush-error callback.
- **The local Parquet spool and its retention bounds** (`CacheDir`, `CacheMaxBytes`, `CacheMaxAge`). These are configuration rather than constants for a reason the others do not have: how much local disk a deployment can spare for a convenience is not something a library can guess, and the same code path has to serve a test that keeps two files and a workstation that keeps ten gigabytes.
- **Local-only mode** (`LocalOnly`). A boolean rather than an inference, per the decision above.

All of these are fields of the one `Config` struct written out in "Public API surface" above, which is the authoritative list; this section is the rationale for why they are configuration at all rather than constants. Every field in the local-state, object-storage, batching and resource-bound groups is required and rejected at zero — there are no silent defaults for the knobs that shape how much data sits where — subject to the local-only matrix above, which is the one thing that re-scopes what "required" means, and by requiring the *absence* of a field rather than by defaulting it. The spool's four fields are the deliberate exception to the no-zero rule: `CacheDir` empty means no spool, which is a real choice and not a missing one, and the two bounds are refused unless there is a `CacheDir` for them to bound.

**Guidance on the three knobs that are actually hard to pick, written here because "it is configuration" is not by itself help.** *Upload cadence* is not a separate mechanism and never was: "upload every thirty minutes or every gigabyte, whichever comes first" is `FlushInterval: 30 * time.Minute` with `FlushMaxBytes: 1 << 30`, and the flush trigger already means whichever trips first. *The staging ceiling* should be at least two to three times `FlushMaxBytes`: a batch has to be able to fill while the previous one is still uploading, and a ceiling below that refuses records for a reason the caller cannot act on. *Memory* is the one people get wrong, because the ceiling paragraph above says the ceiling bounds it and that is true of the steady state rather than of the moment that matters: during a flush, one batch exists as staged rows, as an Arrow record, and as an encoded Parquet buffer more or less at once, so plan for roughly three to four times `FlushMaxBytes` of headroom while a flush is in flight, and keep `FlushMaxBytes` at or below 256 MiB unless the deployment has been measured. The spool does not add to that figure — it writes the same buffer the upload sends — but `AddFiles` re-reading the object does, as the commit-path decision above already records.

Test configuration should default to small size/time thresholds (so tests can trigger multiple flushes/snapshots quickly without writing large volumes of data) and a low compression level; production configuration should default the other way. See `TESTING.md`.

## Testing strategy (summary — see `TESTING.md` for the full design)

End-to-end validation runs against a local **Chainguard MinIO** container as a stand-in for R2 (S3-compatible, no real Cloudflare account needed for automated tests), using icelake itself for the write path and **DuckDB** purely as a read-side validation tool (DuckDB usage remains outside icelake's own scope, per the query-side section above — it's a test dependency, not a library dependency). The anchors are an end-to-end volume/round-trip test, a crash-recovery test over the staging layer, a catalog-deletion-and-rebuild test (the concrete proof of the disposability claim above), a startup-migration test, and a demonstration of DuckDB's `cache_httpfs` extension against the same local bucket — plus, added alongside the 2026-07-30 API decisions above, dedicated scenarios for the API contract (concurrent `Insert`, non-blocking flush, drain on `Close`), for every fail-loudly guardrail (config validation, name validation, staging ceiling, poison records, the schema cross-check, per-table failure isolation), for bounded flush retry and self-healing after an outage, and for the mirroring hook, the status surface, and the flush-interval floor. Added alongside the M10 decisions above: a dynamic-writer round trip declared from a schema document instead of a struct; the spool and its retention, including the case that matters most — a file the bucket has never confirmed surviving every sweep while the cache sits far over its bound; local-only mode with the transition drain behind it, whose local-only half needs no container at all and says so; and the `icelake` command, first hermetically and then against the real substrate through a real pipe.

## Data classification: what belongs in icelake, and what doesn't

Investigating both motivating cases surfaced a recurring three-way split that should be applied to any future candidate service before adopting icelake for it:

- **Append-only fact data — the clean fit.** Data that, once written, is never edited (archive-style event logs, derived records keyed by an immutable source identity). This is icelake's core use case and needs nothing beyond plain Iceberg appends.
- **Mutating projections — a harder fit, needs a deliberate choice.** Data that gets edited in place after being written (e.g., a message row updated by a later edit event). Iceberg supports this via equality-delete/merge-on-read or copy-on-write rewrite, but iceberg-go's support for this path is newer and less proven than its append path. Two honest strategies, not a universal answer: implement the equality-delete upsert directly, or keep a hot/cold split (recent mutable rows stay in a local operational store; only rows old enough to be stable get compacted into icelake).
- **Operational/transactional/decisioning state — does not belong in icelake, ever.** High-frequency, small, ACID-dependent state consulted on a live decision path (e.g., a rate-limit/ban-risk ledger deciding "is it safe to make another call right now") is the wrong shape for an object-storage-backed table format regardless of volume. This stays in whatever local transactional store the service already uses.

A related rule, carried over from a convention already proven in the authors' private projects (a fact/policy boundary: facts are immutable observations; policy-derived values are never persisted as truth): **icelake fact tables should hold raw observations only, never a value derived from a policy or rate that might later be revised.** If a derived value (e.g., an estimated USD value computed from an exchange rate) needs correcting later, recomputing it at query time from raw facts plus a policy version is strictly simpler than needing to mutate an append-only table to fix it.

## Query side: deliberately not this project's problem

Because Iceberg's whole point is engine portability, reading back what icelake writes is already solved by existing tools against the same bucket + catalog, with no new code:

- **DuckDB** has native Iceberg read (and write) support and can query R2-backed tables directly via its S3/httpfs support. For a long, heavy analysis session issuing many queries, DuckDB's own in-process cache is memory-only and does not persist across queries by default — the community extension `cache_httpfs` gives real on-disk persistent caching across a session, which is the recommended pattern over re-fetching from R2 on every query. A one-time bulk sync of a working set to local disk (`rclone`/`aws s3 sync` against R2's S3-compatible endpoint) is an equally valid, simpler alternative for a single heavy-analysis day.
- **PyIceberg** is the mature choice for any Python-side reader, and is likely also the right choice for any Python-side *writer* that isn't part of this Go ecosystem (see below).

**What the spool — decided at M10, built at M11 — adds to this section is an option, not a component.** With `CacheDir` set, the recent window is already on local disk, in a directory tree DuckDB reads directly — `read_parquet('<CacheDir>/<namespace>/<table>/data/*.parquet')` — at no request cost whatever, which is the same working-set-on-local-disk pattern the two bullets above recommend, arrived at from the write side and without a download. It is written here so a reader of this section knows the files exist, and it changes none of this section's decisions. Those files carry no manifest and no snapshot, so nothing resolves a schema change across them (two shapes are two Parquet schemas the reader unions itself), retention deletes them on its own schedule, and none of them is authoritative about anything. Anything that needs the *table* queries the table. Local-only mode is the one case where the directory is all there is, and that compromise is stated where it is made, under `Config` above.

Cost shape worth remembering when choosing how to query: R2 bills reads by request count with **zero egress cost**, so direct access (DuckDB/httpfs or a bulk sync) is nearly free regardless of how much data is scanned. Cloudflare's own R2 SQL, by contrast, bills by bytes scanned ($2.50/TB) — for a day of many exploratory queries over large scans this can land meaningfully higher than direct access, despite being "inside the network." This is why icelake has no query-serving component of its own: there's no cost or architectural reason to build one.

## Observability: explicitly out of scope

Decision (2026-07-27): icelake does not ship its own metrics, logging hooks, or an injectable instrumentation interface. Every operation returns plain Go errors/results; the embedding service is expected to wrap call sites with whatever observability convention it already has (e.g. an existing Prometheus registry) exactly as it would for any other library call. This mirrors the same reasoning behind keeping querying out of scope: the caller almost always already has a better, more consistent answer for this than icelake could impose generically, so building it in here would be scope creep rather than a real gap.

The optional `OnFlushError` callback added on 2026-07-30 (see "Failure handling") is not a retreat from this decision, and the boundary between them is worth stating so the next reader does not have to guess. Every *synchronous* operation still returns a plain error to its caller and reports nothing itself. The callback exists solely for the one class of failure that has no synchronous caller to return to — a background flush — because the alternative is not "the caller instruments it themselves," it is "nobody ever finds out." It carries an error and the identity of what failed, and nothing else: no counters, no timings, no levels, no interface to implement. A caller wanting metrics builds them in that callback, with its own registry, exactly as this section intends.

The `OnAccept` callback and `Status()`/`WriterStatus` added the same day (see "Mirroring and visibility" above) sit on the same side of this boundary as `OnFlushError`, for the same reason, and it's worth being just as explicit about why. Neither is a general instrumentation system: there is no metrics interface, no pluggable exporter, no level or category to configure. `OnAccept` exists because it is the only mechanism that actually solves the dual-write problem it targets — a caller cannot achieve "one decision point, two stores" from outside icelake, since the decision point in question is inside `Insert`. `Status()` exists because it reports exclusively on R2 operation volume icelake itself generates, which is the one piece of this system's own cost behavior that no amount of the caller's own instrumentation could observe from outside it — everything else about "how is my service doing" remains entirely the caller's own, better-equipped domain, exactly as decided above.

**One thing about the shape of this boundary changed at M10 and is written down so the decision is not read as having quietly softened.** This repo carries an embedding service of its own: `apps/icelake`, the CLI daemon decided at M10 and built at M13 (`PLAN.md`). So "the embedding service wraps call sites with whatever observability convention it already has" has, in exactly one case, an embedding service these authors wrote — and its convention is stderr. It prints its resolved configuration once at startup with secrets redacted, prints one line per flush error from inside `OnFlushError`, and prints nothing else. That is this decision being *exercised*, not amended: the wrapping lives at the call site, in a program beside the library, where a different embedder would put something else. Inside the library nothing moved. There are still no metrics, no logger, no levels, no exporter and no instrumentation interface; every synchronous operation still returns a plain error and reports nothing itself; `OnFlushError` still carries an error and an identity and nothing more. The scope sentence is therefore narrowed to what it always meant rather than weakened: observability is out of scope for the *library*, and a program that embeds it is entitled to do what any embedding service does.

## Multi-language story: unresolved by design, not by accident

icelake is a Go library. That gives data-shape agnosticism (any Go caller can define its own schema) but not calling-language agnosticism — a Go library cannot be imported from Python. The motivating trade-decoding case is pure Python. Two real options exist and neither is adopted yet:

1. **Parallel implementation.** A Python-side writer using PyIceberg, following the same conventions (batching thresholds, fact/policy boundary, single-writer-per-table) as a matching pattern rather than shared code. Lowest new operational surface, but two codebases to keep aligned.
2. **Local sidecar.** Python calls a small local process (this Go module, exposed over loopback gRPC/HTTP) rather than reimplementing anything. Real shared code, but introduces a process and a network hop per non-Go caller — a much lighter version of the "one central ingestion service" shape than depending on Cloudflare's managed Pipelines, but not nothing.

**The CLI (`apps/icelake`, decided at M10 and built at M13) is adjacent to option 2 and is deliberately not it, which is worth a boundary sentence before someone reads it as the sidecar having shipped.** That program is a *writer fed by a pipe*: one process, one `staging.db`, one set of tables, reading JSON lines on stdin, with the pipe as the only channel in and no address, no request, no response and no second caller. A sidecar is an RPC server — several callers, a wire protocol to version, per-call errors to return, and a lifetime independent of any one client — and none of that exists here. What the CLI does settle is the *other* half of the question: a non-Go program that can write a line to a pipe no longer has to reimplement anything to get records into an Iceberg table, which covers the common shape (a producer with a stdout) and leaves the shape option 2 exists for (a library call from inside a Python program, with an error returned to that call) exactly as open as it was.

This should be decided per adopting service rather than forced into one answer up front.

## Alternatives considered and explicitly rejected (with reasons)

- **Cloudflare R2 Data Catalog + Pipelines** — the closest managed equivalent to this whole design (HTTP-post ingestion, automatic Parquet/Iceberg batching, hosted catalog). Rejected as the foundation specifically because it makes the write path depend on a Cloudflare-hosted control plane rather than a bucket the team fully owns; both products are also still in beta.
- **Cloudflare R2 SQL** — bytes-scanned billing model, still beta, joins/aggregations only recently added; not adopted as a query layer given direct R2 access is both simpler and cheaper for this workload shape.
- **Self-hosted REST catalog servers (Lakekeeper, Apache Polaris, Project Nessie)** — all are catalog-only (none write data files themselves) and all require running and operating a server plus (for Polaris/Nessie) a real backing database. Unnecessary given icelake's single-writer-per-table topology; Lakekeeper (single Rust binary + Postgres) remains the fallback if multi-writer or externally-reachable catalog access is ever needed.
- **Redpanda Iceberg Topics** — would have been close to ideal (produce a plain message, get an Iceberg table transparently) but the feature is Enterprise-license-only, not available in the free/self-hosted edition.
- **Apache Arroyo** (the engine behind Cloudflare Pipelines) — genuinely open source and self-hostable, with a real Iceberg sink, but its ingestion side is pull-based (Kafka source or polling HTTP), not push, meaning it would need an additional message bus (e.g. Redpanda) in front of it to get push semantics; combined with thinner community-investment certainty post-acquisition, judged as more moving parts than a purpose-built library for this project's scope.
- **iceberg-rust** — real and improving write support, but assessed as less consolidated than iceberg-go's (ecosystem split between an official crate and community forks), and the projects this library was built to serve are already Go-heavy. iceberg-go was chosen as the primary implementation target for that reason.
- **Cloudflare D1** for this volume — ruled out early: at hundreds of GB to low TB with continuous writes, D1's storage price alone (50x R2's per-GB rate) plus per-row write billing make it categorically the wrong tool next to R2's near-zero cost for this access pattern.
- **A job queue in front of the staging store (e.g. `River`)** — considered and rejected: the staging store plus the in-memory batcher's size/time timer already is a durable queue with its own trigger for when work gets processed, entirely within the same process. A job queue on top would manage the same work a second time. The spool does not change that and is worth distinguishing from it explicitly, since "files on disk waiting to be uploaded" is what a queue directory looks like: the spool is the *same* durable queue's output made visible on local disk, not a second queue with its own ordering, its own retries or its own claim semantics — nothing is ever read back out of it to decide what to do next, and the only thing that decides what gets uploaded is still the staging rows and the flush worker in front of them. `River` also remains Postgres-first; its 2026 SQLite support is explicitly labeled experimental by its own maintainers and measured around 4x slower than its Postgres path — not a fit for a project that has otherwise deliberately stayed single-process/embedded-only with no external database server.
- **Plain Hive-partitioned Parquet with no table format at all** — a real pattern the authors have already run in production, with content-hash-verified idempotent uploads. It remains the right choice for tables that are purely append-only *and* never need a schema change more disruptive than "add a column" (which DuckDB's `union_by_name` already handles for free without any table format). icelake — and real Iceberg semantics — earn their keep specifically where a table needs safe **rename**, **type-widening**, or (eventually) **row-level mutation**, none of which plain Parquet can do without a rewrite. Adopting a service into icelake versus just extending that simpler pattern should be a deliberate per-service decision, not a default.

## Reference cost model (Cloudflare R2, observed at time of writing)

- Storage: $0.015/GB-month. Egress: $0, always.
- Class A operations (writes/lists): $4.50/million. Class B operations (reads): $0.36/million.
- Reads are billed by request count, not bytes moved — scanning large volumes via direct access (DuckDB/httpfs, or a bulk sync) is cheap regardless of total data size, as long as request counts stay reasonable (i.e., avoid pathologically small files).

## Open questions carried forward, not resolved by this document

- iceberg-go's production-adoption evidence is thin relative to PyIceberg or the JVM reference implementation. Its append path is being trusted here; its row-delta/equality-delete path (needed for the "mutating projections" case above) is the least-proven part of it and needs real validation before any adopter depends on it for irreplaceable data.
- ~~The catalog-rebuild-from-bucket recovery tool is new code this project owns even though the SQL catalog backend itself is not — it needs explicit end-to-end test coverage (see `TESTING.md`) proving the rebuild path actually works before it's trusted.~~ **Closed at M6.** The tool exists and `TESTING.md`'s scenario 3 runs it for real: two tables written through the write path, `catalog.db` deleted from disk, rebuild given nothing but an endpoint, a bucket, a prefix and a place to write, both tables rediscovered by listing alone, and the same DuckDB queries returning identical results through the rebuilt catalog — which is then also appended to. What that does *not* cover is unchanged and still open: it says nothing about R2's list consistency, which remains the manual procedure below.
- No decision yet on the multi-language (Python) story; deferred per adopting service as noted above.
- **Schema evolution for nested (non-flat) fields is deliberately unimplemented, and lists of groups are not declarable at all.** `SCHEMA.md`'s reconciliation loop is scoped, as of 2026-07-30, to flat top-level fields only: it diffs single-segment field paths and has no handling for a field inside a group. Declaring a plain nested struct still works for a table's *initial* creation, but changing a nested shape afterwards is not covered and must fail loudly rather than half-work. Separately, and verified at M0: a *slice* of structs cannot be declared through this path even for initial creation, because arrow-go gives the list's synthesized element node no field ID and the Arrow-to-Iceberg conversion then refuses the schema. Neither example table needs either shape today; the first table that does will need the loop extended to walk full field paths and, for lists, a way to attach a field ID to a list element that arrow-go's tag vocabulary does not currently offer. Design that then, with a real case in front of it, rather than speculatively now.
- **Decimal columns are capped at precision 18 by the current declaration path** — at the *declaration* seam specifically, and this was stated imprecisely until M4. A decimal declared on a Go `int64` field derives to a Parquet INT64 column in the declared schema, and arrow-go's own applicability check limits an INT64-backed decimal to precision ≤ 18 (verified from source), which is what imposes the cap. The *written* file is a different matter and does not carry that limit: icelake builds its data files from Arrow `Decimal128` columns through `pqarrow`, so the object in the bucket carries `FIXED_LEN_BYTE_ARRAY` DECIMAL(18,9) — verified by reading a committed file's schema back at M4. So the physical type in the bucket is already the one higher precision would need; what blocks higher precision is the declaration path, where the unscaled value is a Go `int64` and the two derivations disagree about what a fixed-size byte array field means (see `SCHEMA.md`). Adequate for both example tables and for the motivating cases; a future table needing 38-digit precision will need that gap closed first.
- **Snapshot expiration and small-file compaction over a table's life are not addressed at all.** Every flush appends a data file and a snapshot; nothing in this design ever removes an old snapshot, expires metadata, or rewrites many small data files into fewer large ones. The irony is worth naming rather than hiding: this project exists specifically because a motivating case accumulated an ever-growing pile of small uncompacted archive files, and a long-lived icelake table with an aggressive time threshold and a low-traffic stream would recreate a tidier, better-compressed version of the same shape. The batching thresholds bound how bad it gets, so this is genuinely deferrable for an initial implementation, but it cannot stay silent forever — Iceberg has real, standard answers here (`expireSnapshots`, rewrite/compaction actions), and the open question is which of them `iceberg-go` actually implements today and whether icelake should invoke them or leave them to an operator-run maintenance job. **The spool's retention, decided at M10, is not an answer to any of this and must not be read as one:** it deletes *local* copies of files that are already committed, and it removes nothing from the bucket, expires no snapshot, rewrites no data file and touches no metadata. A table whose spool has been swept clean has exactly as many small files and as many snapshots as it did before. The two mechanisms share a word and nothing else, and this entry stays open.
- **Every flush reads its own data file back, and the read leaks a reader upstream.** An M4 decision, recorded above next to the code path it concerns: `AddFiles` re-reads the uploaded object because the statistics machinery that would let icelake build an `iceberg.DataFile` itself lives in an internal package of `iceberg-go`. Measured at three ranged GETs per flush; the cost that will actually force the issue is the latency and memory of a whole extra transfer and parse of a full-sized batch, serialized in front of the next commit. It becomes cheap the moment the statistics helpers are exported upstream, and it is invisible in the public API either way. **Separately, that same re-read leaks:** the file IO's own reader is not closed on this path (`blob.Reader … was never closed`, from `io/gocloud/blob.go` in the pinned version), so every flush finalizes one abandoned reader. It is upstream code on an upstream path — icelake hands over a location and gets a `DataFile` back, with no handle in between to close — so there is nothing to fix here without either patching upstream or leaving `AddFiles` behind, which is the same fork in the road as the paragraph above. Tracked here so it is a known cost rather than a mystery in a heap profile, and it disappears with either resolution: the S3-only file IO listed in `PLAN.md` closes what it opens, and building the `DataFile` locally removes the read altogether. (The other M4 dependency decision, the `io/gocloud` import, was an open question for about an hour before being promoted to an owned pre-release item in `PLAN.md` — it has a fix, an owner and a deadline, which is what disqualifies it from this list.)
- **Orphaned data files have no described cleanup path.** A data file uploaded to R2 whose commit never lands — an abandoned stuck flush, a quarantined batch whose upload had already succeeded, a violated single-writer assumption — stays in the bucket forever, costing storage and referenced by nothing. It is harmless to correctness (no snapshot points at it, so no reader will ever see it) but it accumulates silently, and this design offers no tool to enumerate or remove it. The content-hash keying makes such files at least identifiable in principle, since a batch's key is reproducible from its staged rows. Deferred, but it belongs in the same future maintenance story as compaction above.
- **Partitioning is deliberately absent, per the creation-properties decision above.** Tables are created unpartitioned; if a future read-heavy, time-sliced consumer genuinely needs partition pruning, adding a partition spec to an existing table is a supported Iceberg evolution, but it changes file layout expectations and interacts with batch-splitting — design it then, against that real case.
