# icelake — implementation plan

This is the build-order companion to the three design documents. Reading order for anyone (human or agent) starting work here: `ARCHITECTURE.md` (what and why), `SCHEMA.md` (schema declaration and evolution), `TESTING.md` (test philosophy — binding — and scenarios), then this file (what to build, in what order, and what "done" means). The design documents own every decision; this file only sequences them. If this file ever appears to contradict a design document, the design document wins and this file has a bug.

## Module and package layout

The library is the **repo root module**, because this repo exists to ship one importable library and import paths are permanent (see "Distribution" below). Deployable binaries are small nested modules under `cmd/`, wired together with `go.work` at the repo root.

- **Root module** — `github.com/gvkhna/icelake` (finalized 2026-08-04, before the first version tag — the module path is permanent from that moment on). Contents:
  - package `icelake` (module root) — the entire public API: `Open`, `Store`, `OpenWriter`, `Writer[T]`, `Config`, `TableConfig`, `FlushPolicy`, `WriterStatus`, `Clock`; the runtime-schema and spool half, decided at M10 and built at M11–M12 — `Record`, `FieldSpec`, `TableSchema`, `NewTableSchema`, `ParseSchemaDocument`, `DynamicTableConfig`, `DynamicWriter` (a defined struct embedding `*Writer[Record]`, not an alias for it: a method cannot be declared on an instantiated generic type, and `InsertJSON` is a method — see the API sketch in `ARCHITECTURE.md`), `OpenDynamicWriter`, `(*DynamicWriter).InsertJSON` and `(*Store).DrainSpool`; the batch door added at M15 — `(*Writer[T]).InsertBatch` and `(*DynamicWriter).InsertJSONBatch`; the ingest entry point and the second encoding added at M16 — `IngestStream`, `IngestOptions`, `IngestNotice`, `IngestNoticeKind` with its two constants, the six `DefaultIngest*` constants, and `(*DynamicWriter).InsertCBOR` and `InsertCBORBatch`; and all of `ARCHITECTURE.md`'s error taxonomy except the four names only catalog rebuild returns, which from M10 includes `ErrLocalOnly`, `SpoolError`, `RecordError` and `SchemaDocError`.
  - `rebuild/` — the public `Rebuild` function, its options/report types, the four error names only it returns (`ErrCatalogExists`, `RebuildPrefixKind`, `RebuildPrefixError`, `RebuildStorageError`), and aliases for three names it returns that the root package exports too (`CatalogError`, `ConfigError`, `ConfigFieldError`), so that a caller who imports only this package is not sent to the root package for a name to match those against. It reads the bucket through `aws-sdk-go-v2` directly and never loads a table, so it does not pull `iceberg-go/io/gocloud` into a consumer that imports only this package.
  - `internal/errdef/` — the declared home of every error type in `ARCHITECTURE.md`'s taxonomy. The public packages alias from it so that the root package and `rebuild/` can both return the shared types without importing each other: `icelake` re-exports everything except the four rebuild-only names, and `rebuild/` re-exports those four plus the three shared names it also returns. (Added to this list at the post-M9 completeness audit — the package existed and was documented in `ARCHITECTURE.md` from the start; this list had simply omitted it.) **Corrected at the audit's fifth round (2026-08-01), because the sentence above used to describe an overlap as a partition.** It read "`icelake` re-exports everything except the four rebuild-only names, which `rebuild/` re-exports", which says of every name in the taxonomy that it has exactly one public home. Three of them have two: `rebuild/errors.go` aliases `CatalogError`, `ConfigError` and `ConfigFieldError`, and the root package re-exports all three as well. The code is the right side of this disagreement and nothing about it should change. An alias is the same type rather than a copy, so `errors.As` against `rebuild.ConfigError` matches an error built anywhere in the library and `errors.As` against `icelake.ConfigError` matches one `Rebuild` returned — the duplication buys a caller who imports one package the names for what that package hands back, and costs nothing at all, which is why the file's own comment introduces the two `Config` ones as a deliberate reuse. What was wrong was only this summary, and it was wrong in the direction that does damage: a reader who believes the partition either goes hunting in the root package for a name that is already in front of them, or concludes that two identically-spelled `ConfigError`s in two packages must be two types that will not match each other, which is the one thing about aliases worth knowing and the opposite of true. One boundary is worth stating rather than leaving to be inferred, since a partition reading gets it backwards a second time: the aliasing stops at the error types. `CatalogKind` and its three constants, which a caller reads off `CatalogError.Kind`, are exported by the root package and not by `rebuild/`, so branching on which part of the catalog failed means importing both.
  - `internal/catalogdb/` — the catalog name, the `catalog.db` open path and pragmas, and the one direct row insert catalog rebuild needs. Shared by the write path and `rebuild/` so the two cannot disagree about the file.
  - `internal/s3cfg/` — the `aws.Config` construction and the credential-form rule, shared for the same reason.
  - `internal/schemamap/` — the three-call schema derivation, the two-derivation cross-check, and the column adapter: one switch with an identity arm, three conversion arms and a loud default (`SCHEMA.md`). **Corrected at the completeness audit's fifth round, in its repair pass (2026-08-01):** this line called it "the two-case column adapter", and the adapter has had four non-default arms since M4, when the `Int64`→`Timestamp(us, UTC)` rescale was added — the one conversion that actually reaches a data file, which is what makes leaving it out of the count worse than an arithmetic slip. The identical wrong count was corrected the same day in `SCHEMA.md`, in both its adapter decision and its section "What's hand-written code, and what's a library call", and in `internal/schemamap/adapt.go`'s own doc comment; a twin of it survived in `internal/schemamap/crosscheck.go` and was corrected alongside this line. `adapt.go`'s correction is what found this copy: it named this file as the one still outstanding, and that sentence is the only reason anybody came looking. The count has deliberately not been swapped for a fresher count — the arms are written out instead, because a bare number in a package list is a fact about one milestone that goes on being read as a fact about the code, which is exactly how this one survived from M4 to now.
  - `internal/canon/` — canonical record encoding, decoding by recorded descriptor, schema fingerprint, batch hash. The golden-fixture unit tests live here.
  - `internal/staging/` — `staging.db` access: embedded goose migrations (`migrations/`), `queries.sql`, sqlc-generated code, replay index, ceiling counters.
  - `internal/spool/` — the local Parquet spool: the write (temporary file, fsync, rename, directory fsync, then the one transaction that records the file and its descriptor), the retention sweep, and the reads the transition drain is driven from (`Backlog`, `Schema`, `MarkCommitted`). It owns the cache directory and nothing else; the durable rows it reads and writes live in `staging.db` (`ARCHITECTURE.md`, "The local Parquet spool"). **Corrected at M11, when it was built:** this line used to say the package owns the transition drain as well, and it does not. The drain loads and reconciles Iceberg tables, uploads to the bucket and commits through the catalog — every one of which is the root package's — so it lives in `drain.go` beside the writer whose open runs it, and reaches into this package only for the three reads above. A drain inside `internal/spool` would have had to import the catalog, the S3 client and `internal/schemamap`, which is most of the library, in a package whose whole claim is that it owns a directory.
  - `internal/flush/` — batch sealing, Parquet encode, upload, commit, retry, quarantine, the worker and timer loops, the named crash points.
  - `internal/testsubstrate/` — the MinIO container harness every storage-facing test runs against (`TESTING.md`, "Test substrate"). It is a normal package rather than a `_test.go` file because more than one package's tests need it; it imports `testing` and is imported only by tests.
- **`cmd/icelake-rebuild`** — module `github.com/gvkhna/icelake/cmd/icelake-rebuild`; thin CLI wrapper over `rebuild.Rebuild`, no logic of its own. It requires the root module through a local `replace` directive, because `go work` covers building and `go mod tidy` does not: without the replace, tidying this module would try to fetch an unpublished path from the network. The replace is harmless where it lives — apps are never published.
- **`cmd/icelake`** — module `github.com/gvkhna/icelake/cmd/icelake`; the daemon, and the only app a user installs. It is a thin wrapper in the full sense of the rule in `AGENTS.md`: it reads its configuration from the environment, loads a schema document through `ParseSchemaDocument`, opens one dynamic writer per table, and pumps JSON lines from stdin through `InsertJSON` — every decision it appears to make (batching, retention, local-only, replay, backpressure) is a library decision it passes along. Subcommands are `run`, `usage` (an embedded manual), `version` and `rebuild` (a wrap of `rebuild.Rebuild` taking its configuration from the same environment, and refused outright when that environment says local-only, since a store with no catalog has no catalog to rebuild — a refusal the command makes against its own configuration, not a library error path). Same `replace` directive and the same reason for it as the other two apps.
- **`cmd/icelake-r2check`** — module `github.com/gvkhna/icelake/cmd/icelake-r2check`; the one-off manual R2 verification program (`TESTING.md`, "Real R2 verification"). **Corrected at the post-M9 completeness audit's third round (2026-08-01):** this bullet used to end "Never run in CI", and that became false earlier the same day, when the audit's repair round gave the program a substrate-backed test that runs its whole procedure against the MinIO container. What is never run in CI is the run this program exists for — a real bucket, real credentials, by hand — which is the only run that says anything about R2. The program's own code, including the happy path of its three provider checks, does run in CI. `TESTING.md` owns that decision and states the coupling it accepts; this file only sequences it.

`sqlc.yaml` sits at the repo root; generated code is committed (see the codegen decision in `ARCHITECTURE.md`). The apps are not importable deliverables — only the root module is the public surface, and only it gets plain `vX.Y.Z` tags.

**Layout reorganization (2026-08-05, owner's call):** `apps/` was renamed to `cmd/`, the conventional Go name (module paths under it renamed to match — safe precisely because those modules are never published); the design documents (`ARCHITECTURE.md`, `SCHEMA.md`, `TESTING.md`, this file, `RELEASING.md`) moved from the repo root to `docs/`; and the root-level scenario test files moved to `internal/e2e` as `package e2e`, leaving at the root only the public API sources and the one godoc example pkg.go.dev requires there. Every move was `git mv` plus the package or path line it forced — no code changed. Prose throughout the tree cites the documents and test files by bare name, and those names still hold.

## Distribution and open-source publication

**This repo is written for public, open-source release.** That is the distribution mechanism, not just a philosophy: Go has no package registry — a public repo *is* the package host. Downstream consumers (including the authors' own private projects) simply `go get github.com/gvkhna/icelake@vX.Y.Z`; Google's module proxy caches every published version and the public checksum database verifies it. No `GOPRIVATE` configuration, no fetch tokens in CI, no private-module machinery anywhere downstream. Dependency flows strictly one way: private projects import this module; nothing in this repo ever references them (see `AGENTS.md`'s open-source posture).

The rules that make this safe:

- **`<owner>` is finalized: `gvkhna` (2026-08-04).** The module path is `github.com/gvkhna/icelake`, everywhere, permanently. Until this date the tree used `github.com/icelake-authors/icelake` as a syntactically valid stand-in (because `<owner>` is not valid `go.mod` syntax) and these documents said `<owner>` in prose; both were find-and-replaced in one pass when the owner chose the real name, which was always the plan recorded here.
- **Nothing is tagged until the pre-publication pass is done.** Once any version is fetched through the module proxy it is cached there permanently — deleting the repo does not unpublish it, so a leak in a tagged version is unrecoverable. Working rule now, gate later.
- **Replace the `io/gocloud` file IO before the first tag.** An S3-only `iceberg-go` `io.IO` over `aws-sdk-go-v2` — which this module already depends on — registered for the `s3` scheme, removing 55 modules and 37MB from every consumer's binary. The surface is small (`Open`/`Remove`, `Create`/`WriteFile`) and every object it touches is small except the data-file footer read on the commit path. **Corrected at M6: no directory walk is needed.** An earlier version of this bullet said `WalkDir` would be wanted "once catalog rebuild needs it"; rebuild shipped reading the bucket through `aws-sdk-go-v2` directly, because it never opens a table and so has no reason to reach for a registered `io.IO` at all — which is also why the rebuild CLI links none of `gocloud.dev`. It is deferred out of M4 for sequencing, not design: standing up a bespoke file IO alongside the write path itself would have meant debugging two new things against each other. Nothing caller-visible depends on it, so it can land in any milestone before the tag — but it must land *before* the tag, because a published version's dependency graph is cached by the module proxy forever. **Amended (2026-08-04): "the tag" this gates is `v1.0.0` final, not the release-candidate tags.** The owner chose to ship `v1.0.0-rc1` first and land this swap between rc and final. **Amended again the same day: it gates no tag at all any more — `v1.0.0` shipped without it, on the owner's call.** The swap changes no behaviour and no API, so holding the release protected nobody; what it buys (the smaller consumer graph, and the one seam through which every storage call passes — where call metrics and a runaway-call fuse belong) is unchanged and lands in a later minor. The cost accepted is that the 1.0-line graph the proxy caches includes `gocloud` until then. What the proxy caches forever about an rc is its dependency graph, and a heavy graph in a pre-release is a cosmetic cost, not a leak: Go tooling never selects a pre-release version unless asked for it by exact name, so no consumer inherits the weight by default, and every later version has the slim graph. The unrecoverable-leak rule (the bullet above) is about *content*, and that gate still applies in full to rc1 — the sanitize pass and fresh history precede any tag whatsoever. When the swap lands it will also be the seam that makes every bucket call countable and cappable, and the extension point for per-provider drivers (S3 first, others as separate opt-in packages), which is the recorded direction for multi-cloud support.
- **Pre-publication pass, in order:** a fresh scan-and-sanitize review of every file (automated scan plus human read — the standing posture makes this a verification, not a cleanup); then publish. (Finalizing `<owner>` used to sit between the two; it happened 2026-08-04, see above.)
- **Publish with fresh git history.** The private ancestor (the development history, which predates the sanitization pass) is never pushed. (Amended 2026-08-04: this bullet originally said the public repo starts from one clean initial commit. It starts instead from a *curated sequence* of logical commits rebuilt from the final tree — foundation, then each layer in dependency order, then apps, then distribution — because a history is documentation, and a tree this size squashed to one commit throws away the one map of it that `git log` could have been. What does not change is the rule that matters: no commit from before the sanitize pass is ever pushed.)
- **License: MIT**, copyright "icelake authors" (`LICENSE` at the repo root). (Amended 2026-08-05, owner's call: the repo shipped its first releases under Apache-2.0, chosen for the patent grant. The owner chose MIT for the simpler, more familiar terms; the license file, README badge and this bullet changed together.)
- **Tagging discipline, amended (2026-08-04): the first tag is `v1.0.0-rc1`, and the rc series plays the role this bullet originally gave to `v0.x`.** The original rule said `v0.x` during build-out and `v1.0.0` at API freeze. By the time anything was actually ready to tag, build-out was over — M0 through M14 complete, the API surface stable — so the owner chose to signal "this is the 1.0 shape, being proven in the field" rather than "this may change", which is what an rc means and a `v0.x` does not. Go treats a pre-release the way this needs: `v1.0.0-rc1` is never selected by version resolution unless asked for by exact name, so nothing depends on it by accident. `v1.0.0` shipped 2026-08-04 (the S3-only file IO moved off its gate the same day — the amendment above). From here: fixes bump the patch, new behaviour bumps the minor, the procedure is `RELEASING.md`. A `/v2` module path if a breaking change is ever needed after 1.0, per Go's usual rule, unchanged.

**The step-by-step procedure for actually cutting a release — the commands, the order, and who presses what — lives in `RELEASING.md` (added 2026-08-04), which sequences the decisions recorded here the way this file sequences the design documents.**

**Binaries are distributed separately from the module, and the two ride the same tags.** The library is distributed by being a public repo; `cmd/icelake` cannot be, because a Go module path is not an installation mechanism for a program most of its users will not be compiling. So:

- **`goreleaser` builds `cmd/icelake` and attaches the artifacts to GitHub Releases.** `CGO_ENABLED=0` — icelake's runtime is pure Go (`modernc.org/sqlite`), and the one cgo dependency in this repo, DuckDB, is test-only — across linux and darwin on amd64 and arm64, with the version stamped in through `-ldflags -X`. Only the `icelake` binary ships: `icelake rebuild` covers what a separate `icelake-rebuild` asset would have, and shipping both would make an installer's prefix matching ambiguous for no gain.
- **Releases ride the root module's `vX.Y.Z` tags.** One tag, one release, one train: the CLI's version is the library's version, so "which icelake is this" has one answer rather than two that drift. The cost is that a CLI-only fix takes a library tag, which is the right trade for a program that is a thin wrapper over that library anyway.
- **Installation is `mise`'s `github` backend** — `mise use -g github:gvkhna/icelake` — which fetches the release asset for the running platform straight off the GitHub release. (Amended 2026-08-04: this originally said the `ubi` backend; mise has since grown a first-class `github` backend and deprecated `ubi` in its favor. Both match assets the same way — by os and arch in the archive name — so nothing about the archive shape below changes, only the install command's spelling.) That is the path the README and the embedded manual document.
- **`go install` of an app is impossible by construction, and stays that way.** Every `cmd/` module carries a local `replace` directive (see the layout above), which is what lets `go mod tidy` run against an unpublished path — and which also means the module proxy can never resolve one, so `go install github.com/gvkhna/icelake/cmd/icelake@latest` cannot work. That is a consequence to state rather than a regression to fix: apps are deliverables and not API, the replace is load-bearing for the workflow, and the binary release is the supported route for exactly the audience that would have reached for `go install`.
- **None of this changes when publishing happens.** Binary releases are tagged releases, so they sat behind the same gate everything else did: the scan-and-sanitize pass and fresh history before any tag (both done 2026-08-04; the S3-only file IO was un-gated the same day — the amendments above). The goreleaser configuration and a `release-check` task that exercises it (`goreleaser check` plus a snapshot build) are written and run long before any tag exists, precisely so that the first real release is not also the first time the configuration is tried. That task stands beside `mise run check` rather than inside it: a snapshot build for four targets is a deliberate act, not something to pay for on every edit. **Both landed at M14, along with one more piece: `.github/workflows/release.yml`, which runs the same two steps on a `v*.*.*` tag and leaves a *draft* release with the artifacts attached.** It was inert until the first tag (2026-08-04), and it originally stopped at a draft for a human to publish. **Amended the day the first release shipped: the workflow publishes directly.** The reasoning that wanted a manual click had it backwards — the irreversibility is a property of the tag, which means the release page gates nothing the tag has not already decided, so the human decision this train protects is pushing the tag (per `RELEASING.md`), and the click after it was ceremony that also demanded repository permissions an operator's token may not have.

## Documentation strategy

Three layers, each with a different change cadence, chosen so integration docs never need a maintenance pass:

- **README.md is the integration doc.** What it is, install, a quickstart, and the "rules that matter" — the operational rules a caller cannot infer from type signatures. Nothing else. It is the only document a downstream integrator (human or agent) must read.
- **Godoc is the API reference.** Every exported symbol carries a doc comment; pkg.go.dev renders the reference site automatically once the module is public. Reference docs live next to the code precisely so they change in the same commit the code does — this is what makes "no separate doc updates" true rather than aspirational.
- **The design documents are decision records.** `ARCHITECTURE.md`, `SCHEMA.md`, and `TESTING.md` are authoritative for *why* and for binding policy (the test philosophy, the fail-loudly rules); they are updated when a decision changes, not when code details do. Their code snippets are already marked illustrative — the code and its godoc are authoritative for exact signatures.
- **The README quickstart is kept honest by a compiled example.** The same example lives as a Go testable example (`example_test.go`) that CI compiles and runs against the test substrate, and that pkg.go.dev displays. The README copy mirrors it; the example proves it.

Accordingly, every milestone's done bar includes: each exported symbol added has a godoc comment, and (from M4 on, when the write path first works end to end) the quickstart example compiles and runs.

## Dependency pins

Exact versions were chosen at M0 by fetching and building against every one of them together, and change only deliberately from here.

**Toolchain: Go 1.25.7 is a hard floor.** The floor is the maximum `go` directive across *every* pinned dependency, not just the two obvious ones — each was read individually at M0. `github.com/pressly/goose/v3` declares `go 1.25.7` and is the binding constraint; `github.com/apache/iceberg-go` declares `go 1.25.5`; `github.com/apache/arrow-go/v18`, `modernc.org/sqlite` and both `testcontainers-go` modules declare `go 1.25.0`; the four `aws-sdk-go-v2` modules and `duckdb-go/v2` declare `go 1.24`/`go 1.24.0`. No earlier toolchain can build this module without silently downloading a newer one — and `mise.toml` sets `GOTOOLCHAIN=local`, so it cannot download one: a floor violation is a loud error, never a silent toolchain swap. `mise.toml` pins `go = "1.25.12"`; the `go` directive in every module here is `1.25.7`, the true minimum. Re-derive this the same way — across all pins — on any dependency bump.

**One deliberate indirect override, taken at M3: `modernc.org/libc` is held at `v1.74.4`.** Nothing in the table above names it, but minimum version selection would otherwise pick `v1.74.3` — which its own author has *retracted* (a `freeaddrinfo` leak that deadlocks name resolution, fixed in `v1.74.4`) — because `github.com/pressly/goose/v3` requires that exact version while `modernc.org/sqlite` asks only for `v1.74.1`. SQLite performs no name resolution, so the practical exposure here is nil, but a library published for public consumption must not ship a retracted version in its transitive graph: every downstream `go get` would print the retraction warning about a choice its author never made. The override is a one-line indirect requirement within the same minor version and moves nothing else.

**A second cost, added at M4, much larger, and deliberately temporary: importing `github.com/apache/iceberg-go/io/gocloud` pulls `gocloud.dev` plus the Google Cloud and Azure SDKs into the module graph** — 55 new modules, and a measured 37MB (43%) added to a minimal consumer's binary, all of it linked by every downstream consumer because that one package registers S3, GCS and Azure from a single `init` that dead-code elimination cannot see past. Unlike the test-only entries above these are real runtime dependencies. Why it was taken, and why the two arguments originally given for keeping it do not hold, are recorded in `ARCHITECTURE.md` ("Committing the uploaded file, and the file IO that makes it possible"). It is a stopgap with an owner, listed as a pre-release item below rather than as an open question. No pinned version in the table above moved to accommodate it.

**Decision (2026-08-04, M16): `github.com/fxamacker/cbor/v2` is added as a runtime dependency, and it is the first one this project has chosen rather than inherited.** Every other runtime entry in the table above arrived because something else required it — arrow-go and iceberg-go are the formats, the AWS SDK is the protocol, goose and modernc.org/sqlite are the staging store, and the 55 modules under `gocloud.dev` came in through one import that `ARCHITECTURE.md` records as a stopgap with an owner. This one is a deliberate addition to a repository that is dependency-averse on the record, so it is argued rather than assumed.

**What it costs, measured rather than estimated.** The module is 8,896 lines of pure Go across its non-test files and pulls exactly one thing behind it, `github.com/x448/float16`, which is one file of 302 lines with no dependencies of its own and exists to convert half-precision floats. Two modules, no cgo, no build tags, nothing platform-specific, and nothing that registers itself in an `init` — which is the failure mode the `io/gocloud` entry above is a record of. So the cost to a downstream consumer is two `go.sum` lines and whatever of it the linker keeps.

**The rejected alternative is hand-rolling the decoder, and it is worth being specific about what that would have meant, because "CBOR is a simple format" is true and is not the point.** Reading a CBOR item is genuinely a few hundred lines. What this milestone actually needs is: well-formedness checking strict enough that a refusal is a refusal rather than a mis-parse; duplicate map keys detected rather than resolved; UTF-8 validated on every text string; indefinite-length items refused everywhere; a decode that stops at the end of one item and says how many bytes it used, which is what makes an RFC 8742 sequence framable at all; and all of that correct on inputs a hostile producer chose. That is not a few hundred lines, it is a security boundary, and a bug in it is a bug in the one place this project reads bytes it did not write. `fxamacker/cbor` is the CBOR implementation the Go ecosystem has converged on, it is fuzz-tested against the RFC's own test vectors, and it is what the strictness this design needs is expressible in at all — `DupMapKeyEnforcedAPF`, `UTF8RejectInvalid`, `IndefLengthForbidden` and `ExtraDecErrorUnknownField` are its options, and every one of them is a refusal `SCHEMA.md` states. Writing those four checks correctly ourselves is most of the work and none of the confidence.

**The second alternative, and the one that was closer, is not supporting CBOR.** It is rejected on what the format buys, measured at M16 and recorded in `TESTING.md`'s benchmark section rather than assumed: 17.6% fewer bytes on the wire for the same records, integers exact past 2^53 where JSON's number path cannot promise it, and bytes into a `binary` column with no base64 step. As first shipped it also measured ten to fifteen percent *slower* to decode, which a same-day profile traced to the decode reading every record twice; `SCHEMA.md` records the correction, and the decode now measures fifteen to twenty percent faster than JSON's. The speed was found rather than promised: the case for the format was made, and holds, on the other three properties alone.

**One accepted cost, recorded so it is a decision rather than a surprise: `internal/testsubstrate` keeps testcontainers, moby and OpenTelemetry in the root module's `require` set.** They are test-only in every sense that matters — module graph pruning means no downstream consumer ever *builds* them — but they are real lines in this module's `go.mod` and `go.sum`, because Go does not distinguish test dependencies at the module level and the harness has to live in the module whose tests use it. The alternative is a second module for test support, which buys a smaller `go.sum` at the cost of a `go.work` entry, a second dependency set to keep pinned, and an import path for something that is not a deliverable. Accepted as-is; the same reasoning already applied to `duckdb-go/v2` when it was pinned as a test-only dependency above.

**Corrected at the post-M9 completeness audit's fourth round (2026-08-01): a second module now pays that cost, and the paragraph above was written when only one did.** `cmd/icelake-r2check`'s tests import `internal/testsubstrate`, so that module's `go.mod` picked up roughly fifty new indirect requirements — testcontainers-go and its MinIO module, the moby client and API, containerd, the OpenTelemetry set, gopsutil — and its `go.sum` grew by 161 lines. That is exactly the class of thing this bullet exists to record, so it is recorded rather than left for the next audit to find. It is accepted for a reason the root module's case does not have available to it: `cmd/` modules are never published, so no consumer's dependency graph is touched at all, and the alternative is what the audit that prompted this actually found — a program that writes into an operator's real, paid bucket, with its preflight, its record-before-write ordering and its cleanup held by no test of any kind, which is the state `TESTING.md`'s "Real R2 verification" section argues against in its own words. One arrival is worth naming so a future reader does not mistake it for a sanctioned choice: `stretchr/testify` and its `go-spew`/`go-difflib` companions came in transitively with testcontainers. This project asserts with the standard library and nothing else, in every module; testify appearing in a `go.sum` is a dependency's dependency, never an invitation. The same holds for `cmd/icelake`, whose substrate-backed tests import the harness for the same reason and on the same terms: three of the workspace's four modules carry it, and the one that does not is `cmd/icelake-rebuild`, whose own tests are hermetic. **One arrival at M13 is larger than the harness and is recorded here so it reads as a decision:** `cmd/icelake`'s tests also import `github.com/duckdb/duckdb-go/v2`, which is cgo, because `TESTING.md`'s scenario 13 asks its substrate half to validate what the daemon wrote "exactly as scenario 1 does" — and scenario 1 validates with DuckDB, deliberately, because an independent reader is the only thing that proves a table is queryable rather than merely written. Reusing the root module's test helpers was not available: they are in that module's `_test` files. The alternative was to weaken the scenario to a row count read back through the library that wrote it, which is the assertion `TESTING.md` spends a section explaining is worth nothing. It is accepted on exactly the terms above — an `cmd/` module is never published, so no consumer's graph is touched — and it is test-only: the shipped binary is `CGO_ENABLED=0`, since icelake's own runtime is pure Go.

**A number in the paragraph above was wrong and has been removed at the audit's fifth round (2026-08-01).** It used to weigh those roughly fifty indirect requirements against "five hundred lines writing into an operator's real, paid bucket", and that count was already out of date when it was written: `cmd/icelake-r2check/main.go` was 523 lines at the commit before the change this paragraph is about, and 892 lines after it, because the same change that gave the program its tests is the one that added the preflight and the measured cleanup those tests hold. So the cost side of this trade was compared against a program about three fifths the size of the one that actually exists — which does not reverse the trade, and if anything makes it easier, but a cost/benefit argument that gets one of its two quantities from a stale number is not one a later reader can check. It has been replaced with no figure rather than with today's, because a line count written into prose is a fact about one commit that goes on being read as a fact about the file: this one stood in three documents at once — this file, `AGENTS.md` and `TESTING.md` — was already false in each of them on the day it was written into them, and was copied forward rather than recounted. `AGENTS.md` and `TESTING.md` are corrected in the same round and the same way.

**Decision (2026-08-04, M17): `github.com/ClickHouse/clickhouse-go/v2` is added as a runtime dependency of the root module, and the owner's call was explicitly that it lands here rather than in a second module.** This is the second chosen runtime dependency after CBOR's, and it is much the larger of the two, so it gets the same treatment: measured, not estimated, and argued against the alternative that was actually available.

**What it costs, measured on a minimal consumer program that imports `github.com/gvkhna/icelake` and calls `Open`, built `CGO_ENABLED=0` with `-trimpath -ldflags="-s -w"`.** The module graph goes 144 → 151 modules, this module's `go.mod` 188 → 195 requirements, its `go.sum` 708 → 721 lines, and the consumer's binary 85,311,650 → 90,534,050 bytes: **seven modules, 4.98 MiB, 6.1%**. The seven are `ClickHouse/clickhouse-go/v2`, `ClickHouse/ch-go` (its low-level protocol half), `go-faster/city` and `go-faster/errors` (that half's hashing and errors), `segmentio/asm`, `shopspring/decimal`, and `paulmach/orb`, which arrives because the driver supports geospatial column types this library will never declare. No cgo, and — the property that made the `io/gocloud` entry above cost 37MB instead of five — nothing that registers itself from an `init` the linker cannot see past.

**The rejected alternative is a separate or nested module, and it was rejected on what it would cost the feature.** `ARCHITECTURE.md`'s M17 decision holds the argument: a module boundary between the flush path and the mirror turns the record's lifetime, the file schema's timestamp widening and the batch key into public API, and the entire point of the design is that the mirror receives the same in-memory Arrow record the Parquet file is written from. The accepted cost is that consumers who never set `Config.ClickHouse` carry those seven modules anyway. It is accepted on the measurement above and on the ordering it implies: a consumer for whom five megabytes matters has the `io/gocloud` stopgap to remove first, which is worth seven times as much and already has an owner.

Every Go version above was fetched and resolved together in one throwaway module that imports all eleven, including the cgo-requiring `duckdb-go/v2`, and that module builds — they are not independently-latest guesses that have never seen each other. That same module is also how the toolchain floor was checked rather than assumed: pointed at all eleven pins, `go mod tidy` computes the `go` directive as exactly `1.25.7`, and the module refuses to build at `1.25.6`. The skeleton's `go.mod` files stay minimal until M1, when the first real import lands; this table is the record until then.

The docs cite specific library behaviour verified from source and by running it (tag parsers, `arreflect`, the schema-evolution call chain, catalog internals). Those citations are true of the pinned versions; any upgrade of `arrow-go` or `iceberg-go` is a change that must pass the entire e2e suite, not a routine bump.

Done.** `Config`'s four new fields and their validation matrix; goose migration `00002` and its sqlc queries; `internal/spool` and the write seam in `internal/flush` (including the `PointAfterSpoolBeforeUpload` crash point and marking committed at both commit-confirmed sites); the retention sweeper owned by the `Store`; local-only `Open`/`OpenWriter`; the per-table drain inside `OpenWriter` and the exported `Store.DrainSpool`; `SpoolError` and `ErrLocalOnly`, added in the same change as the code that returns them. - **M13 — the `icelake` command. Done.** A new `cmd/icelake` module added to `go.work`; `run`, `usage`, `version` and `rebuild`; the environment table that drives reading, validating and documenting the configuration from one source; the stdin envelope grammar and its malformed-line semantics; the drain-on-signal path; the embedded manual. Proof: scenario 13, both halves. **Four decisions taken here are worth recording rather than leaving in the code.** A malformed line ends the run *without* draining: what was accepted is already durable in staging and is replayed and committed by the next start, and draining on the way out of a failure nobody has diagnosed would make "restart and it picks up where it stopped" mean something slightly different depending on how the run ended. `icelake rebuild` deliberately does not require `ICELAKE_SCHEMA_FILE`, because a rebuild opens no schema document — requiring a file the operation never reads, at the moment an operator is recovering a host, is the kind of configuration that makes disaster recovery harder than it has to be; the daemon still requires it. An explicitly-set `ICELAKE_CATALOG_PATH`, `ICELAKE_CACHE_MAX_AGE` or `ICELAKE_CACHE_MAX_BYTES` is *refused* in local-only mode rather than ignored, which is the same reading of the library's own matrix: passing zero for a value an operator wrote down would be a silent substitution. And a configuration the library refuses is mapped back to the command's own usage sentinel, so a bad `Config` exits 2 like every other configuration refusal rather than 1 — whichever of the two layers noticed it, restarting will not help. A fifth decision was forced by review rather than chosen: `ICELAKE_MAX_LINE_BYTES` is the length of the longest *line*, and the scanner is given two bytes more than it so that the line terminator — one byte for LF, two for CRLF — is not counted against the line. Without that, a line of exactly the configured length is accepted or refused depending on whether the input happened to end there or on how the producer ends its lines, which is a bound that depends on the file rather than on the number; the first fix budgeted only for LF and was caught refusing a CRLF line of exactly the configured length.

That task is deliberately **not** part of `[tasks.check]` — a cross-compiled snapshot build across four targets is not something to put in the loop a developer runs on every change — so it is a task run on purpose, before a tag and on any goreleaser bump, rather than a gate. Publishing is not part of this milestone and stays behind the pre-release train below.

Done.** `Writer[T].InsertBatch`, `DynamicWriter.InsertJSONBatch` (and `InsertBatch` promoted through the same embedding that promotes `Insert`), `staging.Store.AppendBatch` as one transaction with the descriptor upserted once per distinct fingerprint, the batch-aware atomic ceiling charge on the store's counters, `BatchError` in the taxonomy, and chunked ingest in `cmd/icelake` — the pump now blocks for one line, takes whatever else has already arrived, and writes one transaction per table. Proof: scenario 14 in full, including the regression tripwire, plus the existing daemon scenarios unchanged. The M4 conclusion that a caller needing more than a few hundred records a second "is asking for a batching layer of its own in front of this one" is superseded in `ARCHITECTURE.md` rather than deleted, and `synchronous=FULL` did not move: the whole milestone exists to amortize the fsync instead of weakening it. **Four things landed differently from the sketch and are recorded here rather than left to be rediscovered.** The measured bottleneck was not where the fsync argument implied it would stay: once records were grouped, half the remaining cost was the pure-Go driver *parsing SQL*, so `InsertStagedRow` gives its id back as the statement's last insert rowid rather than through a `RETURNING` clause (43 microseconds a row to 14) and `sqlc.yaml` now emits prepared queries, prepared once after the migrations run (14 to 7.7). Both are recorded as their own dated decision in `ARCHITECTURE.md`, because a `RETURNING` clause reads like a free convenience and is not one. The daemon halves a group that the staging ceiling refuses, rather than retrying the identical group forever: a chunk follows the producer and the ceiling is the operator's number, so a group larger than the whole ceiling is reachable and would otherwise hold stdin for good — `TestBackpressureHoldsStdinAndResumes`, with its ceiling of five, is the case that would have hung. The daemon's "everything before the bad line is durable" promise needed the chunk to be *truncated* at a row the library refuses and the group written again, not merely abandoned, which is what `TestMalformedLineDiesLoudlyAndLosesNothing` measures to the record; the one residue is that a chunk interleaving two tables can have committed the other table's later lines already, and `usage.md` states that rather than rounding it off. And the regression tripwire is not the rows-per-fsync ratio it was drafted as: that ratio collapses on any filesystem whose sync is nearly free — measured at 0.0 on a tmpfs — so it was replaced with a comparison of the two doors against each other on the same machine, which falls to between 1.0 and 1.6 exactly when the regression happens and measured between 4.1 and 6.2 over thirty-five consecutive tmpfs runs when it does not.
- **M15's review round, and what it changed.** Seven findings were substantive and all of them are recorded in the code or the documents they touch rather than only here, but three are worth naming because each was a defect the whole suite was green over. The chunked pump read "a chunk came back empty and the input has not ended" as the end of the run, so **a blank line arriving on a live stdin exited zero and dropped the rest of the pipe** — invisible to every test in the tree, because a test that writes its input in one go always has the next line queued and never produces an empty chunk; the loop now distinguishes three outcomes instead of two, and `TestABlankLineOnALiveStdinDoesNotEndTheRun` writes through a real pipe with pauses to hold it. Two tests that named the batch's atomicity **passed against a mutation that opened a transaction per row**: scenario 14's cancellation clause, because a one-millisecond starting budget cancels before the first per-row transaction commits, and its crash clause, because a kill timed by a clock lands wherever the machine got to — the first now derives its deadline from a batch it has just timed, and the second watches the staging row count *during* the batch rather than only after the kill, which is the difference the two designs cannot hide. And `internal/staging.AppendBatch` had no direct test at all, so ids returned in the wrong order and a batch recording only its first descriptor both survived the suite; both are now caught by name, verified by making each mutation and watching the test fail. The lesson the round leaves is the one this repo keeps re-learning in a new place: a test that names a property is not the same as a test that could fail if the property went away, and the only way to tell them apart is to take the property away and look.
- **Deliberately not done at M15, with the number that decides it:** the flush path still reads its rows one query per id and seals and deletes them one statement per id. A flush of 100,000 rows takes 1.9 seconds end to end in local-only mode, of which roughly 1.3 goes into those loops — down from about 3 before the prepared statements, which is most of what a batched read would have bought — so the sqlc.slice rewrite of `Store.Rows`, `Store.Seal` and `Store.Delete` is left for the milestone that has a reason to want it, rather than bolted onto this one. `Seal`'s per-row work is not a plain read either: it rewrites re-encoded payloads and checks that each update matched exactly one row, which is the guard that stops a batch key naming bytes it does not name.

- **M16 — library: the ingest entry point, and CBOR input. Done.** `IngestStream` with `IngestOptions`, `IngestNotice` and the six exported defaults; the record framing that decides each record's encoding from its own first byte; `DynamicWriter.InsertCBOR` and `InsertCBORBatch`; `[]byte` added to the coercion table's `binary` row; `IngestError` in the taxonomy; `github.com/fxamacker/cbor/v2` pinned with the dated argument above; and `cmd/icelake`'s `run` shrunk back to translation. Proof: scenario 15 in full, plus scenario 13's three M15 streaming tests unchanged and still passing against the new `run` — which is the acceptance test for the move, since the behaviour did not change and only its address did. `AGENTS.md`'s placement bullet said "as of this decision `run` fails the test"; that is now closed in the same file, and `run` names `icelake.IngestStream`.
- **What the owner changed mid-milestone, and what it cost.** The first build of this had an `ICELAKE_INPUT_FORMAT` environment variable and an `IngestOptions.Format` field, both of which are gone. The replacement is the per-record dispatch, and the requirement that forced it is one sentence: one producer must be able to write JSON into a running daemon while another writes CBOR into the same pipe, interleaved, with nothing configured. **The change made the CLI smaller** — it removed a translation rather than adding one, which is the direction `AGENTS.md`'s rule points in — and it removed a public type (`InputFormat`) and a whole class of misconfiguration. What it cost was real and is recorded rather than smoothed over: the framing had to be rewritten, because a line scanner and a CBOR stream decoder cannot share a reader — each reads ahead into a buffer of its own, and whichever ran last has eaten bytes the other needed — so the two separate framings became one buffer that owns the bytes and hands out records. That rewrite is also what made the size bound mean the same thing for both encodings, since the check is now on the finished record either way. And it forced the error to carry two coordinates instead of one relabelled: `Record` always, `Line` only when the record is not CBOR, with the rule stated in one sentence in `ARCHITECTURE.md` because a stream that changes encoding per record has no single coordinate.
- **Three things landed differently from the sketch and are recorded here rather than left to be rediscovered.** The ingest layer decodes each row itself, through the writer's own decoder, rather than handing bytes to `InsertJSONBatch` or `InsertCBORBatch` — which is what lets one chunk carrying both encodings for one table still be one transaction, since a decoded row no longer remembers how it arrived, and it also means a row that will not decode is found before anything in the chunk has been written instead of a group having to be written twice. The two public CBOR doors still exist and are the surface a caller with bytes uses; they are also what makes the coercion matrix testable one row at a time. Every CBOR tag is refused rather than tags 0 and 1 being accepted for `timestamptz`, on the argument `SCHEMA.md` records; the two-step decode that first paid for that sharpness measured ten to fifteen percent slower than the JSON one and was corrected the same day to a one-pass decode with the two-step kept as the error path's wording — the correction and its profile are in `SCHEMA.md`. And the benchmark the milestone was asked for measured the opposite of what it was added to measure: `BenchmarkDynamicInsertCBORBatch` and its JSON twin are indistinguishable, because a staging transaction dwarfs either decode, so two decode-only benchmarks were added — using the doors' own documented decode-before-lifecycle-check ordering against a closed writer, so no seam was cut for them — and those separate cleanly. The numbers are in `TESTING.md`.

- **M19 — the daemon backgrounds itself. Done (2026-08-05).** `icelake run` now validates the whole configuration and the schema document on the caller's terminal, then re-execs itself as a detached session (`Setsid`) holding stdin, a locked pid file (`ICELAKE_PID_FILE`, default `<data dir>/icelake.pid`, `flock` — the lock rides into the child on its inherited descriptor, so it lives exactly as long as the daemon), and a log file (`ICELAKE_LOG_FILE`, default `<data dir>/icelake.log` when backgrounded; a foreground run logs to stderr unless it is set); the starter exits 0 only after the daemon has reconciled every table, which it hears on a readiness pipe, and relays the daemon's own exit code if it dies first. `-f`/`--foreground` stays attached (systemd's mode, the tests' mode); `-v`/`--version` and `-h`/`--help` are the only other flags anywhere, all valueless, so the env-only configuration channel is untouched. - **M20 — the drain's clock rule, and the log that answers questions. Done (2026-08-05), and the milestone exists because a real bulk load earned it:** 29.6M records piped in, twenty minutes of clean work, and the end-of-input drain died on the 30-second shutdown default reporting "context deadline exceeded" — data all safe in staging, log silent about that in every way that mattered. Two changes. **The clock rule:** end of input drains to completion, unbounded — the remaining work is finite and abandoning it buys nothing; `ICELAKE_SHUTDOWN_TIMEOUT` now bounds only a signal's drain (a signal arriving mid-drain starts the clock then), and a cut-short drain exits 1 carrying the full account: the variable's name, `staged=`, `staging=`, `lost=0`, and that the next run replays and commits them. **The log:** every runtime event is one logfmt line through the single `log/slog` logger — plain-sentence `msg`, data in keys — with the lifecycle's fixed points (`starting` with the resolved config, `opening table` and `table ready` with the previous run's staged count, `reading records`, the end-of-input/signal summary, `committing` progress every five minutes or every five seconds once a signal makes it urgent, and a final line that is either the all-clear or the account). `ICELAKE_LOG_LEVEL` (slog's own spellings) adds a 30-second per-table activity heartbeat at debug. - **Manifest maintenance — scheduled when iceberg-go releases `RewriteManifests`.** Every new table now enables automatic append-time manifest merging with `commit.manifest-merge.enabled=true`, `commit.manifest.target-size-bytes=8388608`, and `commit.manifest.min-count-to-merge=100`; this prevents the one-file-per-append writer from permanently growing reader metadata work. - **M18 — the mirror's row expiry. Done.** `MirrorTTL` on `TableConfig` and `DynamicTableConfig`, `ICELAKE_CLICKHOUSE_TTL` in the daemon's environment (`namespace.table=DURATION@COLUMN`, bound to the document's tables at startup and refusing an entry no table claims), the TTL clause in the mirror's generated DDL, and the one overwriting reconciliation the mirror has (`MODIFY TTL`, argued in `ARCHITECTURE.md`'s M18 decision — tuning, not data shape). Expiry is the server's own, applied at its merges and at an insert's own part write, which is why the scenario proves it long-TTL-first. The lake is untouched by expiry, always: raw rows leave the mirror, materialized-view targets keep what they computed, and expired rows are recoverable from the Parquet collection. **The milestone also set a rule, and set it the hard way: a first draft carried the expiry (and a flush block) in the schema document's table entries, and the owner refused it — the document declares shape, never configuration.** The draft was reverted before it was ever committed, the rule is recorded in `SCHEMA.md`, `AGENTS.md` and on the parser's own type, and `usage.md`'s claim that a per-table flush policy rode in the document — written at M17, before any parser supported one — is corrected to what is true: per-table flush is the library API's capability, and the command's thresholds are store-wide.
